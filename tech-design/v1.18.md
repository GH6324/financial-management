## D1 · 来源信息存在哪里

| | 方案 | 取舍 | 结论 |
|---|---|---|---|
| A | **每张流水表加一列 `source_tag`** | 读路径零 JOIN;每张表都要改;列值语义要靠枚举约束 | **选定** |
| B | 单独一张 `ledger_source` 关联表(表名 + 行 id + tag) | 主表不动,回滚最干净;但时间线渲染要多 4 次 JOIN 或一次大 IN 查询,而这页已经是 4 张表 union 的热点 | 不选 |
| C | 复用已有的 `audit_log` 反查 | 零 schema 改动;但 audit_log 是操作日志、按 family+time 组织,反查某一行流水的来源要全表扫,而且系统写的行未必都有 audit 记录 | 不选 |
| D | 不存,渲染时按 `note` 文案倒着猜 | 零改动;但 `note` 是**用户可见文案**(`"系统估值同步"` / `"开账自动延续上期末余额…"`),随时会改措辞,判据挂在它上面等于把 UI 文案变成隐式契约 —— 这正是现状的毛病 | 不选 |

选 A 的理由:来源是**那一行流水的固有属性**,不是关系、不是日志。放在行上,读路径就是「本来已经查出来的那一行多一列」。

**为什么 `VARCHAR(24)` 而不是 MySQL `ENUM`**:枚举值会随接入的数据源增加(下一个券商、下一类价格源)。`ENUM` 每次加值都要 `ALTER TABLE` 改列定义,而 prod 已上线 —— 加一个来源就得动一次生产表结构。`VARCHAR` + 应用层枚举 + 「认不出一律 UNKNOWN」的解析,加值时**不需要迁移**。

### 覆盖哪几张表

时间线由 4 张表 union 而成,所以 4 张都要:

| 表 | 时间线上的行 | 写入口数 |
|---|---|---|
| `stock_valuation_event` | `△ 估值` | 1(AccountValuationService) |
| `cash_flow` | `+ 收入` / `- 支出` | 3(EntryService ×2、StockHoldingService ×1) |
| `transfer` | `↳ 划入` / `↱ 划出` | 2(EntryService ×2) |
| `period_snapshot` | `= 校准` | **5**(PeriodOpener、EntryService ×3、AccountValuationService) |

`period_snapshot` 是最需要这一列的一张:`UNIQUE(period_id, account_id)` 决定它是 upsert,**谁最后写谁说话**,而它有 5 个写入口。以前只能靠 note 文案倒着猜(方案 D 的毛病)。

> 一开始我只改了前 3 张,把 `= 校准` 那一行直接标成 `UNKNOWN`,理由是「判据在 `period_todo.done_by_member_id`,这里拿不到」。那是把活干一半:即使将来的数据也永远是 UNKNOWN。补上第 4 张才算真的把「这几类区分开」。

## D2 · 来源怎么定(显式传 vs 推断)

估值刷新有多个调用方(定时任务 / 手动刷价 / 持仓变动 / 券商同步 / 截图导入),它们对「来源是什么」的知情程度不一样:

- **券商同步知道自己是谁** → 显式传 `LedgerSource.ofBroker(vendor)`
- **定时任务不知道** → 它只知道 `TriggerKind.CRON`,来源要看这个账户持的是什么

所以做成 **显式优先 + 推断兜底**:

```java
static LedgerSource inferSource(LedgerSource explicit, TriggerKind trigger,
                                Long refImportId, List<StockHolding> holdings)
```

| 判据顺序 | 结果 | 为什么这个顺序 |
|---|---|---|
| `explicit != null` | 用它 | 调用方比我们更清楚 |
| `refImportId != null` 或 `trigger == IMPORT` | `IMPORT_SCREENSHOT` | 两个信号任一成立都算截图导入 —— 只看 trigger 会漏掉带 import id 但 trigger 没传对的路径 |
| `trigger == MANUAL` | `MANUAL` | 人点的「刷价」 |
| 按持仓 market 取多数 | `SYNC_METAL_API` / `SYNC_CRYPTO_API` / `SYNC_STOCK_API` | 一个账户混持金属和股票时,标成占多数的那一类 |
| 持仓空 / null | `SYNC_STOCK_API` | 兜底不抛异常 |

**备选:不推断,来源不明就写 UNKNOWN。** 不选 —— 那会让 90% 的定时估值行都是「来源未记录」,等于这个功能对最常见的场景没生效。推断的错误代价很小(混持账户可能标成占多数的那类),而收益是绝大多数行有准确来源。

**备选:把来源做成 `TriggerKind` 的第 5、6、7 个值。** 不选 —— 触发方式和数据来源是两个正交维度:同一个 `CRON` 可以是股价也可以是金价,同一个 `HOLDING_CHANGE` 可以是人改持仓也可以是富途同步改的。合成一个枚举会让「富途同步 + 定时触发」这种组合表达不出来。

### 一次刷新只算一次

`refreshAllForFamily` 里同时写 `period_snapshot`(余额)和 `stock_valuation_event`(变动),两处必须是同一个来源。所以 `inferSource` 的结果存到局部变量传给两边,而不是各调一次 —— 两次调用之间 holdings 不会变,但「同一件事算两遍」本身就是将来不一致的入口。

## D3 · 解析永不抛异常

```java
public static LedgerSource parse(String raw) {
    if (raw == null || raw.isBlank()) return UNKNOWN;
    try { return valueOf(raw.trim().toUpperCase(ROOT)); }
    catch (IllegalArgumentException e) { return UNKNOWN; }
}
```

**为什么不 fail-fast**:这一列是**展示用的元信息,不参与任何金额计算**。将来加了新来源、用户又回滚到老版本,老代码读到不认识的值应该显示「来源未记录」,而不是让整个流水页 500。

代价:拼错的 tag 不会被立刻发现。用单测覆盖每个枚举值都有 label + group、以及 `ofBroker` 的映射来补。

同理,四张表的 INSERT 都用 `COALESCE(#{sourceTag}, 'UNKNOWN')` —— 列是 `NOT NULL DEFAULT 'UNKNOWN'`,但 MyBatis 显式传 NULL 会绕过 DEFAULT 直接撞 NOT NULL。任何我漏掉的写入口(以及测试里 builder 不设这个字段的地方)都会安全落到 UNKNOWN,而不是插入失败。

## D4 · 向后兼容(prod 已上线)

schema 四条自检:

| 检查 | 结论 |
|---|---|
| 只做 ADD COLUMN? | 是,4 条 `ADD COLUMN`,不改任何既有列的类型/语义 |
| 动金额了吗? | 没有,不碰任何 `DECIMAL` 列 |
| 老代码读新表? | 正常 —— MyBatis 按列名映射,多一列被忽略 |
| 新代码读老数据? | 回填后没有 NULL / 空串,页面不会出现空标签 |

回滚:回滚到老版本后新列被忽略,不影响老代码读写(它的 INSERT 不带这一列,DEFAULT 生效)。

迁移里除了 `DEFAULT` 还显式写了 4 条 `UPDATE ... WHERE source_tag IS NULL OR source_tag = ''`。`DEFAULT` 已经覆盖了 ADD COLUMN 的场景,显式 UPDATE 是为了**让意图留在迁移文件里**,并覆盖将来有人手工插过空值的情况。

beta 实测(V56 应用后):`cash_flow` 489 / `transfer` 32 / `period_snapshot` 3355 / `stock_valuation_event` 1288,全部 `UNKNOWN`,零 NULL。

## D5 · 失败状态存在哪里

复用已有的 `broker_link.last_status`(VARCHAR),不新增列。

**关键取舍:失败时不写 `last_synced_at`。**

```java
@Update("UPDATE broker_link SET last_status = #{status} WHERE account_id = #{accountId}")
int markFailed(long accountId, String status);
```

`last_synced_at` 的语义是「**上次成功**同步」,页面上显示成「上次同步:…」。失败时更新它,等于把失败伪装成同步过 —— 这正是 v1.17.3 事故里最坏的那一半(页面显示两天前的成功消息)。

**备选:加一列 `last_failed_at` + `last_error`。** 更规范,但要动 prod 表结构,而 `last_status` 本来就是给「上次结果」用的、当前已经在页面上渲染。判别失败用前缀 `同步失败` —— 有点脏,但它同时也是**给用户看的文案**,把判据和文案统一在一个字段上,不会出现「文案改了判据没改」。护栏钉住这个前缀。

## D7 · 标签样式为什么不复用 `.pill`

`.pill` 是 `padding: 4px 10px` + `10.5px` + `0.1em` 字距 + `uppercase`,为「一个区块一枚」设计的。流水时间线是**每行一枚**:

| | `.pill` | 新增 `.src-tag` |
|---|---|---|
| padding | 4px 10px | 1px 5px |
| font-size | 10.5px | 9.5px |
| letter-spacing | 0.1em | 0.02em |
| text-transform | uppercase | 无 |

理由:用 `.pill` 会把行高撑开、把紧凑的账本读感搞散;而且标签内容是中文,`uppercase` 无意义、`0.1em` 字距对中文是负优化。

分组配色沿用既有 token,不新增颜色:auto=黄铜(`--brass-soft`)· broker=石板蓝(`--slate-soft`)· import=森绿(`--forest-soft`)· manual/system=中性 · **unknown=虚线 + 透明底 + `--ink-faint`**。

最后一条是刻意的:历史行占绝大多数(beta 5164 行全是 UNKNOWN),如果它有实色底,整页会变成一片标签墙,反而盖掉真正有信息的那几枚。

## D9 · v1.18.6 · 对账扫描加「第二视角」(判据没错,视角只有一个)

### 问题:一次真实误报,而且方向是「让人删掉真实存在的钱」

v1.18.2 的时间线判据是对的 —— 但它只看**某一个瞬间**:「这次估值的 Δ 恰好抵消了刚进出的钱」。
生产上有一格确实命中,而真相是:

```
07-20 15:03  转入 +A                ← 我漏看了这一笔
07-20 15:08  转入 +B
07-23 14:34  转出 −B
07-23 14:34  估值 Δ +B   (IMPORT)   ← 用户转账后立刻重导了持仓截图
07-31 10:13  估值 Δ  −C  (IMPORT)   ← 8 天后又导了一次,账已经做平
```
(金额用符号代 —— 仓库是公开的,真实余额不进库;见护栏 `v111-NO-PROD-AMOUNTS`)

判据命中了 `07-23` 那一格,于是报「这一笔要补回来」。但**整期一算就自洽**:
`期末 − 期初 − 净流水` 得到的隐含损益,与 `07-31` 那次导入记录的 Δ 吻合到可以接受的范围。
**照着报告去补 = 凭空删掉一笔真实存在的钱。**

维护者当场推翻了我的结论(「这个账户和我真实持仓是对得上的,你为什么判断我要扣那么多?」)。

### 备选方案

| 方案 | 做法 | 取舍 | 选? |
|---|---|---|---|
| **A · 收紧判据** | 只认 `trigger_kind = CRON` 的抹钱,忽略 `IMPORT` | 简单。但**会漏真**:导入同样能抹钱(它就是走同一条写回);而且把「误报」换成「漏报」不是改进,只是换个方向出错 | ✗ |
| **B · 加「已处理」标记** | 页面上给每条 finding 一个人手打的「已处理」按钮 | 直觉上最省事。但**标记会和数据分家** —— 补过之后又被抹一次,标记还挂着「已处理」;而「同一件事两份判据」正是这一整个 bug 家族的形状(已归档 6 次)。用人手标记来治「判据看不见后续」的病,是在原病上再叠一层 | ✗ |
| **C · 加第二视角:整期是否自洽** | 每条 finding 附 `隐含损益 = 期末 − 期初 − 净流水` 与 `残留 = 隐含损益 + 被抹掉的钱`,按残留是否 ≈0 给结论分级 | 判据不动(它没错),补的是**缺失的那个视角**。钱补回来之后同一条痕迹**自动降级**,顺带把 B 想要的效果拿到了,而且是**数据自己说的** | ✓ |
| **D · 直接不报「可能已纠正」的** | 残留 ≫ 0 就整条隐藏 | 页面清爽,但**把判断权从人手里拿走了**。整期视角也有盲区(见下),而且那条痕迹本身是有价值的历史证据 | ✗ |

### 选定:C

```
隐含损益 = 期末 − 期初 − 净流水         (与事实表 periodPnl 同口径)
残留     = 隐含损益 + 被抹掉的钱

残留 ≈ 0 → 期末余额【至今仍差着】这笔钱   → stillMissing,真要动手
残留 ≫ 0 → 期末余额后来被改动过           → 需人工核对,别照着删钱
```

生产两格正好分开:一格残留 = 0(钱确实没回来),另一格残留是 10 万量级(那次重新导入把账做平了)。

配套三件:

1. **口径抄事实表**。`findBalancesForReconcile` 的期初/期末子查询照抄 `FactMapper.xml`
   (期末为空沿用 ≤ 当期的最近一期 —— 用户漏填不该被读成"余额归零";期初取严格更早的一期)。
   两处口径分家正是这个 bug 家族的形状,所以 `v1186-RECONCILE-NO-BLIND-FIX` 连 SQL 的形状一起 grep 住。
2. **措辞降级**。页面不许再出现「需要补回」这类断言,改成「疑似 · 请核对」;
   护栏里有一条**反向** grep 钉住它不会退回去。
3. **排序改成先确定性、再金额**。否则「大额但存疑」的排第一,人照着它去删钱 —— 这正是这次出事的路径。

### 盲区(写出来,免得下一个人以为这是判决书)

整期视角也会错:账户当期真实涨跌**恰好等于**缺口时,残留也会 ≈ 0(概率极低但不为零)。
两个视角都可能出错,所以这一页的定位是**把可疑的地方指出来给人看,不是替人做决定**。
