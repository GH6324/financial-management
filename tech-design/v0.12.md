# Tech Design · v0.12 · 收支填报「收入侧」升级(结构化 · 关联账户 · 直接入账)

> 状态:**待评审(TDD 阶段)** · 对应 `prd/v0.12.md` · 预览 `preview/v0.12/income-entry.html`
> 本文是实施权威源。每个关键决策列备选 + 取舍 + 为什么不选。约束红线:账户级颗粒度 · 10 分钟/月 · 不做逐笔明细账 · prod 已上线须 backward-compat · 币种不变性([[feedback_currency_invariance]])。

## 0. 现状触碰面(实施前必读)

| 组件 | 现状 | 本迭代关系 |
|---|---|---|
| `cash_flow`(表) | (id, period_id, account_id, kind, category_code, amount, occurred_at, note, submitted_by, is_adjustment, deleted_at) · `CashFlowMapper` 有 `insert / findById / findByPeriodAndAccount / softDelete`,**无 update** | 收入录入就写这张表(单一来源) |
| `cash_flow_category` | (code, display_name, kind, sort_order) · 现有 INCOME:salary/bonus/other_income/interest_income | 加 `account_type` 列 + 新类目 |
| `EntryService.addCashFlow` | 写 cash_flow + `applyDeltaToBalance`(改 period_snapshot.end_balance)· 不校验类型 · 类目由 caller 传 | 收入录入的后端底座(增强) |
| `applyDeltaToBalance` | 找当期 snapshot(无则退上期末)+ delta → upsert end_balance | 现金账户收入走它;**股票账户不能走它**(见决策 4) |
| STOCK 账户估值 | 余额 = Σ持仓(AUTO 股数×价 / MANUAL / **CASH 现金行**)· 估值刷新重算并 upsert snapshot → **会覆盖 applyDeltaToBalance 的 delta** | 股票收入必须落 CASH 现金行(`StockHoldingService.adjustAccountCash` 同款) |
| `period_member_cashflow`(PMC「2框」) | 成员级月度总收入+总支出 · 无账户关联 · 驱动人赚/储蓄率(PMC 优先,空则回退 cash_flow) | **收入侧口径切走**(决策 5),支出侧不动 |
| `FactViewServiceImpl` | `pmcFirstNetInflow`/`cashflowBreakdown` = PMC 优先否则 cash_flow;`familyXirr` 外部流入取 `periodIncome/periodExpense`(cash_flow);账户 `netPrincipal` 取 cash_flow | 收入侧统一到 cash_flow 汇总 |
| V33 `is_adjustment` | 手动改股票现金行 → 记一笔 `cash_adjust` 流水(剔出 PnL)· `is_adjustment=1` | 与"真实收入"区分(决策 4) |

## 决策 1 · 收入录入的端点与后端底座

- **背景**:收入侧要收集 `{金额, 类目, 目标账户}` 并落库+入账。现有 `POST /entry/{accountId}/cash-flow → addCashFlow` 已能写 flow + 入账,但:①类目写死、无类型校验 ②对股票账户会走 applyDeltaToBalance(被估值冲掉)。
- **选定**:**新增瘦端点 `POST /entry/income`(params: periodId, accountId, categoryCode, amount, note)**,内部委托增强后的 `EntryService.recordIncome(...)`:校验类目↔账户类型(决策 3)→ 按账户类型路由入账(决策 4)→ 写 cash_flow。删除 `POST /entry/income/{cashFlowId}/delete`,改额 = 删+录。
  - 理由:收入侧是"选账户再录"的表单,accountId 在表单里而非 URL 路径,`/entry/income` 语义更顺;且要塞类型校验 + 股票路由,单独一个方法比在通用 addCashFlow 里加分支干净。
- **备选(否)** 复用 `/entry/{accountId}/cash-flow`:要在通用 addCashFlow 里塞"是否股票→走CASH行""类目校验",把通用现金流入口搞复杂,且账户级 -支出/划转仍用它,职责混淆。
- **备选(否)** 纯前端 HTMX 直接拼 accountId 到旧端点:绕不开股票路由 + 服务端校验,治标。
- 账户级「+收入」按钮(`_row.html` 硬编码 salary 那个):**移除**(收入统一走收入侧);`-支出`/`划转` 保留不动。

## 决策 2 · 类目 ↔ 账户类型 绑定怎么建模

- **背景**:FR-147 要"选类目→筛账户 + 服务端校验",需要知道每个收入类目绑定哪种账户类型。
- **选定**:`cash_flow_category` **加一列 `account_type VARCHAR(16) NULL`**(仅 INCOME 类目填;NULL=不限)。迁移 V34:加列 + 补类目 + 回填现有类目绑定。
  - 绑定:`工资/奖金/利息(interest_income) → CASH`;新增 `stock_salary(薪资-股票)/dividend(股息·分红)/stock_sell(卖出回款·赎回) → STOCK`。`other_income` 留 NULL(不限,兜底)。
  - 类目下拉排序(sort_order):**工资=10、薪资-股票=20**(用户点名的默认前二),其余顺延。
- **备选(否)** 独立映射表 `category_account_type`:多一张表 + join,收益为零(一个类目对一个类型,加列足够)。
- **备选(否)** 代码里写死枚举映射:改类目要改代码 + 违背"运营配置走 DB"([[feedback_admin_runtime_config]] 精神);加列可后续管理页维护。

## 决策 3 · 类目↔账户 联动校验(防录错)

- **选定**:**前端联动 + 服务端红线,两端都做**。
  - 前端:账户下拉每个 option 带 `data-acct-type`;类目 `<select>` 每个 option 带 `data-acct-type`;JS 监听类目 change → 隐藏/禁用不匹配类型的账户 option(反向亦然)。纯 JS、无请求。
  - 服务端(红线):`recordIncome` 里断言 `category.accountType == null || category.accountType == account.type`,否则抛 `IllegalArgumentException`("类目「工资」不能录入股票账户")。前端可绕过,服务端不可。
- **备选(否)** 只前端过滤:可被改 DOM / 直接打接口绕过 → 脏数据。必须服务端兜底。
- **备选(否)** 只服务端(报错):体验差(录完才报错);前端联动是体验、服务端是正确性,二者都要。

## 决策 4 · 股票账户收入落点(FR-144 核心正确性)

- **背景**:股票账户余额由估值算出(持仓+CASH现金行);`applyDeltaToBalance` 直接改 snapshot 的值**会被下一次估值刷新重算覆盖** → 股息凭空消失。且股息是**外部现金进账**(落券商现金),不是持仓市值涨。
- **选定**:`recordIncome` 按账户类型路由:
  - **CASH/其它非股票账户**:`applyDeltaToBalance(+amount)`(现状,snapshot 就是余额真值)。
  - **STOCK 账户**:调 `adjustAccountCash(familyId, accountId, 账户币种, +amount)` —— 加到该账户的 **CASH 现金行**(没有则建);估值刷新只重算 AUTO 持仓市值、**不动 CASH 行** → 股息稳定留存。**同时**该账户 snapshot 由估值链路自然含入 CASH 行(不手动 applyDelta,避免双加)。
  - 两类都写一条 `cash_flow`(INCOME · category · **is_adjustment=0** · 真实外部收入),被 PnL 正确剔除(外部流入)。
- **与 V33 `cash_adjust` 的区别**:`cash_adjust`(is_adjustment=1)= 用户手动改现金行的本金进出(无语义收入);本迭代的股息/薪资-股票 = **真实外部收入**(is_adjustment=0,有类目),两者都进净流入被剔出 PnL,但收入类的计入"家庭收入汇总"(决策 5),`cash_adjust` 不计入。
- **备选(否)** 股票收入也 applyDeltaToBalance:被估值刷新覆盖,收入丢失 —— 这正是要修的 bug。
- **备选(否)** 股票收入只记 flow 不落 CASH 行:flow 有了但账户余额不涨(与"直接入账"矛盾)。
- **股息是"人赚"还是"钱赚"?**(语义,见决策 5 的待定项):本迭代按 PRD 口径"收入=外部流入不进 PnL",故股息不抬高 XIRR;是否计入家庭"人赚/储蓄率"分子见决策 5。

## 决策 5 · 家庭收入侧口径切换(FR-142 · 最高风险)

- **背景**:收入改由录入(account cash_flow)汇总后,`人赚/净流入/储蓄率/月均收入` 的**收入侧**不能再取 PMC 手填收入(否则与录入双计);支出侧不动。历史"决策 B(储蓄区只统计 PMC)"要做**收入侧反向调整**。
- **选定**:
  - `period_member_cashflow` 的 `total_income_input` **停用**(2框 → 只留支出框);历史值只读保留(不迁移)。
  - `cashflowBreakdown` / `pmcFirstNetInflow` 改为:**收入 = `periodIncome(slice, period)`(cash_flow INCOME 汇总,本位币口径,已含币种换算)始终生效**;**支出 = PMC 有填用 PMC.totalExpense×factor,否则回退 cash_flow expense**(支出侧维持原逻辑)。
  - `HouseholdCashflowService`(月均收入 / 储蓄率):收入侧同样切到 cash_flow INCOME 汇总;支出侧不动。
  - `familyXirr` 外部流入已用 cash_flow(`periodIncome−periodExpense`),**天然一致**,不改。
  - **币种不变性**:收入汇总走 `incomeBase`(本位币)再 ×`baseToViewFactor`,与现有 KPI 同法 → 三币种比值不变(纳入 `CurrencyInvarianceTest` 扫描)。
  - **成员归属**:收入按"目标账户 primary owner"归成员;成员储蓄率分子 = 该成员名下账户的 INCOME 汇总,分母同;家庭 = SUM。
- **待你拍板的语义(建议默认)**:投资类收入(股息/利息)是否计入"人赚/储蓄率"分子?**建议:全部收入都计入(口径统一、用户直观)** —— 与 PRD 一致;若你想只让"工资/薪资-股票"计入储蓄率、股息/利息另归,标注后我再拆。
- **护栏(防双计/口径漂)**:新增 `IncomeSourceInvarianceTest`:构造 PMC 收入框已停用 + 若干 INCOME cash_flow,断言 `cashflowBreakdown.income == Σ cash_flow INCOME`(不叠加 PMC 收入),且 `net == income − expense`;qa-run 加静态守护"pmcFirstNetInflow 收入侧不再读 total_income_input"。
- **备选(否)** 保留 PMC 收入作 fallback:PMC 填了 + 录入也填 → 双计,正是要消除的双录。
- **备选(否)** 全砍 PMC、支出也切 cash_flow:超出本迭代(支出侧不动),且账户级支出汇总要处理家庭内转账抵消,风险大。

## 决策 6 · 删/改与余额冲回(FR-145/148)

- **背景**:收入录入=账户那条 cash_flow(同一行);删/改要冲回余额,且**不串扰**余额校准值与其它流水。
- **选定**:**删除 = `cashFlowMapper.softDelete(id)` + 重算该账户当期 end_balance**;改额 = 软删旧 + 录新。重算口径:
  - **CASH/非股票账户**:`end_balance = 上期末 + Σ本期(income − expense) + Σ本期(transferIn − transferOut) + 该账户本期校准增量`?—— 更稳的做法:**保留"用户校准值为准 + 冲回单笔 delta"**:删收入 → `applyDeltaToBalance(−amount)`(与录入时 +amount 对称、幂等)。因为 addCashFlow 当初就是 +delta,softDelete 后 −delta 即回到原状,不动其它流水/校准。
  - **STOCK 账户**:删收入 → `adjustAccountCash(账户币种, −amount)`(CASH 现金行冲回),估值链路自然回落。
  - 家庭汇总/未解释额是**派生量**(实时从 cash_flow 汇总算),删一行后自动正确,无需额外回写。
- **一致性验收**:删/改后 账户余额、未解释额、家庭收入汇总 三处同时对;账户级其它流水不受影响。
- **备选(否)** 硬删 cash_flow:破坏审计([[feedback_prod_backward_compat]] 忌);已有 softDelete。
- **备选(否)** 只删 flow 不冲余额:余额虚高,与录入时 +delta 不对称。

## 关键流程(伪代码)

```
recordIncome(familyId, periodId, accountId, categoryCode, amount, note):
  period  = requireOpenPeriod(familyId, periodId)
  account = requireAccount(familyId, accountId)             # 非 LOAN
  cat     = requireCategory(categoryCode, kind=INCOME)
  assert cat.accountType == null || cat.accountType == account.type   # 决策3 服务端红线
  cf = insert cash_flow(period, account, INCOME, categoryCode, amount, note, is_adjustment=0)
  if account.type == STOCK:  adjustAccountCash(familyId, accountId, account.currency, +amount)  # 决策4
  else:                      applyDeltaToBalance(period, account, +amount)
  markSnapshotTodoDone(period, account)
  return cf   # 前端把这条追加到"收入侧"列表 + 账户明细(同一条)

deleteIncome(familyId, cashFlowId):
  cf = requireOwnedOpenPeriodCashFlow(familyId, cashFlowId)   # 且 kind=INCOME
  softDelete(cf.id)
  if account.type == STOCK:  adjustAccountCash(-cf.amount)
  else:                      applyDeltaToBalance(-cf.amount)
```

## 护栏 / 测试

- 单测:`IncomeSourceInvarianceTest`(收入侧只来自 cash_flow、不叠加 PMC)· `CategoryAccountTypeValidationTest`(工资→股票账户被拒 / 股息→现金账户被拒)· `StockIncomeSurvivesRevaluationTest`(股票录股息 → 估值刷新后仍在 + 不进 PnL)· `IncomeDeleteReversesBalanceTest`(删收入余额冲回、其它流水不动)· 纳入 `CurrencyInvarianceTest`(收入汇总三币种比值不变)。
- e2e(`scripts/e2e.sh` 加主线):股票账户录股息 → 账户余额+X、流水+1、XIRR 不升 → 刷新估值仍在 → 删除 → 余额回落。
- qa-run 静态守护:类目表含 account_type + 三新类目;`recordIncome` 有类型校验;收入口径不读 total_income_input;`_row.html` 已移除硬编码 salary 的 +收入。

## 风险与红线

- **口径双计(最高危)**:收入侧切 cash_flow 时若漏改任一读 PMC 收入的地方 → 双计。用 `IncomeSourceInvarianceTest` + 全量 grep `total_income_input` 读点收口。
- **股票收入被估值覆盖**:必须走 CASH 行而非 applyDeltaToBalance(决策 4)· `StockIncomeSurvivesRevaluationTest` 网住。
- **backward-compat**:V34 全 ADD COLUMN NULL + 新行 · prod 老数据 0 影响 · 部署走 deploy.sh 交互确认迁移。
- **10 分钟**:收入侧连续加几笔即可,支出仍一个数,不超预算。
- **tag/push/发 prod**:完成后走 [[feedback_tag_must_verify]] · 等你验收 + `release vX.Y.Z`。

## 非目标(承 PRD)
