## 1 · 决策:跨页数值不一致怎么修

### 现象
同一时刻 dashboard 净资产 ¥4,209,016,checkup ¥5399878(≈ dashboard 的总资产),紧急储备 7.2 月 vs 723 月。

### 定位
两处 anchor 账期选取规则不同:

| 页面 | 规则 | beta 上落到 |
|---|---|---|
| dashboard `resolveAsOf` | 优先 OPEN → 否则**不晚于今天**的最新期 → 兜底最新期 | 2026-07 |
| `FamilyDiagnoseService` | 裸 `findLatest(familyId, 1)`(**含未来期**) | 2029-09(测试期) |

讽刺的是 `FamilyDiagnoseService` 的注释写着「改为与 dashboard 同口径」—— 上一次修复误读了 dashboard 的规则。

### 备选方案

| 方案 | 做法 | 取舍 |
|---|---|---|
| A · 抽公共 `PeriodAnchorService` | dashboard / reports / checkup 全走同一个解析器 | 最干净,但 reports 的 anchor 语义本就不同(只取**已关账**期,配合「已关账快照」定位),强行统一会破坏 reports 的产品含义;且改动面扩到 3 个 controller |
| B · checkup 复用 dashboard 规则 + 页面标注账期 ← **选定** | `FamilyDiagnoseService.resolveAnchor()` 逐条复制 dashboard 规则,并把 anchor 回传页面显示 | 改动最小、语义正确;reports 保留自己的「已关账」语义不动 |
| C · 只在页面标注账期,不改规则 | 让用户自己看出两页不同期 | 治标不治本 —— 用户仍会看到两个净资产 |

**为什么不选 A**:三个页面的 anchor 语义**本来就该不同** ——
dashboard 是「进行中的现在」、reports 是「已关账的稳定快照」、checkup 是「体检当下」。
把它们抽成一个函数会诱导后来人误以为三者必须一致,反而埋雷。真正需要统一的只有 dashboard 与 checkup 这一对。

**为什么保留标注**:即便规则统一了,「显示数据账期」本身是必要信息(reports 早就这么做了)。
方案 B = 规则统一 + 标注,两件事都做。

### 落点
- `FamilyDiagnoseService.resolveAnchor(long familyId)`(public,供 controller 回显)
- `CheckupController` 增加 `anchorPeriod` model 属性
- `checkup/family.html` 标题下渲染「数据截至 X · 与仪表盘同期口径」

## 2 · 决策:异常值兜底放在哪一层

紧急储备 = 流动资产 ÷ 月均支出,分母趋零时输出 723 个月。

| 方案 | 取舍 |
|---|---|
| 计算层夹逼(算的时候就 cap) | 会污染真实值,下游 AI prompt / 规则引擎拿到的是被改过的数 |
| **展示层收敛 ← 选定** | 真实值保留给规则与 AI(它们需要知道「极端充裕」这个事实),只在给人看的地方收敛 |
| 阻止计算(分母过小返回 null) | 丢失「充裕」这个有效信息,且 null 会让下游多处判空 |

落点:`FamilyDiagnose.EMERGENCY_OUTLIER_MONTHS = 36` + `emergencyMonthsLabel()` / `emergencyOutlier()`;
`DashboardController.emergencyLabel()` 复用同一阈值常量(避免两处阈值漂移)。

## 3 · 决策:1px 发丝网格的空位露底

旧写法 `grid gap-px bg-rule`:靠**容器底色从 1px 缝隙透出来**画网格线。
格子数不满一行时,空位也透出米灰色,形成突兀色块(9 类型 ÷ 6 列空 3 格 / 5 KPI ÷ 2 列空 1 格)。

| 方案 | 取舍 |
|---|---|
| Thymeleaf 补占位格 | PC 6 列与移动 2 列需要补的数量不同,同一 DOM 无法同时满足 |
| 最后一格 `grid-column: span N` | CSS 无法自动算,仍要服务端算列数 |
| **容器白底 + 子项右下边线 ← 选定** | `.grid-hairline { background:card; border-top; border-left }` + `> * { border-right; border-bottom }`,空位天然是白底;列数无关 |

代价:外框由「容器上左 + 子项右下」拼成,所以原本额外写了 `border border-rule` 的两处要去掉外框(否则双线)。
已全站替换 17 处。

## 4 · 决策:移动端折叠用什么机制

需要「窄屏收起、PC 展开」且**PC 零回归**。

| 方案 | 取舍 |
|---|---|
| 两套 DOM(`md:hidden` / `hidden md:block`) | 双写必然漂移 —— review 里已抓到 accounts 表格有「账本 CSV」而卡片没有 |
| CSS `max-height` + `overflow` 折叠 | 无法可靠计算内容高度,且丢失原生可访问性 |
| **`<details open>` + 窄屏 JS 去 open ← 选定** | 一套 DOM;原生键盘可达;PC 上 `summary` 由 CSS 隐藏且恒 open → 逐像素零回归 |

关键细节:
- `.filter-fold > summary { display:none }` 只在 `min-width:768px` —— PC 看不到折叠条
- HTMX 换入的区块要重新收起(用户刚改完口径,应直接看结果),但**填报行不收起**(那是用户正在操作的行)
- 因此两套折叠的 JS 时机不同:`filter-fold` 监听 `DOMContentLoaded` + `htmx:load`;`entry-fold` 只监听 `DOMContentLoaded`

## 5 · 坑:Tailwind Play CDN 覆盖自有样式

`.kpi-band { display:flex }` 与 `.summary-band` 首次部署后**完全没生效**。

原因:`layout.html` 里 `style.css` 在第 33 行、`tailwind.js` 在第 34 行 ——
Play CDN 运行时注入的 `.grid { display:grid }` 与我们的类**同为单类选择器**,后注入者胜。

解法:`display: flex !important`(仓库既有手法,见 `style.css` 末尾的 `text-[Npx]` 字号档位,
同样是为压 Play CDN 生成值而加 `!important`)。

**教训**:凡是要覆盖 Tailwind 工具类(`grid` / `hidden` / `flex` / `text-*`)的自有类,
都必须提高特异性或加 `!important`,否则静默失效 —— 而且截图不看仔细会以为改好了。

ECharts sunburst 的 label 沿弧旋转,小半径上中文被转到接近垂直 —— 竖排中文不可读,小块还溢出圆外。

## 7 · 决策:风险维度配色

风险是**有序(ordinal)**维度,套分类色板会得到「高风险=紫 / 中风险=粉紫 / 低风险=青」——
从颜色读不出轻重。

实现上不能简单「按维度名判断」,因为 lens 的 `colorMapFor(values, ring)` 只拿到维值数组,不知道当前维度是什么。
做法:**按维值内容识别** —— 命中 `RISK_RANK` 表(覆盖「低/低风险」等两种写法)≥ 2 档即认定为风险维度,
改用 8 档顺序色阶(与 `checkup` 的 `riskColors` 同一套);未分类等给中性纸灰,不参与冷暖序。

取舍:这是启发式而非显式声明,好处是旭日与排行**自动共享**同一判断(它们都调 `colorMapFor`),
坏处是若将来出现名字里带「低/中/高」的非风险维值会误判。当前维度池里无此风险,后续如有需要再改成显式 `dim.ordinal` 标记。

## 11 · v1.6.1 · 自建横屏的技术选择

用户反馈「玩过的游戏类 iOS PWA 能一键切横屏」,推翻了之前「iOS 做不到」的结论。重新评估:

| 方案 | 可行性 | 取舍 |
|---|---|---|
| `screen.orientation.lock('landscape')` | **iOS Safari / PWA 均不支持**(Android Chrome 全屏下可用) | 跨端不一致,不能作为主方案 |
| 请求全屏 + lock | 同上,且 iOS 无 Fullscreen API for `<div>` | — |
| **CSS `transform: rotate(90deg)` + 宽高互换 ← 选定** | 全端可用,无需权限 | 需要用户自己转设备;转了之后必须撤掉旋转,否则双重旋转 |
| 让表格自己变窄(缩字号 / 减列) | 可行但违反 12px 中文红线,且丢信息 | 已在 v1.6.0 用「分组卡片 + 转置」解决默认路径,横屏是「要看原始交叉」的显式入口 |

选定方案的三个关键点:

1. **旋转只在设备竖着时加。** `landscape.js` 用 `innerHeight >= innerWidth` 判方向,
   监听 `orientationchange`(iOS 转屏后尺寸要一拍才稳,故 `setTimeout 220ms`)与 `resize` 动态摘挂 `.rot-rotate`。
   漏了这一步会出现「用户转了手机 → 画面又被我们转回竖的」。
2. **用 `100dvh` 而不是 `100vh`。** iOS 地址栏收放会改 `vh`,旋转后表现为画面被裁或溢出;
   `@supports not (height:100dvh)` 留了 `vh` 回退。
3. **DOM 移入而非克隆。** 克隆会让 `lens.js` 里持有的容器引用失效、并产生重复 id;
   移入 + 占位符回填则对上游脚本完全透明。

触摸滚动不需要额外处理:容器被 transform 后,浏览器把手指位移映射进容器局部坐标系,
用户上下滑 = 视觉上的上下滑,方向天然正确。

顺带修正 v1.6.0 的一处过度设计:KPI 横滑。核心指标的诉求是「一目了然」,
而横滑意味着有指标在屏幕外 —— 与目的相悖。退回网格(主指标跨两列 + 其余 2×2 收紧),
5 个指标同屏可见,高度 358px → 273px。
教训:**「主次分明」不该以「看不全」为代价**;当两者冲突时,先保证看全。

## 12 · v1.6.2 · 两个教训

### 教训一:同一语义的阈值散落在两处 = 必然出盲区

旭日的「哪些块在环内标注、哪些块落图下补注」本质是**一个**分界,v1.6.1 却在两个函数里各写了一个数
(`sliceLabel` 用 40°、`renderLeaders` 用 14°)。改动其中一个就出现了 3.9%~11% 的信息黑洞,
而且**在 PC 上看不出来**(PC 有引导线兜底,盲区不存在),只在窄屏复现 —— 我当时只在移动端截图里
看到「标签不再竖排」就以为改对了,没数有多少块彻底没了标识。

固化:抽成 `SUN_LABEL_MIN_DEG` 单一常量,三处引用(`sliceLabel` / ECharts `minAngle` / `renderLeaders`),
并加反向守护 `! grep -qE "deg >= (40|50|60)"` —— 不许再回退到硬编码角度。

另一个连带教训:ECharts 的 `label.minAngle` 会在 formatter **之前**过滤块,
所以只改 formatter 是无效的,两处必须同步。

### 教训二:"信息减半"不算修复

中间档「只给占比不给名字」看起来是个折中,实际上用户看到 `10.3%` 却不知道是什么资产 —— 
与完全空白的差别不大。宁可整块移到补注列表(那里有名有数),也不要在环上留半条信息。

### 全局横屏为什么转 `<body>` 而不是 `<main>`

转 `<main>` 的话 nav 和浮钮仍按竖屏定位,横屏后会飘在奇怪的位置。
转 `<body>` 则 body 成为 transform 容器,其内的 `position: fixed` 元素(nav 顶部墨条 / 隐私浮钮 / 目录 FAB)
改为相对 body 定位 —— 正好跟着一起转,视觉上就是完整的一页横过来了。

代价两处,都已处理:
- body 带 Tailwind `min-h-screen`(`min-height:100vh`),横屏下会把高度撑回竖屏高度 → `min-height:0 !important`
- body 变 `position:fixed` 后页面滚动交给 body 自身 `overflow-y:auto`,需配 `overscroll-behavior:contain`
  防止滚到底带动外层

## 13 · v1.6.3 · 三次才修对的教训

### 教训:先问「图型容量够不够」,再谈标注策略

旭日空块问题我连续修了三版,前两版都在调阈值(40° → 32° → 引导线),都失败。
根因不在标注,在**图型选择**:320px 的环 × 59 个维值 = 每块 6°,这是容量问题,不是排版问题。
一旦把「小块聚合」这个前提加上,标注策略立刻变得简单(每块都够大,直接写名称+占比即可)。

判据固化进 `visual-spec` §6.7 的图表选型:**维值数超过图型容量时,先聚合再画,不要指望标注技巧救场。**

### 坑一:依赖布局时机的尺寸判断

`el.clientWidth` 在首次渲染时可能还不是最终值(实测同一元素读到 630 与 321)。
用它做响应式分支 → 分支悄悄走错档,而且**改参数没反应**,极难定位(我一度以为是部署没生效,
反复重新打包部署、curl 验证 jar 里的 JS 内容才排除)。

固化:响应式分支一律用 `window.innerWidth`,并加反向守护 `! grep -q "= el.clientWidth < 480"`。

### 坑二:Promise 链里的静默失败

```js
Promise.all([renderSunburst(), renderRanking(), renderPivot()]).catch(function (e) {
  document.getElementById('pivot').innerHTML = '加载失败:' + e.message;   // 会被成功的 renderPivot 覆盖
});
```
旭日抛 TypeError(聚合块没有 `children`,下游 `n.children.forEach` 解引用)→ 落进 catch →
catch 写 `#pivot` → `renderPivot` 自己成功后把这段覆盖掉 → **页面完全无声**:
无 console 错误、无失败请求,只有 skeleton 一直转。

两处修正:
1. catch 里加 `console.error` + 在**出错的那个容器**里就地报错(而不是写到另一个组件的容器)
2. 聚合块显式带 `children: []`,并把下游解引用改成 `(n.children || [])` —— 双保险

这条对整个仓库都适用:**catch 不要把错误写到别的组件的容器里**,否则会被那个组件的正常渲染盖掉。

## 14 · v1.6.4 · 方向锁定的三个坑

做「不响应系统横竖屏」时踩了一串坑,记下来:

### 坑一:用 innerWidth 判断设备尺寸会自激振荡

`lockable()` 原本用 `Math.max(innerWidth, innerHeight) < 1200` 限制只在小屏启用。
但 body 被旋转后,浏览器会**重算 layout viewport** —— 实测 `390×844` 变成 `807×1745`。
于是:加 class → 尺寸被污染 → `maxSide > 1200` → `lockable=false` → 移除 class → 尺寸恢复 → 再加 class……
调试日志里两组尺寸交替出现,页面在抖动。

修:尺寸判断改用 `screen.width/height`(屏幕物理尺寸,不受页面变换影响)。
方向判断仍可用 `innerWidth > innerHeight` —— 污染是**等比缩放**,宽高比不变,「谁大谁小」仍可靠。

### 坑二:在 apply() 里主动派发 resize = 自己喂自己

原本为了让图表按新尺寸重绘,apply 末尾 `dispatchEvent(new Event('resize'))`,
而 apply 本身就监听 resize —— 加上坑一的尺寸翻转,就成了正反馈回路。

修:不再派发全局 resize,改为点名调用 `financeCharts[*].resize()` 与 ECharts 实例的 `resize()`。

### 坑三:无条件重写 class

即使修好前两条,每次 resize 都无条件 `remove` 再 `add` 也会引起 layout 变化、可能再触发 resize。
加**幂等**闸门:算出的目标 class 与当前一致就直接 return,一个字节都不改 DOM。

### 留了调试钩子

`window.__oriLog` 保留最近 12 次判断记录(来源 / lockable / 尺寸 / 期望 / 目标)。
这类「多次触发、最后一次说话」的逻辑靠猜是排不出来的 —— 这次正是靠它一眼看出两组尺寸在交替。

## 15 · v1.6.5 · 一条教训:CSS transform 与媒体查询响应式不能共存

整页旋转我做了三个版本(v1.6.2 全局 class、v1.6.3 修振荡、v1.6.4 双向锁定),
每一版都在修上一版的副作用,直到真机反馈才看清:**方向本身不是问题,响应式断点才是。**

`transform: rotate(90deg)` 改变的是**绘制**,不改变 viewport。而响应式布局的全部判断依据都是 viewport:

| 判断依据 | 旋转后 | 结果 |
|---|---|---|
| `@media (max-width: 767px)` | 仍按 844px 判 | 移动端样式失效(7 处) |
| Tailwind `sm:` / `md:` | 同上 | 切宽屏分支(347 处) |
| `100vw` / `100dvh` | 仍是 viewport 尺寸 | 需要手工互换,易错 |
| `window.innerWidth` | **被 layout viewport 重算污染**(实测 390×844 → 807×1745) | JS 判断不可靠 |

四条里前两条根本无法绕过 —— 除非改用 container query(要重写全站响应式)或 iframe 隔离(太重)。

**判据固化**:要旋转的元素必须是「内部不依赖响应式断点」的独立内容(表格、画布、长图)。
凡是内部有响应式布局的容器(尤其 `<body>`),都不要旋转。

附带教训:这三个版本我都只在桌面 Chromium 模拟移动端验证过,而模拟器的 layout viewport
重算行为与真机不同 —— **涉及 viewport / 方向 / 安全区的改动,桌面模拟不足以验证,必须真机**。

## 16 · v1.6.6 · iframe 隔离:为什么它能绕过响应式冲突

### 决策表(呈现给用户、由用户选定 A)

| 方案 | 能否达成「整页横屏 + 转手机零重排」 | 代价 |
|---|---|---|
| **A · iframe 隔离 ← 用户选定** | 能 | 需要嵌套自检、地址栏显示父页 URL、退出时同步内部导航 |
| B · 加构建 + container query | 能 | 项目从零构建变成有构建;453 处 `sm:`/`md:` 逐个改写 |
| C · 局部横屏(只转宽内容) | 不能(只解决宽表格) | 零风险 |

前置事实(用于判断,实测得出):Tailwind 是 **Play CDN 运行时编译**(`vendor/tailwind.js` 412KB,3.4.1),
`@container` / `container-type` 在包内**均为 0 处** —— 所以 B 必须先引入构建体系,不是改几行配置的事。

### 关键实现点

1. **尺寸进入时定死,之后不变。** 这是「零重排」的唯一来源。用 `inner*` 而非 `screen`:
   `screen` 不含 iOS 地址栏占用,会让 iframe 比可视区高、底部被裁。
2. **只转外层 `.ls-stage`,不转 iframe 本身**,`transform-origin: 0 0` +
   `translate(var(--ls-short), 0) rotate(90deg)`。设备已横屏时直接不加旋转 class。
3. **退出按钮放在 stage 内** → 跟着一起转,视觉位置永远正确(放在 shell 上会错位)。
4. **嵌套自检用 `window.self !== window.top`**,不需要 URL 参数、不需要服务端改动。
5. **退出时同步内部导航**:同源可读 `frame.contentWindow.location.href`,不同则父页面跟过去。

### 附带修的一处守护回归

抽 `hBarConfig` 公共工厂后,`v02-CHART` 守护(按「每个 `new Chart` 旁必须有字面
`ChartDataLabels`」计数)对不上了 —— 工厂里那一次注册被两个图共用。
**没有削弱守护判据**,而是把注册提到各调用点(`Object.assign(hBarConfig(...), {plugins:[ChartDataLabels]})`),
计数恢复相等,同时注册位置更直观。

## 17 · v1.6.7 · 为什么是改断点,而不是继续改旋转

### 选型:三条路都能「不重排」,只有一条能「不切布局」

用户拿了 ChatGPT 的三个方案来对照,先说清它们各自解决什么:

| 方案 | 解决的问题 | 在本项目的结论 |
|---|---|---|
| 固定设计稿 + `transform: scale` | 不重排 | **不适用**:锁死 390 宽,横屏 scale = 390/844 = **0.46×**。要看宽表格的财务看板缩到 0.46 倍,不如不横屏 |
| iframe 隔离 | 页面有独立 viewport | **已采用**(v1.6.6),但它只覆盖「主动点横屏」这一半 |
| Container Query | 响应式架构 | **需要先引构建体系**:Tailwind 是 Play CDN 运行时编译,包内 `@container`/`container-type` 均 0 处 |
| **断点同时看短边**(本版) | **不切布局** | **选定**:一处 `theme.screens` 改动覆盖 453 个断点,零模板改动 |

三个候选方案都只解决「重排」,没有一个解决「跟着切布局」—— 因为它们都没质疑
**断点只判宽度**这个前提。而这正是根因。

### 决策 17.1 · 阈值取 480px

| 备选 | 取舍 |
|---|---|
| 440px | 贴着 iPhone 16 Pro Max 短边(440),没有余量;Safari 横屏工具栏高度还会浮动 |
| **480px ← 选定** | 覆盖全部 iPhone 横屏(短边 ≤ 440),同时 PC 窗口极少矮于 480 |
| 600px | 余量过大,会把 iPad 横屏(短边 768/820)之外的小平板也误判成手机 |

**未选 440 的原因**:Safari 横屏地址栏收放会让 `innerHeight` 在 ~350–440 之间浮动,
阈值必须高于上界才稳定。
**代价(诚实记录)**:PC 窗口高度 < 480px 会退成移动布局。实测 1440×460 确实退化。
判断是可接受的 —— 这种窗口本来也放不下宽屏看板,退成移动布局反而更可用。

### 决策 17.2 · 用 `is-embedded` 排除 iframe,而不是把 iframe 做高

横屏 iframe 也是 844×390,新判据会把它误判成手机 —— 而它恰恰是用户主动要的宽屏视图。

| 备选 | 取舍 |
|---|---|
| 把 iframe 做成 1039×480 再 `scale(0.8125)` | 判据纯靠尺寸、零 CSS 管线;但引入 0.81× 缩放,而且改掉了已验证过的横屏观感 |
| **`html.is-embedded` 排除 ← 选定** | 1:1 像素、不缩放;代价是要在 CSS 里写 `html:not(.is-embedded)` |

**未选缩放的原因**:v1.6.6 的横屏视图用户已经看过,改成 0.81× 是拿已验证的东西去换实现上的便利 —— 这是本项目明确禁止的那类取舍。

只有**真正会改变观感**的规则加 `:not(.is-embedded)`(`.kpi-band` 宫格、`.summary-band` 横滑、
`.filter-fold` 把手);纯字号/内距一类无害的不加,少改一点。

`is-embedded` 的落点很关键:必须**内联在 `<head>`、早于样式表**。
它是 CSS 选择器的一部分,首屏绘制前就得在 DOM 上,否则闪一帧移动布局。

### 决策 17.3 · 22 处硬编码收成一个 `vpNarrow()`

图表脚本里散着 22 处 `window.innerWidth < 640|768`。这与「加枚举值要扫模板串条件」
同一种形状:**一个阈值被复制了 22 份,编译器一个都抓不到**。

不逐点改,收成 `window.vpNarrow(w)` 单一出处,并用守护钉住
「模板与 js 里不得再出现 `window.innerWidth < 数字`」—— 网住整类而不是这 22 个点。

### 决策 17.4 · 旋转遮帘必须「瞬盖淡揭」

第一版写成 `opacity` 双向 `.14s` 过渡,实测 `getComputedStyle` 在加 class 后立刻读到 `1` —— 
过渡刚起步。这不只是测量问题:**旋转已经开始而内容还在淡出,那一眼就露了**。
改成加 class 时 `transition: none`(瞬间盖住),移除 class 时才走 `.18s` 淡入。
```css
.ls-shell.ls-turning .ls-stage > * { opacity: 0; transition: none; }
.ls-stage > * { transition: opacity .18s linear; }
```

### 教训

**「不可能」要分清是哪一层不可能。** 我先前说「屏蔽系统旋转做不到」,用户不接受,是对的：
「不监听事件」能做到,「viewport 不变化」做不到 —— 我把两件事混成一句话说了。
真正卡住的从来不是方向,是**断点只判宽度**。找错层,就会连着四版都在改同一个错地方。

## 18 · v1.6.8 · 决策:尺寸归 CSS,JS 只管开关

### 18.1 · 舞台尺寸:视口单位交换 vs JS 量 px vs 容器查询单位

| 备选 | 取舍 |
|---|---|
| **CSS 视口单位交换 ← 选定** | 两方向下盒子物理矩形自动相同;切换与 iOS 重排同刻生效,没有 JS 可以慢一拍;零监听 |
| JS 量 `innerWidth/innerHeight` 写死 px(v1.6.6) | iOS 两个方向工具栏高度不同 → 量出来的值换方向就不成立;且 toggle 永远晚于 iOS 动画 |
| 容器查询单位 `cqw/cqh` | 也能表达"取父盒子的高作宽",但父盒子是**可见区**,而可见区两方向不对称(竖屏 390×747 / 横屏 844×346)→ 交换后仍是两个不同矩形,反而破坏不变量 |

**关键辨析**:`vh` 是 large viewport(工具栏收起时的高度),**基于屏幕、恒定**;
`dvh` 随工具栏收放变化。所以固定尺寸只能用 `vh`。
代价:`vh` 基于屏幕 → 舞台有一条边会压在浏览器工具栏下。这是"两方向同一矩形"与"全部可见"
之间的物理取舍,不可能同时满足;零重排是用户的硬要求,所以选前者。

### 18.2 · 普通模式冻结:信箱式居中 vs 反向旋转

| 备选 | 取舍 |
|---|---|
| **信箱式居中(锁宽 + 居中)← 选定** | 排版逐像素等于竖屏;无 transform → 无旋转方向歧义、不动滚动容器、不丢滚动位置;**转过去仍可读** |
| 反向旋转钉在设备坐标系 | 严格等同系统旋转锁定,但旋转符号取决于用户转手机的方向(`window.orientation` 90/-90),判错即上下颠倒;`body` 变滚动容器会丢滚动位置;内容躺倒不可读 |

**未选反向旋转的原因**:它更"正宗"却更脆,而且用户拿到的是躺倒的页面 —— 还得把手机转回来。
信箱式的观感代价(两侧留白)用 `--paper-deep` 底色 + `box-shadow` 描边 + 浮钮内收三件事收拾掉了。
用 `box-shadow` 而不是 `border` 画描边:`border` 会把盒子撑宽 2px,那就和竖屏差了 2px。

### 18.3 · 软键盘护栏

`orientation` 的定义是 `height >= width` 才算 portrait(W3C)。竖屏弹出软键盘会让可视高度
小于宽度 → `orientation` 翻成 landscape(SO 8883163 · 112★)。
所以每一处横屏判定都必须叠宽度条件:横屏分支要 `min-width: 480px`,竖屏分支要 `max-width: 479px`。
手机竖屏宽度恒为 390 左右,弹键盘也不变 → 不会误触发。

### 18.4 · 横屏模式去掉顶部导航

不是为了省事,是三条实测理由:844 宽放不下 7 个 tab + 字号钮 + 隐私钮 + 用户名(每项折两行);
390 高里导航占 64px = 六分之一;用户在 v1.6.4 已明确说过不希望横屏时冒出顶部 tab 菜单栏。
横屏是一次性阅读视野,退出钮就在右上角。

### 18.5 · 顺带清掉的债

v1.6.1 的 `.rot-*` 局部旋转层(54 行)JS 已无引用,删除。
值得记的是:**它当年就用对了典范写法**,只错了一个单位(`dvh` 当固定尺寸),
而我没去追那个单位,反而整体推翻改成 JS 量 px —— 把一个一行的单位错误升级成了架构错误。

## 19 · v1.6.9 · 方案 B 的实现与代价

### 19.1 · 一条需要写下来的逻辑约束

**「内容在世界坐标系正立」与「内容在设备坐标系不动」在设备旋转时互斥。**

| 模式 | 选哪个 | 后果 |
|---|---|---|
| 主动横屏(读宽表格) | 世界正立 | 必然"响应"设备旋转 → 只能用遮帘盖过程 |
| 普通模式(方案 B) | 设备不动 | 内容躺倒不可读 → 用户会转回来,这正是"锁定"想要的 |

以后再收到"某个视图也要完全不响应旋转"的需求,先用这条判断它是否与该视图的目的冲突,
不要再去改实现。

### 19.2 · 旋转符号:为什么必须 JS,以及判错会怎样

CSS 媒体查询能知道"现在是横屏",但**不知道用户是顺时针还是逆时针转过来的** ——
两者的 viewport 完全一样。而抵消旋转必须知道方向。

| 备选 | 取舍 |
|---|---|
| **`screen.orientation.angle` ← 选定** | 规范定义清晰(viewport 相对自然方向顺时针角度),iOS 16.4+ 支持(MDN BCD 实测 angle/type/change 均 16.4) |
| `window.orientation` | 已废弃,且不同实现符号约定不一致;只作为 16.4 以下的回落 |
| 固定取一个方向 | 用户反方向转手机时内容上下颠倒,过渡时还会看到 180° 翻转 |

### 19.3 · 滚动位置交接:为什么要 capture 阶段监听

冻结时 `body` 变成滚动容器,元素级 `scroll` **不冒泡**,`window` 上收不到。
用 `document.addEventListener('scroll', fn, true)` 在捕获阶段收,一处覆盖两种滚动容器。
恢复放在双层 `requestAnimationFrame` 里,等样式与布局都落定再写 `scrollTop`。

### 19.4 · 已知代价清单(选 B 就要接受)

1. `position: fixed` 浮层的包含块变成 body 盒子 → 按未旋转视口写的几何会错位。
   已处理:冻结态隐藏目录抽屉/遮罩/目录钮/进度条/toast;保留方向钮与隐私钮(小圆钮随 body 转,自洽)。
   **后续新增任何全屏浮层(模态框/抽屉/日期选择器)都要回来看这条。**
2. 滚动手势方向随内容一起转(向"屏幕横向"滑动才是内容的上下滚动)—— 这是钉设备坐标系的必然。
3. `env(safe-area-inset-*)` 仍按真实视口解析,不随旋转翻转;当前布局未依赖它做关键定位。

### 19.5 · 图标

原图标是摄像机(`rect 2,6,14,12` + `M18 9l4-2v10l-4-2`),语义完全不对,全仓三处都在用。
换成"屏幕旋转":`rect 8.5,2,7,13`(竖屏机身)+ `M19.5 11.5A8 8 0 0 1 11.5 19.5`(顺时针弧)
+ `M9.1 17.1 11.5 19.5 13.9 17.1`(沿弧切线的箭头)。守护里钉住"摄像机路径不得再出现"。

## 20 · v1.6.10 · 横屏导航:用类名钩子而不是结构选择器

### 20.1 · 为什么给 nav.html 加 6 个类名

横屏的覆盖需要精确命中「导航容器 / 左侧组 / 品牌文字 / tab 组 / 右侧组 / 隐私钮」。

| 备选 | 取舍 |
|---|---|
| **加语义类名钩子 ← 选定** | `nav-inner / nav-lead / nav-brandtext / nav-tabs / nav-actions / nav-priv`;不改任何视觉,守护可直接钉住 |
| 结构选择器(`> div:first-child > span.flex-col`) | 零改动,但和 DOM 顺序死绑 —— 以后动一下 nav 结构就静默失效,而且读不出意图 |
| 给 nav 片段做一份横屏专用副本 | 两份要同步维护,必然漂移 |

### 20.2 · 压缩垂直节奏:钉 Tailwind 类名而不是逐页改

页面标题块的 `mt-10` 之类散在各页(`mt-8`×15 / `mt-12`×4 / `mt-10`×1)。
逐页加横屏变体 = 20 处要改且以后新增页会漏。
改成在横屏态下直接覆盖这些 **Tailwind 类本身**(`html.is-embedded main .mt-10 {...}`),
一处覆盖全部,新增页自动继承。

字号只压 `text-4xl` / `text-3xl`(页面大标题),**刻意不压 `text-2xl`** ——
那一档有 74 处、大量用在金额上,压它就违反了 visual-spec 的「可读 > 可点 > 可懂」优先级。

### 20.3 · 退出钮与导航的空间协商

退出钮在舞台层(`.ls-bar`,跟着一起转),导航在 iframe 内 —— 两者互相看不见,
只能靠**约定**:退出钮压到 28px 高、`top:5 right:8`,导航容器 `padding-right: 118px`。
这个 118 与退出钮实际宽度是耦合的,所以两处都写在同一段注释里,守护同时钉住两个数。

## 21 · v1.6.11 · 环图可读性:把旭日图的解法复用过来

### 21.1 · 决策:为什么是聚合而不是换图型

| 备选 | 取舍 |
|---|---|
| **Top N + 其他 N 项 ← 选定** | 把"类目多"这个根因直接解掉;旭日图 v1.6.3 已在真机验证过同一手法;环图的整体感(占比一眼看出)是用户要的 |

### 21.2 · 数字落点:环内占比 + 图例金额

规范要求数字直接落在图上(不能只靠 hover),但环内塞不下「名称 + 金额 + 占比」三样。

`fmtMoney` 对 ≥1 万自动折成「¥182.5万」,图例条目才不会过长换行。

### 21.3 · 一致性判断必须与类目数解耦

`useBar(labels)` 里 `!vpNarrow(640)` 在窄屏恒为 false,**窄屏一致性有数学保证**,
不依赖两个图恰好类目数相近。这一点比 v1.6.4 的 `memFlat`/`flatAlloc` 两个独立变量更强 ——
那种写法只是"当前恰好一致",改动一处就会悄悄分叉,守护也钉不住。

### 21.4 · 踩坑记录:不要读 Chart.js 的已解析 options

验证脚本里读 `chart.options.plugins.datalabels.formatter` 会抛
`Cannot convert object to primitive value` —— `chart.options` 是 Chart.js 的**解析代理**,
读 scriptable 项会被代理立即调用(传入的是它内部的上下文对象)。
要拿原始函数必须读 `chart.config.options`。这是测试侧的坑,不是产品缺陷,
但排查时很容易误判成图表渲染出错。

## 22 · v1.6.12 · 一致性要靠结构保证,不能靠"这次记得改两边"

### 22.1 · 为什么把尺度收进共享常量 / 共用 class

| 备选 | 取舍 |
|---|---|
| **共享常量 `PAIR` + 共用 class `.chart-pair-box` ← 选定** | 一致性由**结构**保证:物理上只有一处可改,不可能单边漂移 |
| 两处各写但"记得同步" | v1.6.11 就是这么坏的 —— `h-[348px]` / `h-[262px]` 当时看着都合理,合起来就不对 |
| 加个守护比较两处数值相等 | 能拦住漂移,但不如"只有一处"来得根本;而且新增第三个图时守护要跟着改 |

一致性问题的通用处理原则:**能用"只有一处"消除的,不要用"两处保持相等"去守护。**

### 22.2 · 环图直径不能交给布局推导

Chart.js 环图默认半径 = f(容器高 − 标题 − 图例)。图例行数随数据条目数变化,
所以**同高容器 + 同样式 ≠ 同直径**。这类"主体尺寸由剩余空间推导"的图,
只要要求并列一致,就必须显式 `radius`。

代价:容器高度得按"最多图例行数"预留,行数少的一侧底部会多一点空白(实测约 20px 视觉偏移)。
这个代价比"两个环一大一小"小得多。

### 22.3 · 删掉按数据量分叉图型的逻辑

`useBar(labels) = 类目 > 6` 这种写法的问题不是判据不对,是**判据是每个图各自算的** ——
两个图数据不同,结论就会不同,于是必然出现一个条一个环。
类目多的真正解法是**聚合**(Top N + 其他,v1.6.3 旭日图已验证),不是换图型。

### 22.4 · 否定断言必须盯代码构造(第三次踩)

`! grep -q "hBarConfig("` 被我自己讲解这段历史的注释扫红了(注释里含 `hBarConfig(窄屏…`)。
前两次是 `100dvh`(注释里在辨析 vh/dvh)和 `window.innerWidth<`(注释里举例)。
**结论:否定断言一律盯代码构造** —— 函数定义 `function X`、调用点 `Object.assign(X`,
不要盯裸标识符,否则解释性注释越写越容易自伤。

## 23 · v1.6.13 · 配色体系的缺口与判据

### 23.1 · 决策:有序色阶放在哪一层

| 备选 | 取舍 |
|---|---|
| **每套方案自带三锚点,插值出 8 档 ← 选定** | 换方案全图一致地跟着走;锚点少(3 个)好维护;能保持各方案性格 |
| 全局一条硬编码色阶(v1.6 UED B4-3 的做法) | 换方案外环不变,且必然与某些方案打架 —— 这正是本次故障 |
| 直接用分类色板 | 颜色读不出高低,B4-3 已否掉 |
| 用 d3-scale / chroma.js 生成 | 要引依赖;项目零构建,不值得为 8 个色值引一个库 |

### 23.2 · 「能不能读出高低」的判据

第一次做的时候用直觉挑锚点,结果 D 的中↔高 距离只有 20(肉眼同色)。
现在有明确判据,写进代码注释与守护说明:

- **相邻档 RGB 距离 ≥ 20**(能分辨)
- **中(rank 4)↔ 高(rank 6)距离 ≥ 40**(最关键的一对,用户最常比这两档)
- **不要求亮度单调下降** —— 绿→黄→红是公认的风险序,而黄最亮;
  拿亮度单调当判据会把标准配色判成不合格(我第一版就这么误判过)

### 23.3 · 聚合块与「未分类」必须分色

两者都是"中性",但语义不同:聚合块是一堆小块的桶(可下钻被禁),未分类是真实维值(可下钻)。
同色会让用户以为是同一类。做法:`aggTint(ring) = mix(NEUTRAL[ring], paper, 0.34)` ——
同族、提亮一档,既不抢维值配色也分得开。

### 23.4 · 两处同步怎么守

`admin/calc-tweaks.html` 的色卡是给用户预览的,值必须与 `lens.js` 一致。
插值后的 8 档没法在 Thymeleaf 里算,只能把结果写进模板 → 天然有漂移风险。
守护利用一个性质:**插值端点就是锚点**(t=0 / t=1),所以只要断言每套的首尾色
同时出现在两个文件里,就能钉住锚点同步。

## 24 · v1.6.14 · 两条会反复咬人的前端事实

### 24.1 · `<main class="relative z-10">` 是层叠上下文

本项目每个页面的 `<main>` 都带 `relative z-10`。后果:

**放在 main 里的任何 `position: fixed` 浮层,都无法升到 `z-30` 的 nav 之上,写多大 z-index 都没用。**

已被它咬过两处(同一天):横屏目录钮被隐私钮压住、抽屉关闭 × 被 nav-inner 压住。

处理原则(按代价从低到高):
1. 让浮层避开 nav 的区域(抽屉 `top: 38px`)—— 零风险,首选
2. 把节点搬出 main(JS 移到 body 下)—— 有风险,涉及事件委托与样式作用域
3. 拆 main 的 `z-10` —— **不要**,它牵连全站的层叠关系

### 24.2 · UI 验证:`display` 不等于"看得见"

`getComputedStyle(el).display !== 'none'` 只说明它参与布局,不说明用户能看到/点到。
必须再验遮挡:

```js
const r = el.getBoundingClientRect();
const top = document.elementsFromPoint(r.left + r.width/2, r.top + r.height/2)[0];
const ok = top === el || el.contains(top);
```

v1.6.13 我断言了 display + 坐标全通过,而用户一眼看出"看不到"。
这条已写进 `AGENTS.md` 护栏,并在 v1613-LS-TOC 的验证脚本里对导航行每个可点元素逐个跑。

### 24.3 · 顺带记一个测试侧的坑

`frame.evaluate(fnString, arg)` —— Playwright 传**字符串**时会当表达式求值,**arg 被忽略**。
我第一版把探针写成字符串模板,结果 `sel` 是 undefined、返回值也不可序列化。
探针要传真函数:`fr.evaluate((sel) => {...}, sel)`。

## 25 · v1.6.15 · 用运行时编译器换断点,替代 iframe 隔离

### 25.1 · 选型重估(v1.6.6 的前提被推翻)

v1.6.6 选 iframe 的理由是「453 处 Tailwind 断点是媒体查询编译产物,无法用 class 覆盖」。
这句话对**静态编译**的 Tailwind 成立,但本项目用的是 **Play CDN 运行时编译器** ——
它可以重新编译。这个前提当时没查。

| 方案 | 切换成本 | 滚动位置 | 复杂度 |
|---|---|---|---|
| iframe 隔离(v1.6.6–v1.6.14) | 1362ms · 整页后端渲染 | 必丢 | 嵌套自检 / URL 同步 / 双文档 |
| **原地换 `tailwind.config` ← 选定** | ~300ms · 零文档请求 | 按章节还原 | 单文档,但要处理 transform 副作用 |
| 引构建 + container query | 0(彻底解决) | 无影响 | 项目从零构建变有构建;453 处要改写 |

**教训**:选型前先确认「限制」是不是真的限制。"编译产物不能改"在运行时编译器面前是假前提,
而我在它上面盖了 9 个版本。

### 25.2 · transform 容器的三个副作用(都实测踩到)

`html.ls-wide > body` 带 transform 之后:

| 副作用 | 表现 | 处理 |
|---|---|---|
| `min-height` 压过 `height` | body 844×844(应 844×390),底部跑屏外 | `min-height: 0 !important` |
| `position: fixed` 变成随内容滚动 | 退出钮滚到 rect 3413,730 | 放进 sticky 导航行,不用 fixed |
| `getBoundingClientRect` 是屏幕坐标 | 章节定位挑错元素(top=3125) | 改用 `offsetTop` 累加 + 直接写 `scrollTop` |

第 2、3 条是同一类:**旋转容器里"视觉坐标"与"布局坐标"分离**。凡是要"钉住"或"定位"的逻辑,
一律走布局坐标(`offsetTop` / `scrollTop`),不要走视觉坐标(`getBoundingClientRect` /
`scrollIntoView` / `elementsFromPoint`)—— 后者只适合判"用户看到/点到什么"。

### 25.3 · 异步重编译要求还原操作幂等且重复

`tailwind.config` 重编译是异步的(~114ms)。任何依赖最终布局的操作(滚动还原)必须:
- 幂等(写同一个 `scrollTop`,不是相对滚动)
- 重复几次覆盖重编译落定的时刻(rAF×2 + 160ms + 400ms)

### 25.4 · 又一次踩「否定断言盯裸标识符」(第 5 次)

`! grep -q "scrollIntoView"` 被我自己那句「不能用 scrollIntoView」的注释扫红。
AGENTS.md 两版前就写了这条规矩,我又犯。已改成 `! grep -qE "\.scrollIntoView\("`。
另外这轮还踩到一个**块删除**问题:用 `s.find('\n# ')` 找守护块尾会匹配到块**内部**的注释行,
只切掉一行 → 出现同名守护两份(一 PASS 一 FAIL)。删块要用块尾的 `log_bad` 行定位。

## 26 · v1.6.16 · 两个可复用的方法结论

### 26.1 · 色板扩容:旋转色相,不要往端点混

需要"同族但更多颜色"时有两条路:

| 做法 | 结果 |
|---|---|
| 往同一端点混(paper / ink) | **会收敛** —— 不同基色混到 50% 时彼此靠得极近。实测同环最小色距掉到 3–7,肉眼同色 |
| **旋转色相、保持明度 ← 选定** | 明度不变 → 内环仍在暗半区、外环仍在亮半区(天然满足"内外环不是一套");色相分开 → 可分辨 |

再加**贪心最小色距筛选**(严格档 ≥24,不够放宽 ≥15,跨环互斥 ≥26),
把"不许撞色"变成构造保证,而不是碰运气。容量 10 → 内环 77 / 外环 45。

### 26.2 · 阈值要按**物理约束**算,不要按比例拍

"多大的扇片才放得下名称"——直觉会写 `pct >= 10%`,但真实约束是**弧长**:
`arc = 2π × 中半径 × pct`。半径变了(窄屏 100 / PC 118)、cutout 变了,同一个百分比
放得下的字数完全不同。按弧长算,阈值一次写对、换尺寸不用重调。

### 26.3 · 图表重排必须显式给尺寸

- `chart.resize()`(Chart.js 无参)实测在容器刚变化时读到旧尺寸 → 必须 `resize(w, h)`
- ECharts 完全不跟容器,必须显式 `resize()`,且要先 `isDisposed()` 判活
- 尺寸来源用 `offsetWidth/offsetHeight`(布局坐标)。**旋转容器里 `getBoundingClientRect`
  宽高互换** —— 我用它量溢出,量出 452px 的假溢出,换 `offsetWidth` 后为 0

### 26.4 · 守护断言不要写死整行

`grep -qF "...{ display: inline-flex !important; }"` 在给同一条规则加一个属性后就红了。
断言写**前缀**或关键片段,别写整行闭合 —— 否则每次微调样式都要回来改守护。

## 27 · v1.6.17 · 三条结构性结论

### 27.1 · 系统级 UI 不能挂在页面加载事件上

`window.load` 等的是**所有子资源**,一个重图表页面能拖两三秒。任何"系统能力"
(方向切换 / 隐私 / 目录)的可用性都不该由它决定。

判断标准:**这个控件的功能是否依赖页面数据?** 不依赖 → 它的可见性也不该依赖数据加载。
本项目的做法:遮罩挂 `DOMContentLoaded`,控件 z-index 抬到遮罩之上。

顺带记一个仍在的限制:浮钮标记在 `footer` fragment(解析最后)→ 大页面上仍要等解析。
前移到 nav 附近会被 `sticky z-30` 的层叠上下文困住(同 `main.z-10` 那个坑),
需要给 nav 换 `th:block` 包装才行 —— 未做。

### 27.2 · 一组同类控件的位置要交给布局,不要各写偏移

三个浮钮原来各写 `bottom: 18 / +48 / +96`。任何一个在某页缺席 → 栈里留洞。
换成 flex 列容器后,"有几个排几个"由布局保证。
**同一族元素的相对位置,交给一个容器;不要在每个元素上算偏移。**
(与 v1.6.12「并列同类元素共用尺度」同源:一致性靠结构,不靠算术。)

### 27.3 · 维度顺序是产品判断,应该写下依据

`LensRegistry.DIMENSIONS` 的注册序直接决定前端下拉顺序。原来的序没有写依据,
所以"风险第一"这种不合适的默认一直没人质疑。现在把依据写在注册处:
**结构类(是什么/在哪/投向/谁的/为什么)在前,属性类(风险/流动性/币种/地域/口径)在后**,
理由是下钻的动机是看结构,属性各自已有专门看板。

### 27.4 · shell 计数陷阱(已进 AGENTS.md)

`grep -c` 对**单个文件**只输出数字、不带「文件名:」前缀;`-r` 或多文件才带。
所以 `grep -c pat file | awk -F: '{s+=$2}'` 在单文件下恒为 0 —— 断言会静默失败。
单文件直接 `-eq N`,多文件才套 awk。

## 28 · v1.6.18 · 三条可复用的结论

### 28.1 · canvas 里的金额,CSS 脱敏管不到

`html.privacy [data-priv] { filter: blur() }` 只作用于 DOM 元素。任何画进 canvas 的金额
(Chart.js datalabels / ECharts label / tooltip)都必须:
1. **生成文案时判隐私**(而不是事后遮)
2. **隐私开关切换时重绘**(已画的像素不会自己变)

本项目已有两处这样做(lens.js 旭日、_region.html 图表),v1.6.18 补上了归因。
**新增任何 canvas 图表都要照这两条做一遍。**

### 28.2 · 跨页面保持的 UI 状态,要在"首次样式计算前"落地

`sessionStorage` 只解决"记住",不解决"闪"。像 `html.ls-wide` 这种影响布局的状态,
必须在 **head 内联脚本**里贴上,并让 tailwind 的**首次编译**就用对应的断点档;
否则新页面先按默认排一遍再被 JS 扳过去。
本项目已有同源做法:隐私模式的 FOUC 防闪(v0.11 决策 129)。

### 28.3 · 「点了没反应」先分清是"没触发"还是"没看见"

用户报"指标放行上点数字没有下钻能力"。实测抽屉**两种位置都打开了**,
差别只是指标放行时表格高数倍、抽屉被推到视口外,而 `scrollIntoView({block:'nearest'})`
只滚最小距离 —— 于是"开了但看不见"被感知为"没反应"。

**排查顺序**:先验事件是否触发、状态是否变化,再验结果是否进入视口。
两者的修法完全不同(前者改绑定,后者改滚动/反馈)。
顺带:任何"点了之后结果在别处"的交互,都该给一个即时确认(本项目用闪一下边框)。

## 29 · v1.6.19 · 写死尺寸的代价要用"缩内容"来还,不能退回自适应

v1.6.12 起两个环图的半径是写死的 —— 那是用户明确要的("两个饼图不能一大一小")。
代价是:**它不会为了让开图例而自动缩**。这次 PC 压图例就是这个代价的兑现。

修的时候有两条路:

| 路 | 取舍 |
|---|---|
| 退回自适应半径 | 一行就能修,但两图又会一大一小 —— **违反上一版用户明确的要求** |
| **保持写死,改布局与内容 ← 选定** | 图例移下方 + 半径降一档 + 图例文案缩短。要多改几处,但两个不变量都守住 |

**通用原则**:当一个不变量(两图同大)与一个约束(空间不够)冲突时,
优先改"可协商的"那一侧(图例位置、文案长度、容器高度),而不是放弃不变量。

另外一条:**同一个信息不要在两处都占空间**。金额自 v1.6.18 起标在环上,
图例里那份就成了纯消耗 —— 去掉它是"缩内容"里最划算的一刀(1024 档全靠这一步过关)。
判据与环上标签共用同一个弧长公式,所以不会出现"两边都没有金额"。
