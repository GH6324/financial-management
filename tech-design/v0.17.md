## 2. 架构选型(每项:备选 → 取舍 → 选定 → 为什么不选其它)

### 决策 1 · 保险落地形态:独立 `INSURANCE` 类型 vs 复用 WEALTH+子标签 vs 复用 OTHER

| 备选 | 优点 | 缺点 |
|---|---|---|
| **A. 独立第 9 类 `INSURANCE`**(选定) | issue 明确要"独立分类";配置/目标/洞察桶**早已按 INSURANCE 预留**,独立类型能直接接线;资产配置能单列"保险占比";保单专属字段有明确归属 | 加枚举要全链扫(§3),CHECK 要 ALTER |
| B. WEALTH + `insurance` 子标签 | 省一个枚举、不改 CHECK | 配置环形图会把保险混进"投资"桶(与 issue 诉求"独立看到保险占比"直接冲突);保单字段塞进 WEALTH 语义含糊;`Bucket.INSURANCE` 预埋位白白浪费 |
| C. 复用 OTHER | 最省 | OTHER 是兜底垃圾桶,语义最差;同样混桶 |

**选 A**。理由:①issue 的核心诉求就是"独立";②代码基建(桶/锚/文案)是**冲着 INSURANCE 独立类型预留的**,复用反而绕开预留、留下死代码;③独立类型的唯一代价(枚举全链扫)已被 §3 清单 + qa 守护网住,是可控的一次性成本。承 [[feedback_enum_add_sweep]]。

### 决策 2 · 保单登记字段落库:account 加可空列 vs 独立 1:1 表 vs JSON 列

字段集(FR-17-3,**全可选**,纯展示、任何引擎都不读):承保公司 / 保单号 / 投保人 / 被保人 / 保额 / 保费 / 缴费周期 / 总期数 / 已缴期数 / 生效日 / 满期日,共 ~11 个。

| 备选 | 优点 | 缺点 |
|---|---|---|
| A. `account` 直接加 11 可空列(loanKind 先例) | 复用 Account mapper,详情/编辑同一次查询,代码最少 | account 是热表(列表/填报/仪表盘每次查),塞 11 个"冷、保险专属、几乎全 NULL"的列是错误形状;loanKind 先例只有 2 列,不可外推到 11 列 |
| **B. 独立 1:1 表 `account_insurance_policy`**(选定) | account 保持精简;保单是冷数据,**只在详情/编辑页 lazy 加载**(且仅保险账户);1:1 干净;向后兼容零 account 列变更 | +1 domain +1 mapper;详情页多一次查询 |
| C. account 加 1 个 `insurance_policy_json` 列 | 只加 1 列、字段灵活 | 违背本仓"类型化列"惯例(loan 用类型化列非 JSON);Thymeleaf 渲染 JSON 笨拙;字段无 schema/无法单独校验;项目仅 `params_json`/`allocation_anchor_custom` 用 JSON,均非展示字段 |

**选 B**。理由:11 个纯展示冷字段与账户核心身份/估值是**不同关注点**,不该污染热表的每次查询;它们只在"查看某张保单"时才需要,天然适合按需 join 的旁表。诚实权衡([[feedback_decision_weight_honesty]]):A 代码更少且贴合 loanKind 先例,但"更少代码"是我的便利、非用户价值,而 11 列冷数据上热表是真实的形状错误;单家庭 <50 账户下 B 的"多一次查询"成本可忽略,换来的是热查询不背保险包袱 + account 表保持内聚。**子类型 `insurance_kind` 也放旁表**(列表只显示"保险"类型 pill,子类型只在详情展示,无需上 account)。

> 若你(Java 工程师)更认同"贴合既有 loanKind 惯例、少一个表" → 可改判 A,我按 A 落列。这是本 TDD 最需要你拍板的一点。

### 决策 3 · 子类型 `InsuranceSubType` 的表达:Java enum + 存 name() vs DB CHECK 强枚举 vs 纯 String

- **选定:Java `InsuranceSubType` 枚举(年金险/增额终身寿/万能险/分红险/投连险/其他储蓄型)提供下拉选项 + 中文 label,持久化存 `name()` 到 `insurance_kind VARCHAR(20)`,DB 不加 CHECK。**
- 取舍:与 `loanKind`(自由 String、无 DB CHECK)同构 —— 未来加子类型只改 Java 枚举、免迁移;DB CHECK 强枚举会让每次加子类型都要 ALTER(过度约束);纯 String 无 Java 枚举则下拉/label 要散在模板里硬编码(违背 [[feedback_user_friendly_naming]] 的"不裸露 code")。
- 子类型仅"展示 + 分组",**不改任何估值/桶逻辑**(所有子类型都是手填现金价值)。

### 决策 4 · 资产配置接入(关键正确性点 · 非选型,是接线纪律)

`AllocationDiff.pickBucket()` 现在**先查 `liquidity_class` 再 fallback type**。保险的产品类目 `SAVINGS_INSURANCE` 流动性 = `SEMI_LIQUID`(可退保变现,定性正确),而 `SEMI_LIQUID → Bucket.INVEST`。**若不特判,保险会被误分进"投资"桶,永远进不了 INSURANCE 桶。**

→ **`pickBucket` 必须在查 liquidity_class 之前,按 `accountType=="INSURANCE"` 短路返回 `Bucket.INSURANCE`。** 这一句是 FR-17-4 的命门,也是 §3 清单里最容易漏的一处。液性仍保 SEMI_LIQUID(供再平衡/体检的流动性判断用),但**配置分桶按类型硬定为保险**。同一句同时修好:环形图 / 再平衡 drift / `d.bucket()` 洞察展示(三者都走 `AllocationService.compute → AllocationDiff`)。

### 决策 5 · 估值:复用手填 snapshot vs 新建保险估值

- **选定:复用 `period_snapshot` 手填,`AccountValuationService` 零改动。** 保险现金价值 = 用户每期手填余额,和 WEALTH/PROPERTY/CASH-手填完全同一条链(FX 折算、净资产、报表全复用)。
- 为什么不新建:保险公司无稳定公开现金价值接口;演示利率不可信且是精算,**不交给系统/LLM 算**(承 [[feedback_llm_no_math]])。手填是唯一可信来源,且已有链路。

### 决策 6 · "已缴保费 vs 现金价值"展示:纯并列 vs 算 IRR/收益

- **选定:详情页把两个**已登记数字**(累计已缴保费、当前现金价值)并列展示,不算差额收益率、不算 IRR、不判好坏。** 早期"已缴 > 现金价值"是保障成本,属正常,只陈述不评价。承 [[feedback_llm_no_math]] + [[feedback_decision_weight_honesty]]。
