> 配 `prd/v1.9.md`(已评审通过)· 范围:**只做「查」**

## 0 · 先盘三个决定设计的事实

### 0.1 nav 数据只能走 `GlobalModelAdvice`

版本徽记的 `appVersion` 来自 `GlobalModelAdvice`(`@ModelAttribute` 注入所有 controller)。
圆点必须走同一条路 —— 它要出现在**每个页面**的 nav 上,不可能让 20 多个 controller 各自塞一遍。

**这条直接推出一个硬约束**:`GlobalModelAdvice` 在**每个请求**上执行。
所以那里面只能做**一次内存读**,绝不能查库、更不能出网。见 §2.3。

### 0.2 已有两条对外调用的先例

`FxService`(汇率)和 `StockPriceFetcher`(股价)都已经在做外部 HTTP + 降级。
本版复用同一套姿势:超时短、失败不抛到调用方、结果落库、**页面只读落库结果**。

### 0.3 `family_runtime_config` 是现成的 KV 表

```sql
family_runtime_config(family_id, key_name, value_text VARCHAR(512), updated_at)
```

已有,主键 `(family_id, key_name)`。够用,**本版零迁移**。

## 1 · 架构选型:检查在哪执行

| 方案 | 怎么做 | 优 | 劣 |
|---|---|---|---|
| **A 前端直连 GitHub** | 浏览器 fetch `api.github.com` | 服务器不出网;实现最简 | ①**每个家人的浏览器**都要能连 GitHub,大陆家用网络时通时不通 ②无法跨用户缓存,60 次/小时的匿名限额按**每个访客 IP** 算但页面刷新即触发 ③服务器不知道结果,`/health` 之类没法用 |
| **B 请求触发懒查(后端)** | 进管理页时若缓存过期就同步查一次 | 不用定时器 | **把网络放进渲染路径**。GitHub 慢 = 管理页慢。违反 PRD FR-300 |
| **C 后台定时查 + 落库,页面只读缓存(选)** | `@Scheduled` 每日一次,结果写 KV;页面永远只读 KV | 渲染永不等网络;跨用户共享一次结果;失败可保留上次成功值 | 多一个定时任务;首次安装当天可能还没查过(可接受:显示「尚未检查」+ 手动按钮) |

**选 C。** 决定性理由是 PRD FR-300 那条硬要求「页面渲染永不等网络」——A 和 B 都做不到。
A 还有个隐性问题:让**非技术家人的浏览器**去连 GitHub,她那边失败会看到控制台报错或空白,而她根本不该被卷进这件事。

> 已验证:beta 上 `api.github.com/releases/latest` 350ms、`compare` 1.5s。
> 但**不能拿这个当依据设计**——「现在能连上」不等于「一直能连上」,这正是我们那条
> 「连通性探针不能当可用性判据」的纪律。所以判据永远是「上一次成功的结果」。

## 2 · 数据与读写路径

### 2.1 KV 键(3 个,全部 `family_runtime_config`)

| key_name | 值 | 说明 |
|---|---|---|
| `update.check.enabled` | `true` / `false` | FR-303 开关,缺省视为 `true`(默认开) |
| `update.check.result` | JSON | 上一次**成功**的结果,见下 |
| `update.check.lastAttempt` | JSON | 上一次**尝试**(含失败),`{at, ok, error}` |

**为什么把「成功结果」和「最近尝试」分成两个键** —— 这是这一版最容易做错的地方:
如果只存一个,失败时要么覆盖掉上次的好结果(页面突然什么都不显示),要么不写(就没法显示「上次尝试失败」)。分开存之后:
**页面读 `result` 渲染,读 `lastAttempt` 显示「检查于 X · 失败原因 Y」。**

`update.check.result` 的形状(压进 512 字符,超了截断版本列表而不是丢字段):

```json
{"at":"2026-08-05T03:00:00Z","latest":"v1.9.0","published":"2026-08-04",
 "behind":14,"mig":{"n":4,"ids":["V50","V51","V52","V53"],"known":true},
 "items":[{"v":"v1.9.0","t":"自动版本查询"},...]}
```

> `VARCHAR(512)` 是既有列宽,不为这个功能改表。`items` 只留最近 5 条(PRD FR-302 就是这么要求的),
> 单条主题超 40 字截断。**写入前做长度校验,超了就逐步丢 `items` 尾部**,绝不写一半 JSON 进去。

### 2.2 谁来写:`UpdateCheckService`

```
UpdateCheckService
  ├─ checkNow(familyId, force)   → 出网 · 写 KV · 返回结果      (定时器 + 手动按钮)
  ├─ cached(familyId)            → 只读 KV · 不出网              (页面)
  └─ enabled(familyId)           → 只读 KV                       (页面 + 定时器)
```

只依赖 `FamilyRuntimeConfigMapper` + 一个 `RestTemplate`/`HttpClient`。
**不依赖任何 service**,和 `ExpenseLedgerService` 同样的理由 —— 谁都能注入它而不成环。

### 2.3 谁来读:`GlobalModelAdvice` 只做一次内存读

圆点要出现在每个页面,只能挂 `GlobalModelAdvice`。但那里**每个请求都会跑**。

| 方案 | 劣 |
|---|---|
| advice 里查库 | 每个请求一次 DB 往返,只为一个圆点。首页、静态页、HTMX 片段全中招 |
| advice 里出网 | 灾难 |
| **进程内缓存(选)**:`UpdateCheckService` 持一个 `volatile UpdateInfo`,启动时 + 每次 `checkNow` 后刷新;advice 只读这个字段 | 多实例部署时各自缓存(本项目单实例,不是问题);写库后要记得刷新内存 |

**选进程内缓存。** advice 里就是一次字段读,零 IO。

> 单实例是这个项目的既定前提(systemd 一个进程 / compose 一个容器)。
> 如果哪天要多实例,这里会漂 —— **在类注释里写明这条前提**,别让后人以为它是集群安全的。

## 3 · 出网:两次调用,各自可失败

### 3.1 取最新版本

`GET /repos/{owner}/{repo}/releases/latest`

- 超时 **connect 3s / read 5s**(比汇率那条更短:这是锦上添花的功能,不值得等)
- 跳过 draft / prerelease(`/releases/latest` 本身就跳过 prerelease,但仍显式判一次)
- UA 带 `financial-management/{version}` —— GitHub 要求带 UA。**注意:这等于把版本号发出去了**,与 PRD FR-303「不带版本号」冲突 → **UA 用固定串 `financial-management`,不带版本**

> 这条是写 TDD 时才发现的与 PRD 的冲突。PRD 承诺「不带版本号」,而 GitHub 要求带 UA,
> 顺手写成带版本的 UA 是最自然的写法。**必须显式写成不带版本**,并落一条守护(§6)。

### 3.2 判断有没有迁移

`GET /repos/{owner}/{repo}/compare/{current}...{latest}` → 数 `files[]` 里 `db/migration/` 开头的。

三种结果,**都要能表达**:

| 情况 | `mig.known` | 页面 |
|---|---|---|
| 拿到清单 | `true` | 「含 N 个迁移(V50…)」/「无 schema 变更」 |
| API 失败 / 当前版本不是合法 tag | `false` | 「**无法确定**,升级前请自行核对 `db/migration`」 |
| `files` 被截断(GitHub 上限 300) | `false` | 同上 |

**截断必须显式判**:响应里 `files.length >= 300` 就当作不可信。
不判的话会得到「无 schema 变更」这个**错误且危险**的结论 —— 这正是 `|| echo 0`
那类"查不出来就当没有"的老毛病(纪律第 8 节)。fail-closed:不确定就说不确定。

### 3.3 失败降级

```
checkNow 失败 → 写 lastAttempt{ok:false,error}
              → result 保持不动(上次成功的还在)
              → 内存缓存不动
```

**永不因为一次失败让页面从"有新版"变成"什么都没有"。**

## 4 · 定时器

复用 `StockPriceScheduler` 那套(项目里已经不用裸 `@Scheduled`,走 `DynamicScheduleConfig`)。

- 每天一次,**时刻错开整点**(用 `03:17` 之类),别和汇率/股价挤在一起
- 启动后延迟 2 分钟再跑第一次 —— 别让启动过程被外部网络拖住
- `enabled=false` 的家庭直接跳过,**一个请求都不发**(FR-303 验收第 6 条)

## 7 · 回答维护者的问题:能不能直接自动更新 + 重启?

### 7.1 结论先说

**能做,而且比我上一版调研时说的容易得多 —— 因为权限通道今天就已经全部存在了。**
**但我建议只做「一键更新」(人点一下),不做「自动更新」(无人值守)。** 区别在 §7.4。

### 7.2 我上次的判断有两条是错的,更正

上次给的四道坎里,前两条不成立:

| 上次说 | 实际 |
|---|---|
| unit 是 `Restart=on-failure`,`exit(0)` 不会被拉起,所以自杀重启那招失效 | **不需要那招**。`deploy.sh` 写的 sudoers 里有 `NOPASSWD: /bin/systemctl restart finance`,应用可以直接重启自己 |
| jar 是 `root:root`,app 跑 `finance`,**无权替换自己的 jar** | **有权**。sudoers 里有 `NOPASSWD: /bin/cp ${REPO_DIR}/target/app.jar /opt/finance/app.jar`,而 `${REPO_DIR}/target` 是 `finance:finance` 可写 |

而且**回滚素材也是现成的**:`cp app.jar → app.jar.prev` 和 `cp app.jar.prev → app.jar` 两条都在白名单里。

**这份 sudoers 是 `deploy.sh` 装给每个直装实例的,不是我 beta 的特例。**

### 7.3 由此带出一个既有的安全属性(与本功能无关,但值得知道)

上面那条通道的另一面是:**任何能在应用里执行代码的漏洞,都能替换 `app.jar` 并重启** ——
即 RCE 可以持久化。危害等级是「以 `finance` 身份持久执行」,不是 root(`cp` 目标固定、
`systemctl` 只能操作 `finance` 服务),但对一个存着全家净资产的应用已经够重。

这是**部署便利带来的既有状态,不是本版引入的**。要收紧的话:把那条 `cp` 换成一个
root 拥有、`finance` 不可写的脚本,脚本内部校验来源和签名。**记进待办,不在本版。**

### 7.4 真正的风险不在技术,在「无人值守」三个字

剩下的技术障碍只有两个,都可解:

- **Release 没有 jar 资产** → 加个 CI job 传 jar(74MB,GitHub 允许);或本地 `git pull && mvn package`(直装用户机器上一定有 maven,是首装脚本装的)
- **DB 迁移单向** → 更新前自动 `mysqldump`(`deploy.sh` 已经在做),但**迁移不会因为回滚而撤销**

风险清单(按我的排序):

1. **一次坏发布 = 所有开了自动更新的实例同时坏。** 他们没有 staging、没有金丝雀、没有灰度。而我们自己的发布流程恰恰有个人工闸门(必须回精确串 `release vX.Y.Z`)—— 因为**我们自己都不信任无人值守的晋级**。自动更新等于把这个闸门从**别人的**实例上拿掉。
2. **GitHub 账号被盗 = 一次 release 推到所有实例。** 供应链攻击面。checksum 防不了这个 —— 攻击者能改 release 就能改 checksums.txt。真要防得签名 + 把公钥硬编进程序。
3. **迁移是单向门。** 自动更新会自动跑迁移;出问题回滚只回 jar,schema 留在新版。旧 jar 读新 schema 通常没事(我们的迁移都是加带默认值的列),但这是**约定不是保证**。
4. **更新时刻不可控。** 无人值守意味着可能在用户正在填报时重启。

一键更新(人在场、点一下、看着结果)把 1 和 4 直接消掉,2 和 3 变成"知情后自担"。
**这就是我建议的分界线。**

### 7.5 如果要做一键更新,路线(登记,不在本版)

1. CI 加 job:构建 jar + 传 Release + 传 `checksums.txt`
2. 更新前:`mysqldump` 备份 + `cp app.jar → app.jar.prev`
3. 下载到 `${REPO_DIR}/target/app.jar`,校验 sha256
4. `sudo -n cp` 换 jar → `sudo -n systemctl restart finance`
5. **健康检查 + 自动回滚**:重启后轮询 `/health`,60s 内没到 200 就 `cp app.jar.prev → app.jar` 再重启(`deploy.sh` 第 12 步已经是这个逻辑,照抄)
6. UI 上必须写明:会重启服务、含 N 个迁移、迁移不可回滚

**Docker 那条路仍然做不了** —— 容器里换 jar 没意义(重建就回旧镜像),要自更新得挂 docker socket,那是把宿主机交出去。和 sub2api 的结论一样:自更新只在直装路径上成立。

## 9 · v1.9.2 修订 · 提示醒目度 + 就地弹窗

### 9.1 徽记:从描边圆点到实心标签

量化过再改,不凭感觉:`--brass-soft #E8D9B6` 对 `--paper #F4EFE6` 约 **1.2:1**;
`--brass-deep #8C6A33` 对纸色约 **4.1:1**。WCAG 非文本元素门槛 3:1,前者不合格。

```css
.ver-new {                       /* 原 .ver-dot 整块删掉,防后人照旧文档加回来 */
  background: var(--brass-deep); color: var(--paper);
  font-size: 7.5px; padding: 2.5px 3.5px 2px; border-radius: 2px;
}
.ver-badge.has-upd { color: var(--brass-deep); }          /* 徽记整体提一档 */
.ver-badge.has-upd:hover .ver-new { background: var(--ink); }
```

**为什么不用红色**(WordPress 的 `#d63638` 是最醒目的方案):红在本项目里是**告警语义**
(`--rust` 用于超支、负值、失败)。把它借给「有新版」这件既不紧急也不是错误的事,
会稀释真告警的信号强度。棕铜色是本项目的「注意」色,语义正好。

**为什么不做闪烁 / pulse**(sub2api 用 `animate-ping` 光环):定位是「每月十分钟」的工具,
顶栏常驻一个动画等于持续索取注意力。静态 4.1:1 已经够看见了。

### 9.2 弹窗挂载点 —— 唯一的技术坑

必须挂在 `<main>` **外面**。`<main class="relative z-10">` 是**层叠上下文**,
放在它里面的 `position: fixed` 浮层无论 z-index 多大都升不到 `z-30` 的 nav 之上,
遮罩会被顶栏压穿(项目里踩过)。

| 备选 | 取舍 |
|---|---|
| 每个页面模板各自在 `</main>` 后引入 | 21 个页面要改 21 处,漏一个就那页没弹窗 · **否决** |
| JS 运行时 `document.body.appendChild` 搬运(`lens-select.js` 的做法) | 能绕开,但要等 JS;首屏点击有竞态 · 否决 |
| **由 `fragments/layout.html` 的 `footer` 片段引入** | footer 只有 `relative`、**没有 z-index**,不成层叠上下文;每页自动都有 · **选定** |

语义上「弹窗写在 footer 里」有点怪,但它是 `fixed`、DOM 位置不影响视觉,
而这是唯一「一处改动、全站生效、且不依赖 JS 时序」的挂载点。同一个 footer 里已经有
`easter520` 这个同形态的注入点,照它的路子走。

### 9.3 渐进增强

徽记保持 `<a th:href="@{/admin(tab='version')}">`,JS 用 `preventDefault()` 接管。
不改成 `<button>` 也不改成 `href="#"` —— 那样禁用 JS 的浏览器点了什么都不会发生。
守护 `v192-UPD-MODAL-DEGRADE` 钉住这一点。

字号全部用 `rem`:根字号可被「A A」缩放控件调,写 `px` 就跟不动。

### 9.4 缓存行里的 `current` 会过期(真 bug)

见 `prd/v1.9.md` 附录。修法是在 `reloadMemo` **内部**用正在跑的 `app.version` 覆盖:

```java
memo = readResult(familyId)
        .map(i -> i.withSummary(...))
        .map(i -> i.withCurrent(appVersion))   // ← 关键
        .orElse(UpdateInfo.unknown());
```

`appVersion` 用**字段注入**而不是构造器参数:单测直接 `new UpdateCheckService(...)`,
不想为它多传一个参。

**为什么不放在调用方**:读缓存的入口有三个(`warmUp` / `setEnabled` / `checkNow` 后回写)。
第一版确实是让调用方传参的,结果只在 `warmUp` 那条路传了 —— 管理页把开关关掉再打开,
`setEnabled` 走的是不带参那条,过期的 `current` 当场复活。收进服务内部就没有漏的入口。

### 9.5 验收方式:让 beta 真的落后

这个功能有个测不动的性质:**开发机的在研版本号永远比已发布最新版更新**,
所以「有新版」那条分支在 beta 上根本不执行(v1.9.1 的 `tagOf` 404 bug 就是这么漏掉的)。

这次不靠手写一行假 KV 数据,而是**临时构建一个 `app.version=1.9.0` 的 jar** 部署到 beta,
让它真的落后于线上的 v1.9.1,然后点「立即检查」走完整链路:
真实 GitHub 调用 → 真实 `latest=v1.9.1` / `behind=1` / `pub=2026-08-06` / 迁移 `known n=0`
→ 真实摘要 → 徽记 → 弹窗里的 Release 链接真的能点开。源码里的版本号立刻改回 1.9.2,
只有产物是 1.9.0。

顺带这也是 §9.4 那条修复的活证明:验收完把 1.9.2 的 jar 部回去,
徽记必须**在重启后立刻消失**,而不是挂到隔天。
