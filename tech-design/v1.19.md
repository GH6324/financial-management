## D1 · 接口选型:为什么最后不是 Managed Agents

维护者的方向很明确:**用阿里云、能复用就复用、不自建编排**。这个方向没变;
变的是**用阿里云的哪个接口** —— 我把三个都查完之后,结论和最初的假设不一样。

| 候选 | 工具怎么执行 | 我们的数据怎么进去 | 结论 |
|---|---|---|---|
| **Managed Agents** | **平台侧**。事件类型是 `tool_call`/`tool_call_output`(沙箱内置工具)与 `mcp_call`/`mcp_call_output`(MCP);**客户端只能写入 `message` 事件** | 只有两条:① 开**公网 MCP 口** ② 把家底**写进云端沙箱文件** | ✗ |
| **Assistant API** | 客户端(`requires_action` / `submit_tool_outputs`) | 客户端执行,不用公网口 | ✗ **官方标注「下线中」**,全站提示迁移 |
| **Responses API** | **客户端**。模型返回 tool_call → 我们执行 → 回传 `function_call_output` | 工具在我们进程里跑,数据不出去 | ✓ **选定** |

### 为什么不选 Managed Agents(它的强项我们一个都用不上)

官方定位是「多步工具调用、**代码执行**、**文件处理**等**长时运行任务**」,卖点是独立沙箱、
装依赖、跨轮保持文件系统状态、中断续接。

我们的场景是**短问答 + 结构化取数**:问一句「哪个账户真在赚钱」,调两三个口径服务,几秒出答案。
不需要 shell、不需要 pandas、不需要跨轮保留文件。

**为用不上的能力付出的代价却是实的**:

- **要么开公网 MCP 口** —— 而百炼的 MCP 托管在函数计算上、**没有固定出口 IP**,做不了 IP 白名单,
  只能靠 Bearer token 护着一个「能读走整个家庭净资产」的公网端点。
  这个产品是**发 Docker 镜像给陌生人自建**的,很多人在 NAT 后面、没有域名 —— 他们直接用不了。
- **要么把家底写进云端沙箱文件** —— 数据落进一个云上容器的文件系统,比「随对话发出去」暴露面更大,
  而且快照是**时点**的,对话中途不更新。

### 为什么 Responses API 是对的

1. **暴露面不变**。工具在我们进程里执行,只有**结果**随对话出去 —— 和现在六个 AI 调用点**完全一样**,没有新增
2. **不开公网口**。NAT 后面、没域名的自建用户照样能用
3. **复用最大化**。端点 `/compatible-mode/v1/responses`,与我们现有通义客户端
   (`dashscope.aliyuncs.com/compatible-mode/v1`)**同一个 base、同一把 key、同一套凭据管理**
4. **没有云端资源要管**。`instructions` + `tools` 随请求发,不是先建好再引用 ——
   原方案里「创建 Agent / 全量替换 + 乐观锁 / 只能归档不能删除 / 并发 upsert」整块消失

### 诚实说这个选择的代价

- **多轮上下文交给了 `previous_response_id`**(服务端托管)。社区反馈它与 `function_call_output`
  配合时有时序问题(`No tool output found for function call`)。对策见 D3。
- **Responses API 本身也在演进**(旧路径 `/api/v2/apps/protocols/compatible-mode/v1/responses` 即将停维,
  要用 `/compatible-mode/v1/responses`)。我们把它包在一个薄适配层后面,见 D2。

## D2 · 分层:哪一层允许知道「我们在用百炼」

这一版最容易做错的是**把供应商细节渗进业务代码**。分三层,每层只知道自己该知道的:

```
web/ask/AskController          SSE 端点 · 只认「事件」不认供应商
   ↓
service/ask/AskConversation     对话编排 · 工具分发 · 本地存储      ← 不知道百炼存在
   ↓
service/ask/AgentRuntime        接口:send(消息, 工具集, 回调) → 事件流
   ├ ResponsesAgentRuntime      唯一实现 · 知道 previous_response_id / function_call_output
   └ (将来) ChatCompletionsAgentRuntime   退路:三家都支持的 /chat/completions + tools
```

**为什么要有 `AgentRuntime` 这层抽象**(而不是直接调):

- Assistant API 三个月前还是官方推荐,现在「下线中」。**这一领域的接口寿命明显短于我们的版本节奏**
- 第一版只保证通义可用,但 PRD §3.2b 定了「不许把只有通义写死进架构」
- 退路是真的存在:`/chat/completions` + `tools` 是三家**都支持**的最小公分母,只是多轮要自己拼

> 备选:不做抽象,直接在 service 里调 Responses。
> **不选的理由**:那样将来换接口要动业务代码,而业务代码里有工具分发和口径引用 ——
> 那是最不该被供应商变更牵动的部分。

## D3 · 多轮上下文:用 `previous_response_id`,但自己留一份

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A · 全靠 `previous_response_id`** | 只传上一轮 id,历史在云端 | 最省。但有已知时序坑;且云端过期/换账号后**无法续接** |
| **B · 全靠自己拼 `input` 数组** | 每轮把完整历史发上去 | 最可控,但 token 成本随轮次线性涨,且放弃了服务端上下文缓存 |
| **C · 主用 A,自己留全量,失败时退 B** ✓ | 正常走 `previous_response_id`;本地**始终**存全量;一旦报 `No tool output found` 或 id 失效,**自动用本地历史重拼 input 重试一次** | 兼顾成本与可靠性。代价是要维护 `call_id` 映射与一次重试路径 |

**选 C**。理由不是折中主义:PRD FR-431 本来就要求**本地存全量对话**(维护者定的),
所以「重拼所需的历史」是**免费**的 —— 我们本来就有。既然有,就不该在云端失效时干瞪眼。

另外开 `x-dashscope-session-cache: enable`(默认 disable),降低多轮延迟与成本。

## D4 · 工具层:边界画在哪、放在哪

### 边界(PRD FR-428 / FR-429 的落地)

工具**只暴露已经算好的口径**,返回值一律带 `账期 / 口径名 / 是否进行中`:

| 工具 | 底层 |
|---|---|
| `资产分布(维度, 账期)` | `FactViewService.allocationByType` + `LensQueryService`(8 个维度)+ 基金穿透 |
| `托管形式(账期)` | **新增派生视图**,见 D5 |
| `账户表现(账期)` | `FactViewService.accountPerformance` |
| `本期资金拆解(账期)` | `cashflowBreakdown` + `openingBaseline`(人赚 / 钱赚 / 开账基线) |
| `归因(账期, 维度)` | `AttributionService` |
| `体检结论` | `CheckupController` 那套规则 + 4 维诊断 |
| `目标进度` / `财富水位` | `GoalProgressService` / `WaterLevelService` |
| `账户流水(账户, 账期)` | `AccountDetailService`(带 v1.18 来源标签) |

**不提供**:任意 SQL、原始 `period_snapshot` / `cash_flow` 行、**任何写操作**。

### 放在哪:复用现有服务,不新建计算

```
service/ask/tools/  ←  只做「参数校验 + 调现有 service + 包上账期/口径元数据」
                       一行计算都不写
```

**这是硬约束,不是风格偏好。** v1.18 整个 bug 家族的形状是「同一件事两份判据」
(已归档 6 次)。如果工具层自己算,那就是**第三份口径** —— agent 说的数会和页面对不上,
而用户没法判断谁对。

> 备选:新建一个「对话专用的宽表/物化视图」,查询更快。
> **不选**:那正是造第三份口径。宁可慢。

### 护栏(静态可校验,不靠自觉)

1. `service/ask/tools/` 下**不许出现算术运算符与 `BigDecimal` 的加减乘除调用**
2. `service/ask/` 下**不许出现** `insert` / `update` / `delete` / `Mapper` 的写方法
3. 工具返回类型**必须**带 `periodId` + `metricKey` + `inProgress` 三个字段(结构性单测遍历所有工具)
4. `service/ask/` 下不许出现 `dashscope` / `qwen` 字样(供应商只许出现在 `ResponsesAgentRuntime`)

## D5 ·「托管形式」:派生视图,不是新维度

查了代码:资产透视现有 **8 个维度**(风险 / 大类 / 行业 / 平台 / 主理人 / 用途 / 地域 / 币种),
**没有**「托管形式」。所以要么新建维度,要么派生。

| 方案 | 取舍 |
|---|---|
| **A · 新增第 9 个透视维度** | 和现有维度一致、能进旭日/透视。但要新增打标(用户要标每个账户是「自己盯」还是「交给产品」)—— **违背 10 分钟硬约束** |
| **B · 派生视图**(选定) | 由已有字段推导,**零新增录入**。代价:规则是我们定的,可能和某个用户的直觉不符 |

**判据(全部来自已有字段)**:

| 托管形式 | 规则 |
|---|---|
| **自己盯** | `STOCK` / `CRYPTO` / `METAL` 账户下,你自己建的标的 |
| **交给产品** | `WEALTH` / 基金类持仓;有穿透结果的走**穿透后成分**(v1.5) |
| **不动** | `PROPERTY` / `INSURANCE` —— 存量登记,估值靠手填 |
| **随时可取** | `CASH` + 被标 `LIQUID` 的货基类 |

另外三个切法**直接复用现有维度,零新增**:钱在哪个机构 → `平台`;谁在管 → `主理人`;
数字怎么来的 → `valuation_mode` + v1.18 **流水来源标签**。

> 加新账户类型时这张表会漏 —— 所以配一条**结构性单测**遍历 `AccountType`,
> 要求每个类型必须落进四类之一或显式列进 `NEITHER`(照抄 `AccountTypeSemanticsTest` 的做法,
> 那条正是为「v0.14 加 METAL 漏了投资类判据」立的)。

## D6 · SSE 怎么落到 Spring MVC

本项目是 **Spring MVC + Thymeleaf + HTMX**,没有 WebFlux。

| 方案 | 取舍 |
|---|---|
| **A · 引入 WebFlux** | 响应式全链路。但要引入一整套新范式,而我们只有**一个**流式端点 —— 收益和成本完全不成比例 |
| **B · `SseEmitter` + 专用线程池**(选定) | Spring MVC 原生支持,不引新依赖。代价:每个进行中的对话占一个线程 —— 对**家庭级并发**(同时最多两三个人)完全不是问题 |
| **C · 轮询** | 最简单,但对话体验差(逐字流是这类界面的基本盘) |

**选 B**。线程池独立配置、有上限,超了直接拒绝并给人话提示(不排队,不拖垮主池)。

## D7 · 对话存储:引用块必须**结构化**存,不存 Markdown

```
ask_conversation   id · family_id · title · provider_ref(云端 response id)· created_at · archived_at
ask_message        id · conversation_id · role(user/assistant)· content_text · seq · created_at
ask_citation       id · message_id · metric_key · period_id · in_progress · amount_text · target_href
ask_tool_call      id · message_id · tool_name · args_json · duration_ms · ok    ← 只存摘要,不存返回体
```

**为什么引用块单独一张表,而不是把 Markdown 存进 `content_text`**:

- PRD FR-427 要求引用块能**点回原页**,且账期标注与那一页**逐字一致**。
  存成 Markdown 就等于把「口径」冻结成了当时的一段文字 —— 页面口径改了(这一年改过三次),
  历史对话里的说法就和现在的页面对不上,而且**没人会发现**
- 结构化存之后,口径口播文案由**渲染时**生成,和页面共用同一份措辞
- 也让「这条对话引用了哪些账期」可查(历史列表上就显示)

**`ask_tool_call` 只存摘要不存返回体**:返回体就是家底数据,存两份没有意义,只增加泄漏面。

> 隐私:对话正文含真实金额 —— 那本来就在用户自己库里,不是新增暴露面。
> 但**不进 `audit_log`**(那张表会被导出)、**不进任何日志**。这条进护栏。

## D8 · 失败面与用户可见行为

| 失败 | 用户看到什么 |
|---|---|
| 没配通义 key | 说明 + 直达「数据源接入」的链接(PRD FR-434),**不是空白页** |
| key 失效 / 型号不存在 | 复用 v1.18.5 的 `classifyLlmError`,点名型号 + 给下一步 |
| 工具执行超时 | 该工具标红 + 其余照常;答案里明说「这一项没查到」,**不编** |
| 云端 response id 失效 | 静默走 D3 的本地重拼重试;**再失败**才提示 |
| 流中断 | 已产生的部分**保留**并落库,给「继续」按钮 —— 不吞掉 |
| 线程池满 | 「同时进行的对话太多,稍后再试」,不排队 |

## D11 · 外壳:一个片段,两种壳(2026-08-26 补 · 推翻了 D6 之前的假设)

> **我原先写的是「一套响应式,不区分 PC / 移动」,那是错的。** 对话**流**是同一个片段;
> **壳**必须分 —— 窄屏放不下侧栏,而 PC 上跳走全屏页会把用户从他正在看的数据上扯开。

| | PC(≥1024px) | 移动 |
|---|---|---|
| 入口 | 右下角**常驻悬浮按钮** | 导航**顶级入口** |
| 壳 | **可拉宽的侧边抽屉** | **全屏页** + 「← 回到刚才那页」 |
| 实现 | 同一个 `ask/_stream` 片段,两个外层模板 | 同上 |

### 跨页面保持:这条决定了实现方式

要求是「切到别的页,抽屉不关、对话不断」。三个做法:

| 方案 | 取舍 |
|---|---|
| **A · 每页整页刷新时重建抽屉** | 简单,但**对话状态会丢**,流也会断 —— 直接违背要求 |
| **B · 抽屉内容走 HTMX 局部替换,页面主体也走局部替换** | 与本项目现有做法一致(趋势 / 支出构成早就是 HTMX 局部替换)。抽屉是**页面级片段**,主体换它不换 |
| **C · 引入 SPA 路由** | 能做到,但要给一个 Thymeleaf 项目引入前端路由 —— 收益与成本不成比例 |

**选 B**。抽屉挂在 layout 上、不随主体替换;导航链接改为 HTMX 局部替换主体区域。
移动端全屏页则是普通页面跳转(那里本来就没有「保持」的需求,只需要「回得去」)。

> 风险要说明:导航从「整页跳转」改成「局部替换」会触到**每一个页面**。
> 所以这条**放第二刀**,第一刀先做「侧栏在当前页可用 + 移动全屏页」,不动导航。
> 分期见 D10。

### SSE 与壳的关系

`SseEmitter`(D6)只和**流**有关,与壳无关 —— 两种壳消费同一个事件流。
但有一条要注意:**移动端全屏页跳走时必须主动关掉 emitter**,否则线程会挂到超时。

### 滚动行为(FR-431d)

流式时滚动停在**新消息顶部**,不追着最后一个字滚。这不是审美选择 ——
追着滚会让用户读不了正在生成的内容,而我们的答案里还有引用块,滚到底会让最重要的数字一闪而过。

实现:新消息插入时记录其 `offsetTop`,流式期间**不再自动滚动**;
只有当用户已经手动滚到底部时才跟随(常见的「stick to bottom only if already at bottom」模式)。

## D12 · 语音输入:第一版不自建(2026-08-26 补)

| 方案 | 取舍 |
|---|---|
| **A · `webkitSpeechRecognition`** | 零成本。但 **iOS Safari 上名义支持、实际不可靠** —— 可能静默失败,`interimResults` 行为与文档不符。而我们的非技术用户**主力就在 iPhone 上** |
| **B · 云端 ASR**(DashScope) | 可靠。但要新开一条**音频出网通道** —— 今天没有的暴露面,还要处理录音权限、上传、计费 |
| **C · 引导系统键盘听写**(选定) | **零代码、零成本、音频不经过我们**。手机键盘上本来就有麦克风 |

**选 C,但必须把这件事说出来** —— 输入框 placeholder 写明「手机上按键盘的麦克风说就行」。
研究里反复出现的一条是**用户不会假设一个功能存在**;不告诉他等于没有。

B 留给第二刀评估,前提是先想清楚音频通道的隐私口径 —— **不能顺手加**。
