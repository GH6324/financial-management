## 0 · 一句话概括这份设计

**自由度不来自「让 agent 碰原始数据」,来自「把我们已有的透视引擎整个交给它」。**

我们已经有一个语义层 —— `LensQuery(rows, cols, measures, filters)` + `PivotEngine`,
它就是资产透视页背后那套东西。把它作为 agent 的主查询接口,一步到位地得到:

- **组合空间巨大**:11 个维度 × 6 个度量 × 任意筛选 × 行列交叉 —— 远超我们能想到的「罐头报表」
- **口径零新增**:算的是**同一份代码**,agent 说的数与页面**必然**一致
- **聚合权在我们手里**:group-by / 小计 / 占比全在 `PivotEngine` 里,**agent 一次加法都不用做**

「禁数学」这条铁律因此不再是**限制**,而是**不必要** —— 它想要哪个切片,直接要就是了。

## 1 · 一次提问的完整链路

```
用户                我们(Spring Boot)                      百炼 Responses API
 │                        │                                        │
 ├─ 提问 ───────────────▶ │                                        │
 │                        ├─ 组装 instructions + tools ──────────▶ │
 │  ◀── SSE:思考中 ──────┤ ◀────────── 流式 delta ────────────────┤
 │                        │                                        │
 │                        │ ◀── tool_call: pivot(rows=[platform])──┤
 │  ◀── SSE:正在查… ─────┤                                        │
 │                        ├─ AskToolDispatcher                      │
 │                        │    └─ PivotEngine(透视页同一份)        │
 │                        ├─ 结果进【本轮引用表】 ────────────────▶ │  function_call_output
 │                        │                                        │
 │  ◀── SSE:正文 delta ──┤ ◀─ 正文(数字位置是【引用标记】)───────┤
 │                        ├─ 渲染:标记 → 真实数值 + 账期 + 跳转    │
 │  ◀── SSE:引用块 ──────┤                                        │
 │                        ├─ 落库(会话 / 消息 / 引用 / 工具摘要)   │
```

**注意倒数第三段**:模型正文里**不写数字**,写的是引用标记 —— 见 §4,这是本版最关键的一条。

## 2 · 接口选型:为什么不是 Managed Agents

方向没变(用阿里云、能复用就复用、不自建编排);变的是**用哪个接口**。

| 候选 | 工具怎么执行 | 数据怎么进去 | 结论 |
|---|---|---|---|
| **Managed Agents** | **平台侧沙箱**。事件是 `tool_call`/`tool_call_output`(内置工具)与 `mcp_call`/`mcp_call_output`;**客户端只能写入 `message`** | 只有两条:开**公网 MCP 口**,或把家底**写进云端沙箱文件** | ✗ |
| **Assistant API** | 客户端(`requires_action`/`submit_tool_outputs`) | 客户端执行 | ✗ 官方标注**「下线中」** |
| **Responses API** | **客户端**:模型返回 tool_call → 我们执行 → 回传 `function_call_output` | 工具在我们进程里跑 | ✓ **选定** |

**不选 Managed Agents**:它的强项是「代码执行 / 文件处理 / 长时任务」+ 独立沙箱,我们**一个都用不上**
(短问答 + 结构化取数,几秒的事);代价却是实的 —— 要么开一个「能读走整个家庭净资产」的公网端点
(百炼 MCP 托管在函数计算上、**无固定出口 IP**,做不了白名单),要么把家底写进云端沙箱文件。
而这个产品**发 Docker 给陌生人自建**,很多人在 NAT 后面没有域名。

**选 Responses API 的三条**:① 暴露面与现有六个 AI 调用点**完全一样**,不新增;② 不开公网口;
③ 端点 `/compatible-mode/v1/responses` 与我们现有通义客户端**同一个 base、同一把 key**。

**代价照实说**:多轮交给 `previous_response_id`,社区反馈它与 `function_call_output` 配合有时序问题
(`No tool output found for function call`)→ 对策见 §6;旧路径 `/api/v2/apps/protocols/...` 即将停维,
所以要包一层薄适配(§5)。

## 3 · 工具接口设计 ——「我们提供哪些接口能力」

### 3.1 三种做法,先说为什么不选另外两种

| 做法 | 自由度 | 口径风险 | 结论 |
|---|---|---|---|
| **A · 罐头报表**<br>`getAllocation()` `getTopLosers()` … 一问一函数 | **低**。我们想到什么它才能问什么;用户一问「按平台看、只看老婆名下的、近三个月」就抓瞎 | 零 | ✗ 这是把「固定卡片」换了个壳,没解决 v1.19 要解决的问题 |
| **B · 裸 SQL / 原始表** | **最高** | **最高**。agent 自己 group-by、自己算占比 → **凭空造出第三份口径**,说的数和页面对不上,而用户没法判断谁对(v1.18 整个 bug 家族就是「同一件事两份判据」,已归档 6 次) | ✗ |
| **C · 语义层查询**(选定)<br>把 `LensQuery` + `PivotEngine` 交给它 | **接近 B**:11 维 × 6 度量 × 任意筛选 × 行列交叉 | **零**。算的是透视页**同一份代码** | ✓ |

**C 的关键性质:聚合权在我们手里。** agent 说「按平台分组」,是 `PivotEngine` 去分组;
它拿到的已经是分好组、算好占比、带小计的结果 —— **没有算术可做**。

### 3.2 主力工具:`pivot`

```jsonc
{
  "name": "pivot",
  "description": "按任意维度交叉查询家庭资产。行/列/度量/筛选自由组合,聚合与占比由系统计算。",
  "parameters": {
    "rows":     ["platform"],            // 行维度,可多个(嵌套)
    "cols":     ["risk"],                // 列维度,可空
    "measures": ["value", "share"],      // 度量白名单
    "filters":  { "owner": ["成员A"] },   // 维度 → 取值
    "period":   "2026-08",               // 缺省 = 当前上下文账期
    "currency": "CNY"                    // 缺省 = 当前视图币种
  }
}
```

**维度白名单(11)** —— 前 10 个是 `LensRegistry` 现有的,第 11 个是本版新增派生视图(§8):

`type` 大类 · `risk` 风险 · `liquidity` 流动性 · `currency` 币种 · `owner` 主理人 ·
`assetClass` 资产类别(穿透后)· `platform` 平台 · `industry` 行业(穿透后)· `region` 地域 ·
`purpose` 用途 · **`custody` 托管形式**

**度量白名单(6)**:`value` 市值 · `share` 占比 · `latestPnl` 本期损益 · `cumPnl` 累计损益 ·
`netPrincipal` 累计净投入 · `openValue` 期初市值

> `PivotEngine.Result` 已经带 `rowTotals` / `colTotals` / `grand` / `holdingLevelSplit`,**直接透传**。
> `holdingLevelSplit` 尤其重要:它标记「本次查询含持仓级维度,收益按持有口径、**不可归因**」——
> 这个警告必须**原样交给 agent**,否则它会拿一个不可归因的数去下结论。

### 3.3 其余工具

| 工具 | 干什么 | 底层 |
|---|---|---|
| `describeCapabilities` | **告诉 agent 它能问什么**:维度 / 度量清单、每个维度的取值、可用账期、账户列表 | `LensRegistry` + `PeriodMapper` + `AccountMapper` |
| `findEntity(q)` | 名字 → id。「我的余额宝」「老婆的账户」→ 账户 / 成员 / 持仓,返回候选 + 置信度 | 模糊匹配 |
| `periodSummary(period)` | 一期全貌:净资产 / 总资产负债 / 人赚·钱赚·开账基线 / 紧急储备 / 负债率 | `FactViewService.kpis` + `cashflowBreakdown` |
| `accountPerformance(period)` | 账户级收益表:XIRR / 累计损益 / 最大回撤 / 持有期数 / 预实 | `FactViewService.accountPerformance` |
| `attribution(period, dim)` | 归因瀑布 + 贡献榜 | `AttributionService` |
| `checkupFindings()` | 体检:规则命中 + 4 维诊断 + 再平衡偏离 | `checkup` 规则集 |
| `goalsAndWaterLevel()` | 目标进度 + 财富水位(CPI / M2) | `GoalProgressService` / `WaterLevelService` |
| `explainMetric(key)` | **一个指标是怎么算的** —— 与页面 tooltip **同一份**口径文案 | `MetricExplainService` |
| `accountLedger(account, period)` | 某账户某期流水明细(带 v1.18 来源标签) | `AccountDetailService` |
| `reportUnmetNeed(...)` | 见 §3.4 ③ | 落 `ask_unmet_need` |

**不提供**:任意 SQL、原始表行、**任何写操作**。

### 3.4 三个专为「自由度」设计的东西

**① `describeCapabilities` —— 不让它猜。**

agent 最大的浪费是**猜参数**:猜维度叫什么、猜账期格式、猜账户名。
所以第一等公民是**自省接口**:先问「你都有什么」,再决定怎么查。
系统提示词明确写:**拿不准维度或取值时先调它,不要猜。**

**② 允许多步、并行、改主意。**

- 一轮内最多 **8 次**工具调用(够走「自省 → 查两三个切面 → 交叉验证」)
- 同一轮的多个 `tool_call` **并行执行**(彼此无依赖)
- **参数校验失败不直接报错,把校验信息回给模型让它改** —— 这也是自由度的一部分

**③ 够不着时:诚实说 + 记下来。**

`reportUnmetNeed(question, whatIWouldNeed)`:agent 发现「用户问的我没有对应能力」时调它,
然后**如实告诉用户拿不到**。我们把它记进 `ask_unmet_need` ——
**agent 的「够不着」变成下一版加工具的产品输入**,比我们坐着猜用户要什么准得多。

> 这也是对「自由度」的诚实回答:**边界总会有**,重要的是它**可见、可反馈、会移动**,
> 而不是让 agent 在边界上编一个答案。

### 3.5 工具层放哪、不许做什么

```
service/ask/tools/   只做三件:参数校验 → 调现有 service → 包上口径元数据
                     一行计算都不写
```

每个工具返回值**必须**带 `periodId` · `metricKey` · `inProgress` · `currency` ——
这四样是 §4 引用块的原料,也是「数字说得清自己是哪一期」的载体。

## 4 · 数字保真:**模型不写数字,只写引用标记**

### 4.1 问题

FR-427 要求每个数字挂账期、点得回原页、与页面**逐字一致**。
如果让模型把 `+¥204,522` 打进正文,有三种翻车方式:少一位、改成「约 20 万」、把 7 月说成 8 月。
**靠 prompt 约束这件事我们已经证明过不可靠** —— 那条「禁止四则运算」的铁律是拿生产事故换来的。

### 4.2 做法

工具结果落进**本轮引用表**,每个可引用数字有一个 id;模型正文写标记:

```
你 8 月净资产涨了 {{cite:c1}},其中投资那份 {{cite:c3}} 占了大头。
```

渲染时替换成引用块组件,数值**直接取自工具结果**:

```
净资产变化 ΔNW      +¥222,522
2026-08 · 进行中   → 仪表盘 · 本期怎么变的
```

### 4.3 为什么这是结构性的,而不是约定性的

- 模型**没有机会**打错数字 —— 它手里根本没有数字字符串,只有 id
- 账期 / 口径名 / 跳转目标由**工具结果**决定,不由模型决定
- 渲染时口径文案与页面**共用一份**(`MetricExplainService`);页面改口径,历史对话跟着改

**兜底**:模型仍可能在正文里手打数字(比如复述)。所以加一道**输出校验** ——
扫正文里的金额 / 百分比形态,**凡不在本轮引用表里的,标灰并加一句「这个数我没核对过」**。
不删(删了句子会断),但**明确降级**。

> 复用现有 `OutputValidator` 的思路:v0.4 起我们就在扫 LLM 输出(那时扫「有没有泄露真名 / 荐产品」),
> 现在多扫一类「有没有凭空出现的数字」。

## 5 · 分层:哪一层允许知道「我们在用百炼」

```
web/ask/AskController            SSE 端点 · 只认事件,不认供应商
   ↓
service/ask/AskConversation      对话编排 · 引用表 · 本地存储        ← 不知道百炼存在
   ↓
service/ask/AskToolDispatcher    工具注册表 · 参数校验 · 并行执行 · 超时
   ↓
service/ask/AgentRuntime         接口:send(消息, 工具集, 事件回调)
   ├ ResponsesAgentRuntime       唯一实现 · previous_response_id / function_call_output
   └ (将来) ChatCompletionsAgentRuntime   退路:三家都支持的最小公分母
```

**为什么抽象**:Assistant API 三个月前还是官方推荐、现在「下线中」——
**这一领域的接口寿命明显短于我们的版本节奏**。而业务层里有工具分发和口径引用,
那是最不该被供应商变更牵动的部分。

> 备选:不抽象直接调。**不选**:换接口就要动业务代码。

## 6 · 多轮上下文:主用云端,自己留一份

| 方案 | 取舍 |
|---|---|
| **A · 全靠 `previous_response_id`** | 最省。但有已知时序坑;云端过期 / 换账号后**无法续接** |
| **B · 每轮自拼完整 `input`** | 最可控,但 token 随轮次线性涨,且放弃服务端上下文缓存 |
| **C · 主用 A + 本地全量 + 失败退 B**(选定) | 正常走 `previous_response_id`;一旦报 `No tool output found` 或 id 失效,**用本地历史重拼 input 重试一次** |

**选 C**,理由不是折中:PRD FR-431 本来就要求**本地存全量**,所以「重拼所需的历史」是**免费**的。
既然有,就不该在云端失效时干瞪眼。另开 `x-dashscope-session-cache: enable` 降低多轮延迟与成本。

**新对话**(FR-431b)= 新的 `previous_response_id` 链;旧链自然失效,不用清理。

## 7 · 系统提示词的结构

放仓库 `resources/prompts/ask-system.md`,**随版本走**,不进控制台。五段:

1. **角色与边界** —— 家庭资产顾问;不预测涨跌、不荐具体产品、不做担保性话术(**与现有六处 AI 共用这一段**,避免边界在两处漂移)
2. **数字纪律** —— 你**不写数字**,只写 `{{cite:id}}`(§4)
3. **怎么用工具** —— 拿不准先 `describeCapabilities`;一轮最多 8 次;够不着就 `reportUnmetNeed` 并如实说
4. **什么时候先反问**(FR-425)—— 凡结论会因一个未知条件**翻转**的问题,先问再答。给正反例:
   「该不该提前还贷」要问现金用途;「我房产占比多少」不需要问
5. **答完给 2–3 条追问**(FR-424b)—— 贴着刚才那段答案,不是一屏

## 8 ·「托管形式」:派生维度

| 方案 | 取舍 |
|---|---|
| **A · 新增维度(需打标)** | 与现有维度一致。但要用户**逐个账户打标** —— 违背 10 分钟硬约束 |
| **B · 派生**(选定) | 由已有字段推导,**零新增录入**。代价:规则由我们定 |

| 托管形式 | 规则(全部来自已有字段) |
|---|---|
| **自己盯** | `STOCK` / `CRYPTO` / `METAL`,你自己建的标的 |
| **交给产品** | `WEALTH` / 基金类;有穿透结果的走**穿透后成分** |
| **不动** | `PROPERTY` / `INSURANCE` |
| **随时可取** | `CASH` + 标了 `LIQUID` 的货基类 |

**落点**:在 `LensQueryService.positions()` 组装 `Position` 时**多填一个 `custody` 标签**,
其余完全复用 —— 于是它自动获得透视引擎的全部能力(能当行、能当列、能筛选、能交叉),
**而且透视页也白捡一个新维度**。

> 配**结构性单测**遍历 `AccountType`,要求每个类型落进四类之一或显式列入 `NEITHER` ——
> 照抄 `AccountTypeSemanticsTest`,那条正是为「v0.14 加 METAL 漏了投资类判据」立的。

## 9 · 外壳与 SSE

### 9.1 两种壳,一个流

| | PC(≥1024) | 移动 |
|---|---|---|
| 入口 | 右下角**常驻悬浮按钮** | 导航**顶级入口** |
| 壳 | **可拉宽侧边抽屉** | **全屏页** +「← 回到刚才那页」 |
| 实现 | 同一个 `ask/_stream` 片段,两个外层模板 | 同上 |

**PC 必须是侧栏**:本版最重的承诺是「数字点得回原页」,侧栏能左边看数右边问话;
独立页每点一次引用块都要跳走再跳回。

### 9.2 跨页面保持

| 方案 | 取舍 |
|---|---|
| **A · 整页刷新重建** | 简单,但**对话会断** —— 直接违背要求 |
| **B · 导航改 HTMX 局部替换**(选定) | 与项目现有做法一致(趋势 / 支出构成早就是局部替换)。抽屉挂 layout 上,主体换它不换 |
| **C · 引入 SPA 路由** | 能做到,但给 Thymeleaf 项目引前端路由,收益与成本不成比例 |

> **风险**:B 触到**每一个页面**。所以单列为第二刀,第一刀先做「当前页可用」。

### 9.3 SSE

Spring MVC 原生 `SseEmitter` + **独立线程池**(不引 WebFlux —— 只有一个流式端点,
引一套新范式不划算)。池子有上限,满了直接拒绝并给人话提示,**不排队、不拖垮主池**。
移动端全屏页跳走时**必须主动关 emitter**,否则线程挂到超时。

### 9.4 滚动(FR-431d)

流式时滚动停在**新消息顶部**,不追最后一个字。实现用
「stick to bottom only if already at bottom」:用户已在底部才跟随。

理由:追着滚会让人**读不了正在生成的内容**;而我们的答案里有引用块,滚到底会让最重要的数字一闪而过。

## 10 · 存储

```
ask_conversation    id · family_id · title · provider_ref · ctx_period · ctx_currency · created_at · archived_at
ask_message         id · conversation_id · role · content_text(含 {{cite:id}})· seq · created_at
ask_citation        id · message_id · cite_key · metric_key · period_id · in_progress · value_text · currency · target_href
ask_tool_call       id · message_id · tool_name · args_json · duration_ms · ok      ← 只存摘要,不存返回体
ask_unmet_need      id · family_id · question · needed · created_at                 ← §3.4 ③
ask_suggestion_skip id · family_id · suggestion_key · shown_count                   ← FR-424b「不重复推」
```

**为什么引用块单独存,而不是把渲染好的 Markdown 塞进 `content_text`**:
存 Markdown 等于把口径**冻结成一段文字**。页面口径改了(这一年改过三次),
历史对话里的说法就和现在的页面对不上,**而且没人会发现**。
结构化存之后,口径文案在**渲染时**生成,与页面共用一份。

**`ask_tool_call` 只存摘要**:返回体就是家底数据,存两份没有意义,只增加泄漏面。

> 隐私:对话正文含真实金额 —— 那本来就在用户自己库里,不是新增暴露面。
> 但**不进 `audit_log`**(会被导出)、**不进任何日志**。这条进护栏。

## 11 · 失败面

| 失败 | 用户看到什么 |
|---|---|
| 没配通义 key | 说明 + 直达「数据源接入」链接,**不是空白页** |
| key / 型号失效 | 复用 v1.18.5 的 `classifyLlmError`,点名型号 + 给下一步 |
| 单个工具超时 | 该工具标灰,**其余照常**;答案里明说「这一项没查到」,**不编** |
| 工具参数非法 | 把校验错误**回给模型**让它改,不直接失败 |
| 云端 id 失效 | 静默走 §6 本地重拼重试;**再失败**才提示 |
| 流中断 | 已产生部分**保留落库**,给「继续」按钮 |
| 正文出现未核对数字 | 标灰 +「这个数我没核对过」(§4.3) |
| 线程池满 | 「同时进行的对话太多,稍后再试」,不排队 |

## 12 · 语音:第一版不自建

| 方案 | 取舍 |
|---|---|

## 15 · 待评审:三处最想听意见

1. **§3 用透视引擎当主查询接口** —— 这是「更高自由度」的答案:组合空间巨大但口径零新增。
   代价是 agent 要学会用 `LensQuery` 那套参数(靠 `describeCapabilities` + prompt 教)。
2. **§4 模型不写数字、只写引用标记** —— 我认为这是本版最重要的一条,把「数字保真」
   从**约定**变成**结构**。代价是渲染层复杂一点,而且模型偶尔不听话(所以有 §4.3 兜底)。
3. **§8 托管形式的四类判据** —— 全版唯一一处「我们替用户下定义」。
