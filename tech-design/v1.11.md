## 1 · 性能(FR-331)· 一次扫描 vs 一条 SQL

**问题定位**:报表页一次请求 **881 条 SQL / 1.25s**。热点是「每期首次出现的账户」——
它决定**开账基线**(人赚 / 钱赚的分界),v0.13 起每个期都要算一次,写成了 per-period 查询
(每期一条,带 `NOT IN` 子查询)。

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · 批量相关子查询 | 一条 SQL,对每行 `period_snapshot` 再查一次该账户的 `MIN(period_start)` | 看着"只有一条 SQL"了 | **实测反而更慢:1.25s → 9.3s**。3600 行 × 每行一次子查询 = O(n²)。**"一条 SQL" ≠ "一次扫描"** |
| B · 窗口函数(选定) | `ROW_NUMBER() OVER (PARTITION BY ps.account_id ORDER BY p.period_start)` 取 `rn=1` | 需要 MySQL 8(项目已经是) | **一次扫描**拿到全部首现关系 |
| C · 落一张「账户首现期」物化表 | 建表 + 触发/定时维护 | 快,但要维护一致性:6 处 `snapshot upsert` 都得更新,漏一处 = 静默错 | 不选:为一次查询引入一个可变状态源不划算 |

**缓存生命周期**也是一个刻意的取舍:

| 方案 | 取舍 | 结论 |
|---|---|---|
| 按 `familyId` 长缓存 | 命中率最高 | **不选**:要在 4 个文件 6 处 `snapshotMapper.upsert` 都失效掉,**漏一处 = 静默算错开账基线**,而它决定人赚/钱赚分界 —— 这种错不会报警,只会让数字慢慢不对 |
| 每次 `load()` 刷新的 `ThreadLocal`(选定) | 单请求内复用,请求结束即弃 | 结构上不可能失效不及时;命中率对本场景足够 |

**实测(优化前 → 后 · 中位数)**:dashboard **1.735s → 0.784s(−55%)**;
reports?range=1Y **1.247s → 0.784s(−37%)**。

**没做完的部分(诚实记录)**:报表页单请求仍有约 **761 条 SQL**。剩余的 N+1 没定位到具体调用点 ——
项目里没有 SQL 采样/慢查询归因的手段,靠 `SHOW GLOBAL STATUS LIKE 'Questions'` 只能拿到总数,
定位不到是谁发的。**要继续优化,先得有 profiling 手段**,这是 v1.12 的前置。

## 2 · 局部替换(FR-332 / FR-336)· HTMX vs 前端状态

| 方案 | 取舍 | 结论 |
|---|---|---|
| A · 整页跳转(现状) | 最简单;但慢 + 丢滚动位置 | 被反馈打掉 |
| B · HTMX `hx-get` + `hx-select`(选定) | 服务端仍渲染整页响应,前端只挑出目标 section 换进去。**保留 `href`** → 无 JS/爬虫仍可用;`hx-push-url` 让地址栏跟着变,可分享、可前进后退 | 选定:不引入前端状态管理,和项目"无 SPA 无构建"的约束一致 |
| C · 拆一个只渲染片段的端点 | 响应更小 | 不选:多一条需要和整页保持同步的渲染路径,而收益只是省几 KB(服务端渲染耗时相同) |

代价说清楚:B 方案服务端仍然算了整页(所以省的是**渲染与滚动**,不是后端耗时)。
在本项目这个体量下,"位置不丢"的体验收益远大于那点带宽。

## 3 · 窗口一致性(FR-335)· 维护者要的"判断"

**判断:同一区内的所有模块必须共用一个时间控件,而且这个控件只能属于「趋势」区。**

理由三条:

1. **并排读会得出错误结论**。「月度收支 + 反推目标月供」原来写死近 12 期,而它就在趋势区里,
   切到 3M 时上图 3 个点、下图 12 个点,视觉上却是一组 —— 这是**制造误判**,不是信息更多。
2. **一区/二区不能有时间控件**,这是 v1.10 定下的结构约束(L13):封板快照的值只由"哪一期"决定。
   所以时间控件天然只属于三区,不存在"全页共享"的说法 —— 全页共享会把 range 泄漏进封板区。
3. **仪表盘的类比要修正**。维护者说"和仪表盘类似,当月账期/区间选择都是全页面共享"——
   仪表盘可以这样,因为它**整页都是实时视角**,没有封板区。报表页是混合视角,不能照搬。

落地:`savingsWindowPeriods(range)` 把 range 翻译成期数(1M→1 / 3M→3 / 6M→6 / YTD→当年月数 /
1Y→12 / ALL→240),储蓄能力、支出构成(v1.11.1)、本金 vs 损益都走它。
`mixWin` 参数保留接受但不再渲染独立控件 —— 老链接不 404。

## 4 · 哪些仪表盘指标值得搬到报表页(FR-337)· 逐项判断

判据只有一条:**这个数在"关账那一刻定格"之后还有意义吗?**
有意义 → 值得进封板区;只有"现在怎样"才有意义 → 留在仪表盘。

| 仪表盘上的东西 | 搬? | 理由 |
|---|---|---|
| 净资产 / 总资产 / 总负债 / 紧急储备 | **已在**(v1.10 期末资产负债表) | 封板月的家底,是后面所有比率的分母 |
| 本月资产收益 | **不搬** | 报表页一区已有资金流瀑布 + 本期归因,是同一件事的更完整表达;再放一个卡片是重复 |
| 净资产趋势 + CPI/M2 线 | **已在**(三区财富水位) | 趋势视角,属于三区 |
| 资产配置环 | **搬 → 已做**:二区「按资产大类」封板分布 | 配置是**结构**,结构在封板月是确定的;而且二区已有集中度/流动性,缺"大类占比"这块基础结构 |
| 成员区(按人看) | **搬 → 已做**:二区「按成员」封板分布 | "这个月谁名下多少"是封板事实,也是家庭沟通时最常被问的一句;仪表盘的成员区是实时值,月底对不上账 |
| AI 洞察 | **不搬** | 它解读的是"当下该做什么",对三个月前的封板月没有行动价值;且每次生成都要花 token |
| CPI 切换器 | **不搬** | 属于交互偏好,不是指标 |
| 填报待办 / 已填进度 | **不搬**(但一区已有**完整度声明**) | 待办是"当期还没做完"的状态;封板月对应的是"这份快照完整吗",v1.10 已用完整度行表达 |
| 人赚 vs 钱赚拆解 | **已在**(一区瀑布 + 三区本金 vs 损益) | 一区给单月分解、三区给累计曲线,两个视角都在 |

**实现范围**:只新增两块(按成员 / 按资产大类),都走 `SealedPeriodService`(签名里没有 range,
传不进去 —— L13 的类型级保证),只统计 ASSET 侧(负债混进占比会让分母失去意义)。

## 5 · 宏观基准的兜底必须明示(FR-334)

**发现**:财富水位的 CPI/M2 不是"当月快照",而是**按年**的宏观序列;当年数据还没发布时,
代码**静默回落到历史均值**。静默是这里唯一不可接受的行为 —— 用户会把兜底值当成真实基准来读。

| 方案 | 取舍 | 结论 |
|---|---|---|
| A · 静默兜底(现状) | 图永远画得出来 | **不可接受**:把估算当事实 |
| B · 缺数据就整块不显示 | 最保守 | 不选:2026 年的 CPI 到次年才定稿,那这一节大半年都是空的 |
| C · 兜底 + 明示(选定) | 用 `Reason` 枚举区分不可用原因,用 `fallbackYears` 记下哪些年份用了兜底,界面上写出来 | 选定:既有图可看,又不谎报 |

顺带修掉一个同源问题:收支稀疏的月份会让比率算出 −2383% 这种数 ——
加 `RATIO_ABSURD_ABS` 阈值,越界就显示"数据太少不足以计算"而不是印一个荒谬数字。

## 6 · 排版/显示类(FR-341 / FR-344 / FR-346)· 值得记的两条

- **覆盖月数与「紧急储备」是同一个数,必须同一条展示规则**。原来两处各自格式化,
  一处封顶一处不封顶 → 同一个事实在两页显示不同。抽 `SealedSnapshot.emergencyLabel()` 共用
  (`> 36 月` 封顶)。这是 AGENTS「一致性能用『只有一处』消除的,别用『两处保持相等』去守护」的应用。
- **瀑布图的遮挡主因不是标签自己**:截断轴的斜纹带原来横贯整宽贴在容器底边,
  而 X 轴标签是**溢出容器之外**画的 → 那条边正好从标签中间穿过。修法是把斜纹带只画在
  **每根柱子内部的底部**(柱底就是轴线,语义一样但不碰字)。
  教训:排版类 bug 要**渲染出来看**,读 CSS 想不出"溢出元素被装饰线穿过"这种交互。

## 7 · 我自己的执行效率(FR-338)· 正面回答

**`(timeout 10m)` 是上限,不是固定等待。** 命令 1 秒结束就 1 秒返回,10 分钟只是"最多等这么久
就判超时"。所以看到 `timeout 10m` 不代表那一步花了 10 分钟。

**真正的耗时环节(实测)**:

| 环节 | 单次耗时 | 说明 |
|---|---|---|
| 全量 `qa-run.sh` | **实测 320s ≈ 5.3 分钟** | 最大的一块;我 2026-08-13 一天里跑了 5 次 ≈ 27 分钟纯等待。注:AGENTS 里长期写着「~45 分钟」,是**过时数字**,这次实测订正 |
| `mvn -o package -DskipTests` | ~1–2 分钟 | |
| beta 重启 + 等 `/health` | ~26 秒 | |
| 无头 Chromium 截图 | ~30–60 秒 | 内存只有 3.5G,不能和 mvn 并行 |

**已落地的机制**:`qa-run.sh --only '<正则>'`,只跑匹配的 section(认证段永远跑,后面全靠它的登录态)。
开发中改一处护栏的反馈从"全量"降到秒级。

**流程上真正的浪费(诚实记录)**:2026-08-13 那轮护栏体检,我**跑了 5 次全量**才收敛到 0 FAIL ——
正确做法是先用 `--only` 把每条红逐个修好,最后**只跑一次全量**收口。这不是工具问题,是我的顺序问题。
另外我用 python heredoc 改文件时多次锚点不匹配(缩进/多空格),每次不匹配就是一次白跑的往返;
改成用精确字符串替换、必要时先打印 `repr()` 定位,能省掉这类空转。
