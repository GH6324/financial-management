# v1.8 · 支出链路改造(技术设计)

> 对应 [`prd/v1.8.md`](../prd/v1.8.md)。核心不是"加一个表单",而是**把散在 10 处的支出取数收敛成一个口径**,
> 并且不碰任何历史数据。

---

## 0 · 先说三个盘出来的事实(它们决定了整个设计)

### 0.1 写路径**已经完整**,不需要新建

`EntryService.addCashFlow` 现有实现已经做全了支出侧需要的一切:

```java
BigDecimal delta = kind == CashFlowKind.INCOME ? amount : amount.negate();
creditAccountBalance(...);                 // 余额:支出取负
insertCashFlow(...);                       // 写 cash_flow
snapshotTodoMapper.markDone(...);          // 标 todo(否则 forceClose 会覆盖回上期末)
auditLogService.record(...);               // 审计
eventPublisher.publishEvent(LensStaleEvent);// 透视缓存换新
```

`softDeleteCashFlow` 也已正确反向冲销支出(`delta = INCOME ? −amount : +amount`),并处理了股票账户落 CASH 现金行。

> **结论:v1.8 的支出录入直接复用 `addCashFlow`,不写新的写路径。**
> 省下的工作量应该花在读路径的口径统一上 —— 那才是风险所在。

### 0.2 **必须区分两个"支出"口径**(本设计最关键的一条)

盘 `cash_flow` 时发现取数 SQL 的收支汇总**不过滤 `is_adjustment`**:

```sql
SUM(CASE WHEN kind = 'EXPENSE' THEN amount ELSE 0 END) AS expense_orig
  FROM cash_flow WHERE deleted_at IS NULL          -- ← 没有 is_adjustment = 0
```

这对 PnL 是**对的** —— 「现金调整」语义上是本金进出,必须被 PnL 剔除,所以要计入外部流出。
但它**不是家庭消费**。beta 实测现存 39 条 `is_adjustment=1` 的行(¥117,000)。

今天这个矛盾没爆,因为家庭支出走 PMC 优先、cash_flow 只是 fallback、极少触发。
**一旦 v1.8 让逐笔成为主口径,现金调整就会被算成家庭消费**,污染储蓄率 / 月均支出 / 紧急储备分母。

所以定义两个互不替代的口径:

| 口径 | 定义 | 用于 |
|---|---|---|
| **A · 家庭支出** | `kind='EXPENSE' AND deleted_at IS NULL AND is_adjustment = 0` | 储蓄率 · 月均支出 · 紧急储备分母 · 人赚 · 支出构成 |
| **B · 账户外部流出** | 现状 `expense_orig`(**含**调整) | 账户级 PnL · NAV 序列 · 最大回撤 |

**B 不动一行**。A 是新增的。两者在代码里必须有不同的名字,注释写明为什么不同 ——
否则下一个人会"顺手统一"掉,然后 PnL 或储蓄率之一静默出错。

### 0.3 依赖方向决定了新方法放哪

| 类 | 现有依赖 |
|---|---|
| `HouseholdCashflowService` | PMC Mapper · **FactViewService** |
| `GoalProgressService` | GoalService · **FactViewService** · PeriodMapper · … · PMC Mapper |

| `CheckupController` | … · **FactViewService** |

## 1 · 架构选型:统一口径放在哪一层

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · 放进 `FactViewService` | 加 `expenseForPeriod(slice, periodId)` | 四个调用方已依赖它;但 `GoalService` 没依赖,要么给它加依赖、要么它继续自己算(=口径分裂) | 否 |
| B · 各处自己按优先级判断 | 每个调用点写一遍 `if (逐笔有) … else …` | 零新类;但这**正是 v1.6.29 的坑** —— 同页两套收入口径就是这么来的 | **绝对否** |
| **C · 新建 `ExpenseLedgerService`** ✅ | 只依赖 `PeriodMemberCashflowMapper` + `CashFlowMapper`,**不依赖任何 service** | 谁都能依赖它(含 `FactViewServiceImpl` 自己),零循环风险;口径只有一份实现 | **选定** |

### 1.1 接口形状

```java
/** 一期支出的口径结果 · source 让页面能说清"用的是哪一种" */
public record PeriodExpense(
        BigDecimal amountBase,   // 家庭支出(口径 A)· 本位币
        Source source,           // ITEMIZED | TOTAL | NONE
        int itemCount            // 逐笔笔数(TOTAL/NONE 时为 0)
) { public enum Source { ITEMIZED, TOTAL, NONE } }

/** 只依赖 mapper,任何 service / controller 都可注入,不会成环 */
public interface ExpenseLedgerService {
    /** 批量取,避免 N+1;返回 periodId → 口径结果 */
    Map<Long, PeriodExpense> byPeriods(long familyId, Collection<Long> periodIds);
    PeriodExpense byPeriod(long familyId, long periodId);
    /** 近 N 期(按 period_start 倒序),给月均 / 中位数 / 已填月数用 */
    List<PeriodExpense> recent(long familyId, int limit);
}
```

**返回本位币**。视图币种由调用方乘 `baseToViewFactor` —— 与 PMC 现在的做法一致
(`pmc.totalExpense().multiply(baseToViewFactor(slice))`),不在新服务里掺币种逻辑。

### 1.2 优先级实现(PRD FR-273)

```java
逐笔合计 = SUM(amount) WHERE family & period & kind='EXPENSE'
                        AND deleted_at IS NULL AND is_adjustment = 0
若 逐笔合计 > 0        → ITEMIZED, amountBase = 逐笔合计
否则若 PMC 总额 > 0    → TOTAL,    amountBase = PMC 总额
否则                  → NONE,     amountBase = 0
```

**不相加**。判据用「逐笔合计 > 0」而不是「有逐笔行」—— 因为一行金额为 0 的逐笔不应压掉总额。

> **与收入侧优先级相反**(收入是 PMC > 0 则用之,否则 cash_flow)。这是历史造成的:
> 收入的历史事实在 PMC 里,支出的更细事实在逐笔里。
> 这条不一致必须同时出现在:`ExpenseLedgerService` 的类注释、`netInflowIncome/Expense` 的方法注释、
> 页面 tooltip、`docs/how-to-record.md`。**四处都写**,因为它反直觉。

### 1.3 新增 mapper 查询

```java
// CashFlowMapper · 家庭支出口径(排除软删 + 排除现金调整)
@Select("""
        SELECT cf.period_id AS periodId, SUM(cf.amount) AS amount, COUNT(*) AS cnt
          FROM cash_flow cf JOIN account a ON a.id = cf.account_id
         WHERE a.family_id = #{familyId}
           AND cf.kind = 'EXPENSE'
           AND cf.deleted_at IS NULL
           AND cf.is_adjustment = 0
           AND cf.period_id IN (...)
         GROUP BY cf.period_id
        """)
List<PeriodExpenseSum> sumRealExpenseByPeriod(...);
```

命名刻意用 `sumRealExpense` 而不是 `sumExpense`,和口径 B 的 `expense_orig` 拉开距离。

## 3 · schema 与数据

### 3.1 迁移 `V53__expense_entry_mode.sql`

```sql
ALTER TABLE family
  ADD COLUMN expense_entry_mode VARCHAR(16) NOT NULL DEFAULT 'TOTAL';

UPDATE cash_flow_category SET display_name = '日常开支' WHERE code = 'consumption';
```

- 只 `ADD COLUMN` 带默认 → 满足「回滚只回 jar,迁移必须向前兼容老 jar」
- 类目**只改 `display_name`,`code` 不动** → 历史 `cash_flow` 行零影响,立刻显示新名字
- 已扫模板:无写死「消费」这个类目中文串的地方(两处命中分别是模板向导正文与手册演示表的行业列)

### 3.2 `Family` 实体加 `expenseEntryMode`

`Family` 已有 `reportingTemplate` 这类字符串枚举字段,照同一模式加即可;
读取时 `fromCode()` 兜底成 `TOTAL`(与 `ReportingTemplate.fromCode` 同一手法),脏值不炸。

## 4 · 写路径与 UI

### 4.1 端点

复用 `EntryService.addCashFlow`。新增一个填报页专用端点,与收入侧 `/entry/income` 对称:

```
POST /entry/expense        { periodId, accountId, categoryCode, amount, note }
POST /entry/expense/{id}/delete
```

删除直接调 `softDeleteCashFlow`(已具备反向冲销 + 审计)。

> 也可以直接复用账户级那个 `addCashFlow` 端点,但**不这么做**:
> 填报页需要"家庭视角的支出列表 + 本月合计",与账户详情页的"该账户流水"是两种视图,
> 各自一个端点更清楚,且便于后续给填报页加校验而不影响账户页。

### 4.2 类目校验 —— 顺带把口径 A 焊死

`cash_flow_category` 有 `account_type` 列(如 `dividend` 限 STOCK),
收入侧已有服务端红线(`EntryService:283` 校验「类目存在 + 是 INCOME + 绑定账户类型匹配」),支出侧照抄。

但支出侧多一条**关键约束**:

> **下拉只取 `kind='EXPENSE'` 的类目** —— 这自然排除了 `cash_adjust`(它是 `kind='BOTH'`)。

于是形成一个闭环:**从填报页录入的支出,`is_adjustment` 必然是 0,天然落在口径 A 里**。
`is_adjustment=1` 只由「手动调现金」那条路径产生(`StockHoldingService`),不经过任何用户表单。
所以口径 A 的 `is_adjustment = 0` 过滤不是"防御性写法",而是**语义边界** —— 注释里要这么写,
免得后人以为可以省掉。

### 4.3 防重复扣(PRD FR-274)的实现

对账提示的判据要能算出来,不能靠猜:

```
本期该账户 既有 sumRealExpense > 0
且 该账户本期 snapshot 是「手工提交」而非由流水推导
  → 显示提示
```

**已核实**:`period_snapshot` 只有 `end_balance / submitted_by / submitted_at / note`,
**没有任何字段能区分"这条余额是人手填的、还是被流水推导改的"** —— 两条路径都走
`snapshotMapper.upsert` 并写同一个 `submitted_by`。所以判据做不到精确。
两个选择:

| 做法 | 取舍 |
|---|---|
| 加一列 `snapshot.source`(MANUAL / DERIVED) | 判定准;但又一次 schema 改动 |
| **只要「本期该账户有逐笔支出」就提示** ✅ | 零 schema;代价是即使用户顺序正确也会看到提示 |

选后者,并把文案写成**中性的对账提醒**而不是警告:
「本期已录 N 笔支出(共 ¥X),已从本账户余额中扣除。核对余额时不必再减一次。」
—— 顺序正确的人看到它也是有用的确认,不会被当成误报。

## 5 · 怎么证明"总额模式逐位相同"(PRD 验收 ①)

不靠"我觉得没动到"。复用 v1.6.30 建的那套**独立模拟器**:

1. 取 prod 快照(只读)→ 用现版 jar 算出全部 KPI,存基线
2. 升级到 v1.8(所有家庭 `expense_entry_mode='TOTAL'`)→ 再算一遍
3. **逐位比对**;任一项不同即回滚查因

模拟器本身已在 v1.6.30 被验证过能精确复现页面值(beta 11/11 一致),可以当尺子用。

另加单测:
- `ExpenseLedgerServiceTest` —— 三种 source 的判定、`is_adjustment=1` 必须被排除、软删行必须被排除、金额为 0 的逐笔不压掉总额
- `ExpenseModeParityTest` —— 同一份数据在 TOTAL 模式下,新旧两条取数路径结果相等

## 6 · 不做什么

- **不迁移历史 PMC 数据**到 `cash_flow`。看着"统一了",但会:丢失"这是手填总额"这一事实、
  凭空给每笔编造账户归属、且不可逆。历史就该长成历史的样子。
- **不动口径 B**(`expense_orig` / PnL / NAV)。
- **不做预算与超支告警**。
- **不给逐笔支出加成员维度的独立字段** —— `cash_flow.submitted_by` 已经能回答"谁录的",
  PRD 里"按成员看构成"用它即可。
