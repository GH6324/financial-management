## 二、一条不能碰的红线:补录路径不许走 reopen/close

最省事的实现是 `reopen → 写入 → close`。**不行**,因为 `forceClose` 里有这一段:

> 找出本期所有 PENDING 的账户,upsert `period_snapshot.end_balance = 上期末`(延续)

重开再关会**再跑一次这个延续逻辑**。虽然它有「snapshot 已存在则不覆盖」的防御(v0.2 那次修的),
但整条路径还会:

- 重新代签 `period_member_completion`
- 触发 metrics 异步重算
- 把账期状态在 CLOSED → OPEN → CLOSED 之间来回翻,审计日志上留下一次「重开」

而用户做的只是「补几笔支出」。**用重开来实现补录,等于把一个小动作伪装成一次封板解除** ——
这正是 PRD §9 失败模式①。

所以:补录必须是**直接写 cash_flow 的独立路径**,绕开 `requireOpenPeriod`,
但用另一套判据(§三)把它限制住。

---

## 三、无论选哪条路都要有的三道闸

1. **只能补上一期**:判据走**账期序**(最近一个 CLOSED 且紧邻当前 OPEN 期),
   不做日期算术 —— 账期类型可切(月/周),跨年 + 切类型时日期算术必错。
2. **强制 `affects_balance = 0`**:这是「不动余额」的唯一实现点。
   它不能是「前端默认不勾」,必须在**服务端写死** —— 前端只防手滑。
3. **缓存失效**:补录后该期的月报 / AI 复盘缓存必须清。
   这个病犯过一次(v1.19.16 / issue #17 第 1 条):数字变了而解读一个字没动,
   旁边还写着「关账后结果缓存可回看」。
