## 一、需求理解(验收口径)

见 PRD §11 的 18 条。其中 4 条是硬门:

- **零差异基线**:`close_delay_days = 0` 时与 v1.22.5 逐分相等
- 余额/估值写入永远落最新 OPEN 期
- 收益类采纳「已自然结束**且填报完成**」的补录期(反向:未填完不采纳)
- 不出现三期同时 OPEN

## 二、关键选型

### 选型一 · 关账判据与触发点放哪

| 备选 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | `PeriodService` 出判据方法;`PeriodOpener` 拆成**两个独立 `@Scheduled`**:`openIfDue()` 只开、`closeIfGraceExpired()` 只关 | 不新增类;**把「关账」从「开账事件」上解耦** —— 这正是 FR-615 要的 |
| B | 新建 `PeriodLifecycleService` 统管开关 | 多一层无状态委托;`PeriodOpener` 里的 `createPeriodAndTodos`(LOAN 预填、todo、快照)搬过去动静太大,而那部分与本版无关 |
| C | 判据内联在 `PeriodOpener` | 判据要被管理页「预告关账时点」(FR-616)和手动提前关(FR-617)复用,内联就得复制三份 |

**为什么 A 的「拆两个定时任务」是关键**:现在的关账是 `closePriorOpenPeriods` 在开新期**之前**顺手做的。
宽限期内「该关的日子」和「该开的日子」不再是同一天,继续挂在一起就会漏关(PRD 失败模式 ⑤)。

**判据(`PeriodService.graceDeadline` / `shouldAutoClose`)**:

```
关账截止日 = period_end + close_delay_days
应自动关 = auto_close_enabled && today > 关账截止日
```

`auto_close_enabled = false`(手动)时走 FR-612 兜底:
**当这个期不再是「最近两期」之一时强制关** —— 即下下期一开就关。
判据用**账期序**不用日期算术(PRD 失败模式 ③:跨年、周/月类型切换时日期算术会错)。

### 选型二 · 30 处调用点怎么收口

| 备选 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | `PeriodMapper` 新增两个**带语义**的方法,`findCurrentOpen` 标 `@Deprecated`:<br>`findBalancePeriod()` = 最新 OPEN(余额轴)<br>`findRecordableOpen()` = 全部 OPEN 升序(收支轴) | **名字自证语义**:以后有人写 `findBalancePeriod` 会停一秒想「我要的是余额期吗」;`findCurrentOpen` 不会。护栏可以硬拦「不许新增 `findCurrentOpen` 调用」 |
| B | 逐处改判断逻辑,方法名不动 | 30 处各自拍脑袋,而且**新人第 31 处还会错** —— 这是 v0.14 加 `METAL` 枚举踩过的同一个坑 |
| C | `findCurrentOpen(familyId, axis)` 加参数 | 参数是 boolean/enum 都读不出意图(`findCurrentOpen(1L, true)` 是什么?);且老调用点不改也能编译 = 静默沿用错语义 |

**映射**:A 类 9 处 → `findBalancePeriod`(行为零变化,只换名字);
B/C 类按 PRD §4 的结论逐个改;`findCurrentOpen` 保留但 `@Deprecated` + 护栏拦新增。

### 选型三 · FR-623 余额传导的时机

| 备选 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | **写入时同步传导**:补录期余额落库后,若下一期那张快照仍是 `CARRIED_FORWARD`,原地更新它 | 用户补完 8 月立刻就能在 9 月看到对的延续值;`period_snapshot` 始终是权威 |
| B | 关账时统一结转 | 宽限期内进行期余额是**错的**(8 月末已变、9 月还按旧值延续),而 dashboard 净资产就锚进行期 → 用户看到的净资产是错的,且要等到关账才对 |
| C | 读取时惰性计算 | `period_snapshot` 不再是权威;而它有 5 个写入者、十几个读取者,惰性计算只在读路径生效 = 两份真相 |

**守门**:只改 `source_tag = CARRIED_FORWARD` 的快照。用户手填/估值写过的一律不动(PRD 失败模式 ④)。

### 选型四 · 收益类锚点判据扩大到「已填报完成的补录期」

| 备选 | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 改 `FactMapper.findClosedPeriodIds` 的 SQL:`status='CLOSED'` **OR**(`period_end < today` AND 无 PENDING todo AND 全员已 complete) | 一条 SQL 算完,`FactSlice` 仍是纯 record;判据与 `markCompletedByMember` 触发自动关账的条件**同源** |
| B | Java 侧装配切片时额外查 todo/completion | 多两次查询;而且 `FactSlice` 的 `closedPeriodIds` 语义会变成「已定稿期」,名字对不上 |
| C | `period` 加物化列 `settled` | 冗余状态要维护一致性(todo 一变就得同步),而这正是 issue #15 那类「同一事实两份状态互相打架」的来源 |

**判据必须是「填完了没有」而不是「关了没有」**(PRD §4.4):
没填就锚它会重演那次「整段净资产变化全算成投资收益」。

**命名**:方法与字段改叫 `settledPeriodIds` —— 「已定稿」覆盖 CLOSED 与「已完成待关账」两种,
而 `closed` 只覆盖前者。留 `closedPeriodIds()` 为 `@Deprecated` 别名,老单测不动。

### 选型五 · 填报页双期切换形态

**选定**:复用现有 `?period=` 参数与 `findSelectedPeriod`(已支持 id / `YYYY-MM`),
在页面顶部加两个 pill(preview 已与维护者对齐)。默认值改为「宽限期内 → 补录期」。

不新建路由、不改表单 action —— 填报页 12 项全部锚「选中期」(PRD §4.2),
参数一改整页自然跟着走。这是三个页面里唯一不需要动取数逻辑的。

## 三、系统概要设计

### 数据架构

`V61__period_close_grace.sql`:`family` 加两列,**只加不改**,默认值 = 现行为。

| 列 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `close_delay_days` | `SMALLINT NOT NULL` | `0` | 关账宽限天数(0/2/5) |
| `auto_close_enabled` | `TINYINT(1) NOT NULL` | `1` | 关 = 手动关账(仍受 FR-612 兜底) |

`CHECK (close_delay_days BETWEEN 0 AND 5)` —— 宽限上限锁死 5 天,
从 schema 层保证「不可能跨到第三期」(PRD §5)。

### 运行架构

```
每日 00:30  openIfDue()            → 到新期起始日:建新期(不再顺手关旧期)
每日 00:35  closeIfGraceExpired()  → 扫全部 OPEN,过了宽限截止日的关掉
                                     手动模式:只关「已不在最近两期」的
```

两个任务错开 5 分钟:**先开新期再判关账**,保证「开新期时上期的宽限还在」这个顺序确定。

## 四、兼容性设计

| 面 | 处置 |
|---|---|
| **schema** | 只加列带默认值;老 jar 读不到新列照常跑 |
| **行为** | `close_delay_days = 0` → `graceDeadline = period_end`,`today > period_end` 即关。
新期起始日一定 > 上期 period_end,所以**与现行为等价**(零差异基线验证这一点) |
| **数据** | 不 UPDATE / DELETE 任何行 |
| **回滚** | 回 jar 即回旧行为;宽限中的期在下次滚动时被关,数据不丢 |

**一处必须注意的顺序差异**:现在是「先关旧期、再建新期」,所以新期预填从**已 force-close 的**
上期结转。拆开之后新期建立时上期可能还 OPEN —— 但 `computePrefillBalance` 读的是
`snapshotMapper.findLatestBefore(账户, 新期起始)`,**只看快照不看期状态**,所以结果不变。
(这也是 FR-623 传导必须存在的原因:上期快照后来又变了。)

## 六、上线与回滚

1. `db/apply.sh` 跑 V61(只加列,秒级)
2. 换 jar
3. 默认 T+0 → **所有家庭行为不变**;维护者在管理页改成 T+2 才进入双活跃
4. 回滚:`bash deploy/rollback.sh`(回 jar,不回 DB)

**可观测**:`closeIfGraceExpired` 每次执行打一行
`[grace-close] family=N period=M deadline=D closed=true/false`,
关账不是「悄悄发生」的 —— 出问题时要能从日志看出它判了什么。
