## 0 · 施工前的查证:PRD 有一处假设不成立

PRD FR-350 把四个属性并成一条「封板被破坏」。逐条追代码后,它们**不在同一条路径上,也不在同一个区**:

| 属性 | 读取路径 | 影响哪些指标 | 所在区 |
|---|---|---|---|
| `account.type` | `FactMapper.queryBase` → `a.type` | 集中度 / HHI / 按类型分布 | **二区(封板)** |
| `product_category.liquidity_class` | `FactMapper.queryBase` → `LEFT JOIN product_category` | 流动性分层 / 紧急储备月数 | **二区(封板)** |
| `account.product_category_code` | `ReportsController:296` 直接读当前 `Account` 列表 | 账户表类目列 + 基准取值键 | 三区(随 range) |
| `product_category.benchmark_pct` | `ReportsController:301` 直接读 `productCategoryService.listAll()` | 账户级 vs 基准 / 家庭加权基准 | 三区(随 range) |

**结论**:前两个确实证伪了 v1.10 的封板承诺;后两个不在封板承诺范围内 —— 三区本来就是随 range 变的趋势视图。
现有的 `SealedPeriodService.driftNotes()` 措辞是准的(它只列了集中度 / 分层 / 大类分布,没提基准)。

后两个仍然要冻,但**理由换一条**:「上个月月报上写跑赢 2 个点,今天重新打开变成跑输」,
违反的是**可复现**而不是**封板**。两条都要修,但设计上必须分开 —— 因为三区那条多一个封板侧没有的问题:
一个 range 窗口里有 N 期,基准该取哪一期?(见 §3.2)

**对 PRD 的影响**:FR-350 的验收第 1 条(「四类指标逐字不变」)拆成两条,分别对二区和三区断言。
PRD 正文不改结论,只在评审时记下这条范围校正。

### 0.1 · 施工中发现的**第三个**漂移入口(设计时漏了)

上表只有两条路径,施工中被验收手段抓出**第三条**:

| 属性 | 读取路径 | 影响哪些指标 | 所在区 |
|---|---|---|---|
| `account.expected_return_pct`(+ 类目 `benchmark_pct`) | `FactViewServiceImpl.expectedReturnByAccount` → `AccountPerformance.planActualDiffPct` | 账户表「预期 vs 实际」列(预实偏离) | 三区(随 range) |

怎么发现的:把某账户的基准 % 调成 99% 做反向验证,二区四类指标都稳住了,
但 3M / 6M / YTD × 三币种的数字还在动 —— 说明还有一条路没堵。

为什么设计时会漏:上表是**按「哪个属性」**列的,而这一条的特征是**同一个属性(基准 %)有两个消费者**,
一个在 `ReportsController` 的基准段(设计里有),一个在 `FactViewServiceImpl` 的预实计算里(设计里没有)。
「列属性」这个盘点方式天生看不见第二个消费者。

**方法论结论**(比这个 bug 本身重要):盘点漂移源要**按调用点**扫,不能按属性列;
而人扫调用点必漏,所以最后落到护栏 + 反向验证(改设置看历史动不动)上,
不指望清单完整 —— 这与 memory `feedback_metric_refactor_baseline`「调用方清单靠人列必漏」是同一条。

## 1 · 决策一 · 定格数据存在哪

### 备选

**A · 给 `period_snapshot` 加列**

- 好处:`FactMapper.queryBase` **已经** `LEFT JOIN period_snapshot`,不新增 join,查询形状不变。
- **否决,而且是硬伤**:`period_snapshot` 只有「用户填了余额」才有行。`queryBase` 里那段
  `COALESCE(ps.end_balance, (SELECT ... 沿用最近一期))`(v0.4.3 B1)就是专门为**没有行**的账户准备的 ——
  也就是说往这张表加列,等于**只给填过余额的账户定格**,靠沿用出现在报表里的账户照漏。
  这是最难发现的一类错:表面上定格了,漏的恰好是最不常动的账户。
- 附带一条:`period_snapshot` 的语义是「谁在什么时候提交了什么余额」(带 `submitted_by` / `submitted_at`)。
  混进系统派生的分类值,这张表就说不清自己是什么了。

**B · 新建旁表 `period_account_attr`** ← **选定**

- 好处:语义单一(「第 N 期关账那一刻,账户 X 的分类属性是什么」),写入点单一,可以独立回填、独立删除。
- 代价:`queryBase` 多一个 `LEFT JOIN`。主键 `(period_id, account_id)` 直接命中,和现有 `period_snapshot` 的 join 同形,
  不引入新的扫描量级(这一点在 §7 分水岭里用实测 SQL 数验证,不靠推断)。

**C · 通用时态表 `account_attr_history(account_id, attr, value, valid_from, valid_to)`**

- 好处:最通用,能回答「任意时刻该账户是什么类目」,不止关账那一刻。
- 否决:要在**每一处属性写入**都闭合上一段 `valid_to` —— 而账户/类目属性的写入点散在管理页账户编辑、
  类目编辑、模板套用、批量导入等多处。**漏一处 = 历史属性静默错**,而错的是历史,用户下次翻月报才发现,
  且无从判断是漏写还是本来如此。这与 v1.10 否决方案 B 时的理由同源:
  **为一次查询引入一个必须处处维护的可变状态源,不划算。**
- 而且它解决的问题超出需要:我们只要「关账那一刻」这**一个时点**,不要连续时间轴。

### 选定表结构

```sql
-- db/migration/V54__period_account_attr.sql
CREATE TABLE period_account_attr (
  period_id             BIGINT       NOT NULL,
  account_id            BIGINT       NOT NULL,
  account_type          VARCHAR(16)  NOT NULL,
  product_category_code VARCHAR(32)  NULL,
  product_category_name VARCHAR(64)  NULL,
  liquidity_class       VARCHAR(16)  NULL,
  benchmark_pct         DECIMAL(6,2) NULL,
  source                VARCHAR(8)   NOT NULL,           -- CLOSE | BACKFILL
  sealed_at             DATETIME(3)  NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (period_id, account_id),
  KEY idx_paa_account (account_id),
  CONSTRAINT fk_paa_period  FOREIGN KEY (period_id)  REFERENCES period(id),
  CONSTRAINT fk_paa_account FOREIGN KEY (account_id) REFERENCES account(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

四条刻意的取舍:

1. **存解析后的值,不只存 `product_category_code`。**
   只存 code 再去 join 当前 `product_category`,挡不住「改类目自己的 `benchmark_pct` / `liquidity_class`」这条 ——
   而这恰恰是最常发生的一种改动(调基准比换账户类目频繁)。代价是类目改档之后历史值和当前类目对不上,**这正是要的效果**。

2. **存 `product_category_name`(显示名),不只存 code。**
   v0.14.1 专门修过「类目列裸露 `GOLD` / `US_STOCK` 这类 code」。若类目此后被删,只存 code 会让历史行退回裸 code —— 那是回归。

3. **不对 `product_category(code)` 建外键。**
   类目可以被删,删了不该连带删掉历史定格行、也不该被历史行挡住删除。存值不存约束。

4. **`source` 区分 `CLOSE` 与 `BACKFILL`。**
   回填出来的行**不是真定格**(见 §4),是拿今天的属性补的。这个字段让任何人事后查历史都能看出区别 ——
   这是 v1.10 方案 C 里唯一值得单独拿过来的设计。

## 2 · 决策二 · 什么时候写

### 备选

**A · 关账时写** ← **选定**

`PeriodService` 有唯一的私有漏斗 `close(long periodId, Long actorMemberId, String summary)`(:202),
三个公开入口(`close(MemberPrincipal,long)` / `close(long)` / `forceClose(long,long)`)全部路由到它。

写入位置:`periodMapper.close(...)` 之后、`runMetricsAfterCommit(periodId)` 之前,**同一事务内**。

- 为什么必须在事务内、而不是挂在 `afterCommit`:定格失败就不该关账成功。
  一个「关了账但没定格」的期,后续读会回落当前属性 —— 表面正常,实际漏保护,且不报警。
- 为什么不放在那三段 `try/catch` 非阻塞钩子里(FIRE 重算 / 再平衡归档 / AI 月报):
  那三段是**衍生产物**,失败可重跑;定格是**这一刻才存在的事实**,过了就没了,不能降级。

**B · 用户提交余额时写(跟 `period_snapshot` upsert 走)**

- 否决理由 ①:提交余额和关账之间还能改账户设置,那段时间的改动应当以**关账时**为准,不是提交时。
- 否决理由 ②:`snapshotMapper.upsert` 有 6 处调用点(v1.11 就是因为这 6 处才放弃了 familyId 级长缓存,
  见 tech-design v1.11 §1 的缓存生命周期选择)。漏一处 = 该账户该期没定格 = 静默漏保护。

**C · 读时惰性写(第一次读到已关账期且无定格行 → 补写)**

- 否决:读产生写副作用,并发下要额外加锁;更致命的是**「第一次读」的时刻是随机的** ——
  定格值取决于谁先打开页面、什么时候打开。这把「不可复现」从属性层搬到了时间层,没解决问题。

### reopen 的处理

`private void reopen(long, Long, String)`(:190)里**删掉该期的定格行**:

```java
periodAccountAttrMapper.deleteByPeriod(periodId);
```

这样 PRD 第三条规则「重开后再关账 = 重新定格」是**结构上必然**的 ——
不需要额外的标志位、版本号或「是否已定格」判断。少一个状态就少一类不一致。

## 3 · 决策三 · 读侧怎么接

### 3.1 封板侧(`FactMapper.queryBase`)

```sql
COALESCE(paa.account_type,     a.type)              AS account_type,
COALESCE(paa.liquidity_class,  pc.liquidity_class)  AS product_liquidity_class,
...
LEFT JOIN period_account_attr paa
  ON paa.period_id = p.id AND paa.account_id = a.id
```

**为什么改 SQL 而不是在 Java 层替换。**
分类值是在 SQL 里 join 进来、装进 `FactBaseRow` 的;消费它的地方(`SealedPeriodService`、`AllocationService`、
`AllocationDiff`、各 lens)全都吃 `FactBaseRow`。改这一处,所有消费者自动受益。

- 备选:在 `SealedPeriodService` 里替换 —— **否决**,`AllocationService` 等并不都走 `SealedPeriodService`,会漏一半。
- 备选:在 `FactViewServiceImpl` 组装 `AccountPeriodFact` 时替换 —— 可行,但需要额外一次按 `(periodId, accountId)` 的查询;
  SQL 侧 join 是同一次查询里带出来的,没有额外往返。

**回落语义:没有定格行 → 用当前属性。** 这不是兜底将就,三种情形下都是正确行为:

1. **未关账的当期**:本来就该跟当前走(仪表盘 = 实时,PRD 规则第二条)。
2. **回填之前**:回填在同一个 migration 里,存量已关账期都会有行。
3. **新建账户**:`queryBase` 是 `FROM account a JOIN period p` 的交叉 —— 今天新建的账户**会出现在去年已关账期的行里**
   (余额走 `COALESCE` 兜到 NULL)。它没有定格行,回落当前属性,正确:它没有历史需要保护。

> **护栏陷阱(必须记下)**:因为第 3 点,护栏**不能**写成「每个已关账期的每个账户都必须有定格行」——
> 新建一个账户就会让它变红,而那是正常的。正确的断言见 §8。

### 3.2 三区侧(`ReportsController` 基准段,:295–340)

现状:`allAccounts`(当前 `Account`)→ `pcCodeByAccountId`;`productCategoryService.listAll()`(当前类目)→ `benchmarkPctByPcCode` / `pcNameByCode`。

改成:这三张 map 按**锚期**从 `period_account_attr` 读,读不到的 accountId 回落当前值。

**锚期取哪一期 = `slice.returnAnchorPeriodId()`。**
这不是新发明的规则 —— `FactSlice.returnAnchorPeriodId()`(:53)= 最新已关账期,是 v1.6.30 定下的**收益类指标锚点**,
`familyXirr` / `familyTwr` / 账户 `xirr` 全锚在它上面。基准是拿来和 xirr 比的,**属性源必须和被比较的对象同期**,
否则就是拿 8 月的基准去比 7 月的收益。

- 备选:窗口内按期加权平均基准 —— **否决**。基准是一个**假设**(「货币基金该有 2%」),
  对一个假设做时间加权平均,得到的是一个库里从不存在、也没人能解释的数字。
- 备选:用 `slice.lastPeriodId()`(窗口最后一期,可能是进行中的 OPEN 期)—— **否决**,
  OPEN 期没有定格行,等于没改。

> **发现的一处既有不一致(本版不改)**:家庭加权基准(:329)按 `slice.lastPeriodId()` 过滤参与加权的行,
> 而账户 xirr 锚在 `returnAnchorPeriodId()`。窗口最后一期是 OPEN 时两者差一期。
> 这属于 v1.11 审计口径范畴,**本版不动** —— 动它会破 §7 的零差异分水岭,分不清是本版引入还是既有偏差。
> 记进 `docs/metric-audit-v1.11.md` 待办,下一版单独处理。
> 本版只改**属性从哪读**,不改**哪些行参与加权**。

## 4 · 决策四 · 回填

放在同一个 `V54__period_account_attr.sql` 里:建表 + 一条 `INSERT ... SELECT` 回填全部 `CLOSED` 期。

```sql
INSERT IGNORE INTO period_account_attr
  (period_id, account_id, account_type, product_category_code, product_category_name,
   liquidity_class, benchmark_pct, source)
SELECT p.id, a.id, a.type, a.product_category_code, pc.display_name,
       pc.liquidity_class, pc.benchmark_pct, 'BACKFILL'
  FROM account a
  JOIN period p ON p.family_id = a.family_id AND p.status = 'CLOSED'
  LEFT JOIN product_category pc ON pc.code = a.product_category_code
 WHERE a.archived_at IS NULL OR a.archived_at > p.period_end;
```

四条约束:

- **幂等**:`INSERT IGNORE` + 主键 `(period_id, account_id)`。重跑无副作用。
- **只回填 `CLOSED`**:OPEN 期不写,当期必须跟当前走。
- **归档过滤必须和 `queryBase` 逐字一致**(`archived_at IS NULL OR archived_at > p.period_end`,v1.10 的 `v110-ARCHIVED-TIME`)。
  两边不一致 → 回填的行集 ≠ 读取的行集 → §7 的零差异当场破。这一条落成护栏(§8)。
- **不循环、单条语句**:beta 约 175 期 × 账户数,一条 `INSERT...SELECT` 即可;prod 只有 3 期。

**备选:写成独立运维脚本手动跑** —— 否决。prod 部署时会漏,而且「跑没跑过」要靠人记。
放进 migration,跑没跑过由数据库说了算,`deploy.sh` 已有的迁移链路自动覆盖。

**为什么零差异是必然、不是「希望」**:回填只能用今天的属性,而现状读的也是今天的属性 ——
两者是**同一份数据**。所以理论差异必须为零。任何差异只可能来自:
① 回填行集 ≠ 读取行集(归档/家庭过滤对不上);② `COALESCE` 顺序写反;③ join 写成 `INNER` 丢了行。
这三种都是 bug。**这就是它作为分水岭的价值** —— 一个不需要判断力的判据。

## 5 · 决策五 · SQL 归因手段(FR-351)

### 备选

**A · MyBatis `Interceptor`** ← **选定**

```java
@Intercepts({
  @Signature(type = Executor.class, method = "query",
             args = {MappedStatement.class, Object.class, RowBounds.class, ResultHandler.class}),
  @Signature(type = Executor.class, method = "query",
             args = {MappedStatement.class, Object.class, RowBounds.class, ResultHandler.class,
                     CacheKey.class, BoundSql.class}),
  @Signature(type = Executor.class, method = "update",
             args = {MappedStatement.class, Object.class})
})
```

拿 `MappedStatement.getId()` = **mapper 方法全限定名**(如 `...FactMapper.queryBase`),
这正是「谁发的」这个问题的答案。`ThreadLocal<Map<String,Stat>>` 累加次数 + 耗时,
请求收尾时按次数排序输出并清空 ThreadLocal(**必须 `finally` 清,否则线程池复用会串账**)。

**实现偏离 · 请求收尾的挂点从 `OncePerRequestFilter` 换成 `HandlerInterceptor`**
(实际类:`SqlProfileWebInterceptor`,注册在 `WebMvcConfig` 的最后一个)。

- 设计时写 filter,是因为 filter 包得最外、统计最完整。
- 实现时不成立:filter 只能在 `chain.doFilter()` **返回之后**写响应头,而报表页这种大页面是
  **chunked 流式**响应 —— 那一刻响应早就 commit 了,`X-Sql-Count` 加不上去(不报错,头就是不出现)。
  这正是 v0.2 让 `/error` 页失效的同一个坑(memory `feedback_thymeleaf_diagnosis`)。
- 换 `HandlerInterceptor` 后:`preHandle` 里 `start()`,`postHandle`(视图渲染前)写头,
  `afterCompletion` 打清单 + `finally` 清 ThreadLocal。代价是统计范围缩到「进入控制器之后」——
  正好是要诊断的范围,而排在它前面的两个 interceptor(改密码检查)发的 SQL 不该进清单,
  所以它**注册在最后**。这个缩小是收益不是损失。
- **开销要如实说**:关闭时**不是零开销** —— 每次 query 多一次 `SqlProfileContext.active()`
  (一次 ThreadLocal 读 + 一次 null 判断)和一次方法调用。说「零开销」是不诚实的。
  它在 JIT 之后接近噪声,而且 MyBatis 的 interceptor 链本来就在那条路径上。
  PRD FR-351 里「关闭状态零开销」这句已改成「不进入统计路径,只多一次 ThreadLocal 读」。
- 开关走 `family_runtime_config`(V26 已有表)+ 管理页,不写服务器配置文件(项目铁律)。
- 输出:日志一份 + 开启时给响应加 `X-Sql-Count` 头(方便 curl 直接读数,不用翻日志)。

**B · p6spy / datasource-proxy**

- 好处:成熟、能拿到真实 SQL 文本和参数。
- 否决(作为主选):它给的是**SQL 文本**,不是调用点。761 条里大量是同一条 SQL 反复执行,
  按文本聚合能告诉你「这条跑了 400 次」,但要回答「谁调的」还得人肉在代码里找。而且多一个依赖。
- **保留为次选**:如果 A 拿到的 statement id 粒度不够(比如一个 mapper 方法内部有动态 SQL 分支,
  同一个 id 对应形状差很远的 SQL),再叠加它看文本。

**C · MySQL `performance_schema` / `general_log`**

- 好处:完全不动应用代码。
- 否决:归因不到 HTTP 请求、也归因不到调用点 —— 这和现在用 `SHOW GLOBAL STATUS LIKE 'Questions'`
  只能拿到总数增量的困境是同一个,换个更贵的方式重复现有的死路。

## 6 · FR-352 / FR-353 的位置

**FR-352(消 N+1)**:清单出来之前不预设改法。设计约束只有两条 ——
① 每修一处都要重跑 §7 的零差异比对(渲染逐字相同,SQL 数可以变);
② 若某个 N+1 恰好被 §1 的定格表顺手消掉(分类属性不再需要逐行 join 当前表),
在最终报告里**归到 FR-350 名下,不重复计功**(PRD FR-352 已要求)。

**FR-352 实测**(beta · profiler 开着数 SQL,关着测耗时;每页 24 页面零差异比对全过):

| 页面 | SQL 条数 | 控制器阶段 DB 耗时 |
|---|---|---|
| `/reports?range=3M` | 586 → **124** | 2320 ms → **973 ms** |
| `/dashboard` | 421 → **90** | 2156 ms → **487 ms** |
| `/checkup` | 583 → **146** | 1539 ms → **368 ms** |

端到端耗时中位数(profiler **关** · 预热后 9 次取中位):
`/reports?range=3M` 1.80 s → **0.61 s** · `range=ALL` 0.89 s → **0.37 s** ·
`/dashboard` 0.62 s → **0.22 s** · `/checkup` 0.42 s → **0.22 s**。

四处改动都是「**同一请求内**重复取数」,不是跨请求业务缓存(那会引入过期语义):
① `FactLoadCache`:同一 GET 请求内同一 `FactFilter` 只 `queryBase` 一次(10 → 6,剩下 6 个是真不同的筛选);
**写请求不记忆切片**(先写后读必须读到新值)。
② 家庭行 / 每期首次出现的账户按请求缓存(`findById` 194 → 19 · `firstAppearance` 21 → 1)。
③ PMC 家庭聚合 + 统一口径支出改按切片批量(180 → 8 · `sumRealExpense` 101 → 17);
新增的批量方法过滤条件与点查**逐字相同**,只是 `IN` + 分组。
④ `FxService.ensure*` 先一条查出已有的 (期, 币种),只对差集补(`findOne` 190 → 0)。

缓存全部打了 **owner 印记**:ThreadLocal 缓存在请求结束时没人清,Tomcat 线程一复用就可能被下个请求读到 ——
读取侧验 owner 不符即当作没有缓存、走原查询。(这是「缓存」这个词在本项目里唯一可接受的形态。)

**FR-353(比率降级)** · 实现与设计的两处修正:

1. **阈值的单位与位置**:设计写 `MetricDisplay.RATIO_ABSURD_THRESHOLD = 500`(百分点),
   实现是 `MetricDisplay.RATIO_ABSURD_ABS = new BigDecimal("5")`(**比率单位**,5 = 500%)。
   原因:代码里这一路的量都是比率(0.48 = 48%),用百分点会在判断处多一次 ×100,
   而那次乘法就是「两种单位混用」的起点。同时 v1.11 已经在 `SealedSnapshot` 里有一个私有的
   500% 阈值 —— **不是新建第二个常量,是把它搬进 `MetricDisplay` 并让 `absurd()` 委托过去**。
   两处各写一个 500% 迟早变成「一处降级一处不降级」,与 v1.11 的 hx-select 落空、
   v0.14 加枚举漏改模板硬编码同类。
2. **文案也必须单一出处**:通过 `GlobalModelAdvice` 的 `@ModelAttribute("ratioNote")` 注入,
   模板一律 `${ratioNote.insufficient()}`,不许再写字面量。两种长度(KPI 用完整 / 表格单元格用短)
   的理由见 PRD FR-353 第 2 条。
3. **降级点在 model 层而不是模板层**(2026-08-14 beta 复验补的第三处)。封板对照表那一行还有
   Δ 环比 / Δ 同比 两个**派生**列,第一版没管 → 值列写着「收支不足」、同比却摆着 −2468.2 pp。
   两种改法:(a) 模板里每个 Δ 单元格再判一次 `r.absurd(...)`;(b) `ComparisonRow.momDelta()/yoyDelta()`
   在任一端点失真时返回 null,模板既有的 `d == null ? '—'` 分支自动接住。
   选 (b):派生值该不该存在是**数据的性质**,不是某个模板的排版选择;放模板里就等于
   「以后谁再渲染一次这个 Row 就要记得再判一次」—— 与项目里反复吃过的「同一条规则散落多处」同型。
   代价:`momDelta()` 由纯减法变成带条件,读代码时要多看一眼注释才知道 null 有两种含义
   (缺期 / 端点失真)—— 所以模板给了两句不同的 title,页面上分得开。

不改计算,只改**显示**。但因此**它按设计就会改变渲染** —— 所以它排在施工顺序最后,
做完**重新取基线**,而不是拿它去撞零差异比对(见 §7)。

## 7 · 施工顺序与分水岭

两件大事同版,v1.8 的教训是必须切开。分水岭放在中间:

1. **建零差异基线**:checkout 已发布 tag `v1.11.3`,把报表页 + 仪表盘在 3 币种 × 6 range 下的渲染存下来。
   (基线必须来自**已发布 tag**,否则分不清代码差异和数据漂移。)
2. `V54` 建表 + 回填;`FactMapper.queryBase` 加 `LEFT JOIN` + `COALESCE`;`PeriodService` 两个漏斗加写/删。
3. **分水岭比对 ①**:与第 1 步逐字比。**有差异 → 停下查因**,不许「看起来更合理就接受」。
4. `ReportsController` 基准段改锚期读取。**分水岭比对 ②**:同样必须逐字相同。
5. 定格证明护栏(`v112-ATTR-*`)。到这里 FR-350 完成。
6. **再**开 FR-351(interceptor + 管理页开关),拿到清单。
7. FR-352 逐个修,**每修一处比对一次**(渲染逐字相同,SQL 数允许变小)。
8. FR-353。

前 5 步和后 3 步的**验收信号是同一个**(渲染逐字相同),所以任何一步引入的问题都会当场暴露,不会攒到发版前。

**第 8 步是这条链的终点,不是链上的一环**:FR-353 按设计要把某些位置的数字换成一句话,

所以顺序上它排最后,做完之后**重新取一次基线**供下一版使用。

## 8 · 护栏

| id | 断言 | 形式(实际落地) |
|---|---|---|
| `v112-ATTR-FREEZE-CLOSED` | 关账在**同一事务内**定格:`freezeByPeriod` 在 `periodMapper.close()` 之后、`runMetricsAfterCommit()` 之前,且方法带 `@Transactional` | qa-run:按**行号先后**断言位置(挪进 `afterCommit` 或包 try-catch 会被抓) |
| `v112-ATTR-LIVE-CURRENT` | 缺定格行时**回落当前属性**,不许抛错/显示空(当期 / 新建账户 / 锚期未关账三种合法缺失) | qa-run grep + `ReportsController` 的 null 分支 |
| `v112-ATTR-BENCH-ANCHOR` | 报表读锚期定格(`accountPerformance(slice, true)` + `returnAnchorPeriodId`),仪表盘走实时重载;`expected_return_pct` 在定格属性里 | qa-run grep(含 dashboard 的**反向**断言) |
| `v112-ATTR-REOPEN-REFREEZE` | reopen 调 `deleteByPeriod` → 再 close 自动重新定格(结构上必然,无标志位) | qa-run grep |
| `v112-ATTR-NO-BYPASS` | `queryBase` 里 `a.type` / `pc.liquidity_class` 不得再裸投影,必须包在 `COALESCE(paa.…, …)` 里 | qa-run grep(正向 + 禁用旧写法) |
| `v112-ATTR-BACKFILL-SCOPE` | 定格 SQL / `V54` 回填 / `queryBase` **三处**归档谓词逐字一致 | qa-run grep(三处 `archived_at > p.period_end`) |
| `v112-SQL-PROFILER-OFF` | profiler 默认关(`K_SQL_PROFILER, false`)· 开关在管理页且进审计 · `active()` 为假立刻 `proceed()` | qa-run grep |
| `v112-RATIO-INSUFFICIENT` | 500% 阈值与降级文案**单一出处**(全 `src/main/java` 只有 `MetricDisplay` 含 `new BigDecimal("5")`)· 三个显示面都接 · 模板无字面量 | qa-run grep + `MetricDisplayTest`(5 条属性断言) |

**为什么最终形式大多是 grep,而设计里写的是 e2e**:定格类断言的 e2e 版本要「真改库 → 真发请求 → 比对 HTML」,
而它要改的是**账户设置**,回滚不干净会污染 beta 的对照数据(下一次零差异基线就废了)。
所以拆成两半:**结构性质**(在事务内 / 有回落 / 三处谓词一致 / 无旁路)交给 grep 常驻守着;
**行为性质**(改设置 → 历史不动、当期动)用**一次性反向验证**在施工时人工跑 ——
FR-350 的第 5 个属性就是这么抓出来的(§0.1)。反向验证的价值在发现未知漂移源,
它不适合做常驻护栏;grep 的价值在防回归,它抓不到未知的。两者不是替代关系。

`MetricDisplayTest.moneyRowsAreNotDegradedByRatioRule` 单列出来说一句:它守的是
「**金额类**不许被比率规则误伤」—— 净资产 100 万的数值远大于阈值 5,判断里漏了 `ratio` 这个前提,
封板对照表的净资产那一行会整行变成「收支不足」,比原来的 −2383% 严重得多。

**为什么 `v112-ATTR-LIVE-CURRENT` 必须存在**:只有「改了历史不变」这一条的话,
一个把所有指标写死成常量的实现也能通过。必须同时钉住「当期要跟着变」。这两条是一对**互补**护栏,不能只留一条。

**为什么没有「已关账期必须都有定格行」这条**:见 §3.1 的护栏陷阱 —— 新建账户会让它假红。

## 12 · v1.12.1 · issue #13 的技术取舍

改的是引导层,但「改哪一层」本身有得选。三个备选:

| 方案 | 做法 | 为什么不选 / 选 |
|---|---|---|
| A · 改 compose,给三个变量默认值 | 把 `${FUTU_ACCOUNT:?…}` 换成 `${FUTU_ACCOUNT:-}` | **不选**。硬失败是这里唯一正确的行为:没有账号密码,OpenD 容器起来了也登录不了,只会变成一个反复重启、日志里报「登录失败」的僵尸容器 —— 把一个**立刻可读的启动期报错**,换成一个要翻容器日志才能发现的运行期故障。用户报的是「文档没说清楚」,不是「compose 写错了」。 |
| B · 向导页做成表单,填完变量替用户生成 `.env` | 页面收集三个变量 → 后端写文件 | **不选**。① app 跑在容器里,写宿主的 `.env` 需要挂卷 + 写权限,为一个一次性动作扩大攻击面;② 写完还得用户自己去宿主机 `docker compose up`,省不掉那一步;③ 富途密码要落到宿主明文文件,和「凭据加密存本机」的既有口径冲突。 |
| C · 只改引导:前提前置 + 模板可抄 + 报错对号 | 模板 / `.env.example` / 指南三处同步 | **选**。缺陷本体就在引导顺序,改引导是最小且正确的修法;零代码、零迁移、对 prod 现有数据零影响。 |

**护栏怎么钉才不假红**:直接 grep 页面文案(比如「先自备镜像」这五个字)会把措辞冻死,以后换句话就误报。
所以断言的是**结构关系**:在向导页 DOCKER 段内,`FUTU_OPEND_IMAGE` 出现的**行号 <** `up -d` 那行的行号。
「前提写在命令前面」这件事本身是可机器校验的,而它正是这个 bug 的本体。
另加 `th:unless="${channel == 'DOCKER'}"` 的存在性断言 —— 它证明那句 Linux 专属标题被 gate 住了,
有人把标题合并回无条件渲染时护栏会红。

**验证方式**:正向 + 负向都跑过 —— 拿 `master` 上的旧文件比对,`.env.example` 三变量命中 0 次、
行号次序反过来、报错串不存在、`th:unless` 命中 0 次,四条都会让护栏变红。
