### 静默失败预检

| 可能的静默失败 | 怎么让它响 |
|---|---|
| 把 `Status=Fail` 的 XML 当报表解析 → 0 笔持仓 → 对账把同步来的持仓**全部归档** → 余额归零 | 解析器先认根元素:`FlexStatementResponse` = 失败/回执,`FlexQueryResponse` = 报表;前者一律抛错。**另加闸**:报表里目标账户不存在或 0 个 `FlexStatement` → 拒绝对账(抛错并写卡片) |
| `BASE_SUMMARY` 行被当成一个币种 → 现金翻倍 | 解析层丢弃;单测样例里必须带这一行 |
| 口令过期后每天失败,但卡片文案被兜底成「同步失败」 | `failureNote` 对 IBKR 错误码逐个映射,**带原话**;护栏守「映射表覆盖 1012/1013/1014/1015/1018/1019」 |
| 加了 `IBKR` 枚举值,模板和来源映射里的二选一 / `default` 把它归成别家或「来源不明」 | `LedgerSource.ofBroker` 改成对 `BrokerVendor` 的穷尽 switch(不留 default);`holdings.html:57` 改用 `vendor.label`;护栏集合比对 |
| XML 外部实体(XXE):报表来自外部网络 | 解析器关闭 DTD 与外部实体(`XMLInputFactory.SUPPORT_DTD=false`、`IS_SUPPORTING_EXTERNAL_ENTITIES=false`) |

## 一、需求分析

### 1. 背景 & 目标

见 PRD §0。技术上的理由:`BrokerClient` 接口从 v0.15 就是为多家券商设计的只读抽象,IBKR 是第一家「不需要常驻进程、也不需要能交易的密钥」的接入,风险面比已有两家都小。

### 2. 需求理解(验收口径)

| FR | 工程判据 |
|---|---|
| FR-750 | 家庭配置键:`broker_ibkr_flex_token`(与老虎私钥同一种存法,页面不回显)、`broker_ibkr_flex_query_id`、`broker_ibkr_token_expires_on`(可空,`yyyy-MM-dd`,填错拒存)、`broker_ibkr_accounts`(最近一次报表里的账户,关联页下拉用)、`broker_ibkr_flex_base_url`(页面不露,e2e 指桩) |

| FR-755 | `assetCategory=STK` → `Position(equity=true)`;其余 → `skippedNonEquity++`;`CashReportCurrency` 去掉 `BASE_SUMMARY` 后逐币种 → `Cash` |

## 二、关键选型

### 选型一 · 用 IBKR 的哪个接口

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| **A · Flex Web Service** | 口令 + 查询号,两步 HTTP GET 取报表 | 无常驻进程;口令**只能取报表**;一年配一次 | 日终数据;要用户在 IBKR 后台配报表 | **选它** |
| B · Client Portal Web API | 本地跑 IBKR 网关,浏览器登录 | 实时 | 网关会话**每天要重新登录**(含二次验证),「配一次就不管」做不到 | 不选 |
| C · TWS API / IB Gateway | 常驻 IB Gateway,类似富途 OpenD | 实时、字段全 | 要常驻进程 + 用**能交易的账户**登录;部署负担与安全面都和富途同级甚至更高 | 不选 |
| D · 用户每月上传 Flex 报表文件 | 手动导出 XML/CSV 上传 | 不依赖服务器能连 IBKR | 每月一步手工操作,和目标相反 | 不选作主路径;**大陆服务器连不上 IBKR 时的兜底**,留作后续 |

### 选型二 · XML 怎么解析

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| **A · JDK StAX 流式读,只取需要的属性** | `XMLStreamReader` 遍历 `FlexStatement` / `OpenPosition` / `CashReportCurrency` | 零新依赖;报表可能很大(全年交易的 query),流式不吃内存;XXE 在工厂上一处关掉 | **选它** |
| B · Jackson XML 映射成对象 | 加 `jackson-dataformat-xml` | 代码短;但字段多、IBKR 会加字段,强类型映射反而脆 | 不选 |
| C · 移植开源的 ibflex | — | 覆盖全;但它是 Python,覆盖的 90% 字段我们用不到 | 不选 |

数字解析单独一个函数:去千分位、`-` / `--` / `N/A` 视为空(开源解析库记录过这些写法),不许把空当 0。

### 选型三 · 「还在生成」怎么等

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| **A · 同步等待,有界重试** | SendRequest → 等 3 秒 → GetStatement;遇 1019 每 5 秒重试,最多 6 次(约 33 秒)。一轮最多 7 次请求,低于「每分钟 10 次」 | 与富途 / 老虎同一种同步语义,对账代码不动;手动「立即同步」会多等十几秒 | **选它**(节奏在拿到 1019 实测时长后定稿) |
| B · 异步任务 + 状态机 | 发请求落库,定时任务回来取 | 不阻塞请求;但多一张表 / 一套状态,只为省十几秒 | 不选 |

限流护栏:`IbkrFlexHttp` 内对同一口令做**最小间隔 1.1 秒**,单测数请求次数。

### 选型四 · 凭据放哪

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| **A · 全局一份(家庭配置)** | 与老虎同构,管理页一处配 | 一个口令本来就覆盖名下全部账户;测试连接可列出全部账户供关联时选 | **选它**(PRD §13② 待裁) |
| B · 每个关联各填 | `broker_link` 加列 | 能支持「两个人各自的 IBKR」;但要加列、关联页多两个密钥框 | 不选作默认;需要时照富途「本关联 OpenD」的做法加 |

### 选型五 · 不在美 / 港 / A 股的持仓(PRD §13① 待裁)

| 方案 | 做法 | 取舍 |
|---|---|---|
| A · 跳过并计数 | 同富途 / 老虎 | 零新机制;但净资产**少算且不报错**,IBKR 用户多市场比例高 |
| **B · 手动估值持仓,单价 = 报表收盘价** | `ValuationMode.MANUAL`,`sync_source='IBKR'`,每次同步用报表 `markPrice` 更新单价 | 不缺数;对账要能处理「同步来的 MANUAL 行」(现在只处理 AUTO + CASH)—— 改动集中在 `reconcile` 一处 |

倾向 B。市场归一表(`BrokerTicker.fromIbkr(listingExchange, currency, symbol)`)以实测为准,初稿:`NASDAQ/NYSE/ARCA/AMEX/BATS/IEX` + USD → US;`SEHK` + HKD → HK(代码补足 5 位);沪深股通(`SEHKNTL` / `SEHKSZSE`,CNH)→ CN;其余 → B 方案。

## 三、系统概要设计

### 1. 整体设计思路

```
管理页:口令 / 查询号 / 到期日 ──► family_runtime_config(口令页面不回显)
                                        │
BrokerSyncService.sync(account) ─► clientFor(IBKR) = IbkrFlexClient
                                        │
                     IbkrFlexHttp:SendRequest ─(等)─► GetStatement(1019 重试 · 1.1s 间隔 · 带 UA)
                                        │  XML
                     IbkrFlexParser(纯函数):Fail 信封 → 抛错;报表 → 按账户切 → Snapshot
                                        │
                     现有 reconcile(只动 sync_source='IBKR')→ 现有估值刷新(来源 SYNC_BROKER_IBKR)
```

**新逻辑只在「取数 + 解析」两层**;对账、估值、落期、失败落库全部复用。

### 2. 领域模型设计

| 概念 | 变化 |

| `BrokerVendor` | 加 `IBKR("盈透")` |

| 报表口令 / 查询号 | 新配置项,见 §一.2 |

`AGENTS.md` 领域概念节补「报表口令」,并把「刻意不做」里的「券商 API 直连」改成「券商 API 直连**下单**」+ 只读例外说明(PRD §4)。

### 3. 代码架构设计

## 五、稳定性与质量保障

### 1. 兼容性设计

- **老数据 × 新代码**:没有 IBKR 关联时,所有路径与现在逐字相同。
- **新数据 × 老代码(回滚窗口)**:库里有 `vendor='IBKR'` 的关联时,老代码把它读成枚举会失败(`BrokerVendor.valueOf`)→ 券商页报错。**回滚步骤**:先在新代码下把 IBKR 关联解绑(同步来的持仓保留为普通持仓),再回滚 jar。写进 `deploy/rollback.sh` 的注释与发版说明。
- **富途 / 老虎**:共用 `reconcile`,但它只动 `sync_source=vendor` 的行;`LedgerSource` 改成穷尽映射后,已有两家的映射结果不变(单测守)。

### 2. 性能评估

一轮同步多一次外部请求往返 + 最多约 33 秒等待(见选型三)。手动「立即同步」请求会等这么久 —— 页面按钮要有「IBKR 报表生成中,一般十几秒」的提示,不许看起来像卡死。报表流式解析,不整份读进内存。

### 3. 安全性设计

- **凭据**:口令存家庭配置(与老虎私钥同一套,**明文**,不是加密 —— 现有页面上「加密保存」的说法与实现不符,已单独报),页面不回显,日志与审计不写值;建议用户在 IBKR 后台绑定本服务器 IP。
- **只读的物理保证**:Flex Web Service 口令**只能**取报表 —— 不是靠 prompt 或约定。
- **XXE**:解析器关闭 DTD / 外部实体。
- **响应大小上限**:单份报表超过 20 MB 直接拒绝(正常持仓报表几十 KB)。
- **日志**:只记计数(几户 · 几笔 · 几个币种)与 IBKR 错误码,**不记报表正文、不记账号全文**。

## 六、护栏设计

| 护栏 ID | 守的设计意图 | 判据怎么写 |

### 附:同步失败记录被事务回滚(v1.17.3 起的老问题 · 本版一并修)

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · `@Transactional(noRollbackFor = …)` | 失败不回滚 | 对账做到一半失败时,半截的持仓更新也会提交 —— 比不记失败更糟 | 不选 |
| B · `markFailed` 用 `REQUIRES_NEW` | Mapper 方法上开新事务 | 要么改 Mapper 层的事务语义(别的调用方也受影响),要么多一个 bean 只为包一行 | 不选 |
| **C · 取数不在事务里;对账 + 记成功用 `TransactionTemplate`;失败在事务外记** | `BrokerSyncService.sync` 去掉 `@Transactional` | 边界清楚:写库的只有对账那一段;失败记录一定落库;定时任务与页面两条路行为一致 | **选它** |

`TransactionTemplate` 通过 setter 注入(`required = false`),单测不起 Spring 时直接跑,老的四参构造器不变。护栏 `v126-BROKER-FAIL-OUTSIDE-TX`。


### 附:透视合计与总资产差一分(v1.20 余数归位漏了账户这一层 · 本版一并修)

2026-09-25 验收时 regression-data「两条独立路径的总资产逐字一致」两次红、单跑又绿。按币种拆透视,定位到一个美元账户:几条持仓逐条 `× FX 因子 → setScale(2)`,加起来比账户现值多 0.01。

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · 透视合计改成按账户现值加 | `PivotEngine` 另取账户级合计 | 合计与各行之和对不上,用户一眼就看出「行加起来不等于合计」—— 把不一致从两页之间挪到了一张表里 | 不选 |
| B · 逐条不取整,只在输出时取整 | 头寸值保留全精度 | 下游(引用块、占比、分桶)都按两位小数写,改动面大,且每个输出点都要记得取整 | 不选 |
| **C · 逐条取整后把零头补给最大那条** | `LensQueryService.baseValues`,复用 v1.20 的 `residualToLargest` | 与已有的「拆多份」那层同一个办法;各条之和精确等于账户现值;补偿落在最大那条,相对误差最小 | **选它** |

与 IBKR 无关(`LensQueryService` 本版之前一行没动),是股价变了才露出来。护栏 `v126-LENS-ACCOUNT-RESIDUAL`。

### 附:两个缺口补上入口(2026-09-27 维护者「要加上」)

**提醒时间放哪、怎么填**:

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| **A · 提醒页,填整点** | 「截止前几天」旁边加「每天几点提醒」,「10,20」→ `0 0 10,20 * * *`(`RemindTimes`) | 管提醒的人在提醒页找;不懂 cron 也能改;覆盖了实际需要(一天一两个整点)。手工配过的自定义 cron 页面照原样显示、留空不改,不会被一次保存冲掉 | **选它** |
| B · 数据源接入页,填 cron | 跟行情 / 汇率的 cron 放一起 | 按技术分类(都是 cron)而不是按用户的事;填提醒的人要懂 cron | 不选 |

**再平衡比例放哪**:数值阈值页「录入提示阈值」那一组 —— 它就是「在填报页记一笔划转时,怎么判定」的阈值,和智能转账阈值同一类;
页面百分比、库里小数(`AdminController.rebalanceMatchFraction`),读的一边(`RebalancePlanService.onTransfer`)一字不动。
**为什么要单测守格式**:存成「90」不会报错,只会让门槛变成 90 倍、所有条目永远是「待执行」—— 典型的静默算错。

**调度即时生效**:保存提醒时间后 `DynamicScheduleConfig.rescheduleAll()`;调度的默认值改为引用 `RemindTimes.DEFAULT_CRON`,页面与调度同一份默认。
