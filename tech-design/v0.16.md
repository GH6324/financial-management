# Tech Design · v0.16 · 目标模块重构(通用追踪目标)

> 对应 `prd/v0.16.md`。核心:把目标从「三类写死口径」重构成「绑 0–N 账户 + 任一账户/家庭衍生指标 + 目标值(≥/≤)+ 时间范围」的通用模型;旧退休/教育/应急作为**智能预设**保留全部既有能力;移动端多目标瘦身。本文档只讲架构选型与取舍,不贴实现清单。

## 0. 复用地图(不重复造轮子)

- 指标计算全部复用 `FactViewService`(`factview` 包):
  - `loadDefault(familyId) → FactSlice`;`kpis(slice) → KpiSnapshot`(净资产/总资产/总负债/储蓄率/紧急储备月数…)。
  - `accountPerformance(slice) → List<AccountPerformance>`:**每账户**本位币口径的 current_value / xirr / return_base / cum_pnl / net_principal / latest_pnl / mom_pct / share_pct / max_drawdown 等——正是 PRD 指标全集的来源。
  - `familyTwr / familyXirr / savingsRate / momYoy` 家庭级口径(0 账户时用)。
- 指标目录与账户/报表**同源**:`MetricPrefsService.ACCOUNT/FAMILY` 已定义 key→label,目标指标枚举与之对齐(key 一致),避免两套命名漂移。
- 旧三类的目标值推导 / 三情景 / AI 月报 / FIRE 自动支出:`GoalService`、`GoalProjector`、`goal_ai_report` 全部原样保留。

## 1. 决策 A · 数据模型:通用模型如何落库

**备选**
1. **新表 + 迁移旧数据**:建 `goal_v2`,把 family_goal 三类搬进新模型,旧表废弃。
2. **扩现有 `family_goal`(加列)+ 新关联表 `goal_account`**(选定)。
3. **双表并存**:旧 `family_goal` 管三类,新 `custom_goal` 管通用,列表 UNION。

**取舍**
- 方案 1:模型最干净,但要迁移线上真实目标数据 + 重写三类的推导/三情景/AI 关联,**破坏面大、回滚难**,违反 [prod 已上线 backward-compat] 红线。
- 方案 3:两套表两套 CRUD/进度/模板分支,列表要 UNION 排序,**长期维护双轨**,且「统一进度组件」要兼容两种行入参,反而更乱。
- 方案 2:纯**加列**(可空)+ **新表**(0..N 绑定),存量行默认值即旧行为,零破坏零回滚风险;三类与通用共用一张表、一套进度组件,`kind` 区分是否走预设推导。

**选定:方案 2**。`family_goal` 加:`kind`(复用现 `goal_type` 语义,值域加 `CUSTOM`)、`metric`(VARCHAR,默认按 kind 回填)、`comparator`(`GTE`/`LTE`,默认 GTE)、`time_mode`(`OPEN`/`DEADLINE`)。绑定关系入新表 `goal_account(goal_id, account_id)`,0 行=全家。`target_value`/`target_date`/`params_json` 语义不变(通用金额型直接用 target_value;截止型用 target_date)。

**为什么不改列名而保留 `goal_type`**:列名 `goal_type` 保持不动(避免改列名的迁移),Java 侧枚举 `GoalKind` = 原 `GoalType` + `CUSTOM`;DB 存字符串,向后兼容。

## 2. 决策 B · 指标计算:如何统一算「一个账户组的某指标」

**备选**
1. **在 GoalProgressService 里按 metric 巨型 switch**(硬编码每个指标怎么算)。
2. **`GoalMetric` 枚举 + 单一 `GoalMetricEvaluator`**:evaluator 拿 `FactSlice` + 绑定账户集,`accountPerformance` 过滤到账户子集后按指标聚合;0 账户走家庭级 `kpis`/family 方法(选定)。
3. **复用报表 `MetricPrefsService` 的计算管线**直接取值。

**取舍**
- 方案 1:指标一多(13+)switch 爆炸、聚合规则散落、难测。
- 方案 3:报表管线是「展示某期某账户的值」,没有「账户子集聚合成一个数」的语义,硬套要塞很多参数,耦合报表内部结构。
- 方案 2:每个 `GoalMetric` 声明三件事——**归属**(账户级可聚合 / 家庭级)、**聚合算子**(SUM / 价值加权 / 取家庭 KPI)、**方向**(GTE/LTE 默认)。evaluator 一处实现聚合,新增指标=加一个枚举项 + 声明,不改流程。纯函数、易单测。

**选定:方案 2**。签名草案:
```
BigDecimal GoalMetricEvaluator.eval(FactSlice slice, GoalMetric metric, Set<Long> accountIds)
```
- 账户级金额指标(current_value/cum_pnl/net_principal/latest_pnl/mom_amount):`accountPerformance` 过滤子集后 `Σ`;account 集为空→对应家庭 KPI(net_worth/…)。
- 现金合计:子集里 CASH 类账户余额和;空→全家现金。
- 比率指标(xirr/return_base/mom_pct):子集**价值加权平均**(Σ(metric_i × value_i)/Σ value_i);空→家庭 `familyTwr`/`momYoy`。
- 占比 share_pct:Σ子集 current_value / netWorth。
- 家庭独有(savings_rate/emergency_months/total_assets/total_liab):只在 0 账户时可选,直接取 KPI。

## 3. 决策 C · 收益率「账户子集」聚合的口径取舍

**问题**:严格的组合 TWR 需要把子集账户的现金流合并成一条序列再算,成本高、要改 FactSlice 内部。

**备选**
1. 精确:为任意账户子集重算合并现金流 TWR。
2. **近似:各账户已算好的年化(xirr/return_base)按当前价值加权**(选定)。
3. 只允许「全家收益率」(0 账户)与「单账户收益率」(1 账户),不做多账户聚合。

**取舍与选定**:方案 1 精确但要动估值内核、性价比低;方案 3 又砍掉了用户明确要的「某 3 账户合计收益率」。选**方案 2 价值加权近似**——与用户直觉一致(大账户权重高)、复用现成的账户级年化、O(n) 无额外查询;文档标注这是加权近似(非严格组合 TWR),在收益率型目标详情用小字注明口径。**为什么可接受**:目标是「趋势达标追踪」而非审计级收益归因,加权近似的量级误差不影响「到没到 X%」的判断。

## 4. 决策 D · 时间维度与「进度 vs 时间」判定

- `time_mode=OPEN`(长期):无截止日;退休/教育仍由 `GoalProjector` 给三情景达成年份(长期型的补充展示)。
- `time_mode=DEADLINE`:有 `target_date`;快捷 1/3/5 年 = 创建日 + N 年(存绝对日期,不存「N 年」,避免口径漂移)。
- **pace 判定**(纯函数 `GoalPaceCalculator`):
  - 达标率 `attain% = 当前 / 目标`(LTE 收敛类取反向口径,见决策 F)。
  - 时间进度 `time% = (今天 − 创建日) / (截止日 − 创建日)`。
  - `attain% ≥ time%` → 良好/领先(forest);`time% − attain% > 阈值(默认 15pp)` → 落后(rust);之间 → 追踪中(brass)。
  - **仅金额类**参与 pace 判定;**比率类只展示倒计时**(FR-16-4b:收益率非线性累计,时间落后判定会误导)。阈值走硬编码常量(与三情景固定利率同理,不开放用户配置,沿用「决策 22」精神)。

## 5. 决策 E · 旧三类兼容 + 迁移回填

- 读路径:列表/详情统一走**新的进度组件**(GoalProgress VO 增补 metric/attain/pace/countdown 字段);三类的 target/PV 仍由既有 `GoalProgressService.computePv` 按 kind 算(退休/教育=netWorth、应急=CASH),等价于「金额类 + 0 账户 + OPEN」,不改其数值。
- 写路径:三类新建/编辑仍走各自向导(参数推导不变);CUSTOM 走新通用向导。
- **迁移回填**(见 §7):存量行 `kind=原值`、`metric` 回填(退休/教育→`net_worth`、应急→`cash_amount`)、`time_mode=OPEN`、`comparator=GTE`;`goal_account` 无行(全家)。行为完全等价于迁移前。

## 6. 决策 F · 达标方向 ≥/≤

`comparator` 列(GTE/LTE)。多数指标默认 GTE(达到/增长);`total_liab`、`max_drawdown` 默认 LTE(降到/控制在)。达标率与 pace 对 LTE 取反向口径(如负债:`attain% = (起点−当前)/(起点−目标)`,起点=创建时值,存 `params_json.baseline`)。UI 方向按 metric 默认给出、允许用户改。**为什么现在做**:不做 LTE 则「总负债/回撤」这类指标没法当目标,与 PRD「指标全集」矛盾;LTE 只是比较符与达标率公式的分支,成本低。

## 7. 迁移与向后兼容(prod 红线)

- `db/migration/V41__goal_generic.sql`:`family_goal` 加列 `kind`(先建列再 `UPDATE kind=goal_type` 回填)/ `metric VARCHAR(32) NULL` / `comparator VARCHAR(4) NOT NULL DEFAULT 'GTE'` / `time_mode VARCHAR(8) NOT NULL DEFAULT 'OPEN'`;`UPDATE` 按 goal_type 回填 metric。全部**加列可空 / 带默认**,存量行零影响。
- `db/migration/V42__goal_account.sql`:新表 `goal_account(goal_id BIGINT, account_id BIGINT, PRIMARY KEY(goal_id,account_id), INDEX idx_goal(goal_id))`;纯新增。
- **4 条 schema 自检**([feedback_prod_backward_compat]):①加列均可空/默认 → 旧 INSERT 不炸;②旧查询不 SELECT 新列 → 不受影响;③`goal_account` 空 = 全家,旧目标语义不变;④回滚只回 jar,新列/新表留着无害(旧 jar 不读)。
- 迁移顺序:V41 先加列+回填,V42 建表;`db/apply.sh` 幂等 sha256。

## 8. 移动端瘦身(UI 架构)

- 抽 `goals/_goal-bar.html` fragment(紧凑条:名+迷你进度+%+状态点+倒计时),列表与 Dashboard 条带共用;桌面端用信息密度更高的紧凑卡(压高),手机默认紧凑条、点开展开详情(纯 `<details>` 或 HTMX 局部,避免整页刷)。
- Dashboard `_progress-strip` 手机端限 2 条 + 「查看全部」;桌面端维持网格。
- 排序:DEADLINE 型按剩余天数升序在前,OPEN 型在后。

## 9. 领域 / 服务 / 控制器 / 模板 改动面(概要)

- 领域:`GoalKind`(=旧枚举+CUSTOM)、`GoalMetric` 枚举(key 对齐 MetricPrefsService)、`GoalComparator`、`TimeMode`;`Goal` 加字段;`goal_account` mapper。
- 服务:`GoalMetricEvaluator`(§2)、`GoalPaceCalculator`(§4)、`GoalProgress` VO 增补;`GoalProgressService` 分流(CUSTOM→evaluator;三类→既有 computePv)。
- 控制器:`/goals/new/custom`(向导)、create/edit 接账户多选 + metric + comparator + time_mode;列表/详情复用。
- 模板:`new.html` 加第 4 卡;`new-custom.html` 向导;`_goal-bar.html` + 列表/详情/条带改造。
