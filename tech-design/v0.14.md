## 0. 现状触碰面(实施前必读)
- 持仓模型:`stock_holding`(AUTO/MANUAL/CASH · shares + cost_basis + currency)· `Market` 枚举 US/CN/HK/CRYPTO · `AccountType` 枚举含 CRYPTO(V36 先例)。
- 拉价:`StockPriceFetcher` 按 `Market` 路由;`SinaStockClient`(主)已能解析新浪行情;crypto 走 Binance/CoinGecko/Coinbase 三级链(V36 + PR#2 先例)。快照落 `stock_price_snapshot(ticker, market, trade_date, close_price, currency, source)`,V37 已把 close_price/cost_basis 放宽到 DECIMAL(20,6)。
- 估值:`AccountValuationService` AUTO 分支 = `shares × 最新价`,已含 FX 到本位币;PnL/成本机器对 AUTO 持仓已就绪。
- LLM:5 处调用(体检/月报/目标/调仓/洞察)统一走 `LlmDiagnoseService` 的 `List<LlmClient>` 链,`@Order(1)` Qwen 主、`@Order(2)` DeepSeek 备(优先级写死);温度写死 0.5;Qwen 多模型轮询摊额度,DeepSeek 模型写死。
- 配置:`FamilyConfigService`(DB `family_runtime_config` → @Value → code default 三层),管理页 `/admin/integrations` 已有 LLM/股票/FX 段。

## 1. 决策 A · 贵金属账户类型与 Market

**问题**:贵金属挂在哪种账户/市场上?

- **备选 A1 · 复用 `CRYPTO`**:把金银当"另类资产"塞进加密类型。✗ 语义混淆(加密≠贵金属),体检/配置分类/文案全错位。
- **备选 A2 · 复用 `STOCK` + 一个 isMetal 标记**:✗ STOCK 带 ticker/市场语义,标记会污染大量股票逻辑分支;账户列表/报表要处处特判。
- **选定 A3 · 新增 `AccountType.METAL` + `Market.METAL`**(与 crypto V36 完全对称)。**为什么**:独立类型 = 独立标签/模板/单位/拉价路由,零污染既有类型;`supportsHoldings()` already 泛化,加 METAL 即复用整条持仓/估值链。**为什么不 A1/A2**:见上,语义与维护成本。

**落地**:
- `AccountType` 加 `METAL("贵金属")`;`Market` 加 `METAL`。
- `supportsHoldings()` / 账户类型 CHECK 约束 / 账户模板 加 METAL(迁移 V38,照 V36 套路)。

## 2. 决策 B · 品种 × 价格源 如何编码(复用列 vs 新列)

**问题**:金/银/铂/钯 × (SGE 国内 / 国际现货) 怎么存,才能既复用 `stock_holding`/`stock_price_snapshot`,又让快照 key 不撞车?

- **备选 B1 · 新增 `metal` + `source` 两列**:✗ 多两列 + 快照表也要跟着加,key 变复杂;与"复用 AUTO 模型"背道而驰。
- **选定 B2 · 用 `ticker` 编码"品种×源",`currency` 定源币种**(完全复用现有列,和 crypto `ticker=BTC` 同构)。
  - 映射(holding.ticker → 新浪 symbol):
    | ticker | 源 | currency | 新浪 symbol | 原生计价 |
    |---|---|---|---|---|
    | `AU9999` | SGE 黄金 | CNY | `gds_AU9999` | 元/克 |
    | `AGTD`   | SGE 白银 | CNY | `gds_AGTD` | 元/**千克** → 归一 ÷1000 |
    | `PT9995` | SGE 铂金 | CNY | `gds_PT9995` | 元/克 |
    | `XAU` | 国际金 | USD | `hf_XAU` | 美元/盎司 |
    | `XAG` | 国际银 | USD | `hf_XAG` | 美元/盎司 |
    | `XPT` | 国际铂 | USD | `hf_XPT` | 美元/盎司 |
    | `XPD` | 国际钯 | USD | `hf_XPD` | 美元/盎司 |
  - **建仓 UI 给用户看的是"品种(金/银/铂/钯)+ 源(上海/国际)"**,后台映射到 (ticker, currency);快照 key `(ticker, METAL, date)` 天然唯一(SGE 金与国际金 ticker 不同)。
  - 钯金 SGE 无常见公开盘 → 钯只提供国际(USD/XPD);UI 里"钯 + 上海"置灰并提示。**为什么**:诚实,不假装有源。

## 3. 决策 C · 计价单位(克/盎司)存储与换算

**问题**:单位是持仓属性(PRD 已定),怎么存、估值/盈亏怎么算不出错?

- **备选 C1 · 归一到克存储(unit 仅显示)**:入库时 oz→g(×31.1035),shares/cost 都存克,估值 = shares_g × 克价,和现有 AUTO 完全一致。✗ 存的不是用户输入(填 10 oz 存成 311.035 g),入库即引入换算舍入 + "我明明填 10 盎司"的困惑,违"非技术家属看得懂 + 不截断精度(承 v0.13.1)"。
- **选定 C2 · 存用户原样(shares/cost_basis 按 holding 单位),估值层做一次换算**。新增 `stock_holding.unit`(`GRAM`/`OUNCE`,仅 METAL 用,其余 NULL)。
  - **快照归一**:`MetalPriceClient` 把每个 ticker 的现价统一成 **"原生币种 / 克"** 落 `close_price`(SGE 银 ÷1000;国际 USD/oz ÷31.1035 → USD/克)。即快照永远是"每克价"。
  - **估值**(`AccountValuationService` METAL 分支):
    `每持仓单位价 = 每克价 × (unit==OUNCE ? 31.1035 : 1)`;
    `市值(原币) = shares × 每持仓单位价`;再经既有 FX → 本位币。
  - **盈亏**:`(每持仓单位价 − cost_basis) × shares`(cost_basis 与 close 同币种同单位,恒等口径一致)。
  - **为什么 C2**:存录入真值(可审计、无入库舍入),换算只发生在"每克快照 → 持仓单位"这一处、集中在估值层一个分支;精度承 V37 的 DECIMAL(20,6)。**为什么不 C1**:入库改写用户输入的代价大于估值层一次乘法。
  - 常量 `GRAMS_PER_TROY_OUNCE = 31.1035`,单一常量类,测试钉死。

## 4. 决策 D · 金价拉取 client

**问题**:金价源怎么接?

- **备选 D1 · 第三方金价 API / SGE 官方接口**:✗ 引新供应商 + 可能要 key/额度;SGE 官方数据接口不稳且非公开直连友好。
- **选定 D2 · 复用现有新浪主源基础设施,新增 `MetalPriceClient`**(实现 `StockClient`,`StockPriceFetcher` 里 `Market.METAL` 路由到它,和 crypto 分支对称)。已实测 `gds_*`(SGE)+ `hf_*`(国际)全品种可直连返真值。
  - 解析:新浪 `gds_`/`hf_` 格式与股票不同(字段序不同),`MetalPriceClient` 独立解析;取"现价"字段;银 ÷1000;国际 ÷31.1035 归一到每克。
  - 熔断/降级:复用既有断路器风格(连续失败短熔断),与 Sina/Tencent 一致。
  - 定时:`StockPriceFetcher` 已有 cron 调度;新增 `K_METAL_CRON`(默认 SGE 收盘后一次,如 `0 20 16 * * MON-FRI`),接入源页可改。
  - **默认源**:`K_METAL_PRICE_SOURCE`(sge/intl · 默认 sge)= 新建贵金属持仓时的默认源(决定默认 ticker/currency/unit);**已建持仓各自记 ticker/currency,不受全局开关回溯影响**。这解决了"全局源开关 vs 用户同时持有两种"的张力:全局=新建默认,持仓=既成事实。

## 5. 决策 E · LLM 供应商自选 + 模型级联

**问题**:让管理员选主用谁、选模型、调温度,且不动 5 处调用各自的 prompt。

- **选定**:配置驱动 + client 统一重排,不碰调用点业务逻辑。
  - `LlmClient` 接口加 `vendor()`(返回 `"qwen"`/`"deepseek"`)。
  - `LlmDiagnoseService.runDiagnose()` 遍历 `clients` 前,按 `K_LLM_PRIMARY_VENDOR`(默认 qwen)把主选排到最前;其余保持,故障自动切(既有 failover 不变)。**为什么**:5 处调用已共用这条链,一处改动全局生效。
  - **温度**:两 client 的 `chat()` 读 `K_LLM_TEMPERATURE`(默认 0.5)。
  - **模型级联下拉(FR-B3)**:`K_LLM_MODEL` 存所选型号或 `"auto"`(默认)。
    - 候选清单**系统内置、随版本维护**(不接受自由文本):`qwen → [qwen-plus, qwen-flash, qwen-max]`;`deepseek → [deepseek-chat, deepseek-reasoner]`。管理页下拉随 `vendor` 级联(前端 JS,见预览)。
    - `auto`:Qwen 保留既有多模型轮询摊额度;DeepSeek 用默认模型。选具体型号则钉死该型号。
    - 校验:提交的 model 必须属于所选 vendor 的内置清单,否则回落 `auto`(防越权/打错)。
  - **不动**:各处业务 prompt、合规校验、数学禁令([[feedback_llm_no_math]] / [[feedback_llm_validator_diagnosis]])。

## 6. 数据库迁移 V38(backward-compat)

```sql
-- account_template / account 的 type CHECK 加 METAL(照 V36 drop+add)
-- stock_holding 加 unit 列(仅 METAL 用)
ALTER TABLE stock_holding
  ADD COLUMN unit VARCHAR(8) NULL COMMENT 'METAL 持仓计价单位:GRAM/OUNCE;其余类型 NULL';
-- 账户模板种子:贵金属账户
INSERT INTO account_template(code, display_name, type, default_currency, sort_order, is_custom_slot)
VALUES ('metal_account','贵金属账户','METAL','CNY', <next>, 0);
-- product_category / 流动性映射:METAL 归 SEMI_LIQUID(同 crypto 处理)
```
- 纯新增列 + 放宽 CHECK + 加种子 → 对线上现有数据零影响(现有持仓 unit=NULL,非 METAL 不读该列)。
- 配置 key 无需迁移(K-V 缺省走 code default)。

## 7. 币种/单位不变性守护
- 贵金属账户总估值并入净资产/总资产/配置环;**比值类指标(占比/流动性月数等)三视图币种必须完全相等**,金额按 FX 缩放 —— 纳入既有 `CurrencyInvarianceTest` + `v08-CCY-INV-3` 扫描面([[feedback_currency_invariance]])。
- 单位换算(克↔盎司)只影响"数量×单价"的呈现,不改比值口径。
