## 0 · 施工前的查证

### 0.1 · 查出一个真 bug:两处调用点根本不看「主选平台」

六处 `List<LlmClient>` 的注入点,**四处**用了排序助手,**两处没有**:

| 调用点 | 写法 | 结果 |
|---|---|---|
| `LlmDiagnoseService:266` · `ReviewInsightService:61` · `LensInsightService:71` · `LensAiTagService:88` | `for (… : orderByPrimaryVendor(clients, primary))` | 按配置的主选平台优先 ✅ |
| **`RebalanceAdvisorService:201`** · **`GoalLlmService:153`** | `for (LlmClient client : clients)` | **忽略配置** ❌ |

裸循环拿到的顺序不是随机的,是**编译期钉死的**:`QwenLlmClient` 上有 `@Order(1)`、
`DeepSeekLlmClient` 上有 `@Order(2)`。所以这两处**永远先打 Qwen**。

**用户能看见的症状**:管理页把主选切成 DeepSeek 之后,「AI 体检 / 月报洞察 / 透视洞察 / 智能标签」
听话了,**「再平衡建议」和「目标建议」这两处仍然先走 Qwen**。

**为什么一直没被发现**:只有**两把 key 都配了**才看得出来 —— 只配一把时另一家
`available()` 返回 false 被跳过,表现正常。所以这是个「配置越完整越容易撞上」的 bug。

**本版的处理**:不单独发 hotfix。v1.13 把六处全部收进一个 router,这个 bug 是**结构性地**
消失的,而不是被逐点修好的 —— 逐点修法留着同样的形态,第七个调用点还会再犯。护栏钉死裸循环
(§5)。这条已单独告知作者。

### 0.2 · 熔断/HTTP 那套已经复制了两份,而且已经漂移

`QwenLlmClient` 与 `DeepSeekLlmClient` 各有一份 `FAIL_THRESHOLD=3` / `COOLDOWN_MS=60_000` /
`consecutiveFailures` / `breakerOpenedAt` / `currentMaxTokens` / `currentTemperature` /
请求体构造。差异部分是**真差异**(百炼有免费额度轮询 + 6h 冷却),但公共部分已经在两处各写一遍。
再抄第三份(方舟)会把这个形态固化成「三份」,这是 §1.1 选型的直接输入。

顺带记一处**已经存在的漂移**:两家的「越权型号回落」逻辑各写各的 ——
`QwenLlmClient.pinnedModel()` 判 `startsWith("qwen")`,`DeepSeekLlmClient.currentModel()`
判 `startsWith("deepseek")`。这套判断在三级模型下**必须整个拆掉**:方舟上的 `ep-xxxx`
既不以 qwen 开头也不以 deepseek 开头,现有逻辑会把它一律当"越权"丢掉、回落成默认型号 ——
**表现为「存进去了、也不报错,但调的还是老模型」**。

### 0.3 · 作者对 PRD §4 的拍板(2026-08-15)

| # | 问题 | 决定 |
|---|---|---|
| 1 | failover 的单位 | **主 / 备各一个完整三元组**(平台+系列+型号) |
| 2 | 同一系列出现在多平台 | 允许(PRD 已按允许写) |
| 3 | 百炼的免费额度轮询 | **保留**,作为百炼平台的专属属性 |
| 4 | 型号手填 | **放开**给所有平台 |

### 0.4 · 无 DB 迁移

`family_config` 是 KV 表,新增配置键不需要 schema 变更。旧键的处置见 §1.5。

## 1 · 架构选型

### 1.1 · 客户端怎么建模

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · 再抄一个 `ArkLlmClient` | 照 `DeepSeekLlmClient` 复制一份改端点 | 改动最小、最不会碰坏现有两家。但把 §0.2 的重复从两份变三份,而且**已经在漂移**的那部分(越权回落)会被复制成三种互不相同的写法 | 不选 |
| **B · 抽 `AbstractOpenAiCompatibleClient` + 一平台一 bean** | 基类收公共部分(Bearer/请求体/温度/max_tokens/熔断/超时);子类只留差异:端点、key 取哪个、错误码语义、以及百炼的额度轮询 | 三家的**共同点是真的共同**(都是 OpenAI 兼容 chat-completions + Bearer,PRD FR-360 已确认),抽象不是硬凑的。代价是动了两个已上线的类 —— 由「口径不变」验收(PRD §3 第 3 条)兜 | **选定** |
| C · 一个通用 client,平台运行时构造 | base URL 也做成配置项,`LlmClient` 只有一个实现 | 加平台不用发版。但**「自定义任意 OpenAI 兼容端点」是 PRD §2 明确的非目标**;而且各家错误码语义不同(百炼的 `AllocationQuota.FreeTierOnly`、方舟的实名/额度错误),通用实现只能把它们一律当"失败",失去 §0.2 那套按错误类型分流的能力 | 不选 |

**B 的边界**:基类**不含**「多模型轮询」。那是百炼的计费形态(免费额度按模型各给一份),
PRD FR-361 明确要求不要把它提升为公共行为,拍板 3 也确认保留为百炼专属。它留在
`DashScopeLlmClient` 里,`LlmCatalog` 里用一个 `supportsModelRotation` 标记出来 ——
这样管理页上「只有百炼多一块轮询配置」是**显式的平台能力差异**,而不是看起来像漏配了。

### 1.2 · failover 的落地形态(拍板 1)

拍板定的是「主/备各一个完整三元组」。剩下的设计问题是:**这个三元组由谁持有**。

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · 沿用 `orderByPrimaryVendor` 的形态 | 保留 static helper,把参数从 vendor 换成 platform | 签名几乎不变,六处调用点改动小。但它**表达不了型号那一级** —— 主备现在是三元组,不是「哪个 bean 排前面」。而且它是个「每个调用点自己记得调」的 static helper,**六处里已经有两处忘了调**(§0.1)。这个形态本身就是 bug 的温床 | 不选 |
| **B · `LlmRouter` + `LlmInvocation` 值对象** | `LlmInvocation(platform, family, model)`;`LlmRouter.plan()` 返回有序的 `[主, 备]` 调用计划,并已过滤掉「key 未配 / 熔断中」的项;六处调用点统一 `router.invoke(sys, user)` | 多两个类。换来的是**没有旁路** —— 调用点拿不到 `List<LlmClient>`,想绕都绕不过去。§0.1 那个 bug 结构性消失 | **选定** |

**连带的清理**:`@Order(1)` / `@Order(2)` 在 router 之后不再决定任何事。**要删掉**,
不能留 —— 留着会让下一个读代码的人以为顺序还是它定的(它现在唯一的效果就是给
§0.1 那个 bug 提供了一个"看起来有序"的假象)。

**`LlmInvocation` 里的 model 允许为空**,表示「自动」:百炼下为空 = 保持轮询,
其余平台为空 = 用该平台在 `LlmCatalog` 里的默认型号。这一条直接承接旧的 `llm_model = auto`。

### 1.3 · 模型目录只有一份(FR-364)

现在散在四处:`QwenLlmClient.DEFAULT_MODELS` · `IntegrationsController.normalizeLlmModel` 的
服务端白名单 · `integrations.html` 的 JS `LLM_MODELS` · 同页视觉下拉的三个写死 `<option>`。

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · DB 表 `llm_catalog` | 平台/系列/型号落库,管理页读库 | 加平台不用发版。但目录是**代码资产** —— 没有对应的 client 实现就没有那个平台,放进 DB 会出现「库里有平台、代码里没实现」的不一致态,选中即失败。还要写迁移和种子数据 | 不选 |
| B · classpath JSON 资源 | `llm-catalog.json`,启动时加载 | 改文件不重编译。但这个唯一好处被 PRD §2「加平台走版本发布」直接抵消了 —— 反正要发版,重编译不是成本。代价是失去编译期检查,还要写解析 + 校验 | 不选 |
| **C · Java 常量类 `LlmCatalog`** | 平台/系列/型号/默认值/能力标记都是 `record` 常量;服务端校验直接用它;模板通过 `th:inline="javascript"` 拿到它序列化的 JSON | 加平台 = 改一处 + 写一个 client 子类,两件事在同一个 PR 里、编译器帮忙对齐 | **选定** |

### 1.4 · 型号校验:白名单相等 → 格式白名单

现在 `IntegrationsController.normalizeLlmModel` 是**取值白名单**:不在
`qwen-plus/qwen-flash/qwen-max` 或 `deepseek-chat/deepseek-reasoner` 里的一律静默回落成 `auto`。

拍板 4 放开手填,这条必须改 —— 方舟的 `ep-` 接入点 ID 只能从对方控制台复制,带日期的模型 ID
(`doubao-seed-1-6-251015`)意味着**任何写死的清单都会过期**。

| 方案 | 取舍 | 结论 |
|---|---|---|
| A · 保留严格白名单 + 加一个「高级:自定义型号」开关 | 看起来更安全。但用户第一次接方舟就必须打开那个开关 —— **默认路径是坏的**,而且是两套校验逻辑 | 不选 |
| **B · 格式白名单** | 校验改成 `^[A-Za-z0-9._:-]{1,64}$`,清单降级为「推荐项」(下拉可选,也可手填) | **选定** |

**安全边界要说清**(这是放开校验时唯一该问的问题):这个字符串的**唯一去处**是发给对方的
JSON body 里的 `model` 字段。不拼进 URL(不存在路径穿越)、不进 SQL(MyBatis 参数化)、
不回显进 HTML 未转义位。上面那个字符集连引号和空格都不放行。填错的后果是对方接口返回
"model not found",经 `classifyLlmError` 归类后显示 —— 这正是 PRD FR-360 承认的代价。

**静默回落必须一起去掉**。现在填了越权型号会被悄悄改成 `auto`(§0.2 那个漂移),
在三级模型下这会变成「存了 `ep-xxx`,页面显示 `ep-xxx`,实际调的是别的」。改成:
**格式不合法 → 明确报错,不保存**。

### 1.5 · 旧配置迁移(FR-363 · prod 已上线的红线)

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · 启动时跑一次迁移,把旧键写成新键 | `ApplicationRunner` 里 upsert | 之后读取逻辑干净。但要自己处理**可重入**(跑两次)、**中途失败**(写了一半)、**回滚**(回 v1.12 后旧键是否被动过)。三个问题都是自找的 | 不选 |
| **B · 读时派生,一个字都不写** | `LlmSettings.load(config)`:新键有值就用新键;新键缺失,就地从旧键按 PRD FR-363 的映射表推导 | 可重入是**结构上必然**(纯函数,没有写);无「不可用窗口」(不存在迁移这个动作);回滚安全是**结构上必然**(旧键从未被碰过)。代价:派生逻辑永久留在代码里 | **选定** |
| C · 双写 | 读新键,同时把旧键也更新成等价值 | 会改写旧键的语义(`llm_primary_vendor` 要存 platform code?),**直接撞 backward-compat 红线** | 不选 |

**硬规则**:旧的 9 个 `K_LLM_*` 常量**只读、不删、不改写**。用户在新管理页保存时写的是新键;
旧键留在库里作为**回滚锚点**。

**回滚语义要说明白**:升级后改过配置、再回滚到 v1.12 → v1.12 读到的是**升级前的旧值**,
不是新改的值。这是正确的行为("回到升级前"正是回滚的意思),但要写进发版说明,
免得被当成"回滚丢配置"。

**新增配置键**(旧键一个不动):

```
llm_platform / llm_family / llm_model_id                    ← 文本主
llm_platform_backup / llm_family_backup / llm_model_backup  ← 文本备(拍板 1)
llm_ark_api_key                                             ← 方舟凭据
llm_vision_platform / llm_vision_family / llm_vision_model_id
```

`llm_model_id` 刻意不叫 `llm_model` —— 后者是旧键,必须留着不动。

### 1.6 · 视觉(FR-362)

`QwenVisionClient` 现在直接读 `K_LLM_QWEN_KEY`(`QwenVisionClient:53`)、端点写死百炼、
`DEFAULT_MODEL = "qwen-vl-max"` —— 也就是**截图导入被钉死在百炼上**。

改成:走同一套平台/凭据解析(复用 §1.1 的基类拿 base URL 与 key),型号**独立配置**
(可以和文本不同平台)。`off` 保持为**独立开关**,不挤进型号清单当假型号(PRD FR-362 原话)。

**视觉不做 failover** —— 这是设计结论,写明理由:视觉调用发生在用户**等待中的交互路径**上
(上传截图 → 等结果),failover 会把最坏等待时间翻倍;文本调用则多在可重试/后台路径。
PRD §2 也已排除「多平台并发」。视觉侧只有一个三元组。

## 3 · 关键流程

```
LlmRouter.invoke(sys, user)
  ├─ LlmSettings.load()              ← 新键优先,缺失则从旧键派生(§1.5)
  ├─ plan() = [主三元组, 备三元组]    ← 过滤 key 未配 / 熔断中
  └─ 依次尝试:
       platformBean(inv.platform()).chat(inv.model(), sys, user)
       ├─ 成功 → 记 llm audit(实际用了哪个三元组)
       └─ 失败 → 下一个;全失败 → 返回 null(上层维持现有降级,本版不改)
```

管理页「测试连接」按平台单独测,用**该平台当前选中的型号**发一次最小请求;
失败文案一律过 `classifyLlmError`,**不得回显 key 的任何片段**。

## 4 · 口径不变(PRD §3 第 3 条)

这一版只动「调用谁」,**不动「问什么」**:`PromptBuilder` / `OutputValidator` /
各 `*InsightService` 的 prompt 组装**一行不改**。验收方式:同一份数据、同一个型号,
升级前后 dump 出的 system+user prompt 逐字节相同(单测里比对,不靠肉眼)。

memory `feedback_llm_no_math` 的约束不受影响:数值仍由工程算好填进 prompt。
