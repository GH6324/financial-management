# v1.16 技术设计 · 「本期填报完成」只留一个定义

> 对应 [`prd/v1.16.md`](../prd/v1.16.md) · issue #15
> 一句话:把「完成」的判定收回 `snapshot_todo.status` 一列,由**写入侧**(开账)定死,读取侧一律直接读。

---

## 0 · 现状:三个消费者,三份判定

```
填报页每行 ✓      EntryService#rowFor      done = (current != null) || todo.status == DONE
tab 徽标 / 首页横幅 SnapshotTodoMapper      COUNT(*) WHERE status = 'PENDING'
自动关账          PeriodService#markCompletedByMember  ... && pendingTodos == 0
```

`PeriodOpener#createPeriodAndTodos` 开账时做了两件事:写 `period_snapshot`(延续上期末)、插 `snapshot_todo`。
**前者让第一个消费者判 ✓,后者写的却是 `PENDING`**,第二三个消费者判「没完成」。矛盾就产生在这一个方法里。

---

## 1 · 关键选型

### 1.1 口径统一在写入侧,还是读取侧

| | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | **写入侧**:开账写快照的同时把 todo 标 `DONE` | 要一条数据迁移对齐存量;换来 `status` 恢复成唯一真相,三个消费者读同一列 |
| B | **读取侧**:`countPendingByPeriod` 加 `AND NOT EXISTS (SELECT 1 FROM period_snapshot …)` | 改动最小、零迁移;但 `status` 这列从此谁都不能单独信 |
| C | 视图层:模板里判「有没有金额」 | 口径进模板,最不可测,直接排除 |

**为什么不选 B** —— 它看起来更省事,实际是把一份口径抄成两份:自动关账那里也要跟着加同一个 `NOT EXISTS`,
第四个消费者出现时还得再抄一遍。这正是 v1.13 刚刚在 `LlmRouter` 上修掉的那类 bug
(六处各自遍历 `List<LlmClient>`,配置只对其中一处生效),**同一个季度不该在另一张表上再犯一次**。
`status` 是一个状态列,状态列的正确用法是写的时候就把状态写对。

### 1.2 「系统代填」和「人确认过」怎么区分

FR-392 要求提示条只在「没人确认过」时出现,所以 `DONE` 内部还需要能分出两种。

| | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 复用 `done_by_member_id`:**`NULL` = 系统代填** | 零 schema 变更;列名本来就是「谁做的」,没人做就是 `NULL`,语义天然 |
| B | 加第三个枚举值 `TodoStatus.CARRIED` | 表达最直白,但 **prod 回滚会炸** |
| C | 加一列 `carried_forward BOOLEAN` | 表达也直白,但与 `done_by_member_id` 语义重叠,两列能互相矛盾 |

**为什么不选 B** —— `snapshot_todo` 有 `CHECK (status IN ('PENDING','DONE'))`,加值要改约束;
更要命的是**回滚**:prod 已上线(memory `feedback_prod_backward_compat`),
退回 v1.15 的代码读到 `CARRIED` 会在 MyBatis 枚举映射处直接抛异常,填报页整页打不开。
A 方案回滚只是「贷款提示条按旧逻辑不显示」,数据本身仍是旧代码认识的合法 `DONE`。

**为什么不选 C** —— 两个字段表达同一件事,迟早出现 `carried_forward=1` 且 `done_by_member_id=5` 这种自相矛盾的行;
而且要 `ALTER TABLE` 一张热表。

**代价**(诚实写出来):`done_by_member_id` 从此承担了双重语义 —— 既是审计信息,也是「是不是人做的」标志。
所以查询它的地方必须能看懂 `NULL`。目前全项目只有 4 条 SELECT 把它读出来,业务代码一处都没用,
新增的用法就是这一处,风险可控;`markCarriedForward` 也加了 `AND status = 'PENDING'` 保护,
不会把一个已经记名到人的行反向抹成 `NULL`。

### 1.3 存量数据怎么办

| | 做法 | 取舍 |
|---|---|---|
| **A(选定)** | 迁移 `V55` 一次性回填仍 `OPEN` 的账期 | 升级即生效;写死的范围要够窄 |
| B | 读时派生(照 v1.13 `LlmSettings` 的路子) | 无需迁移,但派生逻辑正好落在读取侧 —— 与 §1.1 的结论自相矛盾,且导航栏每次渲染都要多跑一次 join |
| C | 什么都不做,等下个月开账自然对上 | 用户报的就是**当前这一期**,让他等一个月不叫修好 |

回填 SQL 的三条红线:**只动 `OPEN` 账期**(已关账的历史是封板事实,v1.10 的产品承诺)、
**只改状态列**(一行金额都不碰)、**`done_by_member_id` 置 `NULL`**(标记成系统代填,
这样存量的贷款账户升级后提示条照常出现,不会因为回填而丢掉一次决策机会)。

## 2 · 改动清单

### 2.1 `SnapshotTodoMapper` · 新增一个语义明确的更新

```java
@Update("""
        UPDATE snapshot_todo
           SET status = 'DONE', done_at = NOW(3), done_by_member_id = NULL
         WHERE period_id = #{periodId} AND account_id = #{accountId}
           AND status = 'PENDING'
        """)
int markCarriedForward(...);
```

没有复用 `markDone(periodId, accountId, memberId)`,因为那个方法的语义是「**某个人**填完了」,
签名里的 `memberId` 不允许为 `null`;硬塞一个 `null` 进去,读代码的人分不清是系统代填还是漏传参数。

### 2.2 `PeriodOpener#createPeriodAndTodos`

顺序改成:插 todo → 算延续值 → 写 `period_snapshot` → **这一行确实有本期快照** 就 `markCarriedForward`。
判定用「写完之后这个账户有没有快照」而不是「有没有延续值」,两者在正常路径等价,
但幂等重跑 / 快照由别的路径先落库时,前者才是对的。

原有的 `if (todo 已存在) continue;` 保持不动 —— 幂等性靠它,任何人工状态都不会被开账逻辑覆盖。

### 2.3 `EntryService#loanPromptVisible`

第四个参数由 `todoDone` 改为 `confirmedByHuman`:

```java
boolean confirmedByHuman = todo != null
        && todo.getStatus() == TodoStatus.DONE
        && todo.getDoneByMemberId() != null;
```

方法内部的 `!todoDone` 相应变成 `!confirmedByHuman`。**参数名一起改**,
否则下一个读到这段的人会以为它还在看状态列。

### 2.4 `db/migration/V55__align_carryforward_todo_done.sql`

见 §1.3 的三条红线。`JOIN period_snapshot` 保证只对齐「确实已经有数字」的行,
`p.status = 'OPEN'` 把范围锁在在飞账期。

## 3 · 兼容性自检(prod 已上线)

| 项 | 结论 |
|---|---|
| schema | **不改表结构**,只有一条 `UPDATE` 数据迁移 |
| 老数据 | 已关账账期一行不动;在飞账期只把「有快照的 PENDING」推成 `DONE` |
| 回滚到 v1.15 | 安全。回填后的行在旧代码眼里是合法 `DONE`(徽标不计、页面 ✓,与新代码表现一致);唯一差异是贷款提示条按旧逻辑不再显示 —— 那本来就是旧代码的行为 |
| 金额类指标 | 一分不变。这一版没有任何代码路径写 `period_snapshot` / `cash_flow` / `transfer` 的金额 |
| 自动关账 | 触发条件不变(全员提交 **且** 未填数=0),变的是后半条在正常家庭会立刻满足 |

## 4 · 守护

| 手段 | 钉住什么 |
|---|---|
| `PeriodOpenerTodoAlignmentTest`(UT) | 有历史 → `DONE` 且 `done_by_member_id` 为 `NULL`;无历史 → 保持 `PENDING`;重跑不覆盖已存在的 todo |
| `EntryLoanPromptTest`(UT · 补用例) | 系统代填的 `DONE` **仍然**出提示条;人工确认过的 `DONE` 不出 —— 这条正是 FR-392 怕丢的那个能力 |
| `v116-TODO-DONE-SINGLE-SOURCE`(qa-run) | ① `PeriodOpener` 必须调 `markCarriedForward`;② `countPendingByPeriod` 里不许出现 `period_snapshot`(挡住有人把口径又搬回读取侧);③ `loanPromptVisible` 必须看 `DoneByMemberId`,不许只看 `TodoStatus.DONE` |
| `docs/qa-cases.md` | 五条验收路径(见 prd §3) |

第 ② 条是这条护栏里最重要的一句:它挡的不是今天的 bug,是**明天有人为了"省一条迁移"把 `NOT EXISTS` 加回 SQL** ——
那会让口径重新分裂成两份,而且和今天一样不报错。
