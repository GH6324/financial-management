### 0.3 静默失败预检

> 模板要求:列出「会算错但不报错」的点。本版有四条,**SF1 是这一版最大的一个**。

| # | 静默失败 | 为什么不报错 | 防法 |
|---|---|---|---|
| **SF1** | **第二层(消费分类)与第一层(资金性质)口径不一致 —— 四处**,见下表。FR-663 要求两层合计相等,但按 v1.21 的现状**它们本来就不可能相等**,而且差额里混的不是业务事实,是内部不一致 | 两条 SQL 各自都能跑出数,没有任何一方会抛异常。多币种家庭会把 USD 直接加进 CNY,合计只是**偏大**,不是报错 | 选型二 + 选型三:把过滤块提成**编译期共享常量**,两条 SQL 拼同一个串 |
| **SF2** | `one_off` 加了列、改了 `EntryService`,但**漏改 `CashFlowMapper.insert` 的显式列清单** → 勾了一次性,存进去还是 0 | 显式列 INSERT 不会因为表多一列而失败;页面照常跳转,只是那个勾"没生效" | 两条写入路各一条单测,断言**读回来的 `one_off` == 写进去的值**(不是断言"没抛异常") |
| **SF3** | 二级类目继承父级性质时,父级也是 NULL → 如果继承逻辑写成「取父级值」而没有兜底,得到 `null` 再 `valueOf(null)` → NPE 或被 catch 吞掉变成"这一类不显示" | 未分类那一堆本来就常见,少一类在饼图上看不出来 | FR-616 的 NULL→弹性 兜底收在**唯一判据方法**里(选型四),单测覆盖 (null, null) 组合 |
| **SF4** | 常态月均与月均支出**分母不同**(一个 12 期一个 11 期)→ 两个数并排显示,差额不等于"被剔除的一次性支出",用户对不上账 | 两个数各自都"合理",只有减出来才看得出错 | 常态月均**复用 `recentClosed` 返回的同一个期集合**,不自己取期;单测断言 `月均支出 − 常态月均 == 一次性合计 ÷ 期数` |

#### SF1 详表 —— 两层口径的四处分叉(读 SQL 得出)

| 过滤 / 换算 | 第一层 `CashFlowMapper.expenseBreakdown` | 第二层 `ExpenseFlowMapper.sumByCategory` | 后果 |
|---|---|---|---|
| 家庭隔离 | `JOIN account a` + `a.family_id = ?` | **无** —— 只按 `period_id` 过滤 | 账期间接隔离了家庭,但**没有显式校验**;一旦将来有跨家庭共享账期就漏 |
| 归档账户 | `a.archived_at IS NULL` | **无** | 归档账户上的历史支出**只进第二层不进第一层** |
| 现金调整 | `cf.is_adjustment = 0` | **无** | `is_adjustment=1` 的行**只进第二层**(它们多半没有 `expense_category_id` → 落进"未分类",把未分类桶撑大) |
| 换汇 | 逐期汇率折本位币 | **`SUM(cf.amount)` 原币裸加** | 多币种家庭:USD 与 CNY 直接相加。**这一条单独就足以让两层永远对不上** |

**结论**:PRD FR-663 预设差额只有一个来源(「带消费分类的还贷笔」),实际有**五个**(上面四个 + 那一个)。
其中四个是 v1.21 遗留的内部不一致,**不该让用户在"差额说明"里看到**。
处理方式见选型三 —— 这会**改变 v1.21 那三块的数字**,需要维护者知情。

## 一、需求分析

### 1.1 背景与目标(不重复 PRD)

一句话:**把"月均支出"这个承重分母修诚实,顺手把撞车的两个 section 并成一个。**

工程上这一版真正难的只有一件事 —— **新增一整个正交维度(支出性质),却要保证既有 KPI 一个数字都不变**。
所有的设计张力都来自这里:新维度要读 `cash_flow`,而 `cash_flow` 的求和路径正是月均支出的来源。
读同一张表、用同一套过滤、算出并列的第二个读数,**却不能碰第一个读数** —— 这是本版的技术主题。

### 1.2 需求理解:FR → 工程判据

> 只列需要判断的;纯展示类(FR-621/622/634/667/669)在 §三 交互设计里落,不在这里重复。

| FR | 工程判据(可验证的那一句) |
|---|---|
| FR-610/616 | 性质落在 `expense_category.expense_nature`;解析顺序 **本级 → 父级 → 弹性**,三段都在一个方法里 |
| FR-611 | 迁移**按名字**批量填起步包 10 个大类;自建类目留 NULL。按名字填意味着改过名的类目填不上 —— 这是对的(它已经不是起步包那一类了) |
| FR-613/614 | `cash_flow.one_off TINYINT(1) NOT NULL DEFAULT 0`;**只能置 1**,UI 上没有"改回弹性"的路径 |
| FR-615 | `one_off` / `expense_nature` 的判定**只在 `ExpenseNatureService` 一个类里出现**;grep 到第二处 = 护栏红 |
| FR-632 | `常态月均 = averageExpense(同期集合) − 一次性合计 ÷ 期数`,**期集合来自 `recentClosed` 的返回值本身** |
| FR-635 | 不渲染判据:**启用不满 3 期** OR **未分类笔数 ≥ 90%**。两个判据都在服务端算,模板只收一个 boolean |
| FR-636 | 未分类算弹性,但**笔数单独给出**;三分合计 == 本期消费总额(护栏) |
| FR-650~652 | 回流读数一律 `Optional` —— 拿不到就**返回"没有"交回原路径**,不返回 0、不抛异常 |
| FR-663 | 第二层合计 == 第一层"日常开支"片。**按构造保证**(同一条 SQL 出两层),不靠事后校验 |
| FR-665 | top-N:正数组降序累加到 ≥80%,N 夹在 [3,6];**未分类恒定单独成片**;类目总数 ≤6 不合并 |
| FR-670/673 | 三形态由**一个服务端枚举**决定(`TOTAL` / `ITEMIZED_NO_CAT` / `ITEMIZED_WITH_CAT`),模板不做形态判断 |
| FR-674 | 开关关 → 回流读数的 `Optional` **在服务层就为空**,不是在模板里 `th:if` 挡掉 |

## 二、关键选型

> 两条纪律(模板 §二):**① 每个决策给 2–3 个真备选,不写"显然只能这样"。**
> **② 权重只算用户感知得到的**(`feedback_decision_weight_honesty`)——
> 下面任何一张表里都**不会**出现"我写起来省不省事"。

### 选型一 · 三分数据落在哪

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| **甲** | 性质落**类目**(`expense_category.expense_nature`),一次性覆盖落**笔**(`cash_flow.one_off`) | 语义与用户心智一致:"房贷一直是刚性"是类目事实,"这趟旅游是一次性"是单笔事实。改类目性质**立即对全历史生效**(FR-612/W3)而无需回写任何历史行 | 两列在两张表,判定要 join | **选定** |
| 乙 | 全落笔:`cash_flow.expense_nature` | 单表,判定不用 join | **改一个类目的性质 = 批量 UPDATE 历史行**。慢、不可逆、且与 FR-612「立即对全部历史生效」的语义冲突 —— 那不是"生效",那是"改写历史数据" | 否 |
| 丙 | 独立映射表 `expense_category_nature(family_id, category_id, nature)` | 不动既有表 | 与类目**一对一、同生命周期**,多一张表换不来任何甲没有的能力;类目删除还要多维护一条清理路径 | 否 |

**为什么是甲**:FR-612 的裁决(W3 是"无期归属 · 改了立即对全历史生效")已经把性质定义成了**类目的属性**。
乙把它变成笔的属性,直接与那条裁决矛盾;丙是甲的同构复杂化。

### 选型二 · 新增聚合怎么拿数 —— 本版最关键的一个决策

**约束**:F1 是 PRD 排第一的失败模式,FR-671 要求既有 KPI 逐字不变。
月均支出的权威来源是 `CashFlowMapper.sumRealExpenseByPeriod`,它的 WHERE + 换汇块是口径 A 的定义本身。

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| **甲** | 新增一条 `sumExpenseByPeriodCategoryOneOff`,**把 WHERE + 换汇块提成 `public static final String` 常量**,两条 `@Select` 拼同一个常量 | 既有查询产出的 SQL **字节不变**(只是文本来自常量);两条 SQL 同口径由**编译期**保证,不靠 grep 也不靠自觉。新查询一次出全部五块数据(见 §三.1) | 仍是两条 SQL,GROUP BY 不同;常量拼接让 SQL 在源码里不再是一眼可读的整串 | **选定** |
| 乙 | 直接给 `sumRealExpenseByPeriod` 加 GROUP BY 列,既有调用方在 Java 里 roll up | 合计相等**按构造成立**,不可能分叉 | **动了 KPI 主路径的返回结构**,全部既有调用方跟着改 —— 这正是 F1 描述的那种"改一行就做完了"的改动。而且 `RealExpenseSum` 的 `itemCount` / `periodStart` 语义在细分组下会变 | 否 |
| 丙 | 各块各写各的 SQL(v1.21 的做法) | 每块独立,互不影响 | **它已经产出了 SF1 的四处分叉**。同样的做法再来一次,下一版就是第二个 SF1 | 否 |

**为什么是甲**:乙在数学上更强(同一批行,不可能不等),但它把风险放在了**最不能出事的那条路**上。
甲把风险留在新路上,并且用编译器 —— 而不是文档或 grep —— 钉住口径一致。
这是「能机器校验的别只写文档」在这一版的具体落点。

**为什么不怕"第二条求和路径"**:模板 §三.3 要求正面回答这个问题。答:**技术上是,但它被钉住了。**
两条 SQL 的过滤与换汇来自同一个字符串常量,任何一方想改口径都必须改常量 → 另一方同时改 → 零差异基线立刻会红。
另配一条断言常量内容的单测,防止有人"顺手"在某一条上追加 `AND`。

### 选型三 · 第二层的口径怎么办(SF1 的处置)

> 这一条**不在 PRD 已裁的五条里**,是写 TDD 时读 SQL 读出来的新发现。
> 它会**改变 v1.21 那三块的数字**,所以单独列出来请维护者过目。

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| **甲** | 第二层改用选型二的对齐查询;`ExpenseCatQueryService` 的期内 / 年度 / 趋势 / 下钻**全部切到对齐口径** | FR-663 的等式**按构造成立**,差额只剩"带消费分类的还贷笔"这一个**可解释**的来源;多币种家庭的分类构成从"错"变成"对" | v1.21 三块的数字会变(仅限:有归档账户 / 有 `is_adjustment` 支出 / 多币种 的家庭);PRD §6.2「本版不涉及口径变更」要改口 | **选定** |
| 乙 | 不动第二层,把五个差额来源都在"差额说明"里列出来 | 既有数字零变化 | 把内部不一致**转嫁给用户**:让家人去理解"归档账户"和"现金调整"为什么让两个数对不上。而"USD 直接加进 CNY"根本无法向用户解释 —— 它就是错的 | 否 |
| 丙 | 只补三个 WHERE,不补换汇 | 改动小 | 多币种家庭仍然错,且**错得更隐蔽**(其余三项对上了,更像"就差那一点") | 否 |

**为什么是甲**:四处分叉里有三处是**无争议的缺陷**(裸加多币种 / 归档账户混入 / 调整笔混入),
第四处(家庭隔离)是防御缺口。修它们不是"改口径",是把 v1.21 没对齐的地方对齐。
受影响的数字只有一个月大,且变化方向是"变对"。

**代价要如实认下**:
1. PRD §6.2 的「本版不涉及口径变更」**需要加一条例外**(第二层构成对齐第一层),并写清受影响范围。
2. 零差异基线因此要**分两组断言**:FR-671 列举的六个 KPI **必须逐字相等**;
   v1.21 第二层的三块**允许变化,但差异必须能被上面四条逐条解释**,不许有第五种差异。

### 选型四 · 「一次性」判据实现在哪一层(FR-615)

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| **甲** | SQL 只取原始列 `(expense_category_id, one_off)`,判定全在 `ExpenseNatureService.natureOf(...)` 一个方法里 | FR-615 的「只存在于一处」**字面成立**,可被 grep 护栏机器校验;三段兜底(本级→父级→弹性)集中,SF3 有唯一的覆盖点;纯函数,单测可穷举 | 需要先把类目树的性质解析成一张 map 再套用 | **选定** |
| 乙 | SQL 里 `CASE WHEN one_off=1 OR ec.nature='ONE_OFF' ...` 直接分好组 | 一条 SQL 出结果 | 判据会散进**至少 5 条 SQL**(三分块 / 12 期分层 / 瀑布 / 常态月均 / 回流读数),**直接违反 FR-615**;SQL 里的 CASE 没法被单测直接覆盖 | 否 |
| 丙 | MySQL 生成列 | 判据下沉到 schema,不可能绕过 | **物理上做不到** —— 生成列不能跨表引用,而 `one_off` 在 `cash_flow`、`expense_nature` 在 `expense_category` | 否(硬约束) |

**N+1 顾虑的处理**:甲看起来要"取原始行再在 Java 分组",但分组基数极小 ——
`12 期 × ≤40 类目 × 2(one_off)` ≤ **960 行**(`ExpenseCategoryService.MAX_TOTAL=40`)。
SQL 侧已经 GROUP BY 到这个粒度,Java 侧只是给每组贴一个 nature 标签,不是逐笔循环。

### 选型五 · 常态月均算在哪(FR-632)

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|
| **甲** | 新建 `NormalExpenseService`,**复用 `ExpenseLedgerService.recentClosed(familyId,12)` 返回的期集合**,在其上减去一次性 | `averageExpense` **一个字节不动**(F1 的最强防护);分母天然一致(SF4 的防法);开关为空时返回 `Optional.empty()` 天然级联 | 多一个服务类 | **选定** |
| 乙 | 在 `FactViewServiceImpl` 里加 `normalizedAverageExpense` | 与 `averageExpense` 并排,调用方就近 | 把新列**读进了 KPI 主路径所在的类**,护栏 `v1240-EXISTING-KPI-UNCHANGED` 要在同一个文件里区分两个方法读没读新列 —— 护栏变脆,而这条护栏是 F1 的最后一道 | 否 |
| 丙 | 给 `ExpenseLedgerService` 加一个带 flag 的重载 | 不新增类 | 口径权威类里长出**两个月均** —— 项目有过 `findFamilyAggregateRecent` / `ForPeriod` 调错的前科,两个重载摆在一起迟早调错 | 否 |

### 选型六 · FR-674 开关存哪 + 怎么级联

| 方案 | 怎么做 | 优 | 劣 | 结论 |
|---|---|---|---|---|

## 三、系统概要设计

### 3.1 整体思路

核心是一条**对齐口径的聚合查询**,一次出全部五块数据。
这既是 FR-663 等式成立的机制,也是"不产生新口径"的机制。

```
                    ┌─────────────────────────────────────────────┐
                    │  CashFlowMapper.EXPENSE_A_FILTER (常量)      │
                    │  family_id + archived_at + kind=EXPENSE      │
                    │  + deleted_at + is_adjustment=0 + 逐期换汇    │
                    └───────┬─────────────────────────┬───────────┘
                     拼入 ↓                      拼入 ↓
        ┌────────────────────────────┐   ┌──────────────────────────────────┐
        │ sumRealExpenseByPeriod     │   │ sumExpenseByPeriodCategoryOneOff │
        │ (既有 · 字节不变)           │   │ (新增)                           │
        │ GROUP BY period            │   │ GROUP BY period, category_code,  │
        └──────────┬─────────────────┘   │          expense_category_id,    │
                   │                     │          one_off                 │
                   │                     └──────────┬───────────────────────┘
                   ↓                                ↓
        ExpenseLedgerService              ExpenseNatureService
        .recentClosed(fid,12)             .natureOf(oneOff, catId, natureMap)
                   │                          ← FR-615 唯一判据点
                   │                                ↓
                   │            ┌───────────────────┴──────────────────┐
                   │            ↓          ↓          ↓         ↓      ↓
                   │      ①第一层四分  ②第二层分类  ③三分   ④归因瀑布  ⑤一次性明细
                   │            └──────────┬───────────────────┘
                   │                       ↓
                   │        ExpenseSectionViewService(只组装,不查库)
                   │        top-N 归并 / 差额 / 形态判定 / 色板
                   │                       ↓
                   │              _expense-section.html
                   │
                   └──→ NormalExpenseService ──Optional──→ 紧急储备 tooltip
                        (同一期集合,减一次性)              体检流动性
                              ↑                            目标页应急金
                        FR-674 开关在此返回空
```

**读法**:左路是既有 KPI 路径(`averageExpense`),右路是本版新增。两路**共用过滤常量但互不调用** ——
新增的任何东西都进不了左路,这就是 FR-671 的结构性保证。
唯一的交汇点是 `NormalExpenseService` 复用 `recentClosed` 的**期集合**(不是它的金额),保证分母一致。

### 3.6 数据架构

`db/migration/V62__expense_nature.sql`:

```sql
-- v1.24 FR-610 · 类目的支出性质(刚性/弹性/一次性)。
-- NULL = 继承父级;父级也 NULL = 弹性(FR-616)。可空 → 老 jar 照常跑(L7)。
ALTER TABLE expense_category
  ADD COLUMN expense_nature VARCHAR(8) NULL
  COMMENT 'RIGID=刚性 / FLEX=弹性 / ONE_OFF=一次性;NULL=继承父级,父级也空则按弹性';

-- v1.24 FR-613 · 单笔「这笔是一次性的」覆盖。
-- 【纯分析期标记】:不参与余额 / 轧差 / NAV 任何一条链(L13 硬约束⑤)。
ALTER TABLE cash_flow
  ADD COLUMN one_off TINYINT(1) NOT NULL DEFAULT 0
  COMMENT '1=这笔是一次性支出,不进常态月均;只影响分析,不影响任何金额语义';

-- FR-611 · 起步包 10 个大类按名字批量填。
-- 按【名字】填:改过名的类目填不上 —— 这是对的,它已经不是起步包那一类了。
UPDATE expense_category SET expense_nature = 'RIGID'
 WHERE parent_id IS NULL AND name IN ('住房物业','充值缴费','教育培训','医疗健康');
UPDATE expense_category SET expense_nature = 'ONE_OFF'
 WHERE parent_id IS NULL AND name = '数码电器';
UPDATE expense_category SET expense_nature = 'FLEX'
 WHERE parent_id IS NULL AND name IN ('餐饮美食','日用百货','服饰装扮','交通出行','文化休闲');
```

**索引**:`cash_flow` 已有 `idx_cf_expcat (period_id, expense_category_id)`(V59)。
新查询按 `(period_id, category_code, expense_category_id, one_off)` 分组,
`one_off` 是**低基数标记列**,单独建索引没有收益(选择率 ~50/50),**不加索引**。

#### 迁移三问(模板硬要求)

| 问 | 答 |
|---|---|
| **能不能只加不改?** | **能。** 两条 `ALTER ... ADD COLUMN`,零 `MODIFY`、零 `DROP`、零既有行重写。三条 `UPDATE` 只写**新列**,既有列一个字节不动 |
| **能不能回滚?** | **能,且不需要回滚数据。** 回滚 = 回 jar。两列一个可空、一个有默认值,老 jar 的显式列 INSERT 不含它们 → 照常跑(L7)。两列没有任何金额依赖它们 |
| **中途失败留什么状态?** | 三条 `UPDATE` 各自幂等(按名字 + 固定值),重跑无副作用。最坏情况:`ALTER` 成功但 `UPDATE` 只跑了一半 → 部分类目性质为 NULL → **按 FR-616 读作弹性 → 不改变任何既有数字**。**失败的安全方向是"退化成上一版行为",不是"算错"** |

## 六、护栏设计

> 三条纪律(模板 §六):**守意图不守写法** · **能机器校验的别只写文档** · **LLM 护栏要能区分"坏了"和"没给结果"**。

| 护栏 | 守什么意图 | 怎么校验 | 红了说明什么 |
|---|---|---|---|
| `v1240-EXISTING-KPI-UNCHANGED` | 新维度**只被新指标读** | `averageExpense` 实现体不出现 `one_off` / `expense_nature` | F1 发生了:有人让既有 KPI 读了新列 |
| `v1240-ONEOFF-SINGLE-JUDGE` | FR-615 判据只有一处 | `one_off`/`oneOff` 的**判定**只出现在 `ExpenseNatureService`(mapper / domain / 模板展示除外) | 判据被复制了,两处迟早分叉 |
| `v1240-SAME-FILTER-BLOCK` | 两条求和 SQL 同口径 | 两条 `@Select` 都拼 `EXPENSE_A_FILTER`,且常量内容符合口径 A 五要素 | 有人在某一条上"顺手"加了 `AND` |
| `v1240-NO-THIRD-SUM` | 组装层不自己求和 | `ExpenseSectionViewService` 不注入任何 `*Mapper` | 第三条求和路径出现了 |
| `v1240-ONEOFF-NOT-BALANCE` | `one_off` 是纯分析标记 | `one_off` 不出现在余额 / 轧差 / NAV 路径 | L13 硬约束⑤ 又被踩 |
| `v1240-UNCLASSIFIED-IN-SPLIT` | 未分类不被丢掉 | 三分合计 == 本期消费总额(单测) | 有一堆钱在图上消失了 |
| `v1240-UNCLASSIFIED-OWN-SLICE` | 未分类不进「其他」 | 造「未分类 + 12 类目」,断言未分类单独成片 | FR-665 的硬约束被 top-N 吃掉了 |
| `v1240-LAYER-SUM-RECONCILE` | FR-663 两层对得上 | 单测 + 页面断言;不等时**必须渲染出差额说明** | 要么口径又分叉,要么差额被悄悄藏了 |
| `v1240-PIE-TOPN` | 同屏片数 ≤ 7 | 造 15 类目,断言扇片 ≤7 且出现「其他 N 项」 | 色板可读性的前提没了 |
| `v1240-PALETTE-BRAND` | 色板取自品牌色 | 色板 ⊆ `style.css` 品牌色;**相邻 L\* 差 ≥15 用单测算**(shell 算不了 CIE L\*) | 又回到九个泥色 |
| `v1240-TOGGLE-CASCADES` | 开关关掉回流读数一并消失 | e2e:管理页关 → 报表新块**与**紧急储备并列读数同时消失 | 出现"关了支出分析,别处还在冒常态月均"的半开状态 |
| `v1240-NO-JUDGEMENT` | 文案不做价值判断 | 扫模板「建议减少/偏高/超支/冲动/节省」等词 | F6 发生了 |

## 十、补丁 · v1.24.5 · AI 的设置放一处(对应 PRD §14)

### 10.1 端点跟不跟着页面走

| 方案 | 做法 | 取舍 |
|---|---|---|
| A 端点不动 | 表单仍提交到 `/admin/integrations/llm/*`,只改保存后跳回的页面 | 改动最小;但页面在 AI 接入、后端还叫 integrations,下一个排查的人会被带偏 —— 同一天我自己就因为「Key 在哪一页」来回找过 |
| **B 端点跟着搬(选定)** | 新建 `AiModelController`,挂 `/admin/ai-access/llm/{key,models,test}`;方法体逐字搬过来 | 多改 4 个文件(模板、回归脚本、1 个单测);换来「页面在哪、代码就在哪」 |

**为什么不留老路径做兼容**:这几个都是管理页表单的 POST,没有外部调用方;留着只会让「到底哪个在用」多一个问题。

### 10.2 页面数据放哪

「大模型」那一节要显示的东西(凭据状态、三组三元组、型号目录、调用参数)抽成 `LlmSettingsView`(`@Component`),AI 接入页渲染用,端点判「截图识别能不能开」也用。**没有**放进某个控制器再让另一个控制器注入它 —— 控制器之间互相注入会把请求处理和页面组装缠在一起。

### 10.3 模板

第 ① 节连同三个测试连接表单、级联脚本,整段抽成 `admin/_llm-settings.html` 的两个片段(`section` / `script`),内容逐字搬过来,只改三处:端点路径、外层去掉 `max-w-3xl`(与 AI 接入页其它卡片同宽)、挂锚点 `#llm`。保存回执沿用原来的 `flash` / `flashError` 两个名字,AI 接入页顶部补上这两条的显示。

### 10.4 护栏怎么跟

原来有 15 条护栏 grep 的是 `integrations.html` / `IntegrationsController.java`。**判据一个字没改,只换了看的地方**:模板变量改指 `_llm-settings.html`;控制器变量改指一份「控制器 + 视图组件」的合并视图(原来一个文件里的东西现在分在两个文件里)。`v07-CFG-3` 原来查字面量 `/llm/test`,改成查拼起来的完整路径并确认三个测试表单确实提交到那里。新增 `v1245-AI-SETTINGS-ONE-PLACE` 守「不会又长回两处」。入口登记表补上「AI 接入」(原来就漏登记了)。
