## 0 · 施工前的查证:三条与 PRD 不同或 PRD 没说到的事实

PRD 是用户视角,下面三条是翻代码翻出来的、会直接改变设计的事实。

### 0.1 · `MemberPrincipal` 没有 `equals` / `hashCode`

这条决定了 FR-381「当场踢下线」怎么写。`SessionRegistry` 是**以 principal 对象为 key** 的
`ConcurrentHashMap`(`SessionRegistryImpl.principals`)。如果按常规写法

```java
registry.getAllSessions(new MemberPrincipal(member), false)   // ← 永远返回空
```

会一条都找不到 —— 新构造的 `MemberPrincipal` 和登录时放进去的那个不是同一个对象,而
`MemberPrincipal`(`auth/MemberPrincipal.java:18`)只有 `@Getter`,**没有 `equals`**,走的是
`Object` 的引用相等。这是个**不报错、只是没生效**的失败:归档成功了、审计写了、页面也提示了,
只有那个人还在正常用。选型见 §2.1。

### 0.2 · remember-me 的清理有现成 API,但**调用时机**有先后

`PersistentTokenRepository` 接口自带 `removeUserTokens(String username)`
(`SecurityConfig:tokenRepository` 注册的 `JdbcTokenRepositoryImpl` 实现它),不需要自己写 SQL。
但**改名场景必须用旧 username 调,且必须在 UPDATE 之前** —— UPDATE 之后旧名在
`persistent_logins` 里就成了找不到主人的孤儿行,永远删不掉了。

顺带记一条**已经成立的兜底**:即便令牌没删干净,`MemberPrincipalService:19` 的
`.filter(m -> !m.isArchived())` 会让归档者的 remember-me 重认证抛
`UsernameNotFoundException`;改名者则因为旧 username 查不到而同样失败。
所以删令牌是为了**不留静默废票**(用户体验),不是唯一的安全防线。

### 0.3 · `audit_log.type` 是 `VARCHAR(40)`,不是 ENUM

`V1__init.sql:244`。所以 §2.5 新增四个 `AuditLogType` 值**不需要 DB 迁移**。
按 memory `feedback_enum_add_sweep` 的教训,加枚举值要扫「模板里的硬编码串 / 写死的计数分母 /
面向用户裸露 code」三类,已扫:`templates/` 下**没有**任何按 `audit_log.type` 值做的字符串条件,
审计页是直接渲染 `summary` 的。这条扫描是干净的。

**本版不需要任何 DB 迁移**:`member.archived_at` 从 `V1__init.sql:36` 就存在。

## 2 · 架构选型

### 2.1 · 归档「当场生效」怎么做(FR-381 硬约束 3)

要解决的是 PRD §0.2 那个洞:`UserDetailsService` 只在认证那一刻跑,已登录的会话不受影响。

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| **A · `SessionRegistry` + `expireNow()`** | 配 `maximumSessions(-1)` 让每次登录把会话注册进 registry;归档时找出该成员的全部 `SessionInformation` 调 `expireNow()`;`ConcurrentSessionFilter` 在下一次请求时踢出 | 是 Spring Security 的**原生**机制,不引第三方;代价是多两个 bean + 会话表在内存里(单实例部署,见下方边界) | **选定** |
| B · 每请求查库的 `Filter` | 自写过滤器,每个请求拿 principal 的 memberId 查一次 `member.archived_at`,已归档就 `SecurityContextHolder.clearContext()` | 语义上最直接、最不会漏。但**每个请求多一次 DB 往返**,为一个一年发生一次的操作给所有请求上税 | 不选。可以加缓存,但那就是在自造一套会话注册表,不如直接用 A |
| C · Spring Session JDBC | 会话落库,归档时删该成员的 `SPRING_SESSION` 行 | 顺带解决重启掉登录态。但这是**部署面**的改动:新表 + 新依赖 + 会话序列化格式,prod 已上线,收益(重启保登录)与本 FR 无关 | 不选。真要做,单独一版评估,别搭在身份变更里 |

**为什么不选 B 值得多说一句**:B 的诱惑在于「最保险」。但它把一个**事件**(归档发生了)
改写成**轮询**(每个请求都问一遍),这是典型的用持续成本换一次性正确。A 的一次性成本是
两个 bean,可读性也更好 —— 「归档时把他的会话作废掉」这句话在代码里就是字面意思。

**A 的落地细节(踩 §0.1 那个坑)**:

```java
// SessionKiller.java —— 不依赖 MemberPrincipal 的 equals
void killAllSessions(long memberId) {
    for (Object p : sessionRegistry.getAllPrincipals()) {
        if (p instanceof MemberPrincipal mp && mp.getMemberId() == memberId) {
            sessionRegistry.getAllSessions(p, false)   // ← 用 registry 自己给的那个对象实例
                           .forEach(SessionInformation::expireNow);
        }
    }
}
```

这里**刻意不给 `MemberPrincipal` 加 `equals`/`hashCode`**。备选是加(按 `memberId` 判等),
那样可以直接 `getAllSessions(new MemberPrincipal(m), false)`。不选的理由:`MemberPrincipal`
被 Spring Security 放在 `SecurityContext` / remember-me / 各 Controller 的
`@AuthenticationPrincipal` 里到处传,给它换掉**对象同一性语义**是一个影响面远大于本 FR 的改动,
而收益只是省掉上面这个 for 循环。家庭规模下 `getAllPrincipals()` 是个位数,遍历成本是零。

**已知边界(写明,不假装没有)**:`SessionRegistryImpl` 是**单 JVM 内存态**。当前部署是
单个 systemd 单元 / 单个 app 容器,成立;若将来横向扩多实例,这条会退化成「只踢中自己这台」。
不为一个没有的场景先付代价,但登记在这里。

### 2.2 · 改自己登录名之后,当前会话怎么办(FR-380 第 2 条)

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · 就地刷新 principal | 照抄 `AdminController:228` 改 displayName 时的现有写法,把新 `MemberPrincipal` 塞回 `SecurityContext` | 无感,不打断操作。但只修得了**当前这一个**会话 —— 他在别的设备上那个会话里 principal 还是旧名,那台机器上的状态与真相分叉,直到过期 | 不选 |
| **B · 强制全部会话重登** | 复用 §2.1 的 `SessionKiller`:删 remember-me → 作废该成员**全部**会话(含自己这一个)→ 回登录页 | 改完自己名字要重登一次。换来的是「所有设备上的身份状态立刻收敛到一个真相」 | **选定** |
| C · 什么都不做 | —— | principal 里是旧 username,一旦 remember-me 或任何重认证发生就 `UsernameNotFoundException`,表现为莫名其妙被踢 | 不选,这是把问题延后到最不好解释的时刻 |

选 B 的第二个理由是**实现上它不是新东西**:改名和归档共用同一条
「删令牌 → 作废会话」路径,只有 UPDATE 那一句不同。A 反而要维护两套(自己 / 别人)分支。

改登录名在性质上与改密码同级 —— 改密码要求重登是所有人都预期的,这里对齐它。

**顺序是有约束的**(§0.2):`removeUserTokens(旧username)` → `updateUsername` → `killAllSessions`。
中间那步失败要整体回滚,所以三步在同一个 `@Transactional` 里,`killAllSessions` 放
`afterCommit`(内存操作不该在事务里做,失败也不该回滚已提交的改名)。

### 2.3 · 「含已归档」的成员查询怎么加(FR-382)

PRD 已经否掉了「给 `findActiveByFamily` 加 boolean 参数」。剩下的选择是**加到哪一层**。

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · 只在 Mapper 加 `findAllByFamily` | 三处名字映射各自改调新方法 | 最小改动。但「名字映射该含归档」这个知识**散在三个 Controller 里**,第四个页面加映射时没有任何东西提醒它 —— 而这次复查恰恰就漏了 `LensTagController` | 不选(但它是 B 的组成部分) |
| **B · Mapper 加 `findAllByFamily` + 上面套 `MemberDirectory`** | `MemberDirectory` 是展示口径的**唯一出口**,内部固定用含归档的查询;调用点改成一行 | 多一个类。换来的是护栏可以从「检测坏写法」升级成「禁止旁路」—— 见 §5 | **选定** |
| C · 在 SQL 层解决:名字映射改成 `LEFT JOIN member` 直接带出来 | 从根上不需要映射表 | 要改动 3 个页面各自的查询与 DTO,战线远超本版;而且报表侧的 `FactMapper` 是封板路径,不该为改名这件事去动 | 不选 |

B 的关键收益在护栏形态上:PRD §4 要求「钉模式不钉行号」,但模式判据(grep
`findActiveByFamily` 后面跟 `toMap`)是**脆的** —— 换个写法就绕过去了,而且它只能发现
已知的坏写法。有了 `MemberDirectory`,护栏可以直接钉「除白名单外不许出现
`memberMapper.findActiveByFamily(...)`」这条**结构禁令**,这比枚举坏写法强一个量级。

**施工时 B 长出了第三个方法**(设计里只有 `listAll` / `nameMap`):`selectableWith(familyId, current)`。
原因是归档这个动作让一条原本不可达的路径变得可达 —— 账户编辑页和教育目标编辑页的归属下拉
如果只给活跃成员,而这条记录当前挂在一个已归档的人身上,那么**打开表单点保存就把它静默改派了**,
页面上不会有任何提示。这是数据损坏,不是显示问题,所以它必须是名录的一个正式出口(= 活跃 ∪ 当前值),
而不是各页面自己 `if` 一下。新建向导没有这个问题(没有「当前值」),继续用仅活跃。

### 2.4 · 引用扫描:怎么知道「这个人有没有历史」(FR-383)

| 方案 | 做法 | 取舍 | 结论 |
|---|---|---|---|
| A · 查 `information_schema` 自动发现外键 | 运行时列出所有指向 `member.id` 的 FK,逐个 COUNT | 听起来最不会漏,**实际上恰好漏掉全部危险项**:PRD 点名的 3 张无外键表(`period_member_cashflow` V19 · `stock_valuation_event` V24 · V25 提醒发送记录)和 1 处 JSON 引用,`information_schema` 里**根本不存在**。它会自动化出一个**自信的错误答案** | 不选 —— 这是本节最重要的结论 |
| **B · 显式清单 + 逐表 COUNT** | 一张 `(表, 列, 人话说明)` 常量表,逐条 `SELECT COUNT(*)`;JSON 那处用 `JSON_EXTRACT` | 加表要手工登记,会漏。但**漏了有护栏兜**(§5 第 3 条钉住那 4 处必须在清单里),而且清单是**可读的**:页面上「名下 3 个账户 · 12 期填报」的文案直接来自它 | **选定** |
| C · 试删 + 捕外键异常回滚 | `DELETE` 一把,抓 `DataIntegrityViolationException` 就回滚 | 无外键的 3 张表**不会抛异常**,照删不误 → 静默孤儿行。且它是「先破坏再看结果」,与「点删除之前就该看见数字」的产品要求相反 | 不选 |
| D · 软删除(`deleted_at`) | 不真删 | 那就是归档,本版已经有了。issue #12 明确问的是「建错的能不能真删」 | 不选 |

**A 值得单独说**:它是这一节里唯一「看起来更先进」的方案,也是唯一会**造成数据损坏**的方案。
自动发现的前提是「数据库的约束是完整的」,而本项目**恰好不是**(3 张表历史上就没建 FK)。
把不完整的事实自动化,得到的是有信心的错答案。

**JSON 那处的写法**(`family_goal.params_json.child_member_id`,V14):

```sql
SELECT COUNT(*) FROM family_goal
 WHERE family_id = #{familyId}
   AND JSON_UNQUOTE(JSON_EXTRACT(params_json, '$.child_member_id')) = CAST(#{memberId} AS CHAR)
```

用 `JSON_UNQUOTE(...) = CAST(... AS CHAR)` 而不是直接 `= #{memberId}`:params_json 里这个值
**可能是数字也可能是字符串**(取决于写入时的序列化),转成字符串比较对两种都成立。

**分类**:扫描结果分「拥有型引用」(账户 / 快照 / 现金流 / 填报 / 目标 …)和
「流水型引用」(`audit_log` 里 `target_type='member'` 的那些)。前者非零 → 禁止删除;
后者**不计入**(PRD 已明确:那是「发生过什么」,不是「他拥有什么」)。
而 `audit_log.actor_member_id` 算前者 —— 所以「登录后做过任何操作就永远删不掉」,这是想要的结果。

### 2.5 · 审计类型

| 方案 | 取舍 | 结论 |
|---|---|---|
| A · 复用 `FAMILY_UPDATE` | 零改动(`IntegrationsController:153` 现在就这么干)。但身份变更被混进「家庭设置更新」,以后想筛「谁改过登录名」筛不出来,而这**正是这类审计存在的理由** | 不选 |
| B · 复用 `ACCOUNT_ARCHIVE` | 语义是**账户**归档,混用会让审计页读起来是错的 | 不选 |
| **C · 新增 4 个值** | `MEMBER_RENAME` / `MEMBER_ARCHIVE` / `MEMBER_RESTORE` / `MEMBER_DELETE`。因 §0.3 无需迁移、无模板硬编码,成本≈0 | **选定** |

`MEMBER_RENAME` 的 `summary` 必须写成 `登录名变更:旧名 → 新名`(PRD FR-380 第 3 条)。
`MEMBER_DELETE` 的 `actor_member_id` 是操作者(被删者按定义零引用,不可能是 actor),
`target_id` 记被删成员 id —— 该行在成员删除后仍然留存,这是有意的。

### 2.6 · 登录名唯一性冲突

`uk_member_username` 是**全表唯一**(不分家庭)。

- **应用层预查**(`existsUsername`,查全表含归档)→ 给友好提示「这个登录名已被占用」。
- **兜住竞态**:同时 catch `DuplicateKeyException` → 同一句提示。

两者都要。只做预查有 TOCTOU 窗口;只靠异常则用户看到的是数据库错误页。
这不是「双保险」的洁癖 —— 预查负责**说人话**,catch 负责**兜正确性**,两个职责不同。

## 3 · 关键流程

### 3.1 · 改登录名

```
POST /admin/members/{id}/username
  ├─ 校验格式 [a-zA-Z0-9_]{3,40}                     ← 与 createMember 同源
  ├─ existsUsername(新名) 全表含归档 → 占用则回错
  └─ @Transactional
       ├─ removeUserTokens(旧名)        ← 必须在 UPDATE 之前(§0.2)
       ├─ updateUsername(id, 新名)      ← catch DuplicateKeyException → 友好提示
       └─ audit(MEMBER_RENAME, "登录名变更:旧名 → 新名")
     afterCommit: killAllSessions(id)   ← 内存操作,不进事务
```

### 3.2 · 归档 / 撤销

```
POST /admin/members/{id}/archive
  ├─ id == me.memberId          → 拒(且按钮本就不渲染,决定 2)
  ├─ countActiveByFamily() <= 1 → 拒(最后一个活跃成员)
  └─ @Transactional { archive(id) ; audit(MEMBER_ARCHIVE) }
     afterCommit: removeUserTokens(username) + killAllSessions(id)
```

撤销是对称的 `restore(id)` + `MEMBER_RESTORE`,不需要碰会话。

**这里有一条纪律**(PRD 决定 1):归档实现里**一行金额汇总 SQL 都不碰**。
已查证全仓库金额汇总过滤的是 `a.archived_at`(账户),`member` 只作 `LEFT JOIN` 取名字。
「顺手给汇总补一个 `m.archived_at IS NULL` 看起来更对称」是本版最可能发生的手滑,§5 第 1 条钉它。

### 3.3 · 删除

```
GET  /admin/members         → 每个成员带 ReferenceScan 结果(N 账户 · M 期填报 · K 条现金流 …)
POST /admin/members/{id}/delete
  ├─ 要求表单回填该成员的登录名,不匹配则拒
  ├─ 重新扫一次引用(页面上的数字可能已经过时)→ 非零则拒
  └─ @Transactional { deleteById(id) ; audit(MEMBER_DELETE) }
```

页面文案要讲清「他已经产生了 N 条记录,可以改为归档」,而不是把按钮灰掉不给理由。

## 9 · 施工实况 · 与设计的偏差

设计是施工前写的,以下六处施工时和它不一样。记在这里而不是悄悄改掉上文,
是因为**偏差本身比结论有信息量** —— 每一条都是「设计时看不见、动手才暴露」的那类事实。

### 9.1 · 调用点清单错了:9 处 → 15 行 / 11 个文件

PRD FR-382 初稿逐行钉了 9 个调用点。实测(`grep -rn 'memberMapper\.findActiveByFamily\|memberMapper\.countActiveByFamily' src/main/java`)
是 **15 行 · 11 个文件**,改造后共 **25 处**读成员的地方走了名录。漏的集中在 `service/` 层 ——
初稿只翻了 `web/`。**教训不是「下次翻仔细点」**,而是清单这种东西本来就不该由人来维护:
护栏最终钉的是白名单(谁有资格用仅活跃查询),不是那张表里的行号。

顺带一个查证陷阱值得记:`AccountMapper` 和 `GoalMapper` **也各有一个 `findActiveByFamily`**。
用裸方法名 grep 会命中 32 个文件,其中大多数和成员毫无关系;必须带 `memberMapper.` 限定名(12 → 11 个文件)。
差点据此写出一条「看起来很严格、实际在拦别的东西」的护栏。

### 9.2 · 最严重的一处是隐私,不是显示

设计通篇把 FR-382 当**显示问题**处理(名字变空)。施工时扫到 6 处脱敏点 ——
`LlmDiagnoseService` / `GoalLlmService` / `RebalanceAdvisorService` / `LensInsightService` /
`ReviewInsightService` / `CsvExportService` —— 它们建「真名 → 假名」映射表时用的是**活跃列表**。
成员一归档,他就不在表里,于是**他的真名原样进了发给 LLM 的 prompt**。

这直接改变了本版的改造范围:从设计里的「三处名字映射」扩到全部 25 处读成员的地方。
`PrivacyIsolationTest`(静态扫源码的私密红线)守的是「哪些字段不许进 prompt」,
守不住「假名表本身漏了人」—— 那是数据完整性问题,不是字段清单问题。

### 9.3 · `MemberDirectory` 是三个方法,不是两个

多出来的 `selectableWith(familyId, current)` = 活跃 ∪ 当前值。理由见 §2.3 补充段:
归档让「编辑表单里当前值不在候选列表中」这条路径第一次变得可达,而它的后果是
**打开表单点保存就静默改派**。这是数据损坏,必须是名录的正式出口。

### 9.4 · 删除入口只对已归档成员开放

设计没规定删除的前置状态。施工时定成「**先归档,才出现删除入口**」,两个理由:
一是删除是不可逆的,中间隔一道归档等于强制一次冷静期,而归档本身已经把人踢下线了;
二是引用扫描要跑 13 条 COUNT,挂在成员列表上逐行扫会让管理页变慢 ——
只对已归档的人扫,数量天然很少。

### 9.5 · 登录页得解释「你为什么被踢出来」

改名 / 归档会让对方**正在用的会话当场失效**,他看到的是突然跳回登录页。
如果登录页什么都不说,这个体验读起来像 bug。`AuthController` 复用已有的 `stale`
提示位处理 `?expired`,给一句「登录状态已失效 —— 可能是登录名被修改,或该成员已被归档」。
设计里漏了这件事,它不属于任何一条 FR,但没有它整个 FR-380/381 在**被操作那一方**看来是坏的。

### 9.6 · `computeMemberAllocation` 改成 static + 显式传名字映射

成员维度资产配置是「既碰钱又碰名字」的那块,最该有测试,原来却是 Controller 里的私有实例方法、
名字映射在方法内部自己查 —— 要测就得拉起整个 Spring 上下文。改成静态方法 + 名字映射从参数进来之后,
`MemberArchiveMoneyInvarianceTest` 才写得出来,包括那条**反证**(传仅活跃映射进去,断言它产出「成员#7」)。
这是为可测性做的结构调整,不改任何行为。
