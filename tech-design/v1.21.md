## 一、需求分析

### 1. 背景 & 目标

见 PRD §0。工程侧一句话:**在不动 `ExpenseLedgerService` 一行的前提下**,给 TOTAL 模式加一层「分类展开」旁路(树状类目 + 来源行 + 三条进数通道 + 报表扩展)。

### 2. 需求理解(验收口径)

- 零组态(没建类目、没展开)= 与 v1.20.2 **逐字一致**
- 两级恒等式随时成立:`类目显示额 = Σ来源行` · `PMC 月总额 = Σ类目显示额`
- 导入→手改→重导:手填行逐分不变
- 切换深度前后:全期**大类合计**逐分相等
- 删细类:父级合计不变;删大类:进「其他」,全期总合计不变

## 二、关键选型

### 选型一 · 来源行怎么存

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 单表 `expense_split`,一行 =(期×人×类目×来源)** ✅ | 手填是 `source='MANUAL'` 的一行,渠道各占一行;UNIQUE(period,member,category,source) | 两级恒等式是**一条 SUM SQL**;重导=按(期,人,渠道)DELETE+INSERT,天然只动该渠道 |
| B. 手填与导入分两张表 | 手填表 + 导入明细表 | 「显示额」要 JOIN 两表相加,恒等式护栏要跨表;没换来任何好处 |
| C. 只存合成额 + 批次日志 | 类目一行存总数,导入记日志 | **重导无法只替换该渠道**(合成额里拆不出渠道份额)—— 直接违反 FR-533,否 |

**选 A。** 为什么不选 B:两张表就是两条口径的温床(v1.8 的教训是口径来源每多一条就多一次事故)。

### 选型二 · 类目树的表示

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 单表自引用 `parent_id`,应用层限深 2** ✅ | 一张 `expense_category`,一级 parent_id=NULL | 「删细类转父级」= 把 split 行的 category_id UPDATE 成 parent_id,一条 SQL;树读取一次全量(≤40 行)内存组装 |
| B. 大类/细类两张表 | 结构上限死两层 | 「简单版只有一级」时细类表空转;所有查询双表;起步包/映射逻辑写两份 |
| C. 物化路径(path 串) | path='餐饮美食/外卖' | 改名要级联改 path —— FR-503「名字不是数据身份」直接被违反,否 |

**选 A。** 限深靠应用层校验 + 护栏 `TWO-LEVELS-MAX` 扫「parent 的 parent 必为 NULL」;40 行的树不配用复杂方案。

### 选型三 · 「其他」与「未细分」的实体性

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 「其他」= 每家一条系统行(`system_code='OTHER'`);「未细分」= 纯显示层** ✅ | 「其他」要能被选中填数 → 必须是真类目;「未细分」只是「split 行落在一级上」在复杂视图的显示名 → 不建行 | 删大类转其他 = UPDATE category_id,同删细类一个形状;「未细分」零存储零迁移 |
| B. 两个都实体化 | 「未细分」也建行 | 简单→复杂切换要搬数据(把一级行改挂到未细分行)—— 把「切换零成本」这个卖点做没了,否 |
| C. 「其他」用 category_id=NULL 表示 | 省一行 | NULL 参与 UNIQUE 约束在 MySQL 里不唯一(NULL≠NULL)—— 同一格能插多条手填行,恒等式炸,否 |

**选 A。** C 那条是真踩过的坑形状(UNIQUE 含 NULL 列),写进护栏理由里。

### 选型四 · PMC 一致性怎么保证

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 服务层收口:`ExpenseSplitService` 是 split 的唯一写入口,每次写完同事务重算 Σ 并 upsert PMC** ✅ | 与 `ExpenseLedgerService` 同哲学:口径入口唯一 | 恒等式由代码结构保证;护栏扫「除本 service 外无人写 expense_split / 无人在别处 upsert PMC.expense」 |
| B. DB 触发器 | split 表上挂 trigger 维护 PMC | 隐形逻辑,迁移/备份/审计全变难;本项目零触发器先例,不开这个头 |
| C. 异步对账补偿 | 定时任务校平 | 「短暂不一致」对一个记账 app 是不可接受的观感;且多一个失败面 |

**选 A。** 待实测 3(upsert null 语义)解决后,回写只动 `total_expense_input`、绝不碰 income。

### 选型五 · 加密 zip 怎么解

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 引 zip4j(~200KB 无传递依赖)** ✅ | 支持 ZipCrypto + AES 两种;渠道用哪种**待实测 1** | 唯一的新依赖;CN 网络经阿里云镜像可拉(待实测 5) |
| B. 只收用户自解压的 csv | 不引依赖 | 用户多一步;但**无论如何都保留**为兜底路径(zip 解不开时指引降级) |
| C. 自写 ZipCrypto 解密 | 传统算法 ~100 行 | 若渠道实为 AES 就全白写;自研密码学从来是坏主意 |

**选 A + B 兜底。** 若待实测 1 发现拉不下依赖或算法不支持,B 直接顶上,功能不塌。

### 选型六 · 截图转写客户端

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 新建 `ExpenseShotClient`,复制 `VisionLlmClient` 的调用形状,换提示词与输出 record** ✅ | 输出 `(channelGuess, categoryName, amount, confidence)` | 两个场景提示词纪律不同(持仓要代码/市值,账单要类目/金额),硬揉进一个类会互相踩;调用骨架 ~80 行,复制成本低于抽象成本 |
| B. 泛化 VisionLlmClient(传入 prompt+parser) | 一个类 | v1.4 的类注释/护栏都钉着持仓语义;泛化后两边护栏都得改写 —— 为省 80 行冒两处回归,不值 |
| C. 走 LlmRouter 通用视觉 | 统一路由 | LlmRouter 是文本诊断路由,视觉是独立形状;v1.4 当时已论证过不走它 |

**选 A。** 共享的只有「dashscope 视觉调用」这个 HTTP 形状;提示词末尾同样带「只转写不计算、看不清标 ?」纪律(护栏扫)。

### 选型七 · CSV 编码探测

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 双解码打分:分别按 GBK/UTF-8 解前 2KB,含 U+FFFD 或乱码特征者出局** ✅ | 渠道就两种编码,枚举即可 | 零依赖;错判概率极低(GBK 文本按 UTF-8 解必出 FFFD) |
| B. juniversalchardet | 通用探测库 | 又一个依赖,通用性这里用不上 |
| C. 按渠道写死 | 支付宝=GBK 微信=UTF-8 | 渠道哪天改了编码就静默乱码 —— 静默失败预检第一条的反面,否 |

**选 A。**

## 三、系统概要设计

### 1. 整体设计思路

```
                    ┌─ 手抄(展开态表单)─────────┐
进数三通道           ├─ 文件导入(zip/csv 解析)────┤→ ImportDraft(内存)→ 确认页 → ExpenseSplitService
                    └─ 截图导入(ExpenseShotClient)┘                                │(唯一写入口)
                                                                                   ▼
                                                       expense_split(期×人×类目×来源)
                                                                                   │ 同事务 Σ
                                                                                   ▼
                                                       PMC.total_expense_input(既有表,只动这一列)
                                                                                   │
支出报表 ← expense_split(按树 rollup)+ cash_flow(ITEMIZED 既有)          ExpenseLedgerService(零改动)
```

### 2. 领域模型设计

- `ExpenseCategory`:id / familyId / parentId / name / sortOrder / systemCode(OTHER)/ archivedAt
- `ExpenseSplit`:id / familyId / periodId / memberId / categoryId / source(MANUAL·ALIPAY·WECHAT·SHOT)/ amount(MANUAL 可负)/ batchId
- `ExpenseImportBatch`:id / familyId / periodId / memberId / channel / importedAt / rowCount / totalAmount /(replacedBatchId)
- `ExpenseMerchantRule`:familyId / keyword / categoryId(微信商户映射,记忆化)
- 深度设置:`family_runtime_config` 键 `expense_split_depth`(L1/L2);展开偏好键 `expense_split_open_{memberId}`(true/false)—— 复用既有配置表,不加列

### 3. 代码架构设计(新增文件清单)

```
service/expense/
  ExpenseCategoryService     树 CRUD · 起步包 · 删除转移(树语义)· 限深校验
  ExpenseSplitService        ★唯一写入口:saveManual / applyBatch / revokeBatch → 同事务回写 PMC
  ExpenseMixQueryService     报表读:按树 rollup + 未拆分块 + 与 cash_flow 合并
  imports/
    BillParser(接口)· AlipayCsvParser · WechatCsvParser · EncodingSniffer · ZipOpener(zip4j)
    MerchantRuleMatcher      微信商户关键字 → 类目
    ExpenseShotClient        截图转写(qwen-vl,只转写)
    ImportDraft              解析结果(内存,不落盘)
web/expense/
  ExpenseCategoryController  /expense/categories(管理页)
  ExpenseImportController    /expense/import(导入页+确认页,文件收 MultipartFile,zip 密码仅参数)
  (EntryController 扩)      展开态表单读写走 ExpenseSplitService
templates/expense/ + entry 片段 + reports/_expense-mix 扩展
db/migration/V59__expense_category_split.sql(4 张新表,不改既有表)
```

### 4-5. 运行/物理架构

无新进程、无新外呼(截图走既有 dashscope 通道);文件解析全内存(zip ≤20MB、≤300k 行、图 ≤20 张/次,超限人话拒)。自建单家庭,无部署拓扑变化。

### 6. 数据架构设计(V59 骨架)

```sql
CREATE TABLE expense_category (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  family_id BIGINT NOT NULL,
  parent_id BIGINT NULL,                -- NULL=一级;应用层+护栏限深 2
  name VARCHAR(24) NOT NULL,
  system_code VARCHAR(16) NULL,         -- 'OTHER' 每家一条,不可删/停/改名
  sort_order INT NOT NULL DEFAULT 0,
  archived_at DATETIME(3) NULL,
  UNIQUE KEY uk_cat (family_id, parent_id, name)   -- 同层同名拒绝
);
CREATE TABLE expense_split (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  family_id BIGINT NOT NULL, period_id BIGINT NOT NULL,
  member_id BIGINT NOT NULL, category_id BIGINT NOT NULL,
  source VARCHAR(16) NOT NULL,          -- MANUAL / ALIPAY / WECHAT / SHOT
  amount DECIMAL(15,2) NOT NULL,        -- 仅 MANUAL 允许为负(冲正);合成额≥0 由服务校验
  batch_id BIGINT NULL,
  UNIQUE KEY uk_split (period_id, member_id, category_id, source)
);
-- expense_import_batch / expense_merchant_rule 略(见 §三.2)
```

「其他」不用 NULL 表示的原因写在迁移注释里(MySQL UNIQUE 对 NULL 不去重,同格会插出多条手填行)。

## 五、稳定性与质量保障

### 1. 兼容性设计

- 4 张新表,零表改动;老 jar 回滚后新表闲置无副作用
- 零组态逐字一致:所有新 UI 都挂在「家庭有类目/成员已展开」条件后
- ITEMIZED 家庭:类目下拉扩自定义树(既有 `cash_flow.category_code` 不动,自定义类目在下拉里以 `custom:{id}` 编码 —— 待评审确认;或 ITEMIZED 第一期不接自定义树,只做 TOTAL 侧。**倾向后者**,少一条联动链,见 §十)

### 2. 性能评估

split 表量级 =(期×人×类目×来源)≤ 12×2×40×4 ≈ 4k 行/年,忽略不计;导入解析 30 万行 csv 流式单遍,内存峰值 < 50MB。

### 3. 安全性设计

- zip 炸弹:解压前校验声明大小/文件数,流式限额读
- zip 密码/文件字节:方法参数生命周期,不落库不落盘不进日志(护栏扫 log 语句)
- 金额不进 LLM;商户名列表进 LLM 仅当家庭显式勾选(FR 拍板点⑤)
- 上传文件类型白名单(csv/zip/jpg/png),MIME + 魔数双查

## 七、上线与回滚方案

### 1. 可观测

导入批次表本身就是审计日志(渠道/行数/金额/替换链);解析失败原因入 `audit_log`(SYSTEM 类,不含文件内容);无新增外部监控。

### 3. 上线方案

一次发版(V59 自动迁移,建表幂等);无数据回填;起步包是用户主动点的,不预置。分阶段编码顺序(每步全绿再下一步):
① V59 + 类目服务/管理页(含树语义删除)→ ② 手填展开 + PMC 回写(恒等式护栏先立)→ ③ 支付宝解析 → ④ 微信解析 + 商户规则 → ⑤ 截图通道 → ⑥ 报表扩展 → ⑦ e2e + 双端截图 UED。
