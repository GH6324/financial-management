## 一、需求分析

### 1. 背景 & 目标

见 PRD §0。工程侧一句话:**在不动 `ExpenseLedgerService` 一行的前提下**,给 TOTAL 模式加一层「分类展开」旁路(树状类目 + 来源行 + 三条进数通道 + 报表扩展)。

### 2. 需求理解(验收口径)

- 零组态(没建类目、没展开)= 与 v1.20.2 **逐字一致**
- 两级恒等式随时成立:`类目显示额 = Σ来源行` · `PMC 月总额 = Σ类目显示额`
- 导入→手改→重导:手填行逐分不变
- 切换深度前后:全期**大类合计**逐分相等
- 删细类:父级合计不变;删大类:进「其他」,全期总合计不变

## 二、关键选型

> **本节已按第 2 稿重写。** 第 1 稿的选型一(来源行怎么存)、选型四(PMC 一致性)、
> 选型六(截图转写客户端)随 `expense_split` 一起作废 —— 那套设计的前提是
> 「分类是月度总额的展开」,而这条中心决定被否了(prd §14)。
> **作废的选型保留标题并标 `【废】`**,免得后来的人以为漏了编号。

### 选型一 · 分类挂在哪个载体上

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 挂在每一笔上(`cash_flow.expense_category_id`)** ✅ | 记一笔时选一个分类;报表按分类聚合 | 与所有记账软件的心智一致;**可下钻到单笔**;删类目搬家是一条 UPDATE |
| B. 挂在月度汇总上(`expense_split`) | 一个类目一个月一个数 | 第 1 稿,**已否**:「把总数分配到类目里」是人做不来的运算 |
| C. 两者都要 | 逐笔的聚合 + 手填汇总,取大者 | 同一个月的构成有两个出处,迟早对不上;而且要向用户解释「这个数是哪来的」 |

**选 A。** 附带好处不小:B 方案里「删类目搬家」要处理 `UNIQUE(期,人,类目,来源)` 撞键
(先合并同槽行再删源行,一段需要单测钉住的算法),A 方案一条 UPDATE 就够 ——
**每一笔本来就是独立一行**。换载体消掉的复杂度比在原载体上优化算法省得多。

C 被否是因为 v1.8 的教训:家庭支出口径每多一条来源,就多一次事故(那次月均支出差 89%)。

### 选型二 · 性质与消费分类:一个字段还是两个

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 两个字段:`category_code` + `expense_category_id`** ✅ | 性质决定储蓄率/负债口径;分类只回答「钱花在哪」 | 语义正交;`ExpenseLedgerService` **一行不改** |
| B. 合并成一个自定义树,把「还贷」也做成一个类目 | 用户看到的就是一棵树 | **储蓄率会静默算错** —— 还贷被当成消费。这类错误不抛异常,只是数字慢慢不对 |
| C. 两个字段,但界面上也分两步选 | 先选性质、再选分类 | 95% 的笔是「日常开支」,等于给 95% 的情况加一次点击 |

**选 A + 界面合一。** 宫格里同时列消费分类与三个性质项,点哪个都是**一次点击**:
点消费分类 → 性质自动 `consumption`;点性质项 → 分类留空。
底层两个字段、界面一层,是这一版少数几个「两全」的地方。

**写入口过滤**是硬约束:分类只在 `category_code='consumption'` 时写下去,
而且要在 `EntryService` 与 `BillCommitService` **两处**都做 ——
脏数据一旦落库,之后每个读它的地方都要重复同一个 `if`,总有一处会漏。

### 选型三 · 类目树的表示(沿用第 1 稿)

单表自引用、封顶两层、「其他」是每家一条**真实行**(不是用 NULL 表示)。
理由是硬的:MySQL 的 UNIQUE 对 NULL 不去重,用 `category_id=NULL` 表示「其他」会让同名校验失效。

第 2 稿去掉的是**「录入深度」这个设置项** —— 点大类就能提交,想细分再多点一下,
深度变成每一笔的自由选择。少一个设置,就少一整类「切换之后历史怎么办」的问题。

### 选型四 · 【废】PMC 一致性怎么保证

第 1 稿要把 Σ分类 回写 `period_member_cashflow.total_expense_input`。
第 2 稿不需要:逐笔模式下 PMC 总额本来就是 Σ`cash_flow`,没有第二条路径。

> 这一条留下一个**仍然有效**的坑:通用的 `PeriodMemberCashflowMapper.upsert` 是
> **整行覆盖**语义,只传 expense 会把当月收入抹成 NULL 而页面上没有任何报错。
> 第 2 稿没用到它,但下一个想复用它的人要知道(见 PRD §13.1)。

### 选型五 · 重复导入怎么去重

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 按 (家庭, 渠道交易号) 去重** ✅ | 每笔带交易号,已存在的落 SKIPPED 桶 | **精确到笔**;同一份文件导两次不出双份;实现只有一条 IN 查询 |
| B. 整条通道 DELETE + INSERT | 重导某渠道 = 删掉该渠道本期的行再插 | 第 1 稿,配合来源行模型;逐笔载体下等于删掉用户可能已经手改过的笔 |
| C. 按 (日期+金额+商户) 做指纹 | 没有交易号时的兜底 | 同一天同一家店买两次同样价格的东西 → 误判成重复,**静默少导一笔** |

**选 A,不做 C 的兜底。** 拿不到交易号的笔就是无法去重 —— 但这件事要**说出来**
(确认页显示「其中 N 笔没有交易号」),而不是用一个会误杀的指纹假装解决了。

**DB 上故意不建 UNIQUE 约束**:交易号是外部数据,遇到渠道改版/同号复用时,
硬约束会让整批导入 500 而不是跳过那一笔。去重在应用层做,DB 只提供索引。

### 选型六 · 自动归类怎么做

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 三层兜底:渠道分类 → 家庭关键字规则 → AI** ✅ | 前两层零成本零延迟,AI 只处理剩下的 | 覆盖率高且**越用越准**;没配 AI key 也能用 |
| B. 只按渠道分类名严格匹配 | 钱迹的做法 | 对不上就全落「其它」,官方建议用户去 Excel 里 VLOOKUP —— 这正是我们能做得明显更好的地方 |
| C. 全部交给 AI | 每笔都送模型 | 慢、贵,而且渠道自己给的分类**比模型猜的可信** |

**选 A。** 顺序不能反:渠道明说的 > 用户自己定的规则 > 模型猜的。
AI 只对前两层都没命中的送,而且**只送商户名** —— 判据是签名里就没有金额字段
(`classify(List<String>, List<String>)`),不是靠自觉。

### 选型七 · 【废】截图转写客户端

截图产出的是渠道**算好的分类汇总数**,而第 2 稿的载体是逐笔流水 ——
一张截图变不成 96 笔,也没有交易号可以去重(重传同一张图就出双份)。
代码保留、入口不挂,等逐笔线跑顺再决定它落成什么形态(PRD §3.5)。

### 选型八 · CSV 编码探测(沿用第 1 稿)

GBK / UTF-8 双解码,数 U+FFFD 与锚点命中率择优。
金额解析用**只保留数字/小数点/负号**的白名单,而不是枚举要替换的符号 ——
半角 `¥`(U+00A5)在 GBK 里不可映射,一个字符就能静默吞掉一整行(PRD §13.3)。

### 选型九 · 导入落库走哪条路

| 方案 | 说明 | 取舍 |
|---|---|---|
| **A. 批量 insert + 一次余额调整** ✅ | 整批一个事务,余额一次扣完,审计写一条 | 批量导入在用户眼里本来就是**一个**动作 |
| B. 每笔走 `EntryService.recordExpense` | 复用现成的校验与联动 | 300 笔 = 300 次余额更新 + 300 条审计,会把当天别的记录冲到看不见 |

**选 A。** 代价是要自己重复几条校验(账期开着 / 账户归属 / 归档账户 / 负债账户不能记还贷),
这些在 `BillCommitService` 里逐条写明并注明「与 `EntryService` 同一条判据」。


## 三、系统概要设计

### 1. 整体设计思路

```
                    ┌─ 手抄(展开态表单)─────────┐
进数三通道           ├─ 文件导入(zip/csv 解析)────┤→ ImportDraft(内存)→ 确认页 → ExpenseSplitService
                    └─ 截图导入(ExpenseShotClient)┘                                │(唯一写入口)
                                                                                   ▼
                                                       expense_split(期×人×类目×来源)
                                                                                   │ 同事务 Σ
                                                                                   ▼
                                                       PMC.total_expense_input(既有表,只动这一列)
                                                                                   │
支出报表 ← expense_split(按树 rollup)+ cash_flow(ITEMIZED 既有)          ExpenseLedgerService(零改动)
```

### 2. 领域模型设计

```
Family 1 ── N ExpenseCategory        自引用两层树 · systemCode='OTHER' 是每家一条真实行
                    ▲
                    │ expense_category_id(可空)
CashFlow ───────────┘                【载体】性质 category_code 与消费分类是两个字段
   │
   └─ import_batch_id ──▶ ExpenseImportBatch   整批可撤销 · 本身就是审计日志
   └─ ext_tx_no                                渠道交易号 · 重复导入去重

ExpenseMerchantRule   family × keyword → category_id   用户改一笔并勾「记住」就写一条
```

**没有新的金额载体。** 这是第 2 稿与第 1 稿最大的结构差别:
分类不引入任何新的「钱」表,只是给既有的 `cash_flow` 加了一个可空外键。
于是「家庭支出总额」的唯一口径入口 `ExpenseLedgerService` **一行不改** ——
这不是靠测试保证的,是结构上必然的。

**分桶判据的顺序是硬约束**(`BillCategoryResolver.classify`):

```
① 已导过(交易号)      ── 最先判,免得同一笔又走一遍归类
② 退款 / 交易关闭       ── 这笔钱实际没花出去
③ 渠道说「不计收支」    ── 渠道自己的判断,最可信
④ 收入                 ── 默认不导
⑤ 还贷                 ── 【必须在 ⑥ 之前】渠道说是支出就是支出
⑥ 关键字猜的划转        ── 这是猜,不该压过渠道明说的
⑦ 消费 → 三层归类
```

⑤⑥ 顺序反了的后果:`NEUTRAL` 表里有「还款」,于是渠道标成支出的「花呗还款」
先被当划转剔掉,**NATURE 桶永远是空的**,确认页上那个格子形同虚设(踩过,见 PRD §15.5)。


### 4-5. 运行/物理架构

无新进程、无新外呼(截图走既有 dashscope 通道);文件解析全内存(zip ≤20MB、≤300k 行、图 ≤20 张/次,超限人话拒)。自建单家庭,无部署拓扑变化。

### 6. 数据架构设计(V59)

**三张全新表 + 给 `cash_flow` 加三个可空列。**

```sql
expense_category      (id, family_id, parent_id, name, system_code, sort_order, archived_at)
                      UNIQUE(family_id, parent_id, name)   -- 一级 parent_id 为 NULL,MySQL 不去重
                                                           -- → 一级同名靠应用层校验,别指望 DB
expense_import_batch  (id, family_id, period_id, account_id, channel,
                       row_count, total_amount, dropped_count, skipped_count, revoked_at)
expense_merchant_rule (id, family_id, keyword, category_id, hit_count)
                      UNIQUE(family_id, keyword)

ALTER TABLE cash_flow
  ADD expense_category_id BIGINT NULL,     -- 只在 category_code='consumption' 时有意义
  ADD import_batch_id     BIGINT NULL,     -- 整批撤销靠它
  ADD ext_tx_no           VARCHAR(64) NULL -- 去重;故意不做 UNIQUE(见选型五)
```

**三条硬约束**:

1. **新列全部可空、纯新增** —— 回滚只回 jar 不回 DB(联动链 L7),老 jar 见到它们要能照常跑。
   既有的 EXPENSE 流水 `expense_category_id` 为 NULL = 「未分类」,不影响任何金额。
2. **不加外键到 `expense_category`** —— 删类目时我们要自己控制搬家语义
   (删二级转父级 / 删一级转「其他」),外键的 RESTRICT/CASCADE 两种行为都不是我们要的,
   而且会让删除路径在 DB 层报错而不是给出人话提示。
3. **SQL 别名避开 MySQL 8.0 保留字** —— `COUNT(*) AS rows` 直接语法错,
   而且只在真跑到那条查询时才炸(启动/编译/单测全过,报表页 500)。护栏 `v1210-NO-RESERVED-WORD-ALIAS`。

> **V59 直接改,不补 DROP**:第 1 稿的 `expense_split` 从未在 prod 存在过(v1.21 未发布),
> 改本迁移最干净。beta 上手工 DROP 四张表 + 删 `schema_history` 记录后重跑 `db/apply.sh`。


## 四、接口协议设计

### 1. 影响评估

## 五、稳定性与质量保障

### 1. 兼容性设计

- 4 张新表,零表改动;老 jar 回滚后新表闲置无副作用
- 零组态逐字一致:所有新 UI 都挂在「家庭有类目/成员已展开」条件后

- zip 炸弹:解压前校验声明大小/文件数,流式限额读
- zip 密码/文件字节:方法参数生命周期,不落库不落盘不进日志(护栏扫 log 语句)
- 金额不进 LLM;商户名列表进 LLM 仅当家庭显式勾选(FR 拍板点⑤)
- 上传文件类型白名单(csv/zip/jpg/png),MIME + 魔数双查

### 陷阱清单(每一条都真踩过)

> 下面这些**不是预防性清单**,是这一版实际炸过的地方。共同点:
> **编译过、单测过、启动过,甚至 curl 也过** —— 只有真跑到那条路径或真用浏览器看才发现。

| # | 坑 | 为什么难发现 |
|---|---|---|
| 1 | UNIQUE 含 NULL 列不去重 | 一级同名 DB 拦不住,只能应用层校验 |
| 2 | 通用 `upsert` 是整行覆盖 | 只传 expense 会静默抹掉收入,页面无报错 |
| 3 | 文本块以 SQL 关键字结尾 → `SELECTid` | 只在真跑到那条查询时炸 |
| 4 | `COUNT(*) AS rows` 撞 MySQL 8.0 保留字 | 同上;单测用内存假 mapper,根本不碰 SQL |
| 5 | 半角 `¥` 在 GBK 不可映射 | 一个字符静默吞掉一整行 |
| 6 | `#lists` 写在 `${}` 外 | **渲染期**炸,响应截断在半路 |
| 7 | JS 嵌套数组 `[[...]]` 撞 Thymeleaf 内联标记 | 同上,而且 **curl 报 200 + 完整字节数** |
| 8 | 片段参数里的 `T(...)` | 同上;页面从 435KB 掉到 93KB,浏览器等不到 DOMContentLoaded |
| 9 | `th:replace` 吃掉宿主标签的 class | 功能全对,只是排版塌了 |
| 10 | `[hidden]` 打不过 Tailwind 的 `flex` | 该藏的没藏住 |
| 11 | 换控件形态后,读它的旧 JS 抛 TypeError | **只在选中信用卡那一刻**才抛,首屏正常 |
| 12 | 分桶判据顺序错 → 整个桶是死的 | 不报错,那个格子永远显示 0 |
| 13 | 能力做完了没有入口 | 功能验证全绿,用户找不到 |

**共同的应对**:能机器扫的都做成护栏(AGENTS.md 第 8 节纪律);
只有浏览器能发现的(6~11)必须**双端截图 + 看 pageerror**,`curl 200` 在这类问题上是假绿。
