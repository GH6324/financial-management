# Tech-Design · v1.4 · 持仓截图智能解析

> **状态**:草案 · 待评审(承 `prd/v1.4.md`)· 视觉链路已真机 spike 验证
> **范围**:让 WEALTH/CASH(基金/理财/支付宝)大账户支持「截图 → 视觉解析 → 与已有持仓三态对账 → 确认落库」的多真实持仓建模,复用现有持仓 / 估值 / 对账 / 透视全链路,线上历史数据零回溯兼容。

## 1 · 架构决策(备选 + 取舍 + 选定)

### D1 · 数据模型:持仓落在哪张表

| 备选 | 取舍 | |
|---|---|---|
| A. 新建 `fund_holding` 表 | 语义干净,但**复制**估值/CRUD/装配/对账四套逻辑 → 两条平行链路,长期技术债;`LensQueryService`/`AccountValuationService` 都要分叉 | ✗ |
| B. 泛化:`stock_holding` rename 成 `holding` | 语义最正,但**线上表 rename 是高风险迁移**(外键/mapper/历史数据/回滚),只为改名,不值 | ✗ |
| **C. 复用 `stock_holding`(选定)** | 它**本就是通用持仓表**(MANUAL=名称+manual_value 无需 ticker);复用全链路;仅加 3 处向后兼容小改 | ✓ |

**选 C**。代价诚实说:表名 `stock_holding` 对基金语义不够贴切(命名债),但 rename 的迁移风险远大于收益,记为已知债、不动。改动面:
1. `AccountValuationService.supportsHoldings()`:`STOCK/CRYPTO/METAL` → 追加 `WEALTH/CASH`。
2. 加**可空**列 `asset_class_tag`(`VARCHAR(20)`)、`risk_tag`(`VARCHAR(16)`)、`liquidity_tag`(`VARCHAR(16)`);持仓级为空时**回落账户级**同名标签(老 STOCK 持仓全空 → 行为不变)。
3. `sync_source` 允许新值 `SCREENSHOT`(现为 `FUTU/TIGER/NULL`,`VARCHAR(8)` 够放)。

### D2 · 解析技术:视觉大模型 vs OCR(已验证)

选 **`qwen-vl-max`(视觉大模型)**,承 PRD §4。真机 spike 实测:3 张真实截图、~18 支持仓、**市值 100% 对**、自动跳过汇总行、截断行 `confidence:low` 诚实标疑、~10s/张。传统 OCR「文本汤」跨 app 拼行极脆,前端 OCR 手机慢+中文差,均 pass。**关键复用**:同一 DashScope OpenAI 兼容端点 + 现有 Qwen key,零新供应商。

### D3 · 对账 diff:复用券商 reconcile vs 自造

选 **复用 `BrokerSyncService.reconcile` 三态思路**。它已实现「按键匹配 → 新增 insert / 命中 update / 消失 archive,且**只动指定 `sync_source` 的行**,手填(NULL)绝不误删」——正是所需。自造等于重写已被 `BrokerReconcileTest` 网住的逻辑,无谓。**适配点**见 D4/D5。

### D4 · 匹配键:ticker vs 名称 vs 混合

券商用 `ticker+market`(API 已标准化);基金截图**常无 ticker**。选 **混合键**:
- 若截到**基金代码**(6 位数字,如 `005827`)→ 用代码(强键)。
- 否则用**归一化名称**:去空格 / 全角半角统一 / 去常见噪声后缀(`A/C/(LOF)/(QDII-LOF)/联接` 等按规则保留主体)。归一仅用于**匹配**,展示名保留原文。
- 命中阈值:代码精确等价;名称归一后精确等价(不做模糊近似,避免误并两支不同基金)——**匹配不上就当新增**,由用户在确认表手动合并,比自动误并安全。

### D5 · 卖出 / 消失判定:自动归档 vs 用户定夺

选 **用户定夺(默认保留)**。因为 **FR-1 一账户多图**:用户可能只截了列表的一部分(滚动分段),没截到 ≠ 卖出。
- 一次导入的**所有截图先合并成一个持仓集**,再对该账户 `SCREENSHOT` 行算 diff。
- 「库有、合并集无」的行 → 归到确认表「本次未出现」组,**逐条让用户选 保留 / 归档**;默认保留。绝不自动 archive。

### D6 · 估值交接 & 向后兼容:复用 STOCK writeback(关键)

选 **复用 `AccountValuationService` 既有交接机制**,不发明新迁移:
- **历史期零回溯**:P1…P(n-1) 的 `period_snapshot`(手填单一余额)原样保留 → 该段净值曲线**完全不变**。
- **当期交接**:在当前 OPEN 期导入持仓后,`supportsHoldings(WEALTH/CASH)=true` 使 `AccountValuationService` 接管 → Σ持仓 写回当期 snapshot(note=系统估值)。
- **防跳变**:FR-8 对账让用户把 Σ持仓 对齐到账户当前余额(补现金/其他行)→ 交接当期 Σ持仓 ≈ 实际值 → MoM 无虚高尖峰。
- **红线守恒**:导入前该账户 `holdings.isEmpty()` → 系统从不碰其手填 snapshot;导入后才接管;已关账历史期永不改。
- 为什么不「迁移历史成本基础/冲销差额」:现有 STOCK 转持仓从不这么做,曲线照样连续;引入历史回溯反而破坏「已关账不可改」不变量。**否决**。

### D7 · 前端压缩:canvas vs 第三方库 vs 服务端压

选 **前端 canvas 压缩**(复用 logo 模式,参数调大):长边限 ~2000px、`toBlob('image/jpeg',0.82)`(截图多为照片式,JPEG 比 WebP 兼容更稳;文字在 2000px/0.82 下实测清晰)。
- 不选第三方库(browser-image-compression):多一个 vendor 依赖,canvas 够用。
- 不选纯服务端压:大图先过网络到服务器再压,浪费用户流量 + 撞 nginx/multipart 上限。前端压是省流量的正解。
- 服务端仍**保留大小上限兜底**(单图 ≤8MB、单次 ≤ 图数×8MB),防绕过前端直传。

### D8 · 缺 key / 无视觉时的降级

`QwenVisionClient.available()` = Qwen key 非空。不可用时:整功能入口**优雅禁用 + 文案提示**(承 `LlmClient.available()` 与 LensAiTag 模式),不报错、不半吊子。DeepSeek 无视觉 → 视觉链路**只走 Qwen**,不 failover 到 DeepSeek(与文本诊断的多厂商兜底不同,此处显式限定)。

### D9 · 导入任务:临时 session vs 持久化 job(状态机 · 承评审第 6 点)

选 **持久化 job**。评审要求「扫描久用户退出后再进能看到上次结果、不重来」→ 导入不能只放 session。设一张 `holding_import`(状态机)+ `holding_import_item`(逐项):
- 状态机:`UPLOADING`(收图/压缩)→ `SCANNING`(视觉识别中)→ `REVIEW`(识别完待用户比对确认)→ `CONFIRMED` / `ABANDONED`。
- 进某账户导入页时:**先查该账户有没有未完成(REVIEW/SCANNING)的 import** → 有则直接回到那一态(断点续看);无则新建。
- 视觉识别在**后台异步**跑(承 `@Async` / 现有任务模式),`SCANNING→REVIEW` 由后台置位;前端轮询/刷新看进度。这样退出不打断识别。
- 为什么不 session:session 随退出/超时丢,满足不了「续看」;且原图/明细也要持久(D10/D11)。

### D10 · 原图:识别即删 vs 压缩持久化(承评审第 8 点)

**改为压缩持久化**(推翻初版「识别即删」)。评审要回看当时明细 → 存。方案:前端已压到 ~300KB,服务端再存 WebP 到 `${uploadRoot}/family-{id}/holdingshots/{importId}-{n}.webp`,`holding_import_item.shot_path` 记路径。
- **量级**(反驳「太大」):~300KB/张 × 月 15–30 张 ≈ 月 5–9MB、年 ~100MB → 不大,可接受。
- 复用 `LogoUploadController` 存储/`/uploads/**` serve/路径穿越校验;备份自动含(D 见 §5)。
- 隐私:仍上传前明示「发给 AI 识别」;存的是**用户自己的**截图供自查,可加「导入后不保留原图」开关(默认保留)。

### D11 · 持仓变动怎么进流水(承评审第 9 点 · 关键口径)

选 **一条账户级 `VALUATION`(估值调整)流水事件 + 富明细**,不是逐笔收入:
- 持仓涨跌是**钱赚(市场)不是人赚(净流入)**。若记成 INCOME 会污染储蓄率/净流入口径。→ 复用现有 `cash_flow` 的 **`VALUATION` 类型 + `adjustment=true`**(既有「剔出投资损益」语义),记一条账户级事件。
- 该 `cash_flow` 加 `ref_import_id` 指向 `holding_import` → 填报页行内 ledger 展开该条 = **逐项变化(新增/更新旧→新/卖出)+ 当时原图缩略图**(承 `renderLedgerHtml` 既有展开机制)。
- 为什么不逐持仓一条流水:账本是账户级(`cash_flow.account_id`),逐持仓会撑爆 ledger;「逐项」放进这一条的**明细**里更合适。

### D12 · 成本预估 + 扫描动画(承评审第 2、5 点)

- **成本预估**:纯前端,`图数 × 该模型单价`(max ~¥0.01 / plus ~¥0.005 · 常量随模型档),导入前实时显示「≈¥X · 免费额度内≈0」。不调后端、零成本。
- **扫描动画 + ETA**:每图叠一条 CSS「扫描线」动画;ETA = `图数 × ~10s`(spike 实测均值,写常量)。纯前端观感,不影响后端异步识别真实耗时。

## 2 · 数据模型变更(migration)

迁移编号按现状顺延(设 `V48`/`V49`)。全部**加列 / 加表**,无破坏性 DDL。

**① 持仓级标签(`V48`)**:
```sql
ALTER TABLE stock_holding ADD COLUMN asset_class_tag VARCHAR(20) NULL COMMENT '资产类型(AssetClass.name · 空=回落账户级)';
ALTER TABLE stock_holding ADD COLUMN risk_tag        VARCHAR(16) NULL COMMENT '风险(空=回落账户级)';
ALTER TABLE stock_holding ADD COLUMN liquidity_tag   VARCHAR(16) NULL COMMENT '流动性(空=回落账户级)';
-- sync_source 复用既有 VARCHAR(8) 列,新增取值 SCREENSHOT,无需改结构
```

**② 导入任务 + 逐项(`V49`)** — 承状态机(D9)/图片(D10)/明细(D11):
```sql
CREATE TABLE holding_import (
  id           BIGINT PRIMARY KEY AUTO_INCREMENT,
  family_id    BIGINT NOT NULL,
  account_id   BIGINT NOT NULL,
  period_id    BIGINT NOT NULL,                 -- 导入落在哪个开账期
  status       VARCHAR(12) NOT NULL,            -- UPLOADING/SCANNING/REVIEW/CONFIRMED/ABANDONED
  vision_model VARCHAR(32),                     -- 本次用的视觉模型
  cost_est     DECIMAL(10,4),                   -- 前端预估成本(留痕)
  img_count    INT NOT NULL DEFAULT 0,
  created_at   DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  confirmed_at DATETIME(3) NULL,
  INDEX idx_acct_status (account_id, status)     -- 进页查「该账户有无未完成 import」
);
CREATE TABLE holding_import_item (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  import_id     BIGINT NOT NULL,
  parsed_name   VARCHAR(120),                   -- 识别出的名称(原文)
  parsed_code   VARCHAR(16) NULL,               -- 基金代码(若识别到)
  market_value  DECIMAL(20,4) NULL,             -- 识别市值
  confidence    VARCHAR(8),                     -- high/low
  match_state   VARCHAR(10) NOT NULL,           -- UPDATE/NEW/SOLD(匹配更新/新增/卖出)
  matched_hid   BIGINT NULL,                    -- 匹配到的已有 stock_holding.id
  old_value     DECIMAL(20,4) NULL,             -- 旧市值(UPDATE 时,展示旧→新)
  asset_class_tag VARCHAR(20) NULL, industry_tag VARCHAR(20) NULL, platform_tag VARCHAR(40) NULL,
  shot_path     VARCHAR(255) NULL,              -- 该项来自哪张压缩原图(family-{id}/holdingshots/…)
  user_decision VARCHAR(10) NULL,               -- KEEP/ARCHIVE(SOLD 项用户定夺)
  INDEX idx_import (import_id)
);
```

**③ 流水挂钩(`V49`)** — 承 D11:
```sql
ALTER TABLE cash_flow ADD COLUMN ref_import_id BIGINT NULL COMMENT '指向 holding_import · 供 ledger 展开导入明细';
```

**backward-compat**:①三列全 `NULL` → 存量持仓回落账户级、零行为变化;②新表、③新可空列 → 老代码忽略。**纯 ADD,无改列/删列**,在线 DDL 友好,回退 jar 不回 DB 无害。

## 3 · 组件设计

### 3.1 视觉客户端 `QwenVisionClient`(spike 已验证雏形)
- 端点 / 鉴权 / key 与 `QwenLlmClient` 同(`FamilyConfigService.K_LLM_QWEN_KEY`,不碰明文)。
- 模型:`K_LLM_VISION_MODEL`(管理页可配,默认 `qwen-vl-max`)。
- 请求:`messages=[{system:转写规范}, {user: [{type:text,text:PROMPT},{type:image_url,image_url:{url:"data:image/jpeg;base64,…"}}]}]`,`temperature=0.1`。
- Prompt(承 spike + 调优):强约束「只转写屏幕可见、禁计算、禁补全、截断标 low、跳过分类汇总行、市值原样字符串、基金代码若见则填」;输出严格 JSON 数组。
- 解析:抽首个 JSON 数组 → 逐项白名单校验(数值只做格式规整不做运算;标签走 `AssetClass/IndustryTag.fromName`)。
- 故障:复用熔断;失败友好归类(不泄 key)。

### 3.2 导入服务 `HoldingImportService`(有状态 job)
```
startOrResume(accountId, periodId) → HoldingImport         // 查该账户未完成 import;有则返回(续看),无则建 UPLOADING
addImages(importId, List<compressedImg>)                   // 存 WebP 到 uploadRoot(D10)→ img_count++;转 SCANNING
scanAsync(importId)                                        // @Async:逐图 QwenVisionClient 识别 → 合并去重 → 白名单打标
                                                            //   → 与该账户 SCREENSHOT 活持仓做三态匹配 → 写 holding_import_item → 置 REVIEW
confirm(importId, edits) → void                            // 事务:按 item 的 match_state insert/update/archive
                                                            //   → AccountValuationService.refresh(写回当期 snapshot)
                                                            //   → 记 VALUATION cash_flow(ref_import_id)(D11)
                                                            //   → status=CONFIRMED · Lens 缓存失效(AFTER_COMMIT)
```
- **三态匹配**(承 reconcile · D4/D5):按 `parsed_code` 优先、否则归一化名称,与该账户 `sync_source=SCREENSHOT` 活持仓比 → `UPDATE`(命中·记 old_value→market_value)/`NEW`(右有左无)/`SOLD`(左有右无·默认 KEEP,用户可 ARCHIVE)。
- **只碰 SCREENSHOT 源**:手填/券商持仓不进比对、不被删。
- 数学(Σ、涨跌、对账差)工程算,不经模型。

### 3.3 上传端点(加固 · 承 LogoUploadController)
- `POST /entry/accounts/{id}/holdings/import`(multipart 多图)· 认证 + CSRF · 类型 image/* + 魔数 + 单图 ≤8MB · 存 `family-{id}/holdingshots/{importId}-{n}.webp`(**压缩持久化 · 不再即删**,D10)· 审计 `HOLDING_IMPORT`。
- `GET …/import/{id}` 拉当前状态(轮询 SCANNING 进度);`POST …/import/{id}/confirm` 落库。
- 进账户导入页 = `startOrResume`,断点续看(D9)。

### 3.4 前端
- **入口(承评审 1)**:填报页 `entry/_row.html` 账户行(WEALTH/CASH/STOCK)加「AI 截图识别导入」;账户详情持仓页留日常维护入口。
- **压缩 + 多图**(承评审 2):复用 logo canvas 压缩(长边 2000 / JPEG 0.82)· 多选 + 缩略图 + 删 + 补图。
- **成本预估**(承评审 3 · D12):图数 × 模型单价常量,实时显「≈¥X · 免费额度内≈0」。
- **扫描动画 + ETA**(承评审 5 · D12):每图叠 CSS 扫描线;ETA=图数×~10s。
- **左旧右新比对 UI**(承评审 4):左列该账户已有持仓、右列识别结果,自动匹配连线,状态徽记(匹配更新/新增/卖出),可手动改匹配 / 编辑 / 定夺卖出;底部对账条。移动端上下分区呈现。
- **断点续看**(承评审 6):进页若有 REVIEW/SCANNING import → 直接回到那一态。

### 3.5 Lens / 透视
- **零改**:持仓落库 + 缓存失效后,`LensQueryService` 自动把该账户拆 N 持仓,旭日/透视/体检按 industry/assetClass 细分。持仓级标签取 holding 列(空回落账户级)。

### 3.6 流水事件 + 明细回看(承评审 9、8)
- `confirm` 记一条账户级 `cash_flow{kind=VALUATION, adjustment=true, account_id, period_id, ref_import_id}`(不算人赚净流入)。
- 填报页行内 ledger 展开该条 → 渲染**导入明细**:逐 `holding_import_item`(新增/更新 old→new/卖出)+ 该 item 的压缩原图缩略图(`/uploads/family-{id}/holdingshots/…`)。承 `EntryController.renderLedgerHtml` 既有展开机制,加一种 `IMPORT` 明细渲染分支。

## 4 · 端到端数据流

```
填报页选中账户 →「AI 截图识别导入」→ startOrResume(有未完成 import 则续看)
  → 前端 canvas 压缩(长边2000/JPEG0.82)+ 多选;显示预估成本(图数×模型单价)
  → POST /entry/accounts/{id}/holdings/import(多图 · CSRF)→ 存压缩 WebP 到 uploadRoot · status=SCANNING
  → 前端每图扫描线动画 + ETA;后台 @Async 逐图 QwenVisionClient 识别 → 合并去重 → 白名单打标
    → 与该账户 SCREENSHOT 活持仓三态匹配 → 写 holding_import_item · status=REVIEW
  → (用户中途退出 → 再进该账户 = 回到 REVIEW,不重来)
  → 左旧右新比对 UI(自动匹配 + 匹配更新/新增/卖出 + 手调 + 对账条)
  → 用户改/定夺 → POST …/import/{id}/confirm
  → 事务:按 item insert/update/archive(sync_source=SCREENSHOT)
    → AccountValuationService.refresh(Σ持仓 写回当前 OPEN 期 snapshot)
    → 记 VALUATION cash_flow(ref_import_id · adjustment)· status=CONFIRMED
```

## 9 · 成本估算与经济性

**计费规则(已核实)**:按 token 计。**图片 token = 宽×高/(28×28),单张封顶 256–1280 token**(default `max_pixels=1280×28×28`)——再大的手机截图也最多按 1280 token 算。新用户送 **7000 万免费 token**。

**单次调用 token**:图片 ≤1280 + prompt ~300 = 输入 ~1600;输出(7–15 支持仓 JSON)~600。合计 ~2200 token/张。

**单价(估 · 以官方为准)**:`qwen-vl-max` ≈ 输入 ¥3/百万、输出 ¥9/百万;`qwen-vl-plus` ≈ 其半价。
- `qwen-vl-max`:1600×3e-6 + 600×9e-6 ≈ **¥0.01/张**(约 1 分)。
- `qwen-vl-plus`:约 **¥0.005/张**。

**月成本(prod 实测:单家庭 · 17 个候选大账户)**:
- 保守 ~10 个大账户 × ~1.5 图 ≈ 15 图/月;上限(全 17 + 滚动)≈ 30 图/月。
- `qwen-vl-max`:**¥0.15–0.3 / 月**;`qwen-vl-plus`:¥0.08–0.15 / 月。
- **免费额度**:7000 万 token ÷ ~2200 token/次 ≈ **3 万次调用** → 单家庭这点量**几年用不完** → 实际成本 ≈ 0。

**经济性(自托管单家庭定位下)**:每个自托管用户用自己的 key + 免费额度,近乎免费。成本非本迭代瓶颈。

**plus vs max 实测(同 3 张真实截图)**:两档**市值都 100% 对**;但 `qwen-vl-plus` 更脏——把汇总行「多宝理财」误当持仓、收益三列黏在一起、漏字(「海外」)、输出带 ```json``` 围栏;`qwen-vl-max` 干净(跳过汇总行、名称完整)。**结论:成本两档都可忽略,plus 省的两毛钱换来更多要用户改的脏数据不值 → 默认 `qwen-vl-max`,`plus` 作省钱可选。**

**省钱杠杆(已内建可调)**:
1. **默认 `qwen-vl-max`(实测更干净)**,`qwen-vl-plus` 作可选(管理页 `K_LLM_VISION_MODEL`)——成本敏感的自托管用户可切 plus 省半价。模型档可配 = 用户自选「省 vs 更准」。
2. 前端压缩已把图控制在合理分辨率;图 token 本就封顶 1280,再降 `max_pixels` 省得有限、且伤文字清晰,不做。
3. **不选**传统 OCR / 自建 PaddleOCR:每次更便宜甚至免费,但语义结构(区分汇总行/持仓、跨 app 版式)精度差 —— 为省每月两毛钱丢准确率不值。
4. **不选**自建 Qwen-VL 开源权重:需 GPU(beta 3.5G 无 GPU),不适合轻量自托管。
5. 交互式流程,不用 Batch(异步半价但要等)。

**结论**:成本可忽略(月几毛 / 免费额度内近乎 0);TDD 已把模型做成管理页可配(plus/max 自选),用户可自行在「省」与「更准」间取舍。
