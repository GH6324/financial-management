## 二、迁移 V60

```sql
ALTER TABLE cash_flow DROP CHECK ck_cash_flow_amount;
```

**没有备选方案**,因为:

- 改成 `CHECK (amount >= 0)` 不够 —— 维护者要的是负数也能录
- 改成 `CHECK (amount <> 0)` 与「0 元要允许导入」直接冲突
- 保留约束、在应用层把负数存成正数 + 一个方向标记 → 那是「取绝对值」的变体,
  报表侧要处处记得乘回去,漏一处就把退款画成消费(PRD §9 失败模式①)

**向后兼容自检**(`feedback_prod_backward_compat` 四条):

| 自检项 | 结论 |
|---|---|
| 对线上现有数据什么影响 | **零**。只 DROP 约束,不 UPDATE/DELETE 任何行;既有行全部 > 0,放宽后天然满足 |
| 新列可空? | 不加列 |
| 老 jar 见到新 schema 能跑吗 | **能**。老 jar 只写正数,放宽的约束对它无感 |
| 回滚 | 只回 jar 不回 DB(项目惯例)。若真要回滚 schema,得先确认库里没有 ≤0 的行 —— 但那是人工动作,不进自动回滚路径 |

> `transfer` 表上的 `ck_transfer_amount CHECK (amount > 0)` **不动** —— 划转不在本版范围内。

## 三、「支出恒正」假设的实测清单

下面每一处都是 `grep` 扫出来的**实际代码**,不是推测。
放开负数之后,每一处都要**显式表态**:是该改,还是刻意保留。

### 3.1 会静默出错的(必须改)

| 位置 | 现状 | 放开负数后会怎样 |
|---|---|---|
| `ExpenseLedgerService:318` `hasData()` | `totalBase.signum() > 0` | 某月退款多于消费 → 总额 ≤ 0 → **整个「支出构成」段被判成「没数据」直接隐藏**。用户看到的是一片空白,不报错、不解释 —— 这是本版最危险的一处 |
| `ExpenseLedgerService:297` 占比 | `pct = amt × 100 ÷ total` | `total` 可能为 0(除零已挡)或为负(**没挡**);`amt` 为负时 pct 为负 → 饼图扇形画不出来 |
| `ExpenseLedgerService:339` `hasItem` | `itemized.amount().signum() > 0` | 逐笔金额合计为负 → 被当成「没有逐笔数据」,回落到总额模式 |
| `ExpenseLedgerService:340` `hasTotal` | `total.signum() > 0` | 同上 |
| `ExpenseCatQueryService:240` | `if (v.signum() <= 0) return 0;` | 负数被当成「没有」而不是「负的」 |

**判据**:这五处的共同病是 **把「≤0」当成「没有数据」**。
放开负数之后,`0` 和 `负数` 都是**合法的、有含义的值**,
「有没有数据」应该看**有没有行**(`slices.isEmpty()`),不是看金额符号。

### 3.2 分母保护(保留,但要复核)

| 位置 | 现状 | 判断 |
|---|---|---|
| `ExpenseCatQueryService:196` | `if (t.signum() == 0) t = monthlyTotal(...)` | 保留 —— 这是回退取数,不是符号假设 |
| `ExpenseCatQueryService:200` | `if (max.signum() == 0) max = ONE` | **要改成 `max.abs()` 的口径** —— 用作条形图宽度的分母,负数会让宽度为负 |
| `ExpenseCatQueryService:260` | `if (whole.signum() == 0) return ZERO` | 复核:`whole` 为负时应该返回什么 |

### 3.3 导入侧的拦截(本版要改掉的就是这三处)

| 位置 | 现状 | 本版 |
|---|---|---|
| `BillCategoryResolver:235` | `amount.signum() <= 0` → 丢进 DROPPED | 改成 → 进「不建议录入」,**默认不勾但可勾**,理由分「0 元」和「负数」两种 |
| `BillCommitService:130` | `amount.signum() <= 0` → 抛 CommitException | 删掉这道拦截(DB 约束已放开) |
| `ExpenseImportController:339` | `amount.signum() <= 0` → `continue`(跳过) | 同上 |

### 3.4 不受影响(确认过,无需改)

- `applyDeltaToBalance`:支出走 `amt.negate()`,负金额 → 余额加回。**方向天然正确**,不用改
- 储蓄率 / 净流入 / NAV / XIRR:全部按代数和,负支出天然正确
- `LiquiditySurplus:36` `avgMonthlyExpense.signum() <= 0`:这是**应急金月数**的分母保护
  (月均支出为 0 或负时算不出「够花几个月」),保留是对的 —— 但文案要能说明

> **护栏**:`v1220-NO-POSITIVE-ASSUMPTION` 扫 §3.1 那一类形态(把 `signum() > 0` 当成
> 「有数据」的判断),要求每一处要么已改、要么在代码里有一行注释说明为什么保留。
> **判据不许写死行号或个数** —— v1.21.2 刚栽过一次(`-eq 2` 把第三条查询漏掉了)。
