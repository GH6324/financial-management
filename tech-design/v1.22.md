## 二、迁移 V60

```sql
ALTER TABLE cash_flow DROP CHECK ck_cash_flow_amount;
```

**没有备选方案**,因为:

- 改成 `CHECK (amount >= 0)` 不够 —— 维护者要的是负数也能录
- 改成 `CHECK (amount <> 0)` 与「0 元要允许导入」直接冲突
- 保留约束、在应用层把负数存成正数 + 一个方向标记 → 那是「取绝对值」的变体,
  报表侧要处处记得乘回去,漏一处就把退款画成消费(PRD §9 失败模式①)

**向后兼容自检**(`feedback_prod_backward_compat` 四条):

| 自检项 | 结论 |
|---|---|
| 对线上现有数据什么影响 | **零**。只 DROP 约束,不 UPDATE/DELETE 任何行;既有行全部 > 0,放宽后天然满足 |
| 新列可空? | 不加列 |
| 老 jar 见到新 schema 能跑吗 | **能**。老 jar 只写正数,放宽的约束对它无感 |
| 回滚 | 只回 jar 不回 DB(项目惯例)。若真要回滚 schema,得先确认库里没有 ≤0 的行 —— 但那是人工动作,不进自动回滚路径 |

> `transfer` 表上的 `ck_transfer_amount CHECK (amount > 0)` **不动** —— 划转不在本版范围内。

## 三、「支出恒正」假设的实测清单

下面每一处都是 `grep` 扫出来的**实际代码**,不是推测。
放开负数之后,每一处都要**显式表态**:是该改,还是刻意保留。

### 3.1 会静默出错的(必须改)

| 位置 | 现状 | 放开负数后会怎样 |
|---|---|---|
| `ExpenseLedgerService:318` `hasData()` | `totalBase.signum() > 0` | 某月退款多于消费 → 总额 ≤ 0 → **整个「支出构成」段被判成「没数据」直接隐藏**。用户看到的是一片空白,不报错、不解释 —— 这是本版最危险的一处 |
| `ExpenseLedgerService:297` 占比 | `pct = amt × 100 ÷ total` | `total` 可能为 0(除零已挡)或为负(**没挡**);`amt` 为负时 pct 为负 → 饼图扇形画不出来 |
| `ExpenseLedgerService:339` `hasItem` | `itemized.amount().signum() > 0` | 逐笔金额合计为负 → 被当成「没有逐笔数据」,回落到总额模式 |
| `ExpenseLedgerService:340` `hasTotal` | `total.signum() > 0` | 同上 |
| `ExpenseCatQueryService:240` | `if (v.signum() <= 0) return 0;` | 负数被当成「没有」而不是「负的」 |

**判据**:这五处的共同病是 **把「≤0」当成「没有数据」**。
放开负数之后,`0` 和 `负数` 都是**合法的、有含义的值**,
「有没有数据」应该看**有没有行**(`slices.isEmpty()`),不是看金额符号。

### 3.2 分母保护(保留,但要复核)

| 位置 | 现状 | 判断 |
|---|---|---|
| `ExpenseCatQueryService:196` | `if (t.signum() == 0) t = monthlyTotal(...)` | 保留 —— 这是回退取数,不是符号假设 |
| `ExpenseCatQueryService:200` | `if (max.signum() == 0) max = ONE` | **要改成 `max.abs()` 的口径** —— 用作条形图宽度的分母,负数会让宽度为负 |
| `ExpenseCatQueryService:260` | `if (whole.signum() == 0) return ZERO` | 复核:`whole` 为负时应该返回什么 |

### 3.3 导入侧的拦截(本版要改掉的就是这三处)

| 位置 | 现状 | 本版 |
|---|---|---|
| `BillCategoryResolver:235` | `amount.signum() <= 0` → 丢进 DROPPED | 改成 → 进「不建议录入」,**默认不勾但可勾**,理由分「0 元」和「负数」两种 |
| `BillCommitService:130` | `amount.signum() <= 0` → 抛 CommitException | 删掉这道拦截(DB 约束已放开) |
| `ExpenseImportController:339` | `amount.signum() <= 0` → `continue`(跳过) | 同上 |

### 3.4 不受影响(确认过,无需改)

- `applyDeltaToBalance`:支出走 `amt.negate()`,负金额 → 余额加回。**方向天然正确**,不用改
- 储蓄率 / 净流入 / NAV / XIRR:全部按代数和,负支出天然正确
- `LiquiditySurplus:36` `avgMonthlyExpense.signum() <= 0`:这是**应急金月数**的分母保护
  (月均支出为 0 或负时算不出「够花几个月」),保留是对的 —— 但文案要能说明

> **护栏**:`v1220-NO-POSITIVE-ASSUMPTION` 扫 §3.1 那一类形态(把 `signum() > 0` 当成
> 「有数据」的判断),要求每一处要么已改、要么在代码里有一行注释说明为什么保留。
> **判据不许写死行号或个数** —— v1.21.2 刚栽过一次(`-eq 2` 把第三条查询漏掉了)。

## 四、选型与取舍(评审通过后补齐)

> 状态:**已实现**。下面每一节都写了 2–3 个备选 + 为什么不选。

### 4.1 提交参数模型

| | 方案 | 取舍 | 结论 |
|---|---|---|---|
| A | 保留 `drop` + `restore` 两个参数,只改文案 | 改动最小。但两个**方向相反**的参数正是「系统已经删了一批、用户捞回几个」那套心智的化石 —— 它会让「全选」在两个桶之间行为不一致,而那是 v1.21 已经踩过的 | 不选 |
| **B** | **一个 `include` 列表** | 只有一个事实:这一行用户勾没勾。复选框同时是「录不录」和「批量改作用于我」—— 不是偷懒,你要录的那些行才需要改分类,两者天然重合 | **选定** |
| C | `include` + 单独的「选中」态 | 两套勾,用户要理解「勾了但不录」这种状态 | 不选 |

**`include` 为 null 时不能当成「全选」**:HTML 里一个复选框都没勾时浏览器什么都不提交,和「字段不存在」无法区分。当成全选会把用户刚刚全部取消的选择原样录进去 —— 所以 `null == 空集`,前端另有一道拦截保证不提交空集。

### 4.2 「不建议录入」的行放哪

| | 方案 | 取舍 | 结论 |
|---|---|---|---|
| A | 保持独立面板,只改名 | 两张表 → 两套全选 → 又回到「两个桶两种动作」 | 不选 |
| **B** | **并进主表、排最前;页签降级成筛选** | 「全选」只有一套,且只作用于**看得见的行**。点「不建议录入」是筛选而不是切面板 | **选定** |
| C | 排最后 | 默认流程不被打断,但要人看的东西沉到底下几百行之后 | 不选 |

**关键实现**:归类步骤**提前到分桶之前**,于是 SUGGEST_SKIP 的行也带着分类和账户推荐 —— 用户勾上即可直接录。v1.21 里这个桶的分类一律是 null,「采纳建议之外的个别几行」这件事因此很贵,而那正是维护者要的操作。

### 4.3 「已存在」编辑的写路径

| | 方案 | 取舍 | 结论 |
|---|---|---|---|
| A | 复用填报页的改流水接口 | 不用新代码。但那条路径按 `cash_flow.id` 走,而确认页手上只有**交易号**;而且它不处理「改账户要挪余额」 | 不选 |
| **B** | **新服务 `ExistingFlowUpdateService`,按交易号批量改** | 一次查全(避免 N+1)、一个事务、余额挪动走 `EntryService.applyImportedExpense` 的既有路径(审计日志与镜头失效都挂在那) | **选定** |
| C | 直接在 controller 里写 UPDATE | 余额挪动会变成第二套改余额的代码 | 不选 |

**事务边界**:修正排在 `commit` **之前**,而且**不依赖草稿**。它改的是上次已入账的行,和这次要落的新行没有关系 —— 放在草稿检查之后的话,session 一过期,用户在那一桶里改了半天的东西会连同一句「草稿已经过期」一起消失。

### 4.4 构成图的负组

| | 方案 | 取舍 | 结论 |
|---|---|---|---|
| A | 取绝对值凑扇形 | 把一笔 −499 的退款画成一笔 499 的消费。**骗人**,而且用户完全看不出来 | 不选 |
| B | 负组藏掉并从总额里扣走 | 「各组加起来 ≠ 总额」,对账时对不上 | 不选 |
| **C** | **不进扇形、但进总额,图例下方单列一行** | 唯一诚实的一条。占比的**分母用正组之和**而不是总额 —— 否则正组占比会 > 100%(总额被负组拉小),那个数字会让人以为算错了 | **选定** |

### 4.5 窄屏下的逐笔表

7 列表格在 390px 下按比例压缩会把商户名压成**一个字一行**的竖排。备选:① 横向滚动 ② 重排成卡片。
选①:这一页的动作是「逐行核对并改分类/账户」,**列与列的对齐关系本身就是信息**;拆成卡片之后「同一列的值上下对比」这件事就没了,而那正是核对时最常做的。

> 这个问题 v1.21 就存在(同一个表格结构),只是当时拍到的那一屏恰好是空态,没暴露出来。

## 五、实施记录 · 判据被自己的注释绊倒(三次)

护栏写「不许出现某句话」时,如果不先剥注释,**解释这条规则的文字本身会让它变红**:

| 护栏 | 被自己绊倒的那句话 |
|---|---|
| `v1220-NO-DELETE-WORDING` | 注释里的「『已剔除』这个说法没了」 |
| `v1220-PER-ROW-REASON` | 注释里的「『金额是 0 或负数』这种合并说法对用户没用」 |
| `v1220-ACCOUNT-MOVE-BOTH-SIDES` | 注释里解释 `applyImportedExpense` 的方向,把调用数从 2 变成 3 |

另外 Thymeleaf 的注释是 `<!--/* ... */-->` **跨行**的,单行 `sed 's/<!--.*//'` 只能吃掉起始那一行。

> 判据:**凡是扫「不许出现某句话」,先 codeonly / 先按块剥注释。**

## 六、实施记录 · 一处故意保留的正数假设

`ExpenseLedgerService.decide()` 里的 `hasItem` 仍然判 `signum() > 0`,和同文件 `hasData()` 的结论相反。

一度把它改成看 `itemCount` —— 单测 `金额为0的逐笔不得压掉用户手填的总额` 立刻红了,而**那条测试是对的**:一行 0 元把用户手填的总额顶掉,支出会凭空变 0。

两者的区别在**错的后果**:
- `hasData()` 错 → 整段构成图消失(展示层,刷新页面就能发现)
- `hasItem` 错 → **支出金额本身错了**(口径层,会串到储蓄率和净流入)

所以那一处保留,并在代码里写清楚为什么 —— 护栏 `v1220-NO-POSITIVE-ASSUMPTION` 只守 `hasData()`,并要求那一处有说明。
