# Tech Design · v1.2 · 月度归因复盘 + 再平衡执行闭环 + 性能底盘

> PRD:`prd/v1.2.md`(2026-07-20 拍板 A+D+F · D1-D5 按推荐)。
> 一句话架构:**归因 = FactSlice 上的纯函数**(照 PivotEngine 模式,零新落库);**计划 = 两张轻表 + 划转后本地规则核销**;
> **性能 = 埋点定位 + slice 复用 + 重块懒加载**,不改任何数值口径。

## 1. 主题 A · 归因引擎

### 1.1 选型(备选 → 取舍)
- **A. 纯函数 `AttributionEngine`(calc 包)+ `AttributionService` 装配(选定)**:输入 FactSlice(已有 per-账户 per-期 `periodPnlOrig/Base`、收支、余额双币种),输出结构化归因结果;可单测、与 PivotEngine 同构。
- B. SQL 端聚合:口径分散进 SQL,币种换算规则重复实现,**不选**。
- C. 预计算落库:实时算 <10ms(slice 已在内存),落库徒增迁移,**不选**。

### 1.2 口径(恒等式严格闭合 · 无近似残差)
```
ΔNW      = endNW(anchor) − endNW(prev)
人赚      = Σ incomeBase − Σ expenseBase          (household 口径,与现有 cashflowBreakdown 一致)
开账基线  = openingBaselineLast                    (现有口径)
钱赚_i    = periodPnlBase_i                        (账户级,精确)
  标的_i  = periodPnlOrig_i × fx_end_i             (fx_end = endBase/endOrig,零余额回退 prev,再退 1)
  汇率_i  = periodPnlBase_i − 标的_i               (两步法「先量后价」;CNY 账户恒 0;两项和恒等 pnlBase → 闭合)
未归因    = ΔNW − 人赚 − 开账基线 − Σ钱赚_i        (工程期望 ≈0;非零如实显示,不吞不摊)
```
- **维度分组**:账户贡献 × 账户级标签(资产类型(lens 派生同源)/ 成员 / 平台 / 币种 / 账户类型)。
  **行业不做归因维度**(PRD 修订记录:持仓账户的行业在持仓级,账户级恒空 → 全落未分类,信息误导;行业收益看 v1.1 透视的持有口径)。
- **12 期序列**:slice.rows 按期聚 `periodPnlBase`,按当前维度着色堆叠;一次 load 全算(O(rows))。
- LOAN 账户不进钱赚(与 lens 口径一致);瀑布 TopN=4 + 「其他钱赚」合并项。

### 1.3 接口
- `GET /dashboard/attribution?asof=&dim=`(HTMX fragment,懒加载 · F 主题一致):瀑布 + 贡献榜 + 12 期趋势一个片段。
- 结果 record:`Attribution(delta, humanEarned, opening, fxTotal, unattributed, slices[{key,label,pnlBase,underlying,fx}], trend12[{period, byGroup}])`。

## 2. 主题 A · AI 月度复盘

- `ReviewInsightService`(照 LensInsightService 模式):工程信号 → LLM 解读 → 真名脱敏 → follow 主选 vendor。
- 信号集:最大拖累占钱赚亏损 ≥50% / 汇率重估占 |钱赚| ≥20% / 人赚为负(入不敷出)/ 连续 ≥2 期同一账户 top1 拖累(查上期归因)/ 无显著异常如实说。
- **缓存落库**(D5 拍板):`V48` 表 `review_ai_cache(family_id, period_id, dim, text, vendor, created_at, UNIQUE(family_id,period_id,dim))`——关账期结果不可变,长期回看;「重新解读」覆盖写。
- 端点:`POST /review/insight`;月报融合:reports 月报区展示同一缓存文本(只读引用,不做第二套)。

## 3. 主题 D · 再平衡执行闭环

### 3.1 落库(并入 V48)
```
rebalance_plan(id, family_id, period_id, status ACTIVE/ARCHIVED, created_at, closed_at)
rebalance_plan_item(id, plan_id, from_account_id, to_account_id, amount_base, note,
                    status PENDING/EXECUTED/MANUAL_DONE, executed_transfer_id, executed_at)
约束:一个家庭同一时刻至多 1 个 ACTIVE 计划(应用层保证)。
```
### 3.2 采纳与解析
- 现有建议 `rebalance_advice_cache.content_json.actions[{from_account,to_account,amount,reason}]` 已结构化:
  checkup 建议区渲染为**勾选列表**(账户名 → id 按 displayName 精确匹配;失配条目置灰不可选并提示"账户名对不上,可手动添加")。
- 「采纳 N 条为本期计划」→ 创建/追加 ACTIVE 计划;手动加条(from/to 下拉 + 金额);金额可改、条目可删。
### 3.3 核销(纯本地规则 · 不涉 LLM)
- `EntryService` 划转保存成功后回调 `RebalancePlanService.tryMatch(familyId, transferId, fromId, toId, amountBase)`:
  命中 ACTIVE 计划中 同 from/to · `amountBase ≥ item.amount_base × 阈值(默认 0.8,K_REBALANCE_MATCH_PCT 管理页可配)` 的最早 PENDING 条目 → EXECUTED + 回链 transferId。
- 「已在外部完成」按钮 → MANUAL_DONE(标注未经核销)。
### 3.4 生命周期与闭环
- 关账流程(PeriodOpener close)钩子:ACTIVE 计划 → ARCHIVED(可回看)。
- `LlmDiagnoseService` 诊断 prompt 注入上期计划执行率(「上期计划 2/2 执行,高风险 47%→39%」),AI 只解读。
### 3.5 视图
- checkup 页:建议区 + 活动计划卡(进度条 + 条目状态);dashboard 洞察条加一枚「计划 x/y」pill。

## 4. 主题 F · 性能底盘

- **Step1 埋点**:populateModel 各阶段 `log.debug` 耗时(slice load / kpis+trend / accountPerformance / cashflowSeries / momYoy / pendingRows / goals+insight),qa 留观测口。
- **Step2 已知优化点(按 baseline 决定动哪些)**:
  1. `momYoy` 单独再 load 一次 FactSlice → **窗口并集复用**:主 load 起点取 min(rangeStart, asof−12月),momYoy 从主 slice 截取;
  2. `pendingRows` 走 `entryService.listRows`(全行装配含流水)→ 换轻查询(只取未填账户 id+名);
  3. 归因区 / AI 洞察条 / 目标条带保持或改 **HTMX 懒加载 fragment**(归因区天生懒加载);
  4. Thymeleaf 已 prod cache。
- **验收**:beta `curl -w %{time_starttransfer}` 前后各 10 次取中位,目标 P50 ≤ 400ms;数值口径零变化(现有单测 + qa 数值 case 全绿背书)。
