## 1 · 这份文档要回答的两个问题

维护者在批 PRD 时点了两个必须想清楚的点:

1. 仪表盘的「资产收益」现在用的是**上个月**的数;按两页分工的定义,仪表盘应该是**实时本月**。
2. **什么东西落库、什么东西实时计算** —— 而且要考虑 (a) 线上已有数据的兼容 (b) 未来迭代
   (口径转换、新增指标)怎么办。

第 2 点是这一版真正的架构决策,放在 §2;第 1 点在 §6(它的答案跟第 2 点同源)。

## 2 · 核心决策:什么落库、什么实时算

### 2.1 先把「封板不变性」这句承诺拆开

PRD 里写的是「报表页的指标不会再二次变动」。要兑现它,得先问:**一个指标的输入里,
有哪些是冻结的、哪些是可变的?** 我把 v1.10 七个 FR 的输入全查了一遍,结论比预想的严重。

| 输入 | 落库情况 | 可变性 | 影响哪些 v1.10 指标 |
|---|---|---|---|
| 账户期末余额 | `period_snapshot.end_balance`(**原币**) | 冻结(除非走 `period_reopen_log` 重开) | 全部 |
| 收入 / 支出 / 转账 | `period_member_cashflow` + `cash_flow` 按期落库 | 同上 | 瀑布、三列对照、归因 |
| 汇率 | `fx_rate` **按 period_id 落库** | 冻结;且取值规则是「锚点期(`period_start ≤ rangeEnd` 的最新一期)」的汇率 | 全部金额 |
| 持仓估值 | `stock_price_snapshot` 按期落库 | 冻结 | 全部金额 |
| **账户是否归档** | `account.archived_at` | **可变** · 且 `queryBase` 里有 `AND a.archived_at IS NULL` | **全部**(见 2.2 ①) |
| **账户类型 / 资产大类 / 产品类目** | `account.type` / `asset_class` / `product_category_code` | **可变** | 资产负债表分类、集中度、流动性分层 |
| **流动性档位** | 不落库 —— 由 `product_category.liquidity_class` 决定,缺失时按 `account.type` 派生 | **可变**(管理页能改类目) | 流动性分层、流动资产、紧急储备 |
| **月均支出窗口** | 不落库 —— 在切片上算 | **可变**(补录历史期会改;而且**随 `range` 变**) | 紧急储备月数 |

### 2.2 三个实测发现,顺序按严重性

**① 归档一个账户,会改写全部历史快照。**
`FactMapper.xml:161` 有 `AND a.archived_at IS NULL`。归档动作没有时间语义 ——
账户一归档,它的**全部历史事实行**从切片里消失,于是**所有历史期**的净资产、总资产、
集中度分母、分层占比都跟着变小。

这条直接把「封板不变」证伪了:一个纯前台的整理动作(归档一个已经不用的账户)
就能改写去年 12 月的报表。**这是 bug 级的,不是"设计权衡"。**

**② 紧急储备月数会随 `range` 变。**
`avgExpense` 是在页面主切片上算的,而主切片的 `rangeStart` 由 `range` 决定 ——
所以同一个封板期,选 3M 和选 1Y 看到的「紧急储备 N 月」不一样。
这与 FR-320 要求的"切 range 前两区一个数字都不动"直接冲突。

**③ 汇率锚点其实已经是稳定的**(这一条是好消息,推翻了我的初始假设)。
`rangeEnd = anchor.getPeriodStart()`,而 anchor 就是 `asof` 期 —— 所以汇率取值只由 `asof`
决定,不由 `range` 决定。v0.10.1 那个"单一镜头"设计在这里刚好帮了忙,不需要额外处理。

### 2.3 方案选型

#### 方案 A · 指标全实时计算 + 修掉可修的漂移源(**选定**)

- 指标不落库,全部从既有事实切片算
- 修 ①:`archived_at` 过滤加时间语义 —— `archived_at IS NULL OR archived_at > period_end`
- 修 ②:前两区不用页面主切片,按 `asof` 自备切片;月均支出窗口固定为「asof 往前 N 期已关账」,与 `range` 无关
- 埋一个 `MetricFormulaVersion` 常量,在封板抬头显示「口径 vN」

**取舍**:
- 好:**零回填**(prod 3 期 / beta 175 期都不用动)· 加指标不改 schema · 口径改了自动对全部历史生效
  (这正是 v1.9.4 那种修复能"一改就全对"的原因)· 无 schema 变更 = 对 prod 零风险
- 坏:**账户属性变更(类型/类目/流动性档)仍会改写历史** —— 这条 filter 修不了,
  要历史属性版本化才行(见方案 C)
- 坏:每次请求要算;前两区需要额外 2 次切片加载(上期 + 去年同期)

#### 方案 B · 关账时把指标算好落宽表

`period_metric(period_id, net_worth, total_assets, hhi, ...)` 一期一行。

**为什么不选**:
- 加一个指标要 `ALTER TABLE` —— 而这个项目的迭代节奏是几天一版、几乎每版都加指标
- 口径一改要回填 175 期,而指标之间有依赖(紧急储备依赖月均支出依赖支出口径),
  回填顺序错了就是静默错值 —— v1.9.4 的教训说明这个项目最怕静默偏差
- prod 已有 3 期没有行 → 首次上线就要写回填脚本,而回填只能用**今天的**账户属性,
  拿不回封板当时的属性 → 回填出来的"定格值"是假的

#### 方案 C · 关账时落长瘦 KV 指标快照 + 口径版本 + 显式重新封板

`period_metric_snapshot(period_id, metric_key, value_num, formula_version, sealed_at, source)`

**为什么不是现在选**:它才是真正能兑现「绝对定格」的方案 —— 长瘦表加指标不改 schema,
`formula_version` 让新旧口径共存,`source=BACKFILL` 能诚实标注"事后补算"。
MoM/YoY 也刚好适合它(`WHERE period_id IN (cur, prev, yoy)` 一把取出)。

但它的成本集中在**读侧的双轨逻辑**:每个指标都要"有快照读快照、没快照回落实时算",
还要一个"重新封板"入口和它的权限/审计。这套东西的复杂度和 v1.10 的 UI 工作量相当 ——
**一版里同时做完两件大事,是这个项目历史上翻车最多的形态**(v1.8 支出口径 + UI 同版,
就靠零差异基线才捞回来)。

所以定为 **v1.11 的演进路径**,v1.10 先把两个前置条件做掉:
埋 `MetricFormulaVersion` 常量,以及把指标计算收进一个**单一入口**(见 §3),
将来落库时只在那个入口上加"读快照/回落实时"的分支,不用改 7 个 FR 的每处调用。

### 2.4 结论一句话

> **v1.10:指标不落库,但把"实时算"变成一个可验证的性质** —— 修掉归档与 range 两个
> 会改写历史的漂移源,落一条"封板不变性"护栏(同一期 × 不同 range × 不同当前时间
> → 指标逐字相同),并在抬头显示口径版本。**剩下那条修不了的漂移(账户属性变更)
> 写进页面说明,不假装它不存在。**

这一步之后,「不会二次变动」从一句口头承诺变成:**在账户属性不变的前提下可证**。
要拿掉那个前提,走 v1.11 的方案 C。

## 3 · 计算放在哪一层

新增一个 `SealedPeriodService`(`service/report/`),**它是前两区所有指标的单一入口**:

```java
public record SealedSnapshot(
        Period period,                 // asof 锚定的已关账期
        Completeness completeness,     // FR-321 填报完整度 / 估值来源 / 汇率日期
        BalanceSheet balanceSheet,     // FR-322
        Waterfall waterfall,           // FR-323(含 identityDiff)
        Comparison comparison,         // FR-324 本期 / 上期 / 去年同期
        Concentration concentration,   // FR-325a(含上期幽灵值)
        LiquidityTiers liquidity,      // FR-325b
        Attribution attribution,       // FR-326
        int formulaVersion,            // 口径版本 · 抬头显示
        List<DriftNote> driftNotes) {} // 无法定格的说明(账户属性变更等)
```

**为什么要这个单一入口**(而不是让控制器散着调 `factViewService` 的各个方法):

| 备选 | 取舍 |
|---|---|
| 控制器里逐个调 `factViewService.xxx(slice)`(现状风格) | 和现在一致、无新类;但**前两区的"只依赖 asof"这个性质散落在 7 处**,后人加一节就可能又把主切片传进去 → range 污染回归。而且 v1.11 要落库时,得改 7 处调用 · **否决** |
| **`SealedPeriodService` 单一入口**(选定) | 一处收口:切片怎么取、窗口怎么定、口径版本从哪来,全在这里。护栏只需盯这一个类的签名(它**不接受 `range` 参数**,从类型上就传不进去)。v1.11 落库时只在这里加分支 |
| 直接做成 SQL 视图 / 存储过程 | 口径进 SQL 后测不动(现在指标口径全部有单测),也和项目"计算在 Java、SQL 只取事实"的既有分层冲突 · 否决 |

**切片加载**:`SealedPeriodService` 自己按需加载,**不接受外部传入的切片**:

- 本期:`FactFilter(rangeStart = asof, rangeEnd = asof)` 单期切片
- 上期 / 去年同期:各一个单期切片(不存在则 `Optional.empty()`)
- 月均支出窗口:`FactFilter(rangeStart = asof − (N−1) 期, rangeEnd = asof)`,N 取现有口径的窗口长度
  (与仪表盘紧急储备同一常量,避免两页不一致)
- 集中度的「上期幽灵值」复用上期切片,不额外加载

最多 4 次切片加载(本期 / 上期 / 去年同期 / 支出窗口),都是单期或短窗口,比现在的 1Y 主切片更轻。

## 4 · 各 FR 的实现要点

### FR-320 · 三区 · range 不变性

- 前两区渲染只依赖 `SealedPeriodService.load(familyId, asof, viewCurrency)` —— **签名里没有 range**
- 第三区继续用现有主切片(`rangeStart(range, anchor)` → `anchor`),一行不改
- `tocItems` 改成三段式(带区标题锚点),同步 `fragments/_toc`
- 护栏 `v110-SNAPSHOT-RANGE-INVARIANT`:抓 `/reports?asof=X&range=1M` 与 `&range=ALL`
  两次渲染的前两区 HTML,**归一化后必须逐字相同**

### FR-321 · 完整度

| 项 | 取法 |
|---|---|
| 已填 / 应填账户数 | 该期 `period_snapshot` 行数 ÷ 该期应填账户数(复用填报待办的口径) |
| 估值来源 | 该期有 `stock_price_snapshot` 的账户数 = 自动;其余 = 手填 |
| 汇率日期 | 该期 `fx_rate` 行对应期的 `period_end`;无外币账户时显示「无需换算」 |
| 关账时间 | `period.closed_at` |

未填时用 rust 色 + 列出前 3 个账户名(超出显示「等 N 个」),链到填报页。

### FR-322 · 资产负债表

六格直接取 `KpiSnapshot` 的现成字段,**但切片换成本期单期切片** ——
这样它与仪表盘的差异只来自"锚哪一期",满足 PRD 验收 1。

`emergencyFundMonths` 的分母改用 §3 定义的固定支出窗口(修 2.2 ②)。

对称条:两侧宽度 = `totalAssets / (totalAssets + totalLiabilities)`,同一比例尺。

### FR-323 · 瀑布

**截断轴**(PRD 已定):

```
values = [期初, 期初+收入, 期初+收入−支出, 期末]      // 各拐点的累计值
lo = min(values), hi = max(values)
pad = max((hi − lo) × 0.15, 1)                      // 15% 余量,且至少 1 元避免全等时除零
axisLo = lo − pad, axisHi = hi + pad
```

- 轴上显式标注 `轴自 X 起 · 截断轴`
- 段间连接线:上一段端点 y → 下一段起点 y(Chart.js 用 floating bar `[start,end]` +
  一条 `line` dataset 画连接;或纯 CSS 定位,与预览页一致)
- 某段为 0 → 不画零高度柱,连接线直通并显示 `—`

**恒等式校验**:

```
diff = (期末NW − 期初NW) − (收入 − 支出) − 投资损益
```

`|diff| ≤ 1`(元)视为闭合。不闭合时按已知原因排查并给出文案:
① 本期有账户首次出现 → 开账基线 = `openingBaseline(本期)`,差额应等于它
② 本期有账户归档/移出 → 同理
③ 都不匹配 → 显示原始差额 + 「原因未知,请反馈」。**不吞掉、不假装闭合。**

### FR-324 · 三列对照

**取期规则**(PRD 验收 3/4 的实现):

```java
prev = 已关账期中 period_start < asof 的最大一期        // 不是 asof − 1 个月:可能跳期
yoy  = 已关账期中 period_start = asof.minusYears(1)     // 严格同月;周度则同周锚
```

`prev` / `yoy` 任一为空 → 该列与对应 Δ 全部 `—`。

Δ 计算:金额类给 `绝对值 + %`;比率类给 `pp`。**分母为 0 或 null 时 Δ 显示 `—`**,
不显示 `∞` 也不显示 `100%`(这一条落单测 —— 新用户第一期必然踩到)。

### FR-325 · 集中度 / 流动性

```
share_i = |账户 i 期末净值| ÷ Σ|各账户期末净值|        // 取绝对值,否则负债账户会把分母做小
HHI     = Σ share_i²                                  // 0~1
Top1    = max(share_i)
Top3    = 前三大之和
平台集中 = 按 lens platform 维度聚合后的 max
```

**为什么分母用绝对值**:如果直接用净值求和,一个大额房贷会把分母压到接近 0,
HHI 直接爆到 1 —— 集中度就成了"有没有房贷"的函数。取绝对值后它衡量的是
"资产/负债规模的分散度",与直觉一致。**这条落单测**(造一个净资产接近 0 但资产分散的家庭)。

流动性分层:按 `Account.getLiquidity()` 三档 + `NA` 并入「不可动」;分母同上用绝对值。

### FR-326 · 归因

复用 `AttributionEngine`,输入换成「本期 vs 上期」两期切片。

必须排除的两类(PRD 验收 1/2):
- 本期首次出现的账户 → 其贡献 = 期末净值,但那是**资本纳入**,单列不进 Top
- 本期归档的账户 → 同理单列

排除逻辑复用 `openingBaseline` 的 `firstAppearingAccountIds`,不另写一套。

## 5 · 归档过滤的时间语义(2.2 ① 的修复)

```sql
-- 现状(FactMapper.xml:161)
AND a.archived_at IS NULL
-- 改为
AND (a.archived_at IS NULL OR a.archived_at > p.period_end)
```

**这是一个口径变更,会改变现有历史数字**(把归档账户的历史还回来),所以按纪律办:

1. 基线取已发布 tag **v1.9.4** 的 jar,采下报表页 + 仪表盘全部指标 × 6 个 range
2. 改完逐项比对:**只允许出现在"该家庭确实归档过账户"的期**;没归档过账户的家庭必须逐字不变
3. beta 有归档账户(账户列表里见过归档态)→ 能真实验证;prod 3 期需单独确认

**如果比对结果影响面超出预期**,退路是:v1.10 只在 `SealedPeriodService` 内部用新语义
(前两区正确),主切片保持旧语义,趋势区数字不动 —— 代价是两区口径不一致,
要在页面说明。**这个退路要不要用,等基线跑出来再定,不预先决定。**

## 6 · 仪表盘「资产收益」那一格(维护者第 1 点)

### 6.1 它为什么锚在上个月

不是疏忽,是 v1.6.30 修的一个 P0。`ClosedPeriodAnchorTest` 的注释记着当时的实测:

> 进行中的期典型状态是**余额已填、收支未录**(prod 2026-08 实测:21 条余额 / 0 条收支),
> 于是 `(期末 − 期初 − 净流入)` 里净流入 = 0,**把还没录的工资整块算成投资收益**

所以现在 `filingInProgress()` 时,标题会从「本月资产收益」换成「资产收益 2026-07」,
数值退回上一个已关账期。

### 6.2 按新定义应该怎么办

维护者的定义(仪表盘=实时本月)我完全认同,但这一格的问题**不是"锚错了期",
而是"月中原理上算不出来"**:

`投资损益 = ΔNW − 净流入`。月中净流入必然是**不完整**的(工资 15 号才到、支出还在陆续录),
而"本月收支已录完"这个信号**恰恰就是关账**。所以不存在"月中也能算准"的实现 ——
改成实时算,等于把 v1.6.30 那个 P0 原样放回去。

三个可选做法:

| | 做法 | 好 | 坏 |
|---|---|---|---|
| **A** | 保持现状(锚上期,标题换成「资产收益 2026-07」) | 数字永远是对的 | **违反两页分工** · 仪表盘上出现别的月份的数,用户容易当成本月 |
| **B** ← 推荐 | 进行中期显示**待定态**:「本月资产收益 · 待关账」+ 小字「关账后出数;上一封板期 +2.4% 见报表」 | 符合分工(仪表盘只说本月)· 不给错数 · 把"为什么没有"讲清楚 | 月中这一格没有数字可看 |
| **C** | 实时算本月,并标注「填报中 · 收支可能未录齐」 | 严格符合"实时本月" | **会显示明显错的数**(工资算成投资收益,月初尤其离谱)· 等于回退 P0 |

**推荐 B**,理由是:错的数字比没有数字伤害大得多 —— 这一格的读数直接影响"要不要调仓"。
而且 B 仍然满足"仪表盘只代表本月":它诚实地说"本月还没到能算的时候"。

**这条要你点头**:选 B 我就顺手在 v1.10 做掉(改动很小,一格文案 + 一处条件);
你要 C 我也照做,但会在页面上把"可能虚高"写明,并且 `ClosedPeriodAnchorTest`
需要相应放宽 —— 那条护栏现在正拦着这件事。

存量类指标(净资产/总资产/总负债/紧急储备)本来就是实时本月,不受影响。

## 7 · 兼容与迁移

- **无 schema 变更**、无迁移脚本。prod 3 期、beta 175 期都不需要动数据。
- 唯一的行为变更是 §5 的归档过滤语义 —— 按零差异基线流程验证后再合。
- 老浏览器 / 无 JS:三区结构是纯 HTML,瀑布与条形用 CSS 定位实现的部分可见;
  Chart.js 图缺失时不影响表格与 KPI 读数。
- 三币种:新增比率(资产负债率、储蓄率、HHI、Top1/Top3、分层占比)全部纳入
  `CurrencyInvarianceTest` 的属性级扫描 —— 不逐个补,扫"所有比值型 KPI"这个属性
  (v0.8 的教训:逐点补了三次都漏)。
