# 功能入口登记表 · 策略与判据

> 机器可读的登记表在 [`scripts/entry-points.json`](../scripts/entry-points.json)(**单一事实来源**),
> 检查器在 [`scripts/entry-points-check.cjs`](../scripts/entry-points-check.cjs),守护 `v1623-ENTRY-VIS`。
> 本文只写**为什么**和**怎么判**,不重复罗列条目(避免两处清单漂移)。

## 为什么要有这个东西

v1.6.23 之前踩了一次:用户报「券商自动对接(富途 / 老虎)的入口是不是上次优化 UI 丢了?」

查证结果 —— **功能一行没丢**。是 v1.6「UED 批次5 · affordance 与收纳」把账户页 PC 行内那个可见的
「券商」按钮,按「行内按钮太多」的**视觉密度**一刀切收进了没有文字的 `⋯` 更多操作菜单,
和「归档此账户 / 导出账本 CSV / 账户间划转」并列。

对用户来说,**「还在但找不到」和「没了」没有区别**。

更值得记的是:当时**已经有一条守护 `v15-ENTRY-1 · 券商入口在账户页`,而它一直是 PASS**。因为它断言的是

```bash
grep -q '/broker(id=' accounts/index.html
```

—— **「模板里有这个字符串」**。入口被埋进折叠菜单、变成两次点击、图标没有文字,它一条都测不到。
`grep` 类守护**结构上**抓不到「东西还在但用户找不到」。

顺带扫出第二个、比上面更严重的:**`/reports/refinance` 提前还贷决策器全站零入口** ——
页面从 v0.4 就在,README 与落地页都在宣传这个能力,但**没有任何模板链接指过去**
(`git log -S '/reports/refinance'` 只命中它自己的 form action),只能手敲 URL;
而 dashboard 洞察条还会提示「可考虑加速偿还」却不给去处。已补两处入口。

## 两档可见层级

| 层级 | 含义 | 适用 |
|---|---|---|
| `obvious` **一眼可见** | 进入该页面无需任何展开 / 悬停 / 点击就能看到 | **能力入口** —— 通往一整套有自己页面或流程的功能(券商同步、持仓管理、AI 截图填报、提前还贷决策器、资产打标…) |
| `collapsible` 允许收纳 | 可以放进 `⋯` / `details` | **低频维护动作** —— 归档、恢复、删除、导出 CSV |

**判据不是"按钮多不多",是"这一项是能力入口还是维护动作"。** 上次的错就是按数量收纳、把两类混在一起。

## 运行时判据(三条同时成立才算"一眼可见")

对登记表里每条 `obvious`,在 PC 1440×900 与移动 390×844 两端渲染真页面后断言:

1. **有面积** —— `getBoundingClientRect()` 的宽高 > 1(排除 `display:none` 的另一端布局副本);
2. **命中自己** —— `elementFromPoint(中心点)` 追到它本身或其子孙(排除被别的元素压住,见 v1.6.14 的教训);
3. **不在折叠容器内** —— 不在未展开的 `<details>`,也不在 `.row-more-pop`(`⋯` 菜单)里。

> 注意实现细节:命中测试前必须先 `scrollIntoView` 把元素滚进视口 —— `elementFromPoint` 是**视口坐标**,
> 元素在视口外一律返回 `null`,会被误判成"被遮挡"。(第一版探针就是这么误报的。)

入口在二级页时用 `pageFrom.clickHrefMatches` 表达层级(例:持仓管理在账户**详情**页,
从账户列表点「流水档案」进去),而不是把二级页的入口硬写成一级页 —— 那样会制造误报。

## 什么时候必须过这一关

- **任何"收纳 / 精简 / 去杂"类 UI 改动**:diff 里每一个被移除、被移动、或被塞进折叠容器的 `th:href`,
  逐个确认它在别处仍然一眼可见。上次 8 个里 7 个安全、1 个出事 —— 靠人眼扫 diff 是碰运气。
- **新增能力**:同时在 `scripts/entry-points.json` 登记,否则下次别人"优化"时没有任何东西拦着。
- 跑一次:`node scripts/entry-points-check.cjs`(退出码 0 通过 / 1 有入口不可见 / 2 环境不具备)。
