## 4 · 发现清单

### P0 · 所有 KPI 锚定在未关账期上,收益类指标被系统性高估

`FactViewServiceImpl.loadDefault()` 的窗口是 `[本月1号 − 11 个月, 本月1号]`,而 `queryBase`
**不过滤 period.status**。于是 2026-08(OPEN)进入切片并成为 `lastPeriodId` —— 全站 KPI 都锚在它上面。

prod 的 2026-08 现在是这个状态:**21 条余额快照已填,收支一条没填**。后果:

- **本月资产收益 = +0.99%**:分子 `9,322,669.16 − 9,231,554.91 − 0 = 91,114.25`,
  这 9.1 万里**一分钱工资/支出都没扣**,因为 8 月的收支还没录。等用户把 8 月收支填上,这个数会立刻变。
  也就是说:**账期填报中途,「本月资产收益」把"还没录的收支"整个算成了投资收益。**
- **家庭 XIRR 的终值**用的是这个未关账期的净资产,同样偏高。
- 缺快照的账户还会**结转上期余额**(`COALESCE(ps.end_balance, 最近一期)`),所以未关账期永远"看起来是满的",
  用户没有任何提示知道这一期还没填完。

这不是算错,是**锚点选错**:一个只填了一半的账期不该驱动收益率 KPI。
建议:收益类指标(本月资产收益 / XIRR / TWR / 钱赚)锚到**最新 CLOSED 期**;
存量类(净资产/总资产/总负债)可以继续用最新期,但页面要标注「2026-08 填报中」。

### P0 · 总资产口径文案漏了 3 个资产类型

`dashboard/_region.html:178` 与 `checkup/family.html:43`:

> 「CASH + STOCK + WEALTH + PROPERTY 类型合计,不含 LOAN。」

实际代码是 `accountClass == ASSET`,即**除 LOAN 外全部**,包含 **CRYPTO / METAL / INSURANCE**。
beta 上就能看到实证:总资产 ¥3,915,769 里含加密 ¥438,996 + 贵金属 ¥114,140 + 保险 ¥82,400 = ¥635,536,
而 tooltip 说这三类不在里面。prod 目前没有这三类账户所以数字没错,但**用户一加金/币/保险账户,口径说明立刻是错的**。

这正是 memory `feedback_enum_add_sweep` 记的那类坑:加 AccountType 枚举时编译器抓不到模板里的硬编码类型串。

### P1 · 「当期储蓄率 96.66%」不是储蓄率

分子分母来自 2026-07:收入取了 cash_flow 的 ¥654,542.55。那 65 万大概率是投资/划转类流水记成了 INCOME,
不是家庭劳动收入;支出只有 ¥21,837。算出来 96.66% 的"储蓄率"没有解释力。

根因有两层:① 用户 7 月把 PMC 收入填成了 0,触发回落;② `cash_flow.INCOME` 里混了非收入性质的流水。
逻辑本身自洽(回落规则是对的),但**这个指标在当前数据下不该展示**,或至少要提示"本期收入取自流水,可能含非收入项"。

### P1 · 紧急储备的分母口径与 PRD 不符,且样本只有 3 期

- PRD `v0.1.md:839` 写的是 `avg12(ExternalExpense)`(12 期均);
  代码是「取最近至多 12 条 PMC 行,除以**实际行数**」。prod 只有 3 期 → 除以 3。
  除以实际期数比除以 12 更保守(不会低估月均支出),**代码比 PRD 合理**,但 PRD 没跟上。
- 另外 `findFamilyAggregateRecent` **不受 12 个月窗口约束**,理论上可以取到窗口外的历史 PMC 行。
  prod 数据少没暴露,家庭有填报断档时会混期。
- 18.3 月这个结论建立在 3 个月的支出样本上,统计意义弱,页面没有任何"样本不足"提示
  (reports 有「已填 3/12 月」,dashboard/checkup 的紧急储备卡没有)。

### P1 · 流动资产定义:PRD 与代码分叉

PRD `v0.1.md:839` 分子写 `CASH/WEALTH`(WEALTH 整类计入);
PRD `v0.1.md:1625` 又写「流动资产 = LIQUID(现金类)」;
`FactViewServiceImpl.kpis()` 的代码注释写「PRD § 5.11 流动资产 = LIQUID(**仅 CASH**);WEALTH 是 SEMI_LIQUID 不计入」;
**实际行为**是 `product_category.liquidity_class` 优先、缺省才按类型兜底 —— 货币基金类 WEALTH **计入**。

四处说法三个版本。实际行为(v0.3.3 精细化)是最合理的那个,面向用户的 tooltip
(「CASH 类型 + 货币基金等 LIQUID 类目合计」)也是对的,**错的是 PRD 两处和那条代码注释**。

### P2 · XIRR 与基准并排展示,但两者时间基不同

页面呈现是「家庭 XIRR·含收入 0.79% vs 基准 6.13%」。
0.79% 是 **4 期累计**(`periodCount < 12` 走 `cumulativeReturn`,明确非年化),6.13% 是**年化**。
两个数并排放,用户会直接相减得出"落后 5.34pp"的错误结论。

内部算差值时其实是对的(`displayedDiffPercentPoints` 在不满 12 期时会把年化基准折算到窗口),
但**展示层没有把这层折算告诉用户**。v1.6.29 已经给 XIRR 的 tooltip 加了「(不满 12 期 · 累计口径非年化)」,
基准那一侧还没有对应说明。

### P2 · checkup 的 XIRR tooltip 没跟上 v1.6.29

v1.6.29 重写了 reports 页 familyXirr 的 tooltip(加了「与「人赚」同口径」、开账基线、年化/累计标注),
checkup 页仍在用旧的 `familyXirrCalc(ccy, netWorth, xirr)` 短格式。同一个指标两页两种解释。

### P1 · goals 页「储蓄率」目标进度在 prod 上恒为 0%

存在第二份 `savingsRate` 实现:`FactViewServiceImpl.savingsRate()` —— 只读 `cash_flow`、
锚在 `lastPeriodId`(= 未关账期)。它**不是死代码**,`GoalMetricEvaluator:35` 在用它算
`SAVINGS_RATE` 类目标的当前值:

```java
BigDecimal savings = pct(factView.savingsRate(slice));   // → case SAVINGS_RATE -> nz(savingsRatePct)
```

prod 的 2026-08 没有 cash_flow 收入 → `income.signum()==0` → 返回 `null` → `nz()` 兜成 **0**。
**任何"储蓄率达到 X%"的家庭目标,进度都会显示 0%。**

而 reports 页用的是 `householdCashflowService.currentSavingsRate()`(PMC 优先 + cash_flow 回落,
取最近有 PMC 的那一期)= 96.66%。同一个"储蓄率"概念,goals 显示 0、reports 显示 96.66%。

### P2 · 6 月大幅回撤后 7 月几乎等额收复,建议核一眼 6 月估值

逐期投资损益(`ΔNW − 外部净流入(含开账基线)`):

| 期 | ΔNW | 外部净流入 | 投资损益 PnL |
|---|---|---|---|
| 2026-06 | −239,238.18 | 131,184.34 | **−370,422.52** |
| 2026-07 | +984,695.43 | 632,705.55 | **+351,989.88** |
| 2026-08(未关账) | +91,114.25 | 0.00 | +91,114.25 |
| 合计 | | | **+72,681.61** ← 与「钱赚」完全一致 ✓ |

6 月 −37 万、7 月 +35.2 万,接近等额反转(差 1.8 万)。这在真实行情下是可能的,
但也符合"6 月部分账户余额未按当月市值更新、7 月一次性补回"的形态。
**不是代码问题**,合计数也自洽;只建议瞄一眼 6 月各账户余额是否为当月真实市值 —— 若是补录,
6/7 两期的月度收益率和 TWR 分段会失真(合计不受影响)。

## 6 · 修复期间新发现(报告初稿没有 · 渲染验收才暴露)

### 6.1 同名指标跨页两个数:体检 −0.21% vs 报表 +1.11%

把收益类改锚已关账期后,在 beta 上复采页面才发现:体检页窗口(锚进行中期 `−11 月`)里只剩
**11** 个已关账期 → 走「不满 12 期」的累计口径;报表页(自 v0.5.5 起锚最新已关账期)拿得到 **12** 个 → 走年化。
同一个「家庭 XIRR」两页给出 −0.21% 与 +1.11%,还分别走了两条不同分支。

根因是**各页窗口宽度本就不一致**(报表锚已关账期 / 仪表盘 `−12 月` / 体检 `−11 月`),属既存问题,
但被本次改动放大成「连分支都不同」。两处一起改才闭合:`returnPeriodIds()` 统一截到最近 ≤12 个已关账期,
体检页在填报中时窗口回退 12 个月。改完三页收敛:XIRR 均 **+1.11%**(12 期 · 年化 · 终值同为
2026-07 的 ¥4,208,586),TWR 均 **−6.55%**。

### 6.2 体检页「本年累计损益」负号被吃掉 —— 亏损显示成盈利

模板对负数给的前缀是空串、又取了绝对值:

```
(cumulativeYtdPnl.signum() >= 0 ? '+' : '') + '¥' + formatDecimal(cumulativeYtdPnl.abs(), …)
```

于是 **−¥1,580,715 渲染成「¥1,580,715」**,只有颜色类透出亏损,数字本身读起来是盈利
(同文件「本月资产收益」用的 `'+¥' : '−¥'` 才是对的)。

**这条是肉眼看渲染结果发现的** —— 表达式语法合法、指标值也算对了,错在展示,grep 类守护与单测都抓不到;
本报告初稿只比对了 tooltip 里的算式串,没跟卡片上的数字互相对照,所以漏了。
全站扫了 12 处同类写法,只此 1 处同时取了绝对值 → 只此 1 处是缺陷,已修。

### 6.3 排版:口径期标注初版在移动端溢出

初版 KPI 标题「资产收益 · 2026-07」在体检页移动端(容器 145px)实测 **154px 溢出**。
在浏览器里逐个量候选串后改用「资产收益 2026-07」= 145px 正好放下,且保留空格 →
字号放大时换行而非溢出。PC/移动 × 仪表盘/体检 四处复测 `scrollWidth == clientWidth`,均无溢出。
