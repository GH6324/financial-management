# v1.9 · 自动版本查询(知道自己落后了,以及升级安不安全)

> 状态:**待评审**(PRD + preview)· 目标版本 `app.version=1.9.0`
> 范围:**只做「查」,不做「改」**。一键更新 / 一键回滚不在本版,理由见 §7。

---

## 1 · 要解决的真问题

自部署工具有一个结构性缺陷:**用户不知道自己落后了。**

维护者(我)知道,因为发版的人是我。但这个项目是开源自部署的,别人装完之后:

- 没有任何地方告诉他「你跑的是 v1.6.4,现在最新 v1.9.0,你落后 14 个版本」
- 他也不知道**这中间有没有修掉他正在踩的 bug** —— 比如 v1.8.1 修的那个「登录页停留太久后提交甩一个报错页」,他很可能以为是自己部署坏了
- 想升级的时候,他不知道**升级安不安全**:这中间有没有 DB 迁移?我们的红线是「回滚只回 jar 不回 DB」,所以「有没有迁移」直接决定他能不能安全回退

issue #9 那位用户就是活例子:他装了之后自己摸索,反馈的第一条是功能诉求,但从对话里能看出他并不清楚自己那套跑的是哪个版本、离最新差多少。

**这一版只解决「知道」,不解决「自动帮你改」。** 知道之后怎么升级,仍然是他自己敲两行命令。

## 2 · 非目标(明确不做,别提议)

- **不做一键更新** —— 见 §7,前置条件没备齐,而且这是把「远程代码落到本机并执行」产品化,安全设计要单独一版
- **不做一键回滚** —— 同上,虽然素材已经有了(`app.jar.prev` + `deploy/rollback.sh`)
- **不做弹窗 / toast / 红点角标** —— 这个项目的硬约束是「每月 10 分钟、不打扰」。催更式提醒直接违背它
- **不做遥测** —— 不上报版本号、不上报实例标识、不上报任何用户数据。见 FR-303
- **不做「自动下载」** —— 连预下载都不做,本版一个字节的产物都不落盘

## 3 · 功能需求

### FR-300 · 后台定时查一次,不在渲染路径上等网络

系统每天查一次 GitHub Releases,把结果缓存进 `family_runtime_config`。

- **页面渲染永不等网络。** 页面只读缓存里那条记录。GitHub 慢或不通都不影响任何一次点击
- 缓存 TTL **24 小时**;管理页有「立即检查」按钮可以强制刷新一次
- 查不到就保持上一次的结果,并记下「上次检查时间 / 上次失败原因」
- **一次都没查成功过**(比如内网部署、GitHub 不通)→ 页面**什么都不显示**,不显示「检查失败」这种对普通家人毫无意义的红字。只在管理页那张卡里说明

> **为什么强调这条:** 这个项目已经有两条对外调用(汇率、股价),都踩过同一个坑 —— 外部接口挂了要能降级、不能拖着页面。而且我们有条纪律叫「连通性探针不能当可用性判据」,所以这里的判据是**上一次成功的结果**,不是「现在能不能连上 GitHub」。

### FR-301 · 显示在哪:管理页给全貌,`管理` tab 给一个安静的圆点

**这一条是本版最需要评审的取舍。** 先说约束:

`member.role_label` 是自由文本(实际值:丈夫 / 妻子 / foo),**项目里没有「管理员」角色**,`/admin` 也没做权限区分 —— 全家每个人都能进。所以「有新版」的提示放在哪,直接决定会不会吵到非技术的家人。

| 放哪 | 发现得到 | 会不会吵到家人 |
|---|---|---|
| 只放管理页 | 差(维护者可能几个月不进管理页) | 不会 |
| 版本徽记(nav 里 `v1.9.0` 那个)加圆点 | 好 | **会** —— 妻子看到那个点,不知道该做什么,也没法做 |
| **`管理` tab 加圆点 + 管理页给全貌** | 好 | 基本不会 —— 「管理」本来就是维护者的地盘 |
| 引入真正的「维护者」角色,按角色显示 | 好 | 不会 |

**选第三个。** 第四个是架构上更正的答案,但为了一个提示引入角色体系是本末倒置 —— 记进「以后要做」。

具体形态:

- `管理` tab 文字右上角一个 **6px 描边圆点**(brass 色,不是红色 —— 这不是告警)
- 圆点只在「查到有新版」时出现;点进管理页看完之后**不消失**(它反映的是事实状态,不是未读消息)
- 管理页顶部「运行中」那张卡里,把现在的单行版本号扩成一张**版本卡**

### FR-302 · 版本卡要回答三个问题

维护者看这张卡,是为了决定「现在要不要升」。所以卡上必须回答:

**① 我落后多少**

```
当前 v1.6.4        最新 v1.9.0        落后 14 个版本
```

**② 这中间修了什么 / 加了什么**

列出中间每个版本的**一行主题**(取自 Release 标题),最多列最近 5 个,更早的折叠成「另有 N 个更早版本」。每行链到对应 Release 页。

**③ 升级安不安全 —— 这一格是我们和别人不一样的地方**

明确标出**这中间有没有 DB 迁移**:

- **无迁移** → 标「无 schema 变更 · 可随时回退到当前版本」
- **有迁移** → 标「含 N 个 DB 迁移(V53…)· 回滚只回 jar 不回 DB」,并链到我们的升级说明

> **技术上已验证可行**(写 PRD 时实测):GitHub 的 compare API 能直接给出两个 tag 之间的改动文件清单,
> `v1.7.1...v1.8.0` 精确报出 `db/migration/V53__expense_entry_mode.sql`。所以这一格不是猜的。
> 拿不到(API 失败 / 文件清单被截断)→ 显示「无法确定,升级前请自行核对 db/migration」,**不假装没有**。

**④ 怎么升(给命令,不给按钮)**

两行命令都给出来,因为我们没法可靠判断对方是哪种装法:

```
git pull && bash deploy/docker-up.sh     # Docker
git pull && bash deploy/deploy.sh        # 直装
```

### FR-303 · 隐私:必须说清、必须能关

向 GitHub 发请求会把**服务器 IP 暴露给 GitHub**。对一个「数据只在自己服务器上」为卖点的工具,这件事必须摆到明面:

- 管理页那张卡上直接写明:**会做什么**(每天一次 GET `api.github.com`)、**发出去什么**(只有这个请求本身,不带版本号、不带实例标识、不带任何用户数据)、**能不能关**(能)
- 管理页给开关:**自动检查更新** 开 / 关,存 `family_runtime_config`
- 关掉之后:不再有任何后台请求,圆点消失,卡片退化成「只显示当前版本 + 一个手动检查按钮」
- **默认开。** 取舍在下面

> **默认开还是关?** 默认关 → 绝大多数人永远不知道有更新,这个功能等于没做。默认开 → 一天一个
> 不带任何身份信息的 GET。我选默认开,代价是必须把「发了什么」写在用户眼前,而不是埋进文档。
> 反对意见我接受评审时再讨论。

### FR-304 · 只认正式版

- 跳过 draft 和 prerelease
- 版本比较按 `vX.Y.Z` 三段数字;解析不了的 tag 直接忽略,不猜
- 只信**本仓库自己的** releases,仓库地址写死在代码里,不做成可配置项(可配置 = 可被指向任意仓库)

## 4 · 兼容与降级

| 情况 | 行为 |
|---|---|
| 从旧版升上来 | 新增一个 KV 键 + 一张卡。旧数据零影响,无迁移 |
| GitHub 不通 / 内网部署 | 页面什么都不显示,只有管理页卡里说明。**不报错、不阻塞** |
| Docker 装 | 一样能用(`app.version` 来自镜像),命令那格两种都给 |
| 关掉开关 | 零后台请求 |
| 自己 fork 改过版本号 | 解析不了的 tag 忽略;当前版本比"最新"还新 → 显示「已是最新」不显示落后 |

## 5 · 验收

1. **不通也要好**:把出网掐掉,所有页面照常渲染,管理页卡片显示「上次检查:失败(原因)」,`管理` tab 无圆点
2. **一次都没成功过**:全站看不到任何与更新有关的字样(除管理页那张卡)
3. **有新版**:`管理` tab 出现圆点;卡片列出落后数、中间版本主题、**迁移提示**、两行升级命令
4. **已是最新**:卡片显示「已是最新」,无圆点
5. **迁移判定准**:构造 `v1.7.1 → v1.8.0`(真实含 V53)必须标出含迁移;`v1.8.0 → v1.8.1`(真实无迁移)必须标「无 schema 变更」
6. **关掉开关**:无后台请求(看日志)、无圆点
7. **渲染不等网络**:人为把 GitHub 调用延迟到 10s,页面响应时间不受影响
8. **每天只查一次**:连续刷 20 次管理页,只有第一次(或 TTL 过期后)真的出网

## 7 · 为什么这版不做一键更新 / 一键回滚

调研过 sub2api 的做法(它的自更新只在「脚本装 + systemd」这条路上有,Docker 那条没有)。它的核心招数是:优雅退出,靠 systemd `Restart=always` 自动拉起 —— 零 sudo、零进程管理。

我们照搬不了,有四道坎:

| # | 我们的现状 | 卡在哪 |
|---|---|---|
| 1 | unit 是 `Restart=on-failure` | 退出码 0 systemd 不会拉起。那招直接失效 |
| 2 | jar 是 `root:root 0644`,app 跑 `finance` 用户 | 进程**无权替换自己的 jar**。放开权限等于「被入侵的应用可以改自己的可执行文件」 |
| 3 | Release **没有 jar 资产**,CI 只出 Docker 镜像 | 一键更新得有东西可下 |
| 4 | 我们有 DB 迁移,回滚只回 jar 不回 DB | 跨迁移回滚安不安全要逐版判断 |

第 2 条有干净解法(应用只写一个标记文件,root 的 systemd oneshot 单元去做替换和重启,权限隔离不破),但那是另一版的事。

**所以本版的边界是:把「知道」做到位,「改」留给后面。** 而且「知道有没有迁移」这件事本身就是后续做回滚的前提 —— 先把它做出来。
