# v1.22 · 导入确认页:从「我替你删了」改成「我给建议,你拍板」

> 状态:**待评审**
> 目标版本:app.version = 1.22.0(写 PRD 时即 bump)
> 来源:维护者 2026-09-15 原话(见 §2)

---

## 0 · 这一版在解决什么

**背景与现状。** v1.21 的账单导入确认页把行分成五个桶,其中一个叫「**已剔除**」。
那个词描述的是**系统已经执行完的动作** —— 页面告诉用户「这 92 笔我删了,你可以捞回来」。

三个具体问题:

1. **系统不该替用户做删除决定。** 剔除的判据是启发式的(退款 / 划转 / 交易关闭 / 关键字),
   它会错。而「剔错了」的后果是**支出少算**,用户不会立刻发现 —— 一个不可靠的判断,
   却用了一个最不可逆的动词。
2. **有些行连捞都捞不回来。** 金额 ≤ 0 的行在页面上写着「不能捞」,因为 `cash_flow`
   上有 `CHECK(amount > 0)`。用户看到的是一个**被系统单方面否决、且不给申诉**的行,
   而他并不知道那是数据库约束。
3. **「已存在」那一桶只读。** 这些笔上次导过,但**上次可能就归错了分类或落错了账户**。
   现在要改只能去填报页一条条找,或者整批撤销重导。

**服务谁**:维护者本人 + 自建用户里会用账单导入的那部分。都是**已经在用 v1.21 导入**的人。

**主推动力**:**把导入确认页的决策权还给用户**。
不是「加功能」—— 是把一个已经做出的、越权的决定收回来。
0 元/负数放开、已存在可编辑,都是这条主线的推论,不是另外两件事。

**本版新引入的名词**:

| 名词 | 定义 |
|---|---|
| **不建议录入** | 系统判断这一笔不像家庭消费,**默认不勾**,并逐行给出理由。取代 v1.21 的「已剔除」 |
| **未录入** | 提交时没被勾上的行。它是一个**结果状态**,不是操作 —— 没有任何东西被删除,只是没被写进账 |

既有名词(性质 / 消费分类 / 口径 A/B / affects_balance)单一定义在 `AGENTS.md` 与 `prd/v1.21.md`。

## 1 · 调研

**不适用 · 无外部依赖。** 本版不接任何新的外部平台或协议,改的是自己页面上的决策模型。

唯一沾边的是渠道账单里负金额行的含义(支付宝/微信的退款冲正会写成负数),
这一点在 v1.21 解析器里已经处理过,本版只是改变对它的**处置**。

## 2 · 用户故事

维护者原话(2026-09-15):

> 1.目前支出导入页面, "已删除" 指的是 你直接做主删掉的? 这个是不不合适...而且 怎么还有"不能捞"的数据行...
> a.已删除这个页面 也增加全选能力
> b.建议的交互是 你怎么体现不建议导入呢, 比如导入了200行: 你默认选中了180行, 剩下20行是你识别到不建议录入的, 你逐行给出原因即可; 用户可以采纳你的建议 就对180行进行录入, 也可以单独校准其中某几行; 剩余的 未被用户采纳的行 进入"未录入", 不能叫"已删除"
> c.另外 0元单 要允许导入;
> 2.为什么"已存在"的页面行只能看? 这里要允许用户调整/含批量调整他的品类/归属/打标/账户 这些的呀!

**原话里的设计线索**:

- 「**你直接做主**」→ 问题不在文案,在**谁拍板**。改名不够,得把「勾/不勾」这个动作交出去。
- 「**你逐行给出原因即可**」→ 系统的价值是**解释**,不是**执行**。理由必须逐行、具体,
  不能是一个笼统的桶标题。
- 「**也可以单独校准其中某几行**」→ 用户要的是「采纳大部分 + 推翻个别」,
  所以全选/反选/按原因分组全选都得有。
- 「**剩余的未被用户采纳的行**」→ 「未录入」是**提交之后**的说法。
  确认页上它们不叫这个,确认页上它们只是「没勾」。

三个待决点已在评审前问过维护者,结论:

| 问题 | 维护者选择 |
|---|---|
| 负金额行怎么办 | **也允许录入,原样记负数** |
| 「已存在」改账户时余额 | **同步把余额从旧账户挪到新账户** |
| 「归属 / 打标」指什么 | **就是分类 + 账户**(归属跟账户走) |

### 关键文案

这一版的文案本身就是功能 —— 「系统在建议」和「系统已执行」的区别几乎全落在措辞上。

| 位置 | 文案 |
|---|---|
| 页签 | `不建议录入 20` / `点开只看这些` |
| 不建议行的理由列 | `退款` · `交易关闭` · `不计收支(划转)` · `收支方向认不出` · `0 元` · `负数(退款冲正)` |
| 0 元行悬浮说明 | 「0 元通常是全额优惠或积分抵扣。录进来只多一笔记录,不影响金额。」 |
| 负数行悬浮说明 | 「这是一笔退款冲正。勾上会**原样记成负数**,当月支出会相应**减少** —— 如果对应的原单也在这批里,两笔一起录才对得上。」 |
| 表头勾 | `全选`(作用于当前筛选出来的行,不是全表 —— 筛了「不建议录入」时就是全选这 20 行) |
| 提交按钮旁 | `录入 180 笔 · 未录入 20 笔` |
| 结果页 | 「录入了 180 笔 · 未录入 20 笔(**没有被删除,只是这次没记进账**,重新导同一份文件还能再选)」 |
| 已存在桶顶部 | 「这些笔上次导过,**这次不会重复记**。但可以在这里**修正上次归错的分类或落错的账户** —— 改的是已经入账的那一笔。」 |
| 已存在 · 改账户提示 | 「改账户会**同时把余额挪过去**(旧账户加回、新账户扣掉)—— 只对当初勾了「落到账户」的笔生效。」 |
| 已存在 · 已关账行 | 「这笔在 2026-08,那一期已关账 —— 分类可以改,账户不行(改账户要动已关账的余额)。」 |

## 4 · 不做什么

**非目标**:

- **不做「未录入」的持久化清单。** 未录入只是「这次没勾」,不落库、不建表。
  用户想再看就重新传同一份文件 —— 去重逻辑保证不会重复记。
  (做成可查清单要新表 + 生命周期管理,而它解决的问题「我上次没录哪些」重传即可回答。)
- **不做退款与原单的自动配对。** 负数行原样记,不去找它对应的那笔消费做核销。
- **不做「强制再导」**(FR-601)。
- **不改「性质」的可编辑性。** 已存在桶只开分类 + 账户;把一笔从「消费」改成「还贷」
  会直接动储蓄率和负债口径,那是另一个题目(见 §11 的后续项)。

**撞上「刻意不做」清单的**:

- 「逐笔流水账」「消费品类细化」—— v1.21 已经就这两条做过判断并例外(见 `prd/v1.21.md` §4),
  本版**不扩大**那个例外:不新增分类维度、不新增标签体系,只是把已有的决策权交还用户。
- 「银行账单 OCR」—— 不碰,本版只处理已解析出来的行。

## 6 · 存量影响

| 维度 | 这一版的影响 |
|---|---|
| **schema** | **有迁移 V60**:`DROP CHECK ck_cash_flow_amount`(放宽,不是收紧)。既有行全部 > 0,天然满足放宽后的无约束。**只放宽不改数据** |
| **口径** | **有变更**,见下 |
| **UI** | **会变** —— 确认页是这一版的主体。但**没用过导入的用户看不到任何变化**(确认页只在传了账单之后才出现) |

### 口径变更声明

**改的是什么**:`cash_flow.amount` 的取值域从 `> 0` 放宽到**无约束**(可以是 0 或负数),
并且导入路径**允许写入 0 和负数的 EXPENSE 行**。

**旧数据会不会变**:**不会**。V60 只 DROP 约束,不 UPDATE 任何行。
历史上每一笔支出仍然是正数,所有历史指标逐分不变。

**新数据带来的影响**(这是维护者明确选择「原样记负数」之后必须接受的):

| 受影响的地方 | 会怎样 | 是对还是错 |
|---|---|---|
| 家庭消费合计(口径 A) | 按**代数和**算,负数行会让当月支出**变小** | **对**。退款确实应该抵扣当月支出 |
| 账户余额(`applyDeltaToBalance`) | 支出走 `amt.negate()`,负金额 → 余额**加回** | **对**。退款的钱确实回到了账户 |
| 储蓄率 | 支出变小 → 储蓄率**变高** | **对** |
| 账户外部流出(口径 B · NAV/XIRR) | 同上,负流出 = 流入 | **对** |
| **支出构成饼图** | 某一组的合计可能 **≤ 0**(退款多于消费),而**饼图画不了负扇形** | **需要专门处理**,见下 |
| 「导入 N 笔 · 合计 ¥X」 | 合计按代数和,可能明显小于账单总额 | 需要**说明**,否则用户以为少导了 |

**饼图的处理**(这是本版唯一一处需要新规则的地方):

- 分组合计 **> 0** → 照常进饼图
- 分组合计 **≤ 0** → **不进饼图**,在图例下方单独列一行:
  「餐饮美食 −¥120.00(本组退款多于消费,不计入构成占比)」
- **总额仍按代数和**,不因为剔出了负组就变大 —— 否则「各组加起来 ≠ 总额」

不许用绝对值凑扇形:那会把一笔退款画成一笔消费,是**骗人**。

**零差异基线**:基线取 **tag v1.21.2**(已发布),在不引入任何 0/负数行的前提下,
逐期比对 家庭消费合计 / 储蓄率 / 支出构成各组金额 —— 必须**逐分相等**。
分水岭一出差异就停下查因(`feedback_metric_refactor_baseline`)。

**调用方清单**:`amount` 的正数假设可能散落在多处(`signum() <= 0` 之类的早退)。
靠人列必漏 → 落 grep 护栏扫全部 `signum()` / `compareTo(ZERO)` 判断,逐个表态。

## 7 · 开关与默认值

| 开关 | 默认值 | 关掉时的行为 |
|---|---|---|
| 无新开关 | — | — |

**为什么这一版不加开关**:模板的规矩是「改变既有口径或既有视图的能力,默认必须关」。
这一版看似动了口径(允许负数),但:

- **默认行为逐字不变** —— 0 元和负数行**默认不勾**,用户什么都不做的话,
  导入结果与 v1.21.2 完全一致(那些行本来就不会进账);
- 口径变化只在用户**主动勾选**一个负数行之后才发生,而那是他刚刚在页面上做的显式决定,
  不是我们替他改了默认视图。

**换句话说:勾选框本身就是开关,粒度还更细 —— 逐笔。**

「已存在可编辑」同理:不点就什么都不变。

## 9 · 失败模式(pre-mortem)

**① 负数行让某处静默算错。**
最可能的形态:某段代码假设支出恒正,写了 `if (amt.signum() <= 0) continue;` 或者用
`abs()` 做展示。前者**静默少算**,后者**把退款画成消费**。两者都不报错。
→ **怎么发现**:grep 护栏扫全部符号判断并要求逐个表态;零差异基线比对;
构成图专门加一条「负组不进饼图但进总额」的断言。

**② 改「已存在」的账户把余额挪错方向。**
旧账户该 `+amt`、新账户该 `-amt`,写反了余额会错两倍,而且**不报错**。
负债账户存的是负数,方向更容易想反。
→ **怎么发现**:e2e 主线走一次「改账户 → 两个账户余额各自核对」,含负债账户。

**③ 改了已关账账期的余额。**
「已存在」的笔可能落在别的账期,甚至已关账的期 —— 去重范围是**整个家庭**,不限当期。
改它的账户会去动一个已经关账的 `period_snapshot`,那是用户核对过并封存的数字。
→ **怎么发现**:FR-600 在服务端硬拦(不只是前端 disabled),e2e 断言「已关账期的行改账户被拒」。

**④ 「全选」在筛选状态下选了看不见的行。**
用户筛到「不建议录入 20 行」点全选,如果实现成「选中全表 200 行」,
他会在毫不知情的情况下把 180 行的默认状态一起改掉。
→ **怎么发现**:qa-run 钉住「全选作用于当前可见行」;真机点一次。

**⑤ 文案改了、模型没改。**
最可能的偷懒形态:把「已剔除」改名成「不建议录入」,底下还是 `drop`/`restore` 那套。
那样用户第一次点「全选」就会发现两个桶的行为不一致。
→ **怎么发现**:护栏断言 `drop`/`restore` 这两个参数名**已从代码里消失**,
统一成一个 `include` 列表。

## 11 · 回滚与关闭

**关开关够不够**:本版无开关,但**不需要**开关式回滚 ——
用户不勾 0/负数行、不点已存在的编辑,行为就与 v1.21.2 一致。

**回滚 jar**:
- 确认页 UI 立刻回到 v1.21.2 的剔除/捞回模型 —— **可以接受**,没有数据损坏。
- **但**:如果回滚前已经录入过 0 或负数的行,老 jar 读到它们时**不会报错**
  (读路径没有正数假设),只是确认页的模型退回去。
- V60 **不回滚**(项目惯例:回滚只回 jar 不回 DB)。放宽约束对老 jar 无害 ——
  老 jar 本来就只写正数。

**已存在编辑的回滚**:改分类/改账户都是对既有行的 UPDATE,**没有独立的撤销入口**。
如果改错了,路径是再改回来(页面还在)或者去填报页改。
这一点要在 PRD 评审时确认是否够 —— 我的判断是够:
