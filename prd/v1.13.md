## 0 · 这一版在解决什么

表面需求是「再加一家:火山云」。但**照现在的模型加不进去** —— 加进去也是错的。

现在配置里那个字段叫 `llm_primary_vendor`,值是 `qwen` / `deepseek`。这一个词同时背了三件事:

| 它其实在决定 | 现在的取值 |
|---|---|
| **去哪调**(端点 + 用哪把 key) | qwen → `dashscope.aliyuncs.com` · deepseek → `api.deepseek.com` |
| **哪一家的模型** | qwen → 通义 · deepseek → DeepSeek |
| **哪个型号** | 另一个字段 `llm_model` 承担,但取值必须以 `qwen` / `deepseek` 开头(见 `QwenLlmClient.pinnedModel()` 的越权回落) |

前两件事现在**恰好一一对应**,所以这个耦合一直看不见。

火山方舟把它捅破了:**方舟是一个平台,上面同时挂着豆包系列、DeepSeek 系列和其它第三方系列**。于是出现一个当前配置**表达不出来的**组合 ——

> 「我想用火山方舟上的 DeepSeek。」

照现在的模型,选 `deepseek` 就会去 `api.deepseek.com` 拿 `llm_deepseek_api_key`,而不是去方舟拿方舟的 key。**平台和模型系列必须拆开**,这就是 issue #14 第 2 问的答案:不是「配置页要不要顺手改一下」,是**不改就接不进来**。

所以这一版做三件事:拆成三级 → 接火山方舟 → 把旧配置一分不差地搬过去。

## 1 · FR 清单

### FR-360 · 配置模型改为三级:平台 → 模型系列 → 具体型号

**平台**(Platform):决定**端点 + 凭据 + 计费口径**。一个平台一把 key。

| 平台 | 端点 | 凭据 | 备注 |
|---|---|---|---|
| 阿里云百炼 · DashScope | `dashscope.aliyuncs.com/compatible-mode/v1` | 现有 `llm_qwen_api_key` | 已有 |
| DeepSeek 官方 | `api.deepseek.com` | 现有 `llm_deepseek_api_key` | 已有 |
| **火山方舟 · Ark** | `ark.cn-beijing.volces.com/api/v3` | **新增** | 本版新接 |

三家都是 **OpenAI 兼容 chat-completions + `Authorization: Bearer <key>`**,这是能做成「平台是一个可配项」的前提 —— 差异只在 base URL、key、以及各家的错误码语义。

**模型系列**(Family):同一平台上可选的模型家族。方舟上至少有 豆包 / DeepSeek 两支。

**具体型号**(Model):真正发给对方的 `model` 字段值。

**必须允许手填。** 方舟的 `model` 既可以是模型 ID(形如 `doubao-seed-1-6-251015`,**带日期版本号**),也可以是用户自己在控制台建的接入点 ID(`ep-` 开头)—— 后者只能从对方控制台复制,我们不可能预置。而带日期的模型 ID 意味着**任何写死的下拉清单都会过期**。所以型号一栏是「下拉推荐 + 可手填」,手填优先。

**验收**:
1. 选定「火山方舟 + DeepSeek 系列 + `ep-xxxx`」后,AI 体检真的走方舟、用方舟的 key。
2. 三级之间级联:换平台 → 系列清单跟着换 → 型号清单跟着换;手填的型号不被级联清空(除非平台变了)。
3. 型号手填 `ep-` 开头的串能存下、能调通。

### FR-361 · 接入火山方舟(文本)

新增一个 `LlmClient` 实现,与现有两家并列,纳入同一套 available / 熔断 / audit 机制。

**这条要说清一个取舍**:`QwenLlmClient` 里那套「**多模型轮询摊免费额度**」(百炼的免费额度按模型各给一份,用尽某个就冷却 6h 切下一个)是**百炼平台特有的计费形态**,不是通用能力。方舟不是这个计费模型,**不要照搬**。轮询策略应当作为「平台的属性」保留在百炼上,而不是提升为所有平台的公共行为。

**验收**:管理页「测试连接」对火山方舟可用,成功/失败都给不含任何凭据的友好文案(复用 `classifyLlmError`)。

### FR-362 · 视觉模型(持仓截图导入)走同一套三级

现在视觉这一栏是**写死的三个 Qwen-VL 选项**(`qwen-vl-max` / `qwen-vl-plus` / `off`),而且 `QwenVisionClient` 直接读 `llm_qwen_api_key` —— 也就是说**截图导入被钉死在阿里百炼上**。issue #14 的标题明说了「LLM **和多模态图片 OCR** 的模型」,两个都要。

**要求**:视觉也按 平台 → 系列 → 型号 选,可以和文本选不同的平台(常见诉求:文本用便宜的,OCR 用准的)。`off` 保留为独立开关,不要挤进型号清单里当一个假型号。

**验收**:把视觉切到火山方舟的多模态型号后,`/lab` 之外的正式截图导入路径能跑通并出结构化结果。

### FR-363 · 旧配置无缝迁移(issue #14 第 3 问)

**硬要求:升级后打开管理页,看到的选择与升级前等价;key 一把都不用重填;AI 体检和截图导入立刻可用,中间没有「不可用窗口」。**

映射关系必须逐条落实:

| 旧 | 新 |
|---|---|
| `llm_primary_vendor = qwen` | 平台 = 阿里云百炼 · 系列 = 通义千问 · 型号 = 承接 `llm_model` |
| `llm_primary_vendor = deepseek` | 平台 = DeepSeek 官方 · 系列 = DeepSeek · 型号 = 承接 `llm_model` |
| `llm_model = auto` | 型号 = 自动(百炼下 = 保持轮询;其余 = 各平台默认) |
| `llm_qwen_api_key` | 阿里云百炼平台的 key |
| `llm_deepseek_api_key` | DeepSeek 官方平台的 key |
| `llm_qwen_models`(轮询池) | 保留,归属为**百炼平台的属性**(见 FR-361) |
| `llm_vision_model = qwen-vl-*` | 视觉:平台 = 阿里云百炼 · 系列 = 通义千问 VL · 型号 = 原值 |
| `llm_vision_model = off` | 视觉 = 关闭 |
| `llm_temperature` / `llm_max_tokens` / `llm_timeout_seconds` | 不变,仍是全局调用参数 |

**prod 已上线,这里是 backward-compat 红线**(memory `feedback_prod_backward_compat`):旧配置键**不删**,迁移必须可重入(跑两次结果一样),且**回滚到上一版仍能正常工作** —— 也就是说迁移只能是「补写新键」,不能改写或删除旧键的语义。

**验收**(这条必须做成机器可验的,不能只靠肉眼):
1. 拿一份 v1.12 的真实配置快照(含两把 key、非 auto 的型号、非默认视觉型号)启动新版本 → 配置页逐项与升级前一致。
2. 迁移跑两次,`family_config` 表内容一致。
3. 降级回 v1.12 的 jar,AI 体检仍能跑通。

### FR-364 · 模型目录只有一份

现在「有哪些型号可选」这件事**散在四个地方**,加一个平台要同时改四处、漏一处就出诡异行为:

| 位置 | 现在写着什么 |
|---|---|
| `QwenLlmClient.DEFAULT_MODELS` | `qwen-plus,qwen-flash,qwen-max` |
| `IntegrationsController.normalizeLlmModel` | 服务端白名单,硬编码两家清单 |
| `admin/integrations.html` 的 JS `LLM_MODELS` | 前端级联清单 |
| 同页视觉下拉的三个 `<option>` | 写死的 Qwen-VL 三项 |

**要求**:收敛成**一份目录**(平台 → 系列 → 推荐型号),前端级联、服务端校验、客户端默认值都从它读。加平台 = 改一处。

**这条不是重构洁癖**:上面四处已经**事实上不一致** —— 前端清单里有 `auto`,`DEFAULT_MODELS` 里没有;视觉那三项谁都不知道该归谁管。再加一个平台只会更糟。

**验收**:加一条 qa-run 护栏,断言「前端能选到的型号 ⊆ 服务端白名单」,四处清单再分叉就红。

## 2 · 非目标

- **不做**「自定义任意 OpenAI 兼容端点」的通用表单。那是把接入难度转嫁给使用者,和本项目「家里人点几下就能用」的定位冲突。平台是一份**内置清单**,加新平台走版本发布。
- **不做**多平台并发调用 / 结果投票。成本和复杂度都不匹配「10 分钟/月」的定位。
- **不改** AI 体检、月报洞察、目标建议这些**上层功能的输出形态**。这一版只动「调用谁」,不动「问什么、怎么答」。
- **不做** 按功能分别配模型(体检用 A、月报用 B)。除非作者另有指示 —— 文本一套 + 视觉一套,已经覆盖了 issue 里的诉求。

## 3 · 验收(整版)

1. 三家平台各自「测试连接」通过;任一家 key 未配 → 该平台在选择器里明确显示「未配置 key」,而不是选了之后才失败。
2. 主选平台故障 → 自动切到备选,`llm_audit` 里能看出实际用了谁(现有机制不回退)。
3. **口径不变**:同一份数据、同一个型号,升级前后 AI 体检的输入 prompt 逐字相同(这一版不碰 prompt)。
4. 单测 + `scripts/qa-run.sh` 全绿;`scripts/e2e.sh` 主线通过。
5. 管理页 PC + 移动双端截图 + UED 复看(三级选择器在窄屏上不能挤成一坨)。

## 4 · 作者已拍板(2026-08-15 · 四条全部确认)

| # | 问题 | 决定 | 落在哪 |
|---|---|---|---|
| 1 | failover 的单位 | **主 / 备各一个完整三元组**(平台+系列+型号) | FR-360 · TDD §1.2 |
| 2 | 同一系列出现在多平台 | **允许**(靠平台名区分) | FR-360 |
| 3 | 百炼的「轮询摊免费额度」 | **保留**,作为百炼平台的专属属性 | FR-361 · TDD §1.1 |
| 4 | 型号手填 | **放开**给所有平台 | FR-360 · TDD §1.4 |

**决定 1 的代价**:配置页多一组「备选」字段。换来的是「主选方舟的豆包,备用百炼的 qwen-plus」
这类组合能说清 —— 三级之后,「主选火山方舟」在方舟挂着好几个系列时本来就是句不完整的话。

**决定 3 的连带**:三个平台的配置项**不齐整**(百炼多一块轮询池)。TDD 的处置是把它做成
`LlmCatalog` 里的**显式平台能力标记**,让它读起来是「这个平台有这个特性」,而不是
「另外两个平台漏配了」。

**决定 4 的连带**:现在那套「越权型号静默回落成 auto」的逻辑必须**整个拆掉** ——
方舟的 `ep-xxxx` 既不以 qwen 也不以 deepseek 开头,现有逻辑会把它当越权丢掉,
表现为「存进去了、不报错,但调的还是老模型」。改成格式校验 + **不合法就明确报错**
(见 TDD §1.4,含放开校验后的安全边界说明)。

**5(不需要拍板,但要知道)· 火山方舟的 key 申请门槛**:方舟要求实名认证。会写进
`docs/llm-api-keys-setup.md` —— 对「自部署给家里人用」的读者,这是一道真实的坎。
