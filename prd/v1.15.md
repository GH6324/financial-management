## 0 · 这一版在解决什么

issue #12 原话是「要支持账户登录名称可改,目前似乎写死了两个,并不允许修改」,并追问「账户是否允许删除,历史上有过持仓账户的还能不能删,如果不能删至少增加一个归档?或者禁止登录怎么一个形式」。

**这是三件事,查完代码发现它们的性质完全不同**,分开做:

| 诉求 | 现状(已查证) | 这一版的性质 |
|---|---|---|
| 改登录名 | `members.html` 里输入框 `disabled`,底下写着「不可改」;`MemberMapper` 无任何 `username` 的 UPDATE | **推翻一个既有决定**,得先处理掉当初关它的理由 |
| 归档 / 禁止登录 | `member.archived_at` 从 V1 就有 · `Member.isArchived()` 有 · **登录拦截已实现** · 列表已按 `archived_at IS NULL` 过滤 | **补开关 + 善后**,不是从零做 |
| 删除 | 无任何删除入口 | **拆成两种情况**,不是一刀切 |

### 0.1 · 最值得说的发现:归档是一盏通了电但没装开关的灯

`MemberPrincipalService` 第 19 行已经在做 `.filter(m -> !m.isArchived())` —— 也就是 issue 里问的「禁止登录怎么一个形式」,**代码里早就是这个形式了**。

但全仓库**没有一条语句会把 `archived_at` 写进去**,页面上也没有任何入口。所以这个能力现在处于「只有直接改数据库才能触发」的状态。

**因此这一版的工作量不在那条 UPDATE,而在归档之后的善后**(§ FR-382)。

### 0.2 · 第二个发现:登录拦截只在「登录那一刻」生效

`MemberPrincipalService` 是 `UserDetailsService`,只在**认证时**被调用。项目里没有配 `SessionRegistry` / `maximumSessions`(见 `SecurityConfig`),所以:

> **把一个已经登录的人归档,他浏览器里那个会话会继续好用,直到自己过期。**

「禁止登录」如果只做到「下次登不进来」,在「孩子成年了要停掉他的访问」这类真实场景里是不成立的 —— 那个人现在就在用。所以 FR-381 把「当场失效」写成硬要求,而不是留给下一版。

## 1 · FR 清单

### FR-380 · 登录名可改

管理页的「登录名」输入框解除 `disabled`,可改并保存。

**格式与唯一性**:沿用创建成员时的规则(`[a-zA-Z0-9_]+`,3–40 字符)。唯一性校验必须**跨全表**,包括已归档成员 —— `uk_member_username` 是全表唯一约束,只查活跃成员会在保存时炸数据库异常而不是给出友好提示。

**必须一并处理的三件事**(这三件正是当初把它关掉的原因,不处理就是把坑打开):

1. **「记住我」令牌作废**。`persistent_logins` 这张表是**按 username 存**的(`series / username / token`),没有 member_id。改名后那些令牌指向一个不存在的用户名 —— 该成员在别的设备上的免登录会变成一张废票,而且是**静默**的废票。改名时必须删除该 username 名下的全部令牌,让他重新登录一次。
2. **当前会话跟随**。改的是自己的登录名时,会话里的 principal 还是旧 username,后续任何一次 `loadUserByUsername` 都会失败。要么当场刷新 principal,要么强制重新登录 —— 两个方案的取舍写进 TDD。
3. **审计留痕**。改登录名是身份变更,必须写 `audit_log`,且**记录旧名 → 新名**。只记「资料更新」等于把这次变更抹掉了。

**验收**:改名后 → 旧名登不进去、新名能登进去、该成员其它设备上的「记住我」失效需重新登录、`audit_log` 里能查到旧名和新名。

**注意(不是本 FR 要解决的,但要写明)**:项目目前**没有权限分级**,`SecurityConfig` 里除白名单外只有 `.anyRequest().authenticated()`,任何登录成员都能进 `/admin`。也就是说这一版之后,**任何家庭成员都能改别人的登录名**。两口子的家庭账房里这大概率不是问题,但它是这一版带来的新的能力边界,列在 §3 请作者确认。

### FR-381 · 归档入口 + 撤销 + 当场生效

管理页每个成员卡片给一个「归档」动作(二次确认),已归档的给「撤销归档」。写 `archived_at` / 置回 `NULL`。

**四条硬约束**:

1. **最后一个活跃成员不许归档**。`countActiveByFamily` 已经有了,直接用 —— 归档掉最后一个人 = 谁也登不进来,这个系统就废了。
2. **不许归档自己**。当场把自己锁出去,而且因为没有权限分级,救不回来(除非直接改库)。
3. **当场生效**(§0.2 那个洞):归档后该成员**正在使用的会话必须立即失效**,而不是等它自己过期;「记住我」令牌一并删除。
4. **审计留痕**,归档和撤销都记。

**验收**:A 登录着,B 在另一浏览器把 A 归档 → A 下一次点击即被踢回登录页;A 用「记住我」也进不来;撤销归档后 A 能重新登录。

### FR-382 · 归档之后:该看见的地方看得见,不该出现的地方不出现

这是本版真正的工作量。`memberMapper.findActiveByFamily` 现在有 5 处调用点,**归档之后它们的正确行为不一样**,已逐个查证:

| 调用点 | 用途 | 归档后应该 |
|---|---|---|
| `AdminController:213` | 成员管理页列表 | **必须能看见已归档的**,否则归档完人就消失了,连撤销按钮都点不到 |
| `AdminController:419` · `DashboardController:364` | 成员 id → 名字映射 | **必须含已归档的**,否则历史报表里那个人的名字变成空白 |
| `AccountController:181` · `AccountController:213` | 账户归属下拉 | **保持仅活跃** —— 面向未来的选择,不该再选到已退出的人 |
| `NotificationSettingsController:91,104` | 提醒对象 / 发送名单 | **保持仅活跃** —— 不能再给已归档的人发填报提醒短信 |

**要求**:新增一个「含已归档」的查询方法,只给上面前两类用;后两类一行不动。管理页对已归档成员用视觉降级(灰化 + 「已归档」pill),不要做成两个列表 —— 两个列表会让「撤销」变得难找。

> **不要 emoji**,需要图形用项目自带的 Feather-style inline SVG(memory `feedback_no_emoji`)。

**护栏**:加一条 qa-run 守护,钉住「名字映射的两处调用点不得使用仅活跃的查询」。这类回归的特征是**不报错、只是名字变空**,人眼复看很容易放过去。

**验收**:归档一个填过历史数据的成员 → 历史报表里他的名字照常显示;账户归属下拉里没有他;提醒名单里没有他;管理页能看到他并能撤销。

### FR-383 · 删除:零引用才给删,且引用扫描不能靠外键

**有历史的不给物理删除**,理由写在 §2。**零引用的允许真删** —— 建错的账号(名字打错、多建一个)不该被迫在列表里躺一辈子,那是噪音不是历史。

**必须显式扫描引用,不能依赖数据库外键。** 已查证的引用位置:

**有外键的(9 处)**:`account.primary_owner_member_id` · `period_snapshot.submitted_by` · `cash_flow.submitted_by` · `transfer.submitted_by` · `snapshot_todo.assigned_member_id` · `snapshot_todo.done_by_member_id` · `period_member_completion.member_id` · `audit_log.actor_member_id` · `period_reopen_log.reopened_by`(V6)

**没有外键的(3 处 · 这是坑)**:`period_member_cashflow.member_id`(V19)· `stock_valuation_event.triggered_by_member_id`(V24)· 提醒发送记录的 `member_id`(V25)

**藏在 JSON 里的(1 处)**:`family_goal.params_json` 里 EDUCATION 目标的 `child_member_id`(V14)

后四处数据库**拦不住**,删了会静默产生孤儿行 —— 教育目标会指向一个不存在的孩子。所以扫描要逐个数,并把结果**显示在页面上**(「名下 N 个账户 · M 期填报记录 · K 条现金流」),让人看着数字做决定,而不是点了删除才被告知不行。

**一个要诚实说明的推论**:`audit_log.actor_member_id` 也算引用,所以**只要这个人登录后做过任何操作,就永远删不掉了**。这不是缺陷,恰恰是想要的结果 —— 能删的正好就是「建完还没用过」那一类,也就是 issue 里说的「建错了」。这一点要在页面文案里讲清楚,否则用户会以为删除按钮坏了。

**反过来的一条**:`audit_log` 里**以他为对象**的记录(`entity_type='member'`,比如「管理员创建了成员 X」)**不算引用**。那是「发生过什么」的流水,不是「他拥有什么」,删除后保留这条记录是正确的。

**二次确认**:删除要求输入该成员的登录名才放行(和常见的破坏性操作一致),并写 `audit_log`。

**验收**:新建一个成员立刻删 → 成功;让他登录一次再删 → 删除按钮不可用,并提示「他已经产生了 N 条记录,可以改为归档」;删除后 `period_member_cashflow` 等无外键表里不出现孤儿行(这条要有测试,不能只靠肉眼)。

## 2 · 非目标

- **不做权限分级 / 角色体系**(谁能管谁)。现在所有登录成员都能进管理页,这一版**不改这个现状**,只是把它写明(见 FR-380 末尾)。引入角色是另一件事,会牵动每个 `/admin` 页面。
- **不做成员合并**(把两个重复账号的历史并到一起)。听起来像是删除的替代,但它要重写历史归属,和「已关账月份不再变」(v1.12.0)直接冲突。
- **不做多家庭 / 邀请注册 / 自助注册**。成员由管理页创建,这条定位不变。
- **不改密码策略、不改登录方式**。
- **不做「删除时把历史数据一起删」的级联选项**。那是"把家底删掉一块",与项目定位冲突,任何形式都不提供。

## 3 · 需要作者拍板的

1. **归档后,他名下账户的钱还算不算进家庭净资产?**
   我的倾向:**照算**。归档的语义是「这个人不再参与填报」,不是「这笔钱没了」;若不算,一次归档会让净资产曲线凭空掉一截,而且和 v1.12.0「已关账的月份不再变」正面冲突(历史月份的数会因为今天的一次归档而改变)。
   但如果场景是「孩子成年独立,要把他那部分从家庭口径里摘出去」,那是另一种语义 —— 需要的是「移出家庭」而不是「归档」,那会是更大的一版。**已在 issue 里问了报告者的具体场景。**

2. **允许归档自己吗?** 我的倾向:**禁止**(理由见 FR-381),但这会导致「只剩一个人想停用系统」做不到。可接受。

3. **没有权限分级这件事,这一版就这么放着,还是至少加一条「不能操作比自己先创建的成员」之类的软约束?** 我的倾向:**就这么放着**,不要发明半套权限模型 —— 半套比没有更难理解。要做就单独一版做完整。

## 4 · 验收(整版)

1. 改名四条(旧名失效 / 新名可登 / 记住我作废 / 审计有旧名新名)。
2. 归档当场生效:已登录的会话被踢(FR-381 那条 A/B 双浏览器用例)。
3. 最后一个活跃成员、以及自己,都归档不了。
4. 归档后历史报表名字照常显示,账户归属与提醒名单里不出现他。
5. 零引用可删、有引用不可删;删除后无外键表里无孤儿行。
6. `mvn -o test` 全绿 · `bash scripts/qa-run.sh` 全绿,**新增两条护栏**:
   - 名字映射的两处调用点不得使用仅活跃查询(FR-382);
   - 引用扫描必须覆盖那 3 张无外键表 + 1 处 JSON 引用(FR-383)—— 钉的是「表名出现在扫描实现里」,防止以后加表漏扫。
7. 影响登录/会话,跑 `bash scripts/e2e.sh`。
8. 管理页 PC + 移动双端截图 + UED 复看(归档态的灰化不能让人以为是禁用/加载中)。
9. **向后兼容自检**(prod 已上线):本版**不需要 DB 迁移**(`archived_at` 已存在)。若 TDD 阶段发现需要加索引或字段,按 memory `feedback_prod_backward_compat` 的 4+4 条重新过一遍。
