# PRD · v1.6 · UED 专项:看得清、点得中、信得过

> 本版不加新功能,只修体验。来源是一次完整的双端截图审计:`docs/ued-review-2026-07.md`
> (8 个页面 × PC/移动 = 16 张真机截图,对照 `docs/visual-spec.md` 逐条比对,提出 61 条)。
> 设计规范:`docs/visual-spec.md` · 现状梳理:`docs/design-system.md`

---

## 1 · 为什么做这一版

产品功能已经铺到 v1.5(记账 → 报表 → 体检 → 透视 → 基金穿透),但一直没有系统性地检查**用户实际看到的界面**。
这次逐页看真机截图,发现三类问题:

| 类别 | 典型症状 | 用户后果 |
|---|---|---|
| **信不过** | 同一时刻 dashboard 净资产 ¥〈金额已脱敏〉 / checkup ¥5399878,差 119 万;紧急储备 7.2 月 vs 723 月 | 两个数字不一致,用户不知道该信哪个 → 击穿对全部数字的信任 |
| **看不清** | checkup 全页金额无千分位(`¥5399878`);元信息色对比度仅 2.90:1;移动端旭日标签中文竖排 | 数字读不出量级;小字看不见;图表标签不可读 |
| **点不中 / 找不到** | 浮钮压住金额;移动端首屏 0 内容全是控件;填报页 13.9 屏 | 核心任务(每月填报)变成体力活 |

产品硬约束是「每月 10 分钟」,用户一个月来一次 —— **每次访问都是半个陌生人**。
上面每一条都在消耗那 10 分钟。

## 2 · 用户可见的改动

### FR-1 · 数字可信(P0)

- **体检与仪表盘同期同口径**:体检此前取「最新账期」(含测试用的未来账期),仪表盘取「不晚于今天的最新期」。
  两页 anchor 落到不同账期,同名指标数值不同。现统一规则,并在体检页标出
  **「数据截至 YYYY 年 M 月 · 与仪表盘同期口径」**——用户能自己确认两页是否同期。
- **金额一律带千分位**:体检家庭页 / 体检账户页 / 流水档案共 32 处此前直接输出 `5399878`,现为 `〈金额已脱敏〉`。
- **荒谬值不再报数**:紧急储备月数在月均支出接近 0 时会算出 723 个月(60 年),
  现超过 36 个月一律显示「> 36 个月」,并提示「月均支出偏低 · 先去填报补支出」。

### FR-2 · 已关账不再假装可填(P0)

账期关闭后,填报页此前仍铺满 18 个可编辑表单 + 保存按钮,用户填完才发现改不动。现在:

- 页顶「本期已关账 · 只读」横幅:说明原因 + 给三条去处(周期管理重开 / 去最新一期 / 看本期报表)
- 各账户行的余额表单、快捷支出、划转、贷款预测、刷新持仓估值全部不渲染
- 表单位置改显示「本期余额 · 已定稿」+ 锁图标
- 「提交本期」区改为陈述状态 + 看报表 / 回仪表盘

### FR-3 · 移动端首屏给结论,不给控件(P0)

四个分析页(仪表盘 / 报表 / 账户 / 填报)此前 844pt 首屏内看不到任何数据:

- 口径控件(账户范围 + 币种 + 多选筛选)在窄屏收进一行折叠条,摘要显示 `18 个账户 · CNY · 1Y`
- 仪表盘新增**「本期一句话」**:净资产 + 较上期 + 环比 + 储蓄率 + 未填提醒,直接回答「这个月还好吗」
- 说明性长文(流程说明 / 口径说明)窄屏折叠
- 页面顶部留白窄屏 40px → 20px

### FR-4 · 填报页从 13.9 屏压到 6.6 屏(P0)

18 个账户卡片结构完全一致、各约 400px,滚动中完全失去位置感。现在窄屏默认收起填报区,
每行只留摘要(名称 / 上期末 / 本期值 / 待填徽记),点开才展开表单。**PC 保持展开,行为不变。**

### FR-5 · 图表换成窄屏读得懂的形态(P1)

| 图 | 原来 | 现在 |
|---|---|---|
| 旭日图 | 标签沿弧旋转,中文被转到接近垂直、小块溢出圆外 | 环只负责结构:大块横排显示「名称 + 占比」,小块留白,精确数字看下方「切片排行」 |
| 资产配置环图(7 类) | 小扇片标签重叠、引导线在窄侧堆叠 | 类目 > 6 时换横向条形,金额与占比都标得下;≤6 类仍用环图 |
| 账户分布双向柱(21 个) | 全画进去,长尾条几像素,图高 648px | Top N(窄屏 7 / PC 10)+「其他 N 个」聚合 |
| 风险分布配色 | 高风险=紫 / 中风险=粉紫 / 低风险=青,从颜色读不出高低 | 改低→高顺序色阶(与体检风险图同一套) |
| 负债下降曲线 | Y 轴自适应(118 万–125 万),5% 降幅画成陡坡 | Y 轴从零起 —— 绝对量曲线不该夸大波动 |
| 仪表盘 5 个 KPI | 五个同等大小,第 5 个独占整行 | 窄屏主次网格:净资产跨两列 + 大字,其余 4 个 2×2 收紧 —— 5 个同屏可见(v1.6.0 曾做成横滑,经用户 review 退回,见 §5 ③) |

### FR-6 · 不再暴露技术细节(P1)

- 管理页 15 个入口的小标题此前是 URL 路径(`/ADMIN/FAMILY`),改中文功能分类,并按
  **家庭基础 / 口径与标签 / 日常运营 / 系统** 四组重排(此前 15 个平铺无层次)
- AI 诊断徽标 `OK / WARN / RISK` → `正常 / 注意 / 风险`;`cached` → `已缓存`
- 账期状态 `OPEN / CLOSED` → `进行中 / 已关账`;备份 `✓ SUCCESS` → `成功`
- 移除 `Spring Boot 3.3`、`PRD` 等内部术语
- `环比(MoM)` / `同比(YoY)` 去掉英文缩写
- 账户类型的枚举 code(`现金 (CASH)`)在移动端隐藏,PC 保留便于对照
- 基准对比 `跑输 -2.61pp` → `落后基准 -2.61 个百分点`,且去掉边框(它是数据事实,不是需要你决定的警示)

### FR-7 · 视觉阻断与一致性(P1)

- **浮钮不再压住内容**:隐私眼 / 目录钮从左下(内容起始边)移到右下,加 iOS 安全区,
  默认半透明让下方数字仍可读,滚动时进一步淡出,交互时恢复
- **网格空位不再露出色块**:9 个类型 ÷ 6 列、5 个 KPI ÷ 2 列时,空位此前透出米灰底色
- 账户表「主理人」列不再把「王二狗」挤成三行竖排
- 序号列去掉 `☰`(暗示可拖拽排序,但系统并无拖拽功能)
- 账户行 7 个等权操作按钮 → 高频 2 个留行内,其余收进「⋯」
- 目标页空状态:去掉重复的第二个主按钮,4 个入口改等宽 2×2,卡片收窄居中
- 全站 emoji 清零(17 处 🚀🗄💰✨⚠✓ 等换 inline SVG 或纯文字)

### FR-8 · 可读性底线(P1)

- 元信息色从 `#A09486`(对比度 2.90:1,连大字号 3:1 都不到)改为 `#706657`(5.5:1,过 AA)。
  原浅色降级为纯装饰用途。
- 铜金色新增文字专用档 `#85642F`(5.3:1)—— 原 `#B08642` 作小字仅 3.2:1
- 尊重系统「减少动态效果」偏好(此前仅落地页尊重)
- 装饰性英文小标题(`A·L·L·O·C·A·T·I·O·N`)窄屏隐藏 —— 此前把中文标题末字挤到第二行

### FR-9 · iOS 专项(P1)

主力用户是 iOS,以下每条都有具体失效场景:

- 横滑区(指标 pill / 交叉表 / 汇总带 / KPI 带)加 `overscroll-behavior-x: contain` ——
  **此前横滑到尽头继续拖会触发 Safari 返回手势,直接离开页面**
- 横滑区加 `scroll-snap` —— 此前会停在半个 pill 的位置
- 固定底部元素加 `env(safe-area-inset-bottom)` —— 此前在带 home indicator 的机型上贴近系统手势区
- 图表容器关 `-webkit-touch-callout` —— 此前长按图表弹出系统「拷贝图片」菜单

## 3 · 明确不做

| 项 | 原因 |
|---|---|
| 深色模式 | 「起居室里的银行家账册」的核心载体是纸,纸是亮的。做深色等于重定义整套隐喻,收益远小于成本 |
| 「本金 vs 投资损益」柱图分段/双轴 | 前 9 期贴零轴是因为末 3 期极值。改默认区间会牵动整页口径,需单独产品决策 |
| 账户级收益表收敛列数 | 哪些列算次要需要产品判断,不适合在 UED 专项里定 |
| 移动端拆「资产/负债两段列表」 | TopN 聚合后双向柱已降到 8 条可读,再拆收益有限 |
| 统一确认弹层替代原生 confirm | 11 处调用点,涉及交互流程改造,留待下一版 |

> 原列在此处的「移动端横屏看交叉表」已于 v1.6.1 实现 —— 当时判断「iOS 不支持 orientation.lock 所以做不了」是错的,
> 用 CSS rotate 自建即可,见 §5 FR-10。

### FR-10 · 自建横竖屏切换

此前 v1.5.2 与 v1.6.0 的判断是「iOS 不支持 `screen.orientation.lock`,只能提示用户自己转手机」——
这个判断是错的:游戏类 / 漫画类 PWA 早就在用另一条路 **自己用 CSS `transform: rotate(90deg)` 把内容转过来**,
视口宽高互换,用户看到的就是横屏。

现在交叉透视表右上有「横屏看」按钮(仅窄屏出现),点击后:

- 内容进入全屏并旋转 90°,视口宽高互换(`width:100dvh / height:100vw`)—— 表格列一次性铺开,不用横滑
- 顶部提示「把手机转横过来看 · 转好后画面自动扶正」
- **用户真把手机转横之后,自动撤掉我们的旋转**(监听 `orientationchange` / `resize`)——
  否则会把系统已经转正的画面又转回竖的
- 三条退出路径:退出按钮 / Esc / 浏览器返回(`pushState` 拦一层),不会把用户困住
- DOM 是**移入**旋转层而不是克隆,退出时原位放回 —— `lens.js` 持有的容器引用与按 id 重渲染都不受影响

实现是通用的声明式能力(`static/js/landscape.js`):任何元素加
`data-landscape="#选择器"` 的按钮即可获得横屏查看,后续宽内容(长表格等)可直接复用。

## 6 · v1.6.2 追加(用户 review 反馈 · 2026-07-27)

### BUG · 旭日大量扇形块既没名字也没数字(P0 · v1.6.1 引入)

v1.6.1 为了解决「窄屏标签被旋转成竖排中文」,把环内标签阈值提到 40°(占比 11%)——
但图下「小块补注」的阈值仍是 14°(3.9%)。**3.9%~11% 的块两边都不收**,而真实数据里这个区间的块最多,
于是一眼看去大半个环都是无标识的色块,组件几乎不可用。

修法:环内阈值与补注阈值**必须是同一个常量**(`SUN_LABEL_MIN_DEG = 32°`),中间不留缝。
同时取消「只给占比不给名字」的中间档 —— 只有数字没有名字对用户等于没有信息,那是半个盲区。
现在非黑即白:**≥32° 环内给「名称 + 占比」,小于 32° 整块进图下补注** —— 每一块都有名有数。

### FR-11 · 横屏升级为全局顶级功能

用户指出横屏不该只是交叉表的局部能力。现在 nav 里有横屏按钮(与 ☰ 菜单、隐私眼并列,窄屏出现),
汉堡菜单里也有一行带文字的入口;点击后**整页横屏**(转 `<body>`,nav / 浮钮 / 内容一起转),
状态记在 session 里、刷新后保持。交叉表的局部入口保留(用户认可)。

### 关于「屏蔽系统横屏」—— 平台做不到,改为让位

用户希望屏蔽 iOS 自身的横屏,避免"我们转 + 系统转"两次重排。核实结论:

- `screen.orientation.lock()` iOS Safari 与 iOS PWA 都不支持
- manifest 的 `"orientation": "portrait"` 我们**早就设了**(`ManifestController`),但 **iOS 不读这个字段**

所以屏蔽做不到,这是平台限制。改为**和平共处**:一旦检测到设备已物理横屏(系统已给真横屏),
我们就整体退出自己的旋转层,把方向交还系统 —— 用户只经历系统那一次不可避免的重排,
不再叠加"我们撤旋转"的第二次跳动(v1.6.1 是只撤 rotate 但留着层,所以会跳两下)。

## 7 · v1.6.3 追加(用户 review 反馈 · 2026-07-27)

### BUG · 旭日仍有大量空块 —— 前两次都没修对

这个问题我修了三次才对,过程本身值得记:

| 版本 | 做法 | 为什么不对 |
|---|---|---|
| v1.6.1 | 环内标签阈值提到 40°,解决「竖排中文」 | 图下补注阈值仍是 14°,**3.9%~11% 两边都不收** = 信息黑洞 |
| v1.6.2 | 两个阈值合并成一个(32°) | 窄屏本来就不画引导线,于是 32° 以下**全靠补注**;「行业集中」看板 59 块里只有 6 块环内有标签,环上仍是一片无字色块 |
| v1.6.3 | **承认图型容量有限,把小块聚合** | 见下 |

前两次都在「标注策略」上打补丁,而真正的问题是:**一个 320px 的环里塞 59 块,平均每块 6°,无论怎么标注都不可能可读**。
中间还试过给窄屏也开引导线,结果名称被容器裁成残字(「货币基金/存款 4.6%」渲染成「⌐ 4.6%」),
补注列到 22 项、出现 7 个重复的「支付宝·蚂蚁财富」(不同行业下的同一平台),比不标更糟。

最终做法是数据可视化的通行惯例 —— **Top N + Other**:同一层里小于阈值(窄屏 18° ≈ 5%)的块合并成
「其他 N 项」。实测「行业集中」内环 59 块 → 6 块,每块都够大、都有名有数;要穷举请看下方「切片排行」,
它本来就是完整列表。聚合块是虚拟的,点它不下钻,会提示去看排行。

### 连带修掉两个隐蔽问题

- **窄屏判断不能用 `clientWidth`**:原先用 `#sunburst` 的 `clientWidth < 480`,但这个值依赖布局时机 ——
  同一元素在不同时刻会读到 630 / 321 两个值,于是聚合阈值悄悄走了 PC 档,**改了参数却不生效**。
  改用 `window.innerWidth < 768`(与全站响应式断点同源)。
- **渲染失败被静默吞掉**:旭日崩溃时异常落进 `Promise.all().catch()`,而 catch 只往 `#pivot` 写错误、
  又被随后成功的 `renderPivot` 覆盖 —— 结果图表挂了却全站无声。现在同时 `console.error` + 就地在旭日容器内报错。
  (这次排查正是卡在这一点:页面无报错、无失败请求,只有 skeleton 一直转。)

## 8 · v1.6.4 追加(用户 review 反馈 · 2026-07-27)

### BUG · 旭日「一块饼图直接消失」

聚合出的「其他 N 项」内环块此前 `children: []` —— 旭日里内环块没有子块,**它对应的那段外环就是白色缺口**,
看起来像饼图缺了一块(资产类型看板切「下一层按币种」时最明显)。
修:给聚合块一个占满父角度的同族子块(更浅一档灰)。

### FR-12 · 方向切换改为右下浮钮

不再放在顶部导航,改为与隐私眼、目录钮同一列的右下浮钮(仅触屏窄屏出现)。交叉表里的快捷入口保留,
但它现在调用的是同一个开关 —— 不再维护第二套局部旋转层。

### FR-13 · 不再响应手机自身的横竖屏

用户要求「只能通过我们的按钮切换方向,不响应手机本身的旋转」—— **这个能做到**,前两版我判断错了。
系统旋转屏幕我们阻止不了,但「页面要不要跟着转」完全在我们手里:

| 设备方向 | 期望方向 | 我们做什么 |
|---|---|---|
| 竖屏 | 竖屏 | 不动(零开销) |
| 竖屏 | 横屏 | 顺时针 90° |
| **横屏** | **竖屏** | **逆时针 90°(把内容转回竖直)** ← 这一条就是「屏蔽系统横屏」 |
| 横屏 | 横屏 | 不动 |

最后一条是关键:用户把手机转横,我们反向转回来,内容相对机身始终不动 —— 视觉效果与系统竖屏锁定一致。
桌面端完全排除(桌面恒满足「宽>高」,不排除会被永久反转 90°)。

### FR-14 · 两个配置图形态一致

「资产配置」与「按成员分布」此前一个是环图、一个是条形,手机上并列看着不像一套东西。
抽共用工厂 `hBarConfig`,窄屏两者一律横向条形(窄屏环图标签必然重叠);PC 保持「>6 类条形、≤6 类环图」。

## 9 · v1.6.5(用户 review 反馈 · 2026-07-27)· 整页旋转方案作废

用户在真机上试了 v1.6.4 的整页横屏,报了三条:
① 横屏后顶部菜单会莫名展开 ② 三个浮钮消失或显示不稳定 ③ 切成横屏后再转手机,页面仍有大幅转动

三条是同一个根因,而且是**结构性的**:

> **CSS 媒体查询只认 viewport,不认我们的 transform。**

设备横屏时 viewport = 844px,于是:

- 我为 v1.6 加的 **7 处** `max-width:767/640` 移动端样式全部失效 ——
  KPI 带回网格、汇总带回网格、折叠条 summary 显形、**浮钮 `display:none`**(=反馈②)
- 模板里 **347 处** Tailwind `sm:` / `md:` 前缀全部切到宽屏分支 → 布局跳成 PC 版(=反馈③的"大幅转动",
  它不是动画,是整页重排)

而 Tailwind 那 347 处是媒体查询编译产物,**无法用 class 覆盖**。要让"旋转后仍按窄屏渲染",
只能把全站响应式改成 container query,或把页面塞进固定宽度的 iframe —— 都不是这个版本该做的事。

**结论:整页旋转与现有响应式体系不兼容,方案作废。**

### 现在的做法:只旋转宽内容

页面用 `data-landscape-target="标题"` 声明"本页可横屏看的元素"(目前是交叉透视表)。
点右下横屏浮钮 → 只把那个元素移进全屏旋转层,**body 永不旋转**:

- 被转的是独立容器,内部不依赖响应式断点 → 上面三条一条都不会发生
- 页面其余部分完全不受影响
- 没有声明目标的页面,浮钮自动隐藏(不给无效入口)

浮钮可见性只由 `(pointer: coarse)` + JS 判断本页有无目标决定,**不再带任何 `max-width`** ——
那正是反馈②的直接原因。

### 关于"屏蔽手机自身的横竖屏"

这一条**做不到**,如实说明约束:

- `screen.orientation.lock()` iOS Safari / PWA 均不支持
- manifest 的 `"orientation": "portrait"` 我们早就设了,但 iOS 不读该字段
- CSS 旋转能"抵消"系统旋转,但代价是上面那 354 处响应式全部错位

局部横屏不受这条限制 —— 它不关心设备方向:设备竖着时由我们代转 90°,
用户真把手机转横了就摘掉旋转交给系统,两种情况下看到的都是铺开的宽表格。

## 10 · v1.6.6 · 整页横屏(iframe 隔离)· 方案由用户拍板

### 先记一次流程错误

v1.6.5 我在遇到技术障碍后,**未经用户同意就单方面把「整页横屏」改成了「局部横屏」并部署**。
用户明确要求的是整页横屏 + 不响应手机旋转;遇到冲突时正确做法是**把冲突与代价摆出来、等用户决定**,
而不是替他改需求。这个决策权不在实现方。

### 前四版为什么都失败(同一个根因)

v1.6.2 / v1.6.3 / v1.6.4 都是直接 `transform` `<body>`,真机三个副作用:
① 顶部菜单莫名展开 ② 三个浮钮消失或不稳定 ③ 转手机时页面大幅重排。

结构性根因:**CSS 媒体查询只认 viewport,不认 transform**。设备横屏时 viewport = 844px,于是

- 模板里 **453 处** Tailwind `sm:` / `md:` 全部切到宽屏分支
- 自有 **13 处** `@media` 中的移动端规则失效(含浮钮的可见性 → 反馈②)

而 Tailwind 那 453 处是媒体查询编译产物,**无法用 class 覆盖**。

需要说明的是:「屏蔽系统旋转事件」这件事本身**能做到**(不监听即可),但屏蔽事件不等于屏蔽效果 ——
viewport 尺寸是真实变化的,CSS 对它的响应属于渲染管线,没有可移除的监听器。
所以问题从来不是「方向」,是「响应式断点」。

### 现在的方案(用户在三条路里选的 A)

把页面装进一个**固定尺寸的同源 iframe**,只旋转这个 iframe:

- iframe 有独立 viewport → **453 处响应式一行都不用改**,在 iframe 内全部正确
- iframe 尺寸在进入横屏时定死(长边 × 短边,如 844×390),**此后不随设备方向变化**
  → 用户转手机时 iframe 内 viewport 恒定,**内容零重排**(这正是需求③)
- 内部 viewport = 844 → `md:` 生效 → 宽表格真正铺开(这才是「横屏化」的意义)
- 设备已横屏 → 外层不转,直接铺满;设备还竖着 → 外层转 90°
- 同源 iframe 共享 cookie / sessionStorage → 登录态、隐私模式、字号档位全部沿用
- 嵌套自检:iframe 内用 `window.self !== window.top` 识别,隐藏横屏入口(防套娃)、跳过首屏印章动画
- 在 iframe 里导航过的话,退出时把父页面同步到那个地址,不让用户白点

实测(390×844 → 844×390 切换):iframe 内 viewport 恒为 844×390,`body.transform` 恒为 `none`,
顶部菜单不再展开,浮钮不再消失。

## 11 · v1.6.7 · 断点改成「看短边」· 方向这条路我找错了地方

### 用户第五次反馈同一件事

「还是不对劲,依然随着手机横屏转动了」。前四版(v1.6.2/1.6.3/1.6.4 整页 body 旋转、
v1.6.6 iframe 隔离)全都在跟**方向**较劲 —— 方向不是问题所在。

用户确认了两个场景都坏:
1. **普通竖屏页面下转手机** → 页面变宽屏布局。v1.6.6 完全没管这个场景。
2. **进了横屏模式后转手机** → 看见内容转了一圈。

### 真正的 bug:453 处断点全都只判宽度

手机横屏是 **844×390**。只看宽度 → 844 被当成宽屏设备 → 模板里 453 处
Tailwind `sm:`/`md:`/`lg:` 集体切到宽屏分支。

**手机横屏的特征是短边只有 390,不是宽边有 844。** 这句话就是整件事的答案。
iPhone 横屏 `innerHeight` ≤ 440(最大的 16 Pro Max 短边 440),PC 窗口极少矮于 480
→ 判据加一条 `and (min-height: 480px)`,阈值 480。

三处判据必须同源,少一处就是「CSS 是移动的、JS 却是 PC 的」半修状态:

| 判据出处 | 覆盖 |
|---|---|
| `tailwind.config` 的 `theme.screens` | 453 处 Tailwind 断点(一处改动全覆盖) |
| `style.css` 自有 `@media` | 10 处 |
| `window.vpNarrow()` | 图表脚本里原本 **22 处**硬编码宽度比较 |

例外:横屏 iframe 也是 844×390,但那是用户主动点出来的宽屏视图 →
`window.self !== window.top` 自检加 `is-embedded`,走「只看宽度」那一套。

### 场景 2:iOS 那段旋转动画抹不掉,只能盖住

已查证的三条死路,不是推断:

| 手段 | 结论 |
|---|---|
| `manifest.orientation` | iOS Safari **不支持**(MDN browser-compat-data:`safari: false`) |
| `screen.orientation.lock()` | 需要 fullscreen;iPhone Safari 没有元素级 fullscreen |
| `orientationchange` | 事件 non-cancelable,拦不住 |

末态本来就是对的(内容钉在设备坐标系、iframe 内零重排),坏的只是那 0.4s 过程。
所以旋转期间把内容盖成一张纯色纸面 —— 纯色转动看不出转动。
**盖必须瞬间**(`transition: none`),否则旋转已经开始、内容还在淡出,那一眼就露了;揭开才淡入。

### 这一版做到哪、没做到哪(用户选的「分两步」第一步)

- **做到**:手机横屏不再切宽屏布局。实测 844×390 与 390×844 的
  `md:` 状态、KPI 列数、折叠把手可见性、以及全部 Chart.js 图形态**逐项一致**。
- **没做到**:内容仍会横向拉宽到 844(不是布局切换,但仍是变化)。
  要做到完全不动,需要第二步「宽度锁 390 + 反向旋转」—— 等用户看过真机再定。
- **已知副作用**:PC 窗口高度 < 480px 会退成移动布局。取舍见 tech-design §17。

### 顺带发现的一个真 bug(本版未修)

`static/manifest.webmanifest` 是 **0 字节空文件**(2026-05-10 建了就没填过)。
iOS 靠 `apple-mobile-web-app-capable` 撑着还能加主屏,但 Android/Chrome 的 PWA 安装是坏的。
与本次改动无关,单独记一笔。

## 12 · v1.6.8 · 照行业通行写法重做:尺寸交给 CSS

### 用户让我先做调研,调研结论推翻了我的实现方式

查了 GitHub 代码搜索(同类写法 4192 处命中)+ 逐个读源码:

| 来源 | 关键写法 |
|---|---|
| `QiShaoXuan/css_tricks` 横屏范文 | `width:100vh; height:100vw; rotate(90deg)`,由 `@media (orientation: portrait)` 驱动 |
| `MapoMagpie/comic-looms` 漫画阅读器(**有滚动**) | `transform:rotate(90deg); width:100vh; height:100vw; transform-origin:0 0; left:100vw` |
| `TheCaveMembership/izzapay` 游戏方向插件 | `BASE_W=960, BASE_H=540` 固定设计稿 + 整体缩放旋转,内容全绝对定位,**零媒体查询** |
| SO 8883163(112★) | 软键盘弹起会让 `orientation` 翻转 → 必须叠宽度约束 |

**共同点:尺寸用交换后的视口单位,旋转由媒体查询驱动,JS 里一个监听都没有。**

### 我们不行的原因(逐条 diff)

| # | 行业做法 | v1.6.6/1.6.7 的做法 | 后果 |
|---|---|---|---|
| 1 | `width:100vh; height:100vw` + 媒体查询成对交换 → 两方向下盒子**物理矩形自动相同** | JS 进入时量 `innerWidth/innerHeight` **写死 px** | iOS 竖屏工具栏 ≠ 横屏工具栏,竖屏量到的短边在横屏不成立 → 旋转后尺寸错、位移 |
| 2 | 零 JS 监听,媒体查询与 iOS 重排同一时刻生效 | 监听 `orientationchange` + 220ms 后 toggle class | 扳正永远**晚于** iOS 旋转动画 → 先跟着转一圈再被扳回 = 两次运动 |
| 3 | — | 我的媒体查询没防软键盘 | 竖屏打字时 `orientation` 翻成 landscape → 页面会莫名变向 |
| 4 | 单位:`vh`(large viewport,恒定) | v1.6.1 注释写「用 dvh 而非 vh,因为 iOS 地址栏收放会改变 vh」—— **正好说反** | `dvh` 才是随工具栏变的那个;用它当固定尺寸 → 工具栏一收放就重排。这个误解一路带到 v1.6.6 改成 JS 量 px |

**第 1、2 条是根本**:我把本该交给 CSS 的事用 JS 量 + 监听实现,所以必然慢一拍、必然量错。

### 这一版怎么改

**横屏模式**:舞台尺寸全部交给 CSS,`landscape.js` 不再计算任何尺寸、不再监听 `resize`。
另外**横屏模式里不显示顶部导航** —— 三个实测理由:844 宽放不下 7 个 tab(每项都折两行)、
390 高里导航占 64px(六分之一)、以及用户在 v1.6.4 就说过「横屏以后会莫名其妙打开顶部 tab 菜单栏」。

**普通模式(场景①)**:手机横屏时把 `body` 宽度锁回**短边**(= 竖屏那个宽度)并居中。
排版与竖屏逐像素相同,内容一个字不动;两侧留白压深一档 + 描边,读成刻意的信箱边距;
浮钮用 `calc((100vw - 100vh)/2 + 14px)` 收进内容栏内。

### 为什么不做「反向旋转钉在设备坐标系」

那才是严格意义的"等同系统旋转锁定",但代价是:

- 旋转符号取决于用户**顺时针还是逆时针**转的手机(`window.orientation` 90 / -90),判错就上下颠倒
- `body` 变成滚动容器 → 丢滚动位置

而信箱式居中没有这些代价,**转过去内容仍然是可读的**(钉在设备坐标系是躺倒的,用户还得转回来)。
两者是一行之差 —— 真机看过之后由用户定要哪个。

| 项 | 结果 |
|---|---|
| 横屏模式舞台 CSS 盒子 | 竖屏 / 横屏都是 `844×390`,**无任何 JS 内联尺寸** |
| 横屏模式 iframe 内 viewport | 两向都是 `844×390`(零重排) |
| 普通模式排版宽度 | 竖屏 390 / 横屏 390(**逐像素相同**),卡片都是 360 |
| 普通模式横屏居中 | 左边距 227px,无 transform |
| PC 矮窗 1440×460 | body 仍 1440(`pointer: coarse` 挡住了) |

## 13 · v1.6.9 · 方案 B(用户选定)+ 专用方向图标

### 13.1 · 「横屏模式下转手机仍会转一次」—— 这条不是缺陷,是逻辑必然

用户问:这个是不是无法避免?**在 Safari 里无法避免,而且原因不在实现,在需求本身互斥。**

横屏模式的目的是「转过手机来读宽表格」,也就是要求**内容在世界坐标系里保持正立**。
而"不响应手机旋转"要求**内容在设备坐标系里不动**。设备一转,这两件事就是对立的:

- 要正立 → 必须跟着设备方向调整 → 一定"响应"了旋转
- 要不动 → 内容会躺倒 → 转过去也读不了,横屏模式就失去意义

所以横屏模式只能选"正立",剩下能做的只是**把过程盖住**(遮帘)。而 iOS 自己那段旋转动画
无法抹掉,已查证的三条死路:`manifest.orientation` iOS 不支持(MDN BCD:safari `false`)、
`screen.orientation.lock()` 在 Safari 是 `false`(MDN BCD 实测)、`orientationchange` 不可 cancel。
更麻烦的是 iOS 往往在旋转**之后**才派发 `orientationchange`,所以遮帘可能盖不住开头那一瞬。

**游戏为什么看起来没有这个问题**:三种情况 —— ① 它们是横屏专用,用户本来就横着拿,游戏过程中
根本不发生旋转;② 很多"PWA 安装的游戏"其实是 Capacitor/Cordova 之类原生外壳包的,方向锁在
原生层(`UISupportedInterfaceOrientations`),那是网页拿不到的能力;③ 用户自己开了系统旋转锁定。

**给用户的实际办法**:在 iOS 控制中心打开「竖屏方向锁定」。系统就再也不会旋转,
而我们的横屏钮是纯 CSS 变换、不依赖设备方向,照样能用 —— 那时"只能通过我们的按钮切换方向"
就是字面意义上成立的。

### 13.2 · 普通模式改成方案 B(钉在设备坐标系)

用户在 A(信箱式居中)/ B(反向旋转)里选了 **B**。效果 = 只对本 app 生效的「竖屏方向锁定」:
转手机时页面在屏幕上一动不动,要读还得转回来。

零重排的来源:`body` 盒子 = `100vh × 100vw` = 短边 × 长边 = **竖屏那个形状**
(视口单位在横屏自动交换),排版宽度仍是短边。
实测竖屏 / 横屏:`body 390` / 卡片 `360×92` / KPI `360` —— **逐项相同**。

两件 CSS 做不到、必须 JS 兜的事:

1. **旋转符号**:`screen.orientation.angle` 的定义是 viewport 相对自然方向**顺时针**转过的角度,
   抵消就是转 `-angle`。angle 90(设备逆时针转)→ `-90°`;angle 270(设备顺时针转)→ `+90°`。
   iOS 16.4+ 有 `screen.orientation`,更老回落 `window.orientation`。判错的表现是内容上下颠倒。
2. **滚动位置交接**:冻结时滚动容器从 `html` 变成 `body`,两者的 `scrollTop` 是两套值。
   不接一下就会跳回顶部 —— 而「跳回顶部」正是用户最反感的那种"页面动了"。
   实测滚到 600 → 转横屏 `body.scrollTop=600` → 转回竖屏 `documentElement.scrollTop=600`。

### 13.3 · 方案 B 的固有代价(实测踩到了)

`body` 被 `transform` 之后,它内部所有 `position: fixed` 浮层的**包含块从视口变成 body 盒子**。
这些浮层的几何(`inset-x-0`、`bottom: 0`、收起态 `translateY(110%)`)都是按"未旋转的视口"写的,
放进旋转容器就会错位 —— **实测目录抽屉直接漏进屏内**。

冻结态的语义是「用户误转了手机、马上会转回来」的过渡态,不需要这些浮层 →
几何脆弱的一律藏掉(目录抽屉 / 遮罩 / 目录钮 / 顶部进度条 / toast),
但**方向钮必须留着**:用户可能就是横着拿,然后点开横屏视图。

这条代价在 v1.6.8 就写进 tech-design 了(未选 B 的理由之一),现在选了 B,如实兑现。

### 13.4 · 方向图标换成专用图标

原来用的是**摄像机图标**(`<rect x=2 y=6 w=14 h=12/>` + `<path d="M18 9l4-2v10l-4-2"/>`),
全仓三处都是它:右下方向浮钮、交叉表旁「横屏看」按钮、交叉表「手机看」提示。
换成专用的「屏幕旋转」图标:竖屏机身 + 顺时针弧 + 箭头,仍是项目自带的
Feather 风格(24×24 viewBox / `stroke=currentColor` / 描边 2)。
另加状态反馈:`aria-pressed="true"` 时图标本身转 90°,不用看文字就知道当前是哪种状态。

## 19 · v1.6.15 · 横屏切换从 1362ms 降到 ~300ms:去掉 iframe,原地换断点

### 用户的判断是对的:这本该只是前端样式变化

反馈「竖屏切换到横屏会有一段很长的卡顿,这是在干啥?不需要从后端交互吧」。
实测证实:点一下横屏 = **一次完整的 `/dashboard` 后端渲染 + 12 个脚本重跑,1362ms**
(beta 本机热缓存;真机走网络更久)。因为 v1.6.6 起横屏是靠**同源 iframe** 拿"独立 viewport"。
而 iframe 是新文档 → 滚动位置必然丢,这正是反馈④(在旭日章节切完回到顶部)。

### 关键发现:Tailwind 是运行时编译器,可以原地换断点

本项目用的是 **Play CDN 版 Tailwind**(运行时编译)。实测重新赋值 `tailwind.config`
会触发**就地重编译,114ms**,`md:` 当场从 off 翻到 on。所以 iframe 完全不必要:

| | 旧(iframe) | 新(原地) |
|---|---|---|
| 切换耗时 | **1362ms** | **~300ms** |
| 文档请求 | 1 次整页 | **0** |
| 脚本重跑 | 12 个 | 0 |
| 滚动位置 | 必丢 | 按章节还原 |

做法:① `sm`/`md` 换成「永远匹配」的 raw 查询(布局宽度是长边,但媒体查询看的是
`innerWidth`=短边,所以不能靠 min-width)② `body` 锁成「长边 × 短边」并在设备竖屏时转 90°
(视口单位交换,纯 CSS)③ 交回滚动位置。

### 四个实测踩到的坑

1. **`body` 自带 Tailwind `min-h-screen`** → `min-height` 压过 `height`,body 变成 844×844
   而不是 844×390,旋转后底部整段跑到屏外。要 `min-height: 0 !important`。
2. **`position: fixed` 在被 transform 的容器里会跟着内容滚走**(包含块变成 body)——
   退出钮实测滚到 rect 3413,730(屏外)。所以退出钮**放进导航行**(随 sticky 常驻)。
   这同时解决了反馈③:它不再贴着屏幕边缘,不会被 iPhone 圆角切到、按不稳。
3. **章节定位不能用 `getBoundingClientRect` / `scrollIntoView`** —— 横屏时 body 被
   `rotate(90°)`,rect 是**屏幕坐标**,阅读流的"上"映射到屏幕的"右",照它挑会挑到
   毫不相干的元素(实测退出后章节漂到 top=3125)。改成在**布局坐标系**里累加 `offsetTop`,
   并直接写 `scrollTop`。
4. **还原要重复几次** —— Tailwind 重编译是异步的(114ms),`rAF×2` 早于它落定,
   只做一次会被随后的重排冲掉。

### 图标(第四版):改用真实图标库

前三版都是我自绘(摄像机 → 旋转弧 → 竖框+横框+双向箭头),用户一直不满意。
这次按用户要求去搜图标库,选定 **Tabler Icons(MIT · 描边 24×24 stroke-2,与本项目同款)**
的 `device-mobile` / `device-mobile-rotated`,按钮显示**目标状态**:
竖屏时显示"横屏手机"(点它去横屏),横屏时显示"竖屏手机"。

### 已知取舍(如实记录)

图表**不会重建**,所以横屏下它们保留进入前那套配置(移动档:环图底部图例、半径 100)。
iframe 方案靠整页重载"顺便"重建了图表,代价是那 1362ms。
横屏的主要价值(宽表格、交叉表、导航、章节跳转)是纯 CSS,不受影响。
另外切换时会有 1 个 XHR —— 那是章节滚到位后 HTMX 的懒加载(内容分片),不是切换本身。

## 20 · v1.6.16 · 用户第 6 轮反馈六项

### ③ 退出横屏"要点很多次"

原因不是事件绑定,是**触摸目标太小**:旧 `min-height: 26px`,旋转后它在屏幕上只有
26px 宽的一条,远低于 iOS HIG 的 44pt。三处一起改:钮加到 34px、导航行抬到 44px、
加 `touch-action: manipulation`(去掉双击缩放的 300ms 等待 —— 等待期内的点击会被吞),
并在横屏态去掉 `backdrop-filter`(被 transform 的容器里它是 iOS 已知的命中/合成干扰源)。

### ④ 切换后图表溢出

只派发 `window.resize` 不够:
- **Chart.js 无参 `resize()` 实测读到旧尺寸** —— 横屏后画布仍是竖屏宽度,比容器窄 400+px
- **ECharts 根本不跟容器**,必须显式 `resize()`
- 归因等区块是 HTMX 懒加载的,时机更飘

改成**显式给容器 `offsetWidth/offsetHeight`**(布局坐标 —— 不能用 `rect`,body 旋转后宽高互换),
并在重编译落定后补两次。实测 9 个图(含懒加载的归因瀑布 / 12 月趋势 / 旭日)在
竖屏→横屏→竖屏三态下**溢出全部为 0**。

顺带纠正我自己的一次误判:上一轮我用 `getBoundingClientRect` 量溢出,在旋转坐标系里
宽高互换,量出来是假溢出(452px)。判据换成 `offsetWidth` 后全为 0。

### ⑤ 打标页手机端

先量了才知道瓶颈在哪:说明段只占 **186px**,而 **62 行 × 卡片化 ≈ 13800px** 才是主因。
所以三件事都做:
- **「只看未打标」纯前端过滤**(手机默认开)—— 打标是"把没标的标上",已标完的行没必要再占屏。
  只切 `display`,隐藏行照样随「保存全部」提交,**不丢数据**
- 说明段收成 `<details>`(PC 全文常显)
- 底部**常驻保存条** —— 不然要滑一万三千像素才能保存

### ⑥ 穿透资产写进介绍(两处)

`README.md` 与落地页「它解决什么」各加一问:
**「买了一堆基金,家里到底重仓了什么行业?」** —— 基金看不见成分,行业风险藏在名字后面;
穿透到每支基金的真实持仓(股 / 债 / 现金 + 申万行业),再以**家庭为整体**汇总。

## 22 · v1.6.18 · 用户第 8 轮反馈六项

### ① 环上补具体金额

三行(名称 / 金额 / 占比)对径向空间要求 ≈ 3 × 11px = 33px < 环带 42px,放得下;

### ② 「本期怎么变的」收入 / 支出没脱敏

**「本期收入 X − 支出 Y」那两个 `<b>` 根本没挂 `data-priv`** —— 隐私态下明文暴露。

顺带说明为什么既有的静态扫描没抓到:`PrivacyIsolationTest` 管的是 **LLM 脱敏**
(送给大模型的手机号 / 姓名),与 UI 的 `data-priv` 模糊是两码事。
所以这次补的守护是**网住这一类**:`_region.html` 里**所有** `${cf*Label}`(绝对金额)
必须带 `data-priv`,以后新增的也会被抓,不是只补这两处。当前 11 处用法全部合规。

### ③ 指标放行上点数字"没有下钻能力"

**先说实测结论:两种位置抽屉都会打开**,我在无头里逐一验过(指标在列 / 在行都 `OPENED`,
scope 正确)。所以不是失去了下钻能力。

真正的问题是**看不见它开了**:明细抽屉是表格**下方**的页内面板;指标放行时每个实体占 N 行、
表格高出数倍,而原来用 `scrollIntoView({block:'nearest'})` —— 'nearest' 只滚"最小距离",
抽屉常停在视口边缘之外。改成 `block:'start'` 直接带到视口顶部,并在打开时**闪一下边框**
给出"响应了"的确认。实测点第 9 个单元格:`top=620 · inView=true · scope=股票股权 × 共同`。

### ④ 横屏跨页面保持

状态写 `sessionStorage`。**关键不在于"记住",在于时机** ——
必须在 tailwind **首次编译之前**就据它选断点档并贴上 `html.ls-wide`,
否则新页面会先按竖屏排一遍再被 JS 扳过去,闪一下。做法与隐私模式的 FOUC 防闪同源。

实测:dashboard 进横屏 → 跳 `/accounts` → `ls-wide` 在、`body 844`、有 transform、
退出钮在、导航 7 tab 展开;退出后 sessionStorage 清空。

### ⑤ 归因部分坐标没脱敏(用户说"似乎有复现条件")

复现条件就是**它一直没脱敏**:归因的数字画在 **canvas** 上,
`html.privacy [data-priv]` 是 CSS 滤镜,管不到 canvas 像素。两件事都要做:

1. **生成文案时就判隐私**(`fmtShort` 在隐私态返回 `···`)
2. **隐私开关切换后重出图** —— 已经画好的像素不会自己变(与 lens.js 里旭日的同类监听同源)

实测隐私态下瀑布图柱顶全是 `···`,x 轴是类目名(基准 / 人赚 / 蚂蚁财富-基金…)不含金额。

### ⑥ 隐私态下浮钮位置偏移

`html.privacy #priv-float` 会**显出文字标签**变宽,而 dock 原来是 `align-items: center`
→ dock 宽度被最宽的那个撑开,另外两个居中钮跟着左移。

## 26 · v1.6.21 · 大陆用户装不上:去掉 Docker Hub 依赖 + 镜像源由脚本代劳

**用户反馈(第 11 轮)**:「我们的用户,大多都是中国大陆的网络环境,我让一个用户尝试安装,直接提示这个,然后他可能对电脑不太懂,直接卡住了。」

他贴来的实际输出:

```
⚠ 拉取基础镜像 mysql 超时 —— 这是中国大陆访问 Docker Hub 被限速/阻断的典型表现。
  · colima:编辑 ~/.colima/default/colima.yaml,在 docker: 段加 registry-mirrors —
  · Docker Desktop:Settings → Docker Engine,把 registry-mirrors 并进 JSON —
✗ 基础镜像仍拉不下来。按上面的镜像源指引配好 /etc/docker/daemon.json 后,重跑 bash deploy/docker-up.sh。
```

**这是一次真实的上手失败,不是"提示不够清楚"**:脚本诊断得完全正确、指引也精确,但它给出的动作是**让一个不懂电脑的家庭用户手改 Docker 引擎配置文件**。
对本项目的目标用户(家庭记账、非技术)来说,这一步就是终点 —— 提示写得再好也没用。

### FR-26-1 · 大陆默认装机不需要碰任何镜像源配置

| 装的东西 | 从哪来 | 大陆可达 |
|---|---|---|
| app 镜像 | GHCR | ✓ 直连 |
| ~~`mysql:8.0`~~ | ~~Docker Hub~~ | ~~✗ 限速/阻断~~ |
| **`mysql:8.0`(改后)** | **GHCR 上我们镜像的同一份** | **✓ 直连** |

`mysql:8.0` 是默认安装路径上**唯一**还依赖 Docker Hub 的东西。把它也放到 GHCR,大陆用户的默认路径就不再有任何被墙的一跳 ——
不是"给了更好的引导",是**把失败点删掉**。

用户可见效果:`bash deploy/docker-up.sh` 一条命令跑到底,不出现镜像源相关的任何提示。

### FR-26-2 · 万一还要配镜像源,脚本自己配,不要用户动手

兜底路径(GHCR 也不通、或要走本地构建拉 JDK 基础镜像)不再打印一屏教程,而是:

> `要我现在自动配好镜像源并重启 Docker 吗?(本机其它容器会中断十几秒)[Y/n]`

一句 `[Y/n]`,同意后脚本按引擎类型(colima / Docker Desktop / Linux 原生)自己写配置、重启引擎、自动重试。
三条对用户的承诺:**已有镜像源配置不覆盖**(可能是他自己配的)、**改前留 `.bak`**、**OrbStack 不自动改**(配置机制不稳定,宁可退回手动步骤也不写坏他的引擎配置)。
自动路径走不通时才退回原来的手动指引。

### FR-26-3 · 选定的源要记住

脚本探到能用的源后写回 `.env` 的 `MYSQL_IMAGE`,这样用户之后自己敲 `docker compose up -d` 不会又去撞那个不通的源。
想强制走 Docker Hub 官方(海外机器 / 已配好加速):`.env` 里设 `MYSQL_IMAGE=mysql:8.0`。

**存量 systemd 用户迁移(`migrate-to-docker.sh`)同样受益**:它自己生成 `.env`、直接 `docker compose up -d db`,原先也会撞 Docker Hub。
现在同样先探 GHCR 副本 → Docker Hub 并写进 `.env`;真两条都不通时不在迁移流程里改用户的引擎配置,而是指路去跑一次 `docker-up.sh`(那里会问一句后代劳)。

### 不做

- **不换数据库**(改用其他 registry 上的 MySQL/MariaDB):prod 已上线,换 DB 要逐个验 SQL 与迁移,风险远大于收益。
- **不自动改 OrbStack**:见上。
- **不在非交互环境擅自改用户机器**:无 tty 且没显式 `FINANCE_ASSUME_YES=1` → 不动配置,只打印指引。

## 27 · v1.6.22 · 装不上的第二个坎:数据卷是旧的、密码是新的

**用户反馈(第 12 轮)**:v1.6.21 的镜像问题解决了(`✓ GHCR 副本`),但换了个地方卡住 ——

```
· 等应用就绪(最多 ~90s)…
✗ 应用 90s 内没就绪。看日志定位(常见:DB 还在初始化 / 端口被占):
app-1 | ERROR 1045 (28000): Access denied for user 'finance'@'172.18.0.3' (using password: YES)
        …同一段无限重复…
```

用户问的是「是否我们的脚本鲁棒性不够」—— **是**。

### 真实原因(已在本机完整复现,连报错里的容器 IP 都一致)

MySQL 的账号密码**只在第一次初始化数据卷时**写入。而 Docker 的**命名卷不会随仓库目录一起消失**:
用户为了拿 v1.6.21 的修复重新下载了仓库 → `.env` 里生成了**新的随机密码** → 卷里还是**老密码** → 应用一直被拒。

**这个坎是我们自己的升级指引造成的**(上一版让他「重跑同一条命令」),而不是他操作有误。

### 更糟的是:三处判据全给了假阳性,把真因盖住

| 判据 | 本该说什么 | 实际说了什么 |
|---|---|---|
| compose 的 db 健康检查 | 数据库不可用 | **Healthy** |
| 容器入口的就绪检查 | 密码不对 | **「MySQL 就绪」** |
| 「是否全新空库」探测 | 查不了 | **「schema_history 表存在数=1」** |
| 一键脚本的超时提示 | 密码不匹配 | 「常见:DB 还在初始化 / 端口被占」(两个猜测都不对) |

于是用户看到的是「一切正常 → 然后莫名 90s 超时 → 一屏 Access denied」,完全无从下手。

### FR-27-1 · 脚本要自己发现,并且**不删数据**地修好

一键脚本现在会主动验一次数据库账号。进不去时:讲清原因(一句话:卷里是老密码),然后**把新密码同步进那个已有数据库** ——
用 MySQL 官方的密码重置手法,不需要旧密码、**不动任何业务数据**。修完自动继续,用户不需要做任何决定。

### FR-27-2 · 判据不许说谎

- 数据库健康检查、容器入口就绪检查:都改成真实查询。原来用的 `mysqladmin ping` 在「密码错误」时**也返回成功**(MySQL 的既定行为:服务器有应答就算活着)。
- 「是否全新空库」探测:查询失败就如实说「判不了」,不再和「表存在」混成同一个结果。
- 密码不对时**立刻**归因,不再白等 120 秒。
- 超时提示不再给猜测,而是**读日志按特征归因**:是密码问题就当场修;是端口占用就直说端口。

### FR-27-3 · 绝不擅自删用户数据

同步失败(或用户不同意)时,脚本**停在原地不动数据**,并给两条真出路:
① 还留着旧 `.env` → 放回去,数据完整保留(最稳);
② 那个库你从没真正用过 → 可以整卷删掉重来,并明确写出「`down -v` 会删掉全部数据、不可恢复」。
自动化环境里 `FINANCE_ASSUME_YES=1` 只会放行「不删数据的同步」,**永远不会**触发删卷。

## 30 · v1.6.25 · 「我拉了新代码重跑脚本,还是旧版本」—— 更新路径要能自查

**用户反馈(第 15 轮)**:「我们是一个开源软件,很多部署/更新的易用性还是做得很差。
我拉了新的代码重新运行了 `bash deploy/docker-up.sh`,依然是旧代码版本,我们期望我们的用户如何更新版本?」

### 查证:脚本没坏,是三件事叠出来的

端到端复现过(旧镜像在跑 → 跑脚本 → 容器确实换成新镜像),所以脚本的更新能力是好的。真因:

| # | 事实 | 用户感受 |
|---|---|---|
| ① | **`git pull` 拉到的新代码不进容器** —— app 来自 GHCR 预构建镜像;`git pull` 只影响 compose 文件与部署脚本本身 | 以为拉了代码就是新版 |
| ② | 打 tag 到镜像可用之间有**约 12 分钟 CI 构建** | 看到发布消息立刻更新 → 拉到旧镜像 |
| ③ | **脚本从头到尾不说版本**;`/health` 只有 `status`;落地页没有;版本徽记只在**登录后**的 nav 里 | 拿到旧版**无法自查**,而脚本还说「✓ 起好了」 |

③ 是困惑的直接原因 —— 前两条本来只是"要等一会儿",配上"完全没有反馈"才变成"这软件更新不了"。

### FR-30-1 · 版本必须不登录可见

`/health` 返回 `{"status":"UP","version":"1.6.25"}`。用户一条 `curl` 就能确认跑的是哪一版,
部署脚本也能读它。只暴露语义版本,不含构建号 / 主机 / 路径等运维细节。

### FR-30-2 · 脚本要给版本结论,而不是「起好了」

起之前读一次、起之后读一次,四种结论说清楚:

| 情况 | 输出 |
|---|---|
| 更新成功 | `✓ 已更新:v1.6.24 → v1.6.25` |
| 已经最新 | `· 版本无变化:仍是 v1.6.25` + `✓ 已是最新发布版` |
| 落后 | `⚠ 你在跑 v1.6.24,但最新发布版是 v1.6.25` + 「CI 约 12 分钟,过几分钟重跑」+ 说明 `git pull` 管什么 |
| 镜像早于 v1.6.25 | `· 读不到版本` + **仍然告诉他最新是 vX** |

最后一行是自查补的:恰恰是**旧镜像**才不返回 version,而这些用户最需要「最新是 vX」这句话。

与 GitHub 最新 release 对比需要联网;脚本本来就在联网拉镜像,查一个 tag 不新增暴露,
但仍给开关 `FINANCE_NO_UPDATE_CHECK=1`。

### FR-30-3 · 「怎么更新」要是文档里的一等公民

原先升级指令是埋在一大段文字中间的一句 `git pull && docker compose pull && docker compose up -d`,
而且三条并列会让人以为 `git pull` 是关键那步。现在 README 有独立的「更新到新版本」小节,
deploy/README 与 FAQ 各有对应段落,并明确写出上面 ① ② 两个机制。

**不新增更新脚本** —— 项目有入口收敛的原则(v0.7 就把 `docker-init.sh` 合掉了)。
`docker-up.sh` 同一条命令既是首装也是更新,幂等可反复跑。

### FR-30-4 · 顺手兑现上一版记下的两个既存缺陷

- **`/error` 页自己会 500(未登录时)**:真因是 Thymeleaf 的 `th:if` 与 `th:replace` 放在了同一元素上 ——
  片段包含优先级高于条件求值,`replace` 先执行,nav 片段带着 `state=null` 渲染并抛异常,
  **响应截断在 nav 中间**,而且它会**盖住真正的报错**。修法:条件外提;错误页 head 固定自包含
  (**错误页必须零依赖** —— 它依赖的正是刚刚出错的那套机制)。全仓同类共 5 处一并修,并加守护钉住。
- **持仓页异常文案与判据不一致**(仍写「仅 STOCK / CRYPTO / METAL」而判据自 v1.4 起含 WEALTH/CASH)→ 按实际支持集表述。

## 31 · v1.6.26 · 数据被清:定性、定责,以及把清理链全部改成 fail-closed

**用户反馈(第 16 轮)**:「我起了一个项目已经设置好了成员也更新了密码,更新了以后多了两个成员把我旧账户也刷掉了,多了 Alice bob。」

### 定性:Alice / Bob 不是"多出来的演示成员"

它们是 `db/migration/V2__seed.sql` 里**两个内置账号的 `display_name`**(id 1 = `diwa`/Alice、id 2 = `wangergou`/Bob)。

它们出现,只可能是**全新空库跑了 V2 种子** —— 因为 `V1__init.sql` 用的是**裸 `CREATE TABLE`**
(14 个,0 个 `IF NOT EXISTS`),迁移在已有库上重放会在 V1 就失败。所以"迁移把种子重灌进你的库"物理上不成立。

**结论**:那次是**数据卷被换或被删** —— 目录名变了(compose 项目名跟着变 → 新卷),或执行过 `down -v`。

### 定责:`down -v` 是我给的选项,门槛还太低

v1.6.22 我加的「凭据不匹配」指引里,`down -v` 是**并列的第二条出路**,并写着
「那个数据库你从没真正用过 → 可以整卷删掉从零开始」。

用户刚建过成员、改过密码,凭记忆判断"我没什么数据"极易判错,而删卷不可恢复。**这部分是我给的选项的责任。**

### FR-31-1 · 全新空库必须主动告知

`docker-up.sh` 起好后如果发现「只有 2 个内置成员 + 0 个账户 + 没人改过密码」= 全新空库,
就在**用户看得见的地方**说出来,并给出自查命令(`docker volume ls | grep db-data`)与两条回到旧数据的路。
此前这件事只写在容器日志的 `[entrypoint] FRESH_DB=yes` 里,用户直到发现数据没了才知道。

### FR-31-2 · `down -v` 降为第三选项,前两条都不丢数据

1. 放回旧密码(数据完整保留);
2. **保住旧卷,换个新项目名从零开始**(`COMPOSE_PROJECT_NAME=finance-new`,旧数据随时能捞回来);
3. 才是 `down -v`,并明确写出"会永久删除包括你已建好的成员、账户、账期、改过的密码"。
   判断标准也换成可核对的事实:「你有没有登录进去建过成员/账户」,而不是"我印象里没用过"。

### FR-31-3 · 清理链处处 fail-closed(排查中发现的两个真缺陷)

这两条与本次事故无关,但都能在别的场景真删数据:

- **互锁 fail-open**:`$(查询 2>/dev/null || echo 0)` —— 查询一失败就当 0,而 0 表示"没有真实数据、可以清"。
  **一道保命的互锁,在失败时选了破坏性的那一边。** 改成:任何判据查不出来 → 放弃清理。
- **信号太少**:只看 `audit_log` 与 `member.id>2`,"用内置两个账号 + 改过密码"的真实用户两条都不响。
  补上 `must_change_pw=0`(完成过首登改密)与「种子成员已改名」。

另外:**即使判定要清,也先 `mysqldump` 一份**(存到 `backups` 卷的 `pre-clean-*.sql.gz`);dump 失败就不清。
误判的代价从"不可恢复"降到"可恢复"。

### FR-31-4 · 「没有迁移记录」不等于「库是空的」

容器入口原来只看 `schema_history` 是否存在。恢复过 dump(未含该表)、手工建过库、迁移中途断掉,
都会出现"有数据但没迁移记录",而那种情况下按"全新"处理会把 `TRUNCATE` 落到真实数据上。
加第二重判据:业务表里只要有行,一律降级为非全新库。

## 34 · v1.6.29 · 报表 XIRR 的 tooltip 说谎 + 同页两套收入口径(PRD · 待评审)

**用户反馈(第 19 轮)**:「生产上又新的一个账期关账了,可是怎么报表页面计算的家庭 XIRR(含收入)怎么是 0?不对吧,你仔细检查下逻辑。」

### 先给结论:**XIRR 算得是对的**,0.00% 复现无误

在 prod 数据上逐步复算:

| 期 | 净资产变化 | 外部流入 | 投资损益 |
|---|---:|---:|---:|
| 2026-06 | −«A» | «B» | **−«C»** |
| 2026-07 | +«D» | «E» | **+«F»** |
| | | 合计 | **−1.04 元** |

−1.04 ÷ 〈金额已脱敏〉 = −0.00001% → 显示 `0.00%`。**6 月亏 33.03 万、7 月赚回 33.03 万,窗口内正负相消**,不是计算错误。
(7 月 65.47 万外部流入里 39 万是 `stock_salary` 薪资-股票——期权归属,算外部收入正确;6 月另有 12,434 USD ≈ 8.4 万的开账基线。)

**用户的怀疑是合理的,但矛头指错了地方** —— 让他觉得"不对"的是 tooltip,不是 XIRR 本身。

### FR-34-1 · tooltip 必须显示 XIRR 真正用的那两个端点(P0)

现在 tooltip 写:

> 资金流序列:期初净资产 **−¥0**(2026-05) → 各期外部净流入 → 期末净资产 **+¥733,258**(2026-07)

这两个数**都不是净资产**。它们取自 `netWorthTrendExOpening`(剔除累计开账基线的趋势,给财富水位用):

```java
BigDecimal firstNW = trend.get(0).value();   // trend = netWorthTrendExOpening(slice)
```

该序列首期值 = `netWorth(P1) − openingBaseline(P1)`,而首期所有账户都算"首次出现" → **首点按构造恒为 0**。
末点 733,258 也只是"剔掉存量本金后的净值",真实期末净资产是 **〈金额已脱敏〉**。

**XIRR 实际用的是 `−〈金额已脱敏〉 → +〈金额已脱敏〉`。** 一个号称"给你看真实中间数值"的 tooltip 显示了另一套数,
**比没有 tooltip 更糟** —— 它把用户引向"期初净资产怎么是 0"这个不存在的问题。

改法:tooltip 的端点改用 `netWorth(slice, first)` / `netWorth(slice, last)`(与 `familyXirr` 同源),
并把**开账基线**作为独立一项说清(它确实参与外部流入,用户有权知道)。

### FR-34-2 · `familyXirr` 与同页「人赚」统一到同一套收入口径(P0)

同一屏上两个指标读两套账:

| | 收入口径 | 支出口径 |
|---|---|---|
| `familyXirr` | **只读 `cash_flow`** | **只读 `cash_flow`** |
| 同页「人赚 / 累计净投入 / 本金vs收益」 | PMC 优先(`signum()>0`),否则回退 `cash_flow` | 同左 |

prod 上的实际后果:

| 期 | PMC 收入 | PMC 支出 | cash_flow 收入 | cash_flow 支出 |
|---|---:|---:|---:|---:|
| 2026-06 | **«G»** | «H» | **«I»** | 3,000 |
| 2026-07 | NULL(没填) | **21,837** | «E» | **0** |

→ 6 月页面「人赚」按 15.15 万算,而 XIRR 只扣了 8.15 万;7 月用户填的 21,837 支出 XIRR 完全没扣。

改法:`familyXirr`(以及 `familyTwr`,同样用 `periodIncome/periodExpense`)改用
`netInflowIncome/netInflowExpense`(PMC 优先),与 `pmcFirstNetInflow` 同源同分支。

**这会改变线上显示的数值**,必须提前说明:按 PMC 口径重算,prod 上该指标从 `0.00%` 变为约 **−0.20%**
(投入 〈金额已脱敏〉 / 回收 〈金额已脱敏〉)。这是**修正**不是回归 —— 原值少扣了用户已填报的支出。

### 不做

- **不改开账基线语义**:把新纳入的存量账户本金算外部资本流入是对的,继续保持。
- **不改 `stock_salary` 归类**:期权归属是公司发的薪酬,算外部收入正确。用户已用该类别标注,无需按来源再拆。

### 需要用户自查的一件事(非本版改动)

−«C» 与 +«F» **只差 1.04 元**。真实行情两个月一跌一涨到这个精度不合常理,

**结论:计算正确性本身没有查出错。** 24 个 KPI 都能从原始表精确复现,

问题集中在**锚点选择**与**口径文案脱节**。

### FR-236 · 收益类指标锚「最新已关账账期」,存量类仍锚最新一期

**问题**:取数是 `账户 × 账期` 全交叉且**不过滤账期状态**,所以进行中(未关账)的账期会进入窗口
并成为"最后一期"。而进行中账期的典型状态是**余额已填、收支未录**
(prod 2026-08 实测:21 条余额快照 / 0 条现金流 / 无成员收支)。
于是「(期末 − 期初 − 净流入)」里净流入 = 0,**还没录的工资被整块算成投资收益**——
prod 显示「本月资产收益 +0.99%」,那 9.1 万一分钱收支都没扣。

**规则**:
- **存量类**(净资产 / 总资产 / 总负债 / 流动资产 / 净资产环比)**继续锚最新一期** ——
  填报过程中本就该看到最新余额,且缺快照会结转上期,不会凭空缺口;
- **收益类**(本月资产收益 / 家庭 XIRR / 资产年化 TWR / YTD 累计损益 / 人赚钱赚拆解 / 储蓄率)
  改锚**最新已关账账期**;
- 一期都没关账的家庭 → 退回全部期(宁可给个数,不给空页面);
- 页面必须**显示口径期**:进行中时 KPI 标题显示为「资产收益 2026-07」,tooltip 补
  「口径期 2026-07(最新已关账期;当前月仍在填报,收支未录齐故不参与收益计算)」。

### FR-237 · 同名指标跨页必须取到同一批账期

**问题**:各页窗口宽度本来就不一致 —— 报表页自 v0.5.5 起把窗口锚「最新已关账期」
(当时注释写明就是为躲开月中半填的进行中账期),仪表盘用 `锚点 − 12 月`,体检页用 `锚点 − 11 月`。
FR-236 落地后,体检页窗口里只剩 11 个已关账期 → 走「不满 12 期」的累计口径,
而报表页拿得到 12 个 → 走年化口径。**同一个「家庭 XIRR」两页给出 −0.21% 与 +1.11%**。

**规则**:收益类统一取「**最近 ≤12 个已关账账期**」;体检页窗口在锚点仍在填报时多回一个月,
保证窗口内仍有 12 个已关账期。三页对同一指标必须取到同一批期、给出同一个数。

### FR-238 · 口径文案必须与实际计算一致

- **总资产 / 净资产**:文案写「CASH + STOCK + WEALTH + PROPERTY」,实际是「除贷款外的全部资产类型」
  —— **漏列加密 / 贵金属 / 保险**。beta 实测:总资产 ¥〈金额已脱敏〉 里这三类占 ¥635,536,而文案说不在里面。
  (prod 暂无这三类账户所以数字没错,但用户一加就错。)
- **流动资产**:PRD 两处 + 一处代码注释 + 实际实现共三个版本。实际行为(产品类目流动性优先、
  缺省按账户类型兜底,故货币基金类理财**计入**)是对的,错的是 PRD 措辞与那条注释 —— 本版校正文档。
- **紧急储备月数**:PRD 写「滚动 12 期月均支出」,实际是「最近至多 12 期**已填**收支的均值,
  除以实际期数」。实现更保守合理(不会低估月均支出),本版校正 PRD 措辞。

### FR-239 · 储蓄率全站一套口径(修「储蓄率目标进度恒为 0%」)

家庭目标里「储蓄率达到 X%」的当前值取自 `FactViewService.savingsRate`,而该实现
① 只读现金流、不走成员手填收支优先;② 锚最新一期(可能在填报中)。
prod 2026-08 没有现金流收入 → 返回空 → 兜底成 0 → **任何储蓄率类目标进度恒显示 0%**,
而报表页同名指标显示 96.66%。改成与人赚 / XIRR 完全同源(成员手填优先、否则现金流)+ 锚已关账期。

### FR-240 · 体检页「本年累计损益」负号被吃掉

模板对负数给的前缀是空串又取了绝对值 → 亏损 **−¥〈金额已脱敏〉 渲染成「¥〈金额已脱敏〉」**,
只有颜色透出亏损,数字本身读起来是盈利。同文件「本月资产收益」的写法才是对的。
**这条是双端渲染验收时肉眼发现的**:表达式语法合法、指标值也算对了,错在展示,
grep 类守护与单测都抓不到。全站扫了 12 处同类写法,只此 1 处同时取了绝对值 → 只此 1 处是缺陷。

### 线上处置

零 schema 迁移、零存量数据改写、纯读路径;AI 缓存按账期分片(是"那一期的建议"历史快照)不必清;
目标进度实时算不落库。回滚只回 jar。

**会改变线上数值(是修正不是回归)**:prod「本月资产收益 +0.99%」→ 锚 2026-07;
家庭 XIRR 由含进行中期的 +0.79% → 只算已关账期;储蓄率类目标进度由恒 0% → 真实值。

## 36 · 报表「账户级收益」手机端排版(v1.6.31)

### FR-241 · 该表在手机上必须能看到收益数字

用户反馈:「报表页面手机端那个账户明细,排版差劲的不行」。

实测(390×844)确认问题成立且比"不好看"严重:

| 现象 | 实测 |
|---|---|
| 表格宽度 vs 容器 | **1653px / 17 列** 塞进 **358px** |
| 手机首屏可见列 | 只有「账户 / 类型 / 类目」三列 —— **一个叫「账户级收益」的表,收益数字全在屏外** |
| 类型标签 | 列宽被压到 ~40px,「现金」竖着折成两行 |
| 区块高度 | 行高 ~140px × 18 行 = **1480px**,每行只承载账户名 + 折行标签 + 「未设」 |
| 手机专用布局 | **没有** —— 仪表盘 v0.8 起就有卡片块,本节一直漏做 |

**规则**:账户类列表在 <sm 一律用卡片布局,不让用户横向滚十几列。卡片沿用仪表盘既有范式
(同一份数据源 / 同一套「指标设置」门控 / 顶部指标 chips 继续生效),差别是本节主题是
「vs 基准」,所以主行右侧直接给跑赢/跑输判定:

- 主行:`[类型标签][账户名] …… [跑赢/跑输/持平 ±N pp]`
- 次行:`[当前价值 · 收益率] …… [展开]`
- 展开:类目 / 基准% / 其余按用户勾选的指标(两列键值)

两行都两端对齐,保证**有判定标签和没判定标签的卡片等高、右侧不参差**
(实测 18 张卡折叠态高度唯一值 = 67px)。基准% 刻意不放次行 —— 实测窄屏会折行并拖出一个孤立的「·」。

### FR-242 · 「pp」是单位,不该被大写成「PP」

`.pill` 带 `text-transform: uppercase`,于是「跑赢 +9.07pp」渲染成「跑赢 +9.07PP」。
pp = 百分点,是单位不是缩写。给这类判定标签单独关掉大小写变换(PC 与手机同一处修),
账户类型标签仍保持大写不变。

### FR-243 · 站内使用手册 `/help/how-to-use`

正文同 [`docs/how-to-use.md`](../docs/how-to-use.md),按**流程**而非按功能组织:

- **第三部分**:一条总原则 + 场景速查

页面另带**两处解释性动画**(网页版独有,文档版没有),只用在两个实测出来的易错点上:

| 动画 | 解释什么 | 为什么值得做成动画 |
|---|---|---|
| 演示 A | 为什么必须「先录收入、后核余额」 | 录一笔收入会**立即加进账户余额**;顺序反了会重复计。左右对照同起点 ¥16,519,错误侧停在 ¥36,519 变红 —— 文字要讲一整段 |
| 演示 B | 明细抽屉**只能从交叉透视的格子点开** | 很多人在旭日上反复点,不知道明细在哪。三步演示把「旭日缩范围 → 透视定位 → 抽屉落到单笔」的分工演出来 |

带 `prefers-reduced-motion` 降级;不加载任何外部字体 / CDN 资源(与 app 一致,CN 友好)。

### FR-244 · 新手很醒目,老手不打扰

**醒目态**:仪表盘 + 填报页顶部一张引导卡(四步缩略 + 「打开使用手册」+ 「知道了」)。
用 `localStorage.manualHintDismissedAt` 记时间戳,**一年内不再显示**;点「打开使用手册」也算已引导。
卡片默认 `display:none`、由脚本判定后才显示 —— 反过来做会让老用户每次进页面都闪一下卡片。

> 判据用 localStorage 而非服务端状态是用户拍板的。代价是**每台设备各提示一次**、清缓存会再来;
> 对「第一次用」的提示可以接受,换来的是零迁移、纯前端。

**常驻态**(卡片消失后必须还能找到):导航栏「手册」(PC 主栏 + 移动抽屉)、填报页标题旁「怎么填?」。
已登记进 `scripts/entry-points.json`(`id=manual` · `obvious` · pc+mobile),
由运行时入口可见性检查兜底 —— **防的就是「引导卡一年后消失,而常驻入口又被某次 UI 收纳干掉」**。
