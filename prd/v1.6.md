# PRD · v1.6 · UED 专项:看得清、点得中、信得过

> 本版不加新功能,只修体验。来源是一次完整的双端截图审计:`docs/ued-review-2026-07.md`
> (8 个页面 × PC/移动 = 16 张真机截图,对照 `docs/visual-spec.md` 逐条比对,提出 61 条)。
> 设计规范:`docs/visual-spec.md` · 现状梳理:`docs/design-system.md`

---

## 1 · 为什么做这一版

产品功能已经铺到 v1.5(记账 → 报表 → 体检 → 透视 → 基金穿透),但一直没有系统性地检查**用户实际看到的界面**。
这次逐页看真机截图,发现三类问题:

| 类别 | 典型症状 | 用户后果 |
|---|---|---|
| **信不过** | 同一时刻 dashboard 净资产 ¥4,209,016 / checkup ¥5399878,差 119 万;紧急储备 7.2 月 vs 723 月 | 两个数字不一致,用户不知道该信哪个 → 击穿对全部数字的信任 |
| **看不清** | checkup 全页金额无千分位(`¥5399878`);元信息色对比度仅 2.90:1;移动端旭日标签中文竖排 | 数字读不出量级;小字看不见;图表标签不可读 |
| **点不中 / 找不到** | 浮钮压住金额;移动端首屏 0 内容全是控件;填报页 13.9 屏 | 核心任务(每月填报)变成体力活 |

产品硬约束是「每月 10 分钟」,用户一个月来一次 —— **每次访问都是半个陌生人**。
上面每一条都在消耗那 10 分钟。

## 2 · 用户可见的改动

### FR-1 · 数字可信(P0)

- **体检与仪表盘同期同口径**:体检此前取「最新账期」(含测试用的未来账期),仪表盘取「不晚于今天的最新期」。
  两页 anchor 落到不同账期,同名指标数值不同。现统一规则,并在体检页标出
  **「数据截至 YYYY 年 M 月 · 与仪表盘同期口径」**——用户能自己确认两页是否同期。
- **金额一律带千分位**:体检家庭页 / 体检账户页 / 流水档案共 32 处此前直接输出 `5399878`,现为 `5,399,878`。
- **荒谬值不再报数**:紧急储备月数在月均支出接近 0 时会算出 723 个月(60 年),
  现超过 36 个月一律显示「> 36 个月」,并提示「月均支出偏低 · 先去填报补支出」。

### FR-2 · 已关账不再假装可填(P0)

账期关闭后,填报页此前仍铺满 18 个可编辑表单 + 保存按钮,用户填完才发现改不动。现在:

- 页顶「本期已关账 · 只读」横幅:说明原因 + 给三条去处(周期管理重开 / 去最新一期 / 看本期报表)
- 各账户行的余额表单、快捷支出、划转、贷款预测、刷新持仓估值全部不渲染
- 表单位置改显示「本期余额 · 已定稿」+ 锁图标
- 「提交本期」区改为陈述状态 + 看报表 / 回仪表盘

### FR-3 · 移动端首屏给结论,不给控件(P0)

四个分析页(仪表盘 / 报表 / 账户 / 填报)此前 844pt 首屏内看不到任何数据:

- 口径控件(账户范围 + 币种 + 多选筛选)在窄屏收进一行折叠条,摘要显示 `18 个账户 · CNY · 1Y`
- 仪表盘新增**「本期一句话」**:净资产 + 较上期 + 环比 + 储蓄率 + 未填提醒,直接回答「这个月还好吗」
- 说明性长文(流程说明 / 口径说明)窄屏折叠
- 页面顶部留白窄屏 40px → 20px

### FR-4 · 填报页从 13.9 屏压到 6.6 屏(P0)

18 个账户卡片结构完全一致、各约 400px,滚动中完全失去位置感。现在窄屏默认收起填报区,
每行只留摘要(名称 / 上期末 / 本期值 / 待填徽记),点开才展开表单。**PC 保持展开,行为不变。**

### FR-5 · 图表换成窄屏读得懂的形态(P1)

| 图 | 原来 | 现在 |
|---|---|---|
| 旭日图 | 标签沿弧旋转,中文被转到接近垂直、小块溢出圆外 | 环只负责结构:大块横排显示「名称 + 占比」,小块留白,精确数字看下方「切片排行」 |
| 资产配置环图(7 类) | 小扇片标签重叠、引导线在窄侧堆叠 | 类目 > 6 时换横向条形,金额与占比都标得下;≤6 类仍用环图 |
| 账户分布双向柱(21 个) | 全画进去,长尾条几像素,图高 648px | Top N(窄屏 7 / PC 10)+「其他 N 个」聚合 |
| 风险分布配色 | 高风险=紫 / 中风险=粉紫 / 低风险=青,从颜色读不出高低 | 改低→高顺序色阶(与体检风险图同一套) |
| 负债下降曲线 | Y 轴自适应(118 万–125 万),5% 降幅画成陡坡 | Y 轴从零起 —— 绝对量曲线不该夸大波动 |
| 仪表盘 5 个 KPI | 五个同等大小,第 5 个独占整行 | 窄屏主次网格:净资产跨两列 + 大字,其余 4 个 2×2 收紧 —— 5 个同屏可见(v1.6.0 曾做成横滑,经用户 review 退回,见 §5 ③) |

### FR-6 · 不再暴露技术细节(P1)

- 管理页 15 个入口的小标题此前是 URL 路径(`/ADMIN/FAMILY`),改中文功能分类,并按
  **家庭基础 / 口径与标签 / 日常运营 / 系统** 四组重排(此前 15 个平铺无层次)
- AI 诊断徽标 `OK / WARN / RISK` → `正常 / 注意 / 风险`;`cached` → `已缓存`
- 账期状态 `OPEN / CLOSED` → `进行中 / 已关账`;备份 `✓ SUCCESS` → `成功`
- 移除 `Spring Boot 3.3`、`PRD` 等内部术语
- `环比(MoM)` / `同比(YoY)` 去掉英文缩写
- 账户类型的枚举 code(`现金 (CASH)`)在移动端隐藏,PC 保留便于对照
- 基准对比 `跑输 -2.61pp` → `落后基准 -2.61 个百分点`,且去掉边框(它是数据事实,不是需要你决定的警示)

### FR-7 · 视觉阻断与一致性(P1)

- **浮钮不再压住内容**:隐私眼 / 目录钮从左下(内容起始边)移到右下,加 iOS 安全区,
  默认半透明让下方数字仍可读,滚动时进一步淡出,交互时恢复
- **网格空位不再露出色块**:9 个类型 ÷ 6 列、5 个 KPI ÷ 2 列时,空位此前透出米灰底色
- 账户表「主理人」列不再把「王二狗」挤成三行竖排
- 序号列去掉 `☰`(暗示可拖拽排序,但系统并无拖拽功能)
- 账户行 7 个等权操作按钮 → 高频 2 个留行内,其余收进「⋯」
- 目标页空状态:去掉重复的第二个主按钮,4 个入口改等宽 2×2,卡片收窄居中
- 全站 emoji 清零(17 处 🚀🗄💰✨⚠✓ 等换 inline SVG 或纯文字)

### FR-8 · 可读性底线(P1)

- 元信息色从 `#A09486`(对比度 2.90:1,连大字号 3:1 都不到)改为 `#706657`(5.5:1,过 AA)。
  原浅色降级为纯装饰用途。
- 铜金色新增文字专用档 `#85642F`(5.3:1)—— 原 `#B08642` 作小字仅 3.2:1
- 尊重系统「减少动态效果」偏好(此前仅落地页尊重)
- 装饰性英文小标题(`A·L·L·O·C·A·T·I·O·N`)窄屏隐藏 —— 此前把中文标题末字挤到第二行

### FR-9 · iOS 专项(P1)

主力用户是 iOS,以下每条都有具体失效场景:

- 横滑区(指标 pill / 交叉表 / 汇总带 / KPI 带)加 `overscroll-behavior-x: contain` ——
  **此前横滑到尽头继续拖会触发 Safari 返回手势,直接离开页面**
- 横滑区加 `scroll-snap` —— 此前会停在半个 pill 的位置
- 固定底部元素加 `env(safe-area-inset-bottom)` —— 此前在带 home indicator 的机型上贴近系统手势区
- 图表容器关 `-webkit-touch-callout` —— 此前长按图表弹出系统「拷贝图片」菜单

## 3 · 明确不做

| 项 | 原因 |
|---|---|
| 深色模式 | 「起居室里的银行家账册」的核心载体是纸,纸是亮的。做深色等于重定义整套隐喻,收益远小于成本 |
| 「本金 vs 投资损益」柱图分段/双轴 | 前 9 期贴零轴是因为末 3 期极值。改默认区间会牵动整页口径,需单独产品决策 |
| 账户级收益表收敛列数 | 哪些列算次要需要产品判断,不适合在 UED 专项里定 |
| 移动端拆「资产/负债两段列表」 | TopN 聚合后双向柱已降到 8 条可读,再拆收益有限 |
| 统一确认弹层替代原生 confirm | 11 处调用点,涉及交互流程改造,留待下一版 |

> 原列在此处的「移动端横屏看交叉表」已于 v1.6.1 实现 —— 当时判断「iOS 不支持 orientation.lock 所以做不了」是错的,
> 用 CSS rotate 自建即可,见 §5 FR-10。

### FR-10 · 自建横竖屏切换

此前 v1.5.2 与 v1.6.0 的判断是「iOS 不支持 `screen.orientation.lock`,只能提示用户自己转手机」——
这个判断是错的:游戏类 / 漫画类 PWA 早就在用另一条路 **自己用 CSS `transform: rotate(90deg)` 把内容转过来**,
视口宽高互换,用户看到的就是横屏。

现在交叉透视表右上有「横屏看」按钮(仅窄屏出现),点击后:

- 内容进入全屏并旋转 90°,视口宽高互换(`width:100dvh / height:100vw`)—— 表格列一次性铺开,不用横滑
- 顶部提示「把手机转横过来看 · 转好后画面自动扶正」
- **用户真把手机转横之后,自动撤掉我们的旋转**(监听 `orientationchange` / `resize`)——
  否则会把系统已经转正的画面又转回竖的
- 三条退出路径:退出按钮 / Esc / 浏览器返回(`pushState` 拦一层),不会把用户困住
- DOM 是**移入**旋转层而不是克隆,退出时原位放回 —— `lens.js` 持有的容器引用与按 id 重渲染都不受影响

实现是通用的声明式能力(`static/js/landscape.js`):任何元素加
`data-landscape="#选择器"` 的按钮即可获得横屏查看,后续宽内容(长表格等)可直接复用。

## 6 · v1.6.2 追加(用户 review 反馈 · 2026-07-27)

### BUG · 旭日大量扇形块既没名字也没数字(P0 · v1.6.1 引入)

v1.6.1 为了解决「窄屏标签被旋转成竖排中文」,把环内标签阈值提到 40°(占比 11%)——
但图下「小块补注」的阈值仍是 14°(3.9%)。**3.9%~11% 的块两边都不收**,而真实数据里这个区间的块最多,
于是一眼看去大半个环都是无标识的色块,组件几乎不可用。

修法:环内阈值与补注阈值**必须是同一个常量**(`SUN_LABEL_MIN_DEG = 32°`),中间不留缝。
同时取消「只给占比不给名字」的中间档 —— 只有数字没有名字对用户等于没有信息,那是半个盲区。
现在非黑即白:**≥32° 环内给「名称 + 占比」,小于 32° 整块进图下补注** —— 每一块都有名有数。

### FR-11 · 横屏升级为全局顶级功能

用户指出横屏不该只是交叉表的局部能力。现在 nav 里有横屏按钮(与 ☰ 菜单、隐私眼并列,窄屏出现),
汉堡菜单里也有一行带文字的入口;点击后**整页横屏**(转 `<body>`,nav / 浮钮 / 内容一起转),
状态记在 session 里、刷新后保持。交叉表的局部入口保留(用户认可)。

### 关于「屏蔽系统横屏」—— 平台做不到,改为让位

用户希望屏蔽 iOS 自身的横屏,避免"我们转 + 系统转"两次重排。核实结论:

- `screen.orientation.lock()` iOS Safari 与 iOS PWA 都不支持
- manifest 的 `"orientation": "portrait"` 我们**早就设了**(`ManifestController`),但 **iOS 不读这个字段**

所以屏蔽做不到,这是平台限制。改为**和平共处**:一旦检测到设备已物理横屏(系统已给真横屏),
我们就整体退出自己的旋转层,把方向交还系统 —— 用户只经历系统那一次不可避免的重排,
不再叠加"我们撤旋转"的第二次跳动(v1.6.1 是只撤 rotate 但留着层,所以会跳两下)。

## 7 · v1.6.3 追加(用户 review 反馈 · 2026-07-27)

### BUG · 旭日仍有大量空块 —— 前两次都没修对

这个问题我修了三次才对,过程本身值得记:

| 版本 | 做法 | 为什么不对 |
|---|---|---|
| v1.6.1 | 环内标签阈值提到 40°,解决「竖排中文」 | 图下补注阈值仍是 14°,**3.9%~11% 两边都不收** = 信息黑洞 |
| v1.6.2 | 两个阈值合并成一个(32°) | 窄屏本来就不画引导线,于是 32° 以下**全靠补注**;「行业集中」看板 59 块里只有 6 块环内有标签,环上仍是一片无字色块 |
| v1.6.3 | **承认图型容量有限,把小块聚合** | 见下 |

前两次都在「标注策略」上打补丁,而真正的问题是:**一个 320px 的环里塞 59 块,平均每块 6°,无论怎么标注都不可能可读**。
中间还试过给窄屏也开引导线,结果名称被容器裁成残字(「货币基金/存款 4.6%」渲染成「⌐ 4.6%」),
补注列到 22 项、出现 7 个重复的「支付宝·蚂蚁财富」(不同行业下的同一平台),比不标更糟。

最终做法是数据可视化的通行惯例 —— **Top N + Other**:同一层里小于阈值(窄屏 18° ≈ 5%)的块合并成
「其他 N 项」。实测「行业集中」内环 59 块 → 6 块,每块都够大、都有名有数;要穷举请看下方「切片排行」,
它本来就是完整列表。聚合块是虚拟的,点它不下钻,会提示去看排行。

### 连带修掉两个隐蔽问题

- **窄屏判断不能用 `clientWidth`**:原先用 `#sunburst` 的 `clientWidth < 480`,但这个值依赖布局时机 ——
  同一元素在不同时刻会读到 630 / 321 两个值,于是聚合阈值悄悄走了 PC 档,**改了参数却不生效**。
  改用 `window.innerWidth < 768`(与全站响应式断点同源)。
- **渲染失败被静默吞掉**:旭日崩溃时异常落进 `Promise.all().catch()`,而 catch 只往 `#pivot` 写错误、
  又被随后成功的 `renderPivot` 覆盖 —— 结果图表挂了却全站无声。现在同时 `console.error` + 就地在旭日容器内报错。
  (这次排查正是卡在这一点:页面无报错、无失败请求,只有 skeleton 一直转。)

## 8 · v1.6.4 追加(用户 review 反馈 · 2026-07-27)

### BUG · 旭日「一块饼图直接消失」

聚合出的「其他 N 项」内环块此前 `children: []` —— 旭日里内环块没有子块,**它对应的那段外环就是白色缺口**,
看起来像饼图缺了一块(资产类型看板切「下一层按币种」时最明显)。
修:给聚合块一个占满父角度的同族子块(更浅一档灰)。

### FR-12 · 方向切换改为右下浮钮

不再放在顶部导航,改为与隐私眼、目录钮同一列的右下浮钮(仅触屏窄屏出现)。交叉表里的快捷入口保留,
但它现在调用的是同一个开关 —— 不再维护第二套局部旋转层。

### FR-13 · 不再响应手机自身的横竖屏

用户要求「只能通过我们的按钮切换方向,不响应手机本身的旋转」—— **这个能做到**,前两版我判断错了。
系统旋转屏幕我们阻止不了,但「页面要不要跟着转」完全在我们手里:

| 设备方向 | 期望方向 | 我们做什么 |
|---|---|---|
| 竖屏 | 竖屏 | 不动(零开销) |
| 竖屏 | 横屏 | 顺时针 90° |
| **横屏** | **竖屏** | **逆时针 90°(把内容转回竖直)** ← 这一条就是「屏蔽系统横屏」 |
| 横屏 | 横屏 | 不动 |

最后一条是关键:用户把手机转横,我们反向转回来,内容相对机身始终不动 —— 视觉效果与系统竖屏锁定一致。
桌面端完全排除(桌面恒满足「宽>高」,不排除会被永久反转 90°)。

### FR-14 · 两个配置图形态一致

「资产配置」与「按成员分布」此前一个是环图、一个是条形,手机上并列看着不像一套东西。
抽共用工厂 `hBarConfig`,窄屏两者一律横向条形(窄屏环图标签必然重叠);PC 保持「>6 类条形、≤6 类环图」。

## 9 · v1.6.5(用户 review 反馈 · 2026-07-27)· 整页旋转方案作废

用户在真机上试了 v1.6.4 的整页横屏,报了三条:
① 横屏后顶部菜单会莫名展开 ② 三个浮钮消失或显示不稳定 ③ 切成横屏后再转手机,页面仍有大幅转动

三条是同一个根因,而且是**结构性的**:

> **CSS 媒体查询只认 viewport,不认我们的 transform。**

设备横屏时 viewport = 844px,于是:

- 我为 v1.6 加的 **7 处** `max-width:767/640` 移动端样式全部失效 ——
  KPI 带回网格、汇总带回网格、折叠条 summary 显形、**浮钮 `display:none`**(=反馈②)
- 模板里 **347 处** Tailwind `sm:` / `md:` 前缀全部切到宽屏分支 → 布局跳成 PC 版(=反馈③的"大幅转动",
  它不是动画,是整页重排)

而 Tailwind 那 347 处是媒体查询编译产物,**无法用 class 覆盖**。要让"旋转后仍按窄屏渲染",
只能把全站响应式改成 container query,或把页面塞进固定宽度的 iframe —— 都不是这个版本该做的事。

**结论:整页旋转与现有响应式体系不兼容,方案作废。**

### 现在的做法:只旋转宽内容

页面用 `data-landscape-target="标题"` 声明"本页可横屏看的元素"(目前是交叉透视表)。
点右下横屏浮钮 → 只把那个元素移进全屏旋转层,**body 永不旋转**:

- 被转的是独立容器,内部不依赖响应式断点 → 上面三条一条都不会发生
- 页面其余部分完全不受影响
- 没有声明目标的页面,浮钮自动隐藏(不给无效入口)

浮钮可见性只由 `(pointer: coarse)` + JS 判断本页有无目标决定,**不再带任何 `max-width`** ——
那正是反馈②的直接原因。

### 关于"屏蔽手机自身的横竖屏"

这一条**做不到**,如实说明约束:

- `screen.orientation.lock()` iOS Safari / PWA 均不支持
- manifest 的 `"orientation": "portrait"` 我们早就设了,但 iOS 不读该字段
- CSS 旋转能"抵消"系统旋转,但代价是上面那 354 处响应式全部错位

局部横屏不受这条限制 —— 它不关心设备方向:设备竖着时由我们代转 90°,
用户真把手机转横了就摘掉旋转交给系统,两种情况下看到的都是铺开的宽表格。

## 10 · v1.6.6 · 整页横屏(iframe 隔离)· 方案由用户拍板

### 先记一次流程错误

v1.6.5 我在遇到技术障碍后,**未经用户同意就单方面把「整页横屏」改成了「局部横屏」并部署**。
用户明确要求的是整页横屏 + 不响应手机旋转;遇到冲突时正确做法是**把冲突与代价摆出来、等用户决定**,
而不是替他改需求。这个决策权不在实现方。

### 前四版为什么都失败(同一个根因)

v1.6.2 / v1.6.3 / v1.6.4 都是直接 `transform` `<body>`,真机三个副作用:
① 顶部菜单莫名展开 ② 三个浮钮消失或不稳定 ③ 转手机时页面大幅重排。

结构性根因:**CSS 媒体查询只认 viewport,不认 transform**。设备横屏时 viewport = 844px,于是

- 模板里 **453 处** Tailwind `sm:` / `md:` 全部切到宽屏分支
- 自有 **13 处** `@media` 中的移动端规则失效(含浮钮的可见性 → 反馈②)

而 Tailwind 那 453 处是媒体查询编译产物,**无法用 class 覆盖**。

需要说明的是:「屏蔽系统旋转事件」这件事本身**能做到**(不监听即可),但屏蔽事件不等于屏蔽效果 ——
viewport 尺寸是真实变化的,CSS 对它的响应属于渲染管线,没有可移除的监听器。
所以问题从来不是「方向」,是「响应式断点」。

### 现在的方案(用户在三条路里选的 A)

把页面装进一个**固定尺寸的同源 iframe**,只旋转这个 iframe:

- iframe 有独立 viewport → **453 处响应式一行都不用改**,在 iframe 内全部正确
- iframe 尺寸在进入横屏时定死(长边 × 短边,如 844×390),**此后不随设备方向变化**
  → 用户转手机时 iframe 内 viewport 恒定,**内容零重排**(这正是需求③)
- 内部 viewport = 844 → `md:` 生效 → 宽表格真正铺开(这才是「横屏化」的意义)
- 设备已横屏 → 外层不转,直接铺满;设备还竖着 → 外层转 90°
- 同源 iframe 共享 cookie / sessionStorage → 登录态、隐私模式、字号档位全部沿用
- 嵌套自检:iframe 内用 `window.self !== window.top` 识别,隐藏横屏入口(防套娃)、跳过首屏印章动画
- 在 iframe 里导航过的话,退出时把父页面同步到那个地址,不让用户白点

实测(390×844 → 844×390 切换):iframe 内 viewport 恒为 844×390,`body.transform` 恒为 `none`,
顶部菜单不再展开,浮钮不再消失。

## 11 · v1.6.7 · 断点改成「看短边」· 方向这条路我找错了地方

### 用户第五次反馈同一件事

「还是不对劲,依然随着手机横屏转动了」。前四版(v1.6.2/1.6.3/1.6.4 整页 body 旋转、
v1.6.6 iframe 隔离)全都在跟**方向**较劲 —— 方向不是问题所在。

用户确认了两个场景都坏:
1. **普通竖屏页面下转手机** → 页面变宽屏布局。v1.6.6 完全没管这个场景。
2. **进了横屏模式后转手机** → 看见内容转了一圈。

### 真正的 bug:453 处断点全都只判宽度

手机横屏是 **844×390**。只看宽度 → 844 被当成宽屏设备 → 模板里 453 处
Tailwind `sm:`/`md:`/`lg:` 集体切到宽屏分支。

**手机横屏的特征是短边只有 390,不是宽边有 844。** 这句话就是整件事的答案。
iPhone 横屏 `innerHeight` ≤ 440(最大的 16 Pro Max 短边 440),PC 窗口极少矮于 480
→ 判据加一条 `and (min-height: 480px)`,阈值 480。

三处判据必须同源,少一处就是「CSS 是移动的、JS 却是 PC 的」半修状态:

| 判据出处 | 覆盖 |
|---|---|
| `tailwind.config` 的 `theme.screens` | 453 处 Tailwind 断点(一处改动全覆盖) |
| `style.css` 自有 `@media` | 10 处 |
| `window.vpNarrow()` | 图表脚本里原本 **22 处**硬编码宽度比较 |

例外:横屏 iframe 也是 844×390,但那是用户主动点出来的宽屏视图 →
`window.self !== window.top` 自检加 `is-embedded`,走「只看宽度」那一套。

### 场景 2:iOS 那段旋转动画抹不掉,只能盖住

已查证的三条死路,不是推断:

| 手段 | 结论 |
|---|---|
| `manifest.orientation` | iOS Safari **不支持**(MDN browser-compat-data:`safari: false`) |
| `screen.orientation.lock()` | 需要 fullscreen;iPhone Safari 没有元素级 fullscreen |
| `orientationchange` | 事件 non-cancelable,拦不住 |

末态本来就是对的(内容钉在设备坐标系、iframe 内零重排),坏的只是那 0.4s 过程。
所以旋转期间把内容盖成一张纯色纸面 —— 纯色转动看不出转动。
**盖必须瞬间**(`transition: none`),否则旋转已经开始、内容还在淡出,那一眼就露了;揭开才淡入。

### 这一版做到哪、没做到哪(用户选的「分两步」第一步)

- **做到**:手机横屏不再切宽屏布局。实测 844×390 与 390×844 的
  `md:` 状态、KPI 列数、折叠把手可见性、以及全部 Chart.js 图形态**逐项一致**。
- **没做到**:内容仍会横向拉宽到 844(不是布局切换,但仍是变化)。
  要做到完全不动,需要第二步「宽度锁 390 + 反向旋转」—— 等用户看过真机再定。
- **已知副作用**:PC 窗口高度 < 480px 会退成移动布局。取舍见 tech-design §17。

### 顺带发现的一个真 bug(本版未修)

`static/manifest.webmanifest` 是 **0 字节空文件**(2026-05-10 建了就没填过)。
iOS 靠 `apple-mobile-web-app-capable` 撑着还能加主屏,但 Android/Chrome 的 PWA 安装是坏的。
与本次改动无关,单独记一笔。

## 12 · v1.6.8 · 照行业通行写法重做:尺寸交给 CSS

### 用户让我先做调研,调研结论推翻了我的实现方式

查了 GitHub 代码搜索(同类写法 4192 处命中)+ 逐个读源码:

| 来源 | 关键写法 |
|---|---|
| `QiShaoXuan/css_tricks` 横屏范文 | `width:100vh; height:100vw; rotate(90deg)`,由 `@media (orientation: portrait)` 驱动 |
| `MapoMagpie/comic-looms` 漫画阅读器(**有滚动**) | `transform:rotate(90deg); width:100vh; height:100vw; transform-origin:0 0; left:100vw` |
| `TheCaveMembership/izzapay` 游戏方向插件 | `BASE_W=960, BASE_H=540` 固定设计稿 + 整体缩放旋转,内容全绝对定位,**零媒体查询** |
| SO 8883163(112★) | 软键盘弹起会让 `orientation` 翻转 → 必须叠宽度约束 |

**共同点:尺寸用交换后的视口单位,旋转由媒体查询驱动,JS 里一个监听都没有。**

### 我们不行的原因(逐条 diff)

| # | 行业做法 | v1.6.6/1.6.7 的做法 | 后果 |
|---|---|---|---|
| 1 | `width:100vh; height:100vw` + 媒体查询成对交换 → 两方向下盒子**物理矩形自动相同** | JS 进入时量 `innerWidth/innerHeight` **写死 px** | iOS 竖屏工具栏 ≠ 横屏工具栏,竖屏量到的短边在横屏不成立 → 旋转后尺寸错、位移 |
| 2 | 零 JS 监听,媒体查询与 iOS 重排同一时刻生效 | 监听 `orientationchange` + 220ms 后 toggle class | 扳正永远**晚于** iOS 旋转动画 → 先跟着转一圈再被扳回 = 两次运动 |
| 3 | — | 我的媒体查询没防软键盘 | 竖屏打字时 `orientation` 翻成 landscape → 页面会莫名变向 |
| 4 | 单位:`vh`(large viewport,恒定) | v1.6.1 注释写「用 dvh 而非 vh,因为 iOS 地址栏收放会改变 vh」—— **正好说反** | `dvh` 才是随工具栏变的那个;用它当固定尺寸 → 工具栏一收放就重排。这个误解一路带到 v1.6.6 改成 JS 量 px |

**第 1、2 条是根本**:我把本该交给 CSS 的事用 JS 量 + 监听实现,所以必然慢一拍、必然量错。

### 这一版怎么改

**横屏模式**:舞台尺寸全部交给 CSS,`landscape.js` 不再计算任何尺寸、不再监听 `resize`。
另外**横屏模式里不显示顶部导航** —— 三个实测理由:844 宽放不下 7 个 tab(每项都折两行)、
390 高里导航占 64px(六分之一)、以及用户在 v1.6.4 就说过「横屏以后会莫名其妙打开顶部 tab 菜单栏」。

**普通模式(场景①)**:手机横屏时把 `body` 宽度锁回**短边**(= 竖屏那个宽度)并居中。
排版与竖屏逐像素相同,内容一个字不动;两侧留白压深一档 + 描边,读成刻意的信箱边距;
浮钮用 `calc((100vw - 100vh)/2 + 14px)` 收进内容栏内。

### 为什么不做「反向旋转钉在设备坐标系」

那才是严格意义的"等同系统旋转锁定",但代价是:

- 旋转符号取决于用户**顺时针还是逆时针**转的手机(`window.orientation` 90 / -90),判错就上下颠倒
- `body` 变成滚动容器 → 丢滚动位置

而信箱式居中没有这些代价,**转过去内容仍然是可读的**(钉在设备坐标系是躺倒的,用户还得转回来)。
两者是一行之差 —— 真机看过之后由用户定要哪个。

### 实测

| 项 | 结果 |
|---|---|
| 横屏模式舞台 CSS 盒子 | 竖屏 / 横屏都是 `844×390`,**无任何 JS 内联尺寸** |
| 横屏模式 iframe 内 viewport | 两向都是 `844×390`(零重排) |
| 普通模式排版宽度 | 竖屏 390 / 横屏 390(**逐像素相同**),卡片都是 360 |
| 普通模式横屏居中 | 左边距 227px,无 transform |
| PC 矮窗 1440×460 | body 仍 1440(`pointer: coarse` 挡住了) |

## 13 · v1.6.9 · 方案 B(用户选定)+ 专用方向图标

### 13.1 · 「横屏模式下转手机仍会转一次」—— 这条不是缺陷,是逻辑必然

用户问:这个是不是无法避免?**在 Safari 里无法避免,而且原因不在实现,在需求本身互斥。**

横屏模式的目的是「转过手机来读宽表格」,也就是要求**内容在世界坐标系里保持正立**。
而"不响应手机旋转"要求**内容在设备坐标系里不动**。设备一转,这两件事就是对立的:

- 要正立 → 必须跟着设备方向调整 → 一定"响应"了旋转
- 要不动 → 内容会躺倒 → 转过去也读不了,横屏模式就失去意义

所以横屏模式只能选"正立",剩下能做的只是**把过程盖住**(遮帘)。而 iOS 自己那段旋转动画
无法抹掉,已查证的三条死路:`manifest.orientation` iOS 不支持(MDN BCD:safari `false`)、
`screen.orientation.lock()` 在 Safari 是 `false`(MDN BCD 实测)、`orientationchange` 不可 cancel。
更麻烦的是 iOS 往往在旋转**之后**才派发 `orientationchange`,所以遮帘可能盖不住开头那一瞬。

**游戏为什么看起来没有这个问题**:三种情况 —— ① 它们是横屏专用,用户本来就横着拿,游戏过程中
根本不发生旋转;② 很多"PWA 安装的游戏"其实是 Capacitor/Cordova 之类原生外壳包的,方向锁在
原生层(`UISupportedInterfaceOrientations`),那是网页拿不到的能力;③ 用户自己开了系统旋转锁定。

**给用户的实际办法**:在 iOS 控制中心打开「竖屏方向锁定」。系统就再也不会旋转,
而我们的横屏钮是纯 CSS 变换、不依赖设备方向,照样能用 —— 那时"只能通过我们的按钮切换方向"
就是字面意义上成立的。

### 13.2 · 普通模式改成方案 B(钉在设备坐标系)

用户在 A(信箱式居中)/ B(反向旋转)里选了 **B**。效果 = 只对本 app 生效的「竖屏方向锁定」:
转手机时页面在屏幕上一动不动,要读还得转回来。

零重排的来源:`body` 盒子 = `100vh × 100vw` = 短边 × 长边 = **竖屏那个形状**
(视口单位在横屏自动交换),排版宽度仍是短边。
实测竖屏 / 横屏:`body 390` / 卡片 `360×92` / KPI `360` —— **逐项相同**。

两件 CSS 做不到、必须 JS 兜的事:

1. **旋转符号**:`screen.orientation.angle` 的定义是 viewport 相对自然方向**顺时针**转过的角度,
   抵消就是转 `-angle`。angle 90(设备逆时针转)→ `-90°`;angle 270(设备顺时针转)→ `+90°`。
   iOS 16.4+ 有 `screen.orientation`,更老回落 `window.orientation`。判错的表现是内容上下颠倒。
2. **滚动位置交接**:冻结时滚动容器从 `html` 变成 `body`,两者的 `scrollTop` 是两套值。
   不接一下就会跳回顶部 —— 而「跳回顶部」正是用户最反感的那种"页面动了"。
   实测滚到 600 → 转横屏 `body.scrollTop=600` → 转回竖屏 `documentElement.scrollTop=600`。

### 13.3 · 方案 B 的固有代价(实测踩到了)

`body` 被 `transform` 之后,它内部所有 `position: fixed` 浮层的**包含块从视口变成 body 盒子**。
这些浮层的几何(`inset-x-0`、`bottom: 0`、收起态 `translateY(110%)`)都是按"未旋转的视口"写的,
放进旋转容器就会错位 —— **实测目录抽屉直接漏进屏内**。

冻结态的语义是「用户误转了手机、马上会转回来」的过渡态,不需要这些浮层 →
几何脆弱的一律藏掉(目录抽屉 / 遮罩 / 目录钮 / 顶部进度条 / toast),
但**方向钮必须留着**:用户可能就是横着拿,然后点开横屏视图。

这条代价在 v1.6.8 就写进 tech-design 了(未选 B 的理由之一),现在选了 B,如实兑现。

### 13.4 · 方向图标换成专用图标

原来用的是**摄像机图标**(`<rect x=2 y=6 w=14 h=12/>` + `<path d="M18 9l4-2v10l-4-2"/>`),
全仓三处都是它:右下方向浮钮、交叉表旁「横屏看」按钮、交叉表「手机看」提示。
换成专用的「屏幕旋转」图标:竖屏机身 + 顺时针弧 + 箭头,仍是项目自带的
Feather 风格(24×24 viewBox / `stroke=currentColor` / 描边 2)。
另加状态反馈:`aria-pressed="true"` 时图标本身转 90°,不用看文字就知道当前是哪种状态。

+ 字号钮 + 隐私钮 + 账期 pill + 用户名**一起挤**的结果。给横屏一套尺度就全放得下。

### 390 高才是真正稀缺的资源

| 项 | 改前 | 改后 |
|---|---|---|
| 导航栏高 | 64px | **38px** |
| `main` 上/下内边距 | 30 / 30 | 8 / 14 |
| 标题块 `mt-10` | 37.5px | 8px |
| **首张卡片位置** | **221px(屏高 57%)** | **169px** |

压的是**间距与大标题字号,不删任何内容**。`text-2xl` 那一档特意不压 —— 它大量用在金额上,
压了会伤可读性(见 visual-spec「可读 > 可点 > 可懂」的优先级)。

### 隐私钮从浮层挪进导航条

实测隐私浮钮在 390 高的横屏里会**压住内容**(压住交叉表的「AI 解读当前视图」按钮)。
而横屏导航条里 tab 结束在 335px、退出钮从 726px 开始 —— 中间 **390px 全是空的**。
把隐私钮放回导航条:既不压内容,又比浮钮更好找。目录钮在横屏(整页就一屏多点)无意义,一并收起。

### 其余取舍

- 品牌只留印章图标:文字 + 版本徽记在 38px 栏高里是纯消耗,而印章已足够辨识
- 选中态下划线原本靠 `pb-[18px]` 撑到 `h-16` 的底,栏高压扁后必须重算,否则下划线跑到栏外
- 字号档位 / 账期 pill / 用户名 / 退出:横屏是一次性阅读视野,退出横屏后都在
- 竖屏与 PC 实测未受影响(栏高仍 61px,品牌文字与右侧组都在)
