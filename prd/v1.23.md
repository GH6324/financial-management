## 0 · 这一版在解决什么

**背景与现状。** 系统每天 00:30 跑 `PeriodOpener.openIfDue()`:到了新账期起始日,
先把仍为 OPEN 的旧期 `force-close`,再建新期。

于是 **9 月 1 日凌晨 00:30,8 月账期就已经关了**。

而微信、支付宝、信用卡这些 App 最方便拿到的是「**8 月整月支出**」——
那个数字要等 8 月结束之后才确定。用户 9 月 1 日白天打开账单准备填时,8 月已经是 CLOSED,
而已关账的期是**硬拦**的(`EntryService.requireOpenPeriod`、`BillCommitService` 都拒绝写入)。

**剩下两条路,都要额外操作**:

| 路径 | 代价 |
|---|---|
| 月底提前填(PRD v0.4 的默认节奏「月末倒数 2 天」) | 最后两三天的消费要**自己补算** |
| 月初拿到完整账单再填 | 去管理页**重开上期 → 改 → 再关账**,三步,还要填一个原因 |

**一件让这个冲突更严重、而 issue 里没提的事**:v1.21 上线了「**批量导入月账单**」——
传支付宝/微信导出的 csv,几百笔自动归类。而那个功能**天然的使用时点就是次月月初**
(月中导只有半个月的数据)。**我们自己的新功能和旧的自动关账机制正面打架了**,
只是此前没人把这两件事放在一起看。

**这一版换的是什么。** 两件事,一起做:

1. **关账时机从写死的 `00:30` 变成家庭自己配。** `cron = "0 30 0 * * *"` 是开发者定的,
   没有任何理由它该由我决定而不是由这个家庭决定。
2. **让核心能力真正扛得住「上一期还开着、新一期也开着」这个状态** —— 逐组件、逐指标、
   逐操作把数据逻辑说清楚(§4)。

**服务谁**:所有按「每月集中维护一次」使用的家庭 —— 也就是这个项目的主要用法。

**主推动力**:**补上「每月 10 分钟」在真实节奏下漏掉的那一块**。
这不是加功能,是我们承诺的东西在现实节奏下没兑现。

**本版新引入的名词**:

| 名词 | 定义 |
|---|---|
| **关账宽限** | 账期结束后仍保持 OPEN 的天数。家庭可配(T+0 / T+2 / T+5 / 手动)。默认 **T+0 = 今天的行为** |
| **双活跃窗口** | 宽限期内,上一期与新一期**同时 OPEN** 的那段时间 |
| **补录期 / 进行期** | 双活跃窗口内的两期。**补录期** = 已自然结束、宽限内仍可写的上一期;**进行期** = 正在过的新一期 |
| **归属判据** | 一个写操作把数据落到哪一期的规则。三选一:显式选期 / 事件时点 / 永远最新(§4.1) |

既有名词(账期 / 关账 / 封板 / affects_balance / 存量类与收益类 / 口径 A、B)
单一定义在 `AGENTS.md`、`prd/v1.21.md` 与 `FactSlice` 的类注释。

## 1 · 调研

**外部依赖:无。** 改的是自己的账期生命周期。

唯一与外部有关的事实(已由提交者指出、我们复核过):
**自然月账单在自然月结束之后才可得** —— 这是所有支付 App 的共同行为,不是某一家的限制。

### 1.1 真正要调研的是我们自己:30 处「当前账期」

`PeriodMapper.findCurrentOpen` 的 SQL 是:

```sql
WHERE family_id = ? AND status = 'OPEN' ORDER BY period_start DESC LIMIT 1
```

**两期 OPEN 时它静默返回最新那期,不报错、不告警。** 全仓 **30 处**调用点,
每一处都隐含「只有一个 OPEN」的假设。这一版的工程量**主要不在新功能,在这 30 处**。

> **一个必须说清的事实**:双 OPEN **今天就可达** —— 在管理页重开一个已关账期时,
> 它和当前期就同时 OPEN 了。也就是说下面这批问题**现在已经存在**,
> 只是那条路径少有人走,从没被系统性检查过。这一版不是引入风险,是把一个既有的
> 未定义状态变成一等公民并补齐语义。

按「双 OPEN 时选最新对不对」分四类:

**A 类 · 选最新是对的(9 处)· 无需改**

`AccountValuationService` ×3、`StockHoldingService` ×2、`HoldingImportService`、
`FxService`、`AccountService`、`NavService`

理由:这些都是**「现在的市值 / 余额 / 汇率」**。世界上只能有一个「现在」,
估值必须写进最新期,**绝不能回写补录期**。

**B 类 · 双 OPEN 下会算错(7 处)· 必须改**

| 位置 | 双 OPEN 时发生什么 | 严重度 |
|---|---|---|
| `ExpenseLedgerService:198` `recentClosed` | 只剔除**一个** `inProgress` id → **半填的补录期被当成已关账,算进月均支出** | **高** |
| `ReportReminderScheduler:95` | 只对最新期算 `daysLeft` → **补录期宽限快截止了,一条提醒都不发** | **高** |
| `ReportsController:682` `resolveAnchor` | 锚「最近已关账」→ 宽限期内报表**倒退回上上期** | **高** |
| `FamilyDiagnoseService:49` | 家庭体检基于半填期出结论 | 中 |
| `GoalProgressService:104` | 目标进度取错期 | 中 |
| `RebalancePlanController` ×2 | 再平衡计划挂错期 | 低 |

**C 类 · 有选择器,但默认值要重新定义(6 处)**

`DashboardController` ×3、`EntryController:286`、`EntryService:106`、`ReportsController:147`

**D 类 · 管理 / 通知(4 处)· 顺手改**

`AdminController` ×3、`NotificationSettingsController`

**外加一处特殊的**:`ExpenseImportController:269` —— 批量导入落 `findCurrentOpen`。
**这恰恰是 issue #20 的正中心**:9/1 导入 8 月账单,现在会整批落进 9 月期。

### 1.2 关账今天到底做了几件事

`PeriodService.close()` 一次做六件事。**延后关账 = 这六件全部延后**:

| # | 动作 | 延后的后果 | 可接受? |
|---|---|---|---|
| 1 | `period.status = CLOSED` | 写入不再被 `requireOpenPeriod` 拦 | 这正是目的 |
| 2 | `periodAccountAttrMapper.freezeByPeriod` — **分类属性定格** | 宽限期内改账户分类会改写上期归类 | **是** —— 属性本就该在数据落定时定格 |
| 3 | `periodAccountGroupMapper.freezeByPeriod` — **分组定格** | 同上 | 同上 |
| 4 | `runMetricsAfterCommit` — 指标重算 | 上期指标晚 N 天才有 | 是(数据本来就还没填完) |
| 5 | FIRE 目标重算 / 再平衡归档 | 延后 | 是 |
| 6 | **AI 月报 + 偏离预警异步生成** | 延后 | **是,且更对** —— 现在是拿半填数据生成月报 |

### 1.3 最关键的发现:「两类指标分别锚不同期」这个机制**已经存在**

`FactSlice`(v1.6.30)里已经有这个二分,而且**起因与本版完全相同 —— 半填的 OPEN 期**:

| 锚点 | 定义 | 服务哪类指标 |
|---|---|---|
| `lastPeriodId()` | 切片里最后一期,**含 OPEN** | **存量类**:净资产 / 总资产 / 总负债 / 配置 / 账户表现 / 归因 / 透视 |
| `returnAnchorPeriodId()` | 最新**已关账**期 | **收益类**:本月资产收益 / XIRR / TWR / 基准对比 / 钱赚 |

它的类注释把理由写得很清楚:

> 存量类指标锚在它上面是对的(填报过程中就该看到最新余额,缺快照还会结转上期);
> 但收益类指标锚在半填的期上会把「还没录的收支」整个算成投资收益 ——
> 2026-08 的 prod 实测:余额全填、收支 0 条,于是整段净资产变化 «A» 一分不扣地成了投资收益。

**这对本版有两层意义:**

1. **我们不需要发明新抽象** —— §3.0 的「余额轴 / 收支轴」就是给这个既有机制起名字,
   并把它从 `FactSlice` 内部推广成全系统判据。
2. **但双活跃暴露了这个二分法的缺口**(见 §4.4):它只认「OPEN = 不可信」,
   而补录期在宽限末期是**已完整但未关账**的第三种状态。照现行逻辑,
   双活跃下所有收益类指标会**集体锚回上上期** —— 不只报表页,dashboard 也一样。

## 2 · 用户故事

### 2.1 提交者原话

[issue #20](https://github.com/LuoDi-Nate/financial-management/issues/20) · @Pengyang233:

> 核心诉求是:**自然月完整账单通常只能在自然月结束后方便获取,希望系统的月度填报节奏能与这个现实使用方式对齐。**

复现:

> 1. 08/01 系统自动创建 8 月账期;
> 2. 08/28 根据当前提示填写截至当时的月度支出;
> 3. 08/29～08/31 继续发生若干消费;
> 4. 09/01 希望直接从支付宝 / 微信等 App 查看"8 月总支出",再填写最终数字;
> 5. 此时 8 月账期已经在新账期创建前被自动关闭,需要手动重新打开 8 月账期才能修改。

他还指出一处**文档自相矛盾**(复核属实):

| 文档 | 说法 |
|---|---|
| `prd/v0.4.md` | 默认节奏 = 支出**月末倒数 2 天**集中填 |
| `docs/how-to-use.md` | **月初任意一天** → 流程 1 · 填报 |

系统行为站在前者那边,而**后者更接近用户的真实做法**。

### 2.2 维护者改判(2026-09-18)

初版 PRD 的方案是**「补录」**:保持 00:30 关账不变,另造一条「往已关账期写支出、
但强制 `affects_balance = 0`」的旁路,并在「不做什么」里明确写了「不延后 force-close」。

维护者否掉了这个方向:

> 是否可以延迟关账,比如 T+2 关账?然后是个配置项,用户可以选择自己的关账时间。
> 其次,我们所有的核心能力(dashboard 实时数据、报表页归总数据、填报页)是否能兼容有两个活跃的账期?

**这个改判是对的,初版那条理由只成立一半**:

- 「用户会填错期」是**体验问题**,可以靠 UI 解。
- 真正的硬问题是 §1.1 那 30 处的语义分裂 —— 初版下结论时没查到这个量级。
- 而「补录」方案要**新造一条写入通道**;延后关账方案**一条都不用造** ——
  期还开着,现有写入路径原样可用。**后者的新增代码面反而更小**。

### 2.3 数据逻辑细化要求(2026-09-18)

维护者进一步要求:

> 把所有页面(dashboard / 报表 / 填报)三个页面,每个页面所有组件,里面所有指标逐个排查代码,
> 看下如果有两个活跃账期、在一些数据变动的情况下都应该如何变动?详细落到 PRD 里,整理成表格,
> 行上是组件 / 指标,列上是操作。排查我们还有多少用户主动 / 系统自动会影响数据的操作,也整理进去。

他还自己给出了两个判据样例,**这两条直接成为 §4.1 的归属判据分类**:

> 手动填报应该有月份指引,只影响对应月份;股价刷新其实这个操作也是有时间的,
> 即便有两个活跃账期,也只会归属一个账期。

**这两句话是本版数据逻辑的全部基础**:一类操作**由用户指定期**,另一类操作**由事件时点决定期**。
§4 就是把这两条推广到全部 27 个写操作和 42 个组件/指标上。

## 3 · FR

### 3.0 核心抽象:两条轴

| 轴 | 语义 | 能不能有两个「当前」 | 代码里的既有名字 |
|---|---|---|---|
| **余额 / 估值轴**(钱在哪) | **此刻**的事实 | **不能。只有一个现在** | 存量类 · `lastPeriodId()` |
| **收支轴**(钱花在哪 / 赚了多少) | **一段时间**的累计 | **能。8 月的账单 9 月才拿到** | 收益类 · `returnAnchorPeriodId()` |

> **余额 / 估值永远锚最新 OPEN 期;只有收支类允许写进仍在宽限窗口内的补录期。**

这条抽象是本版所有设计决策的唯一依据,TDD 里每一处改动都要能回指到它。

## 4 · 双活跃窗口下的数据逻辑(本版核心)

> 这一章回答维护者的问题:**「在一些数据变动的情况下,每个组件的每个指标都应该如何变动?」**
> 全部结论来自逐个读代码,不是推测。

### 4.1 全部写操作 · 27 个 · 及其归属判据

**判据只有三种**(维护者给的两个样例直接落成前两种):

| 判据 | 含义 | 为什么 |
|---|---|---|
| **① 显式选期** | 用户在页面上选了哪期就写哪期 | 「手动填报应该有月份指引,只影响对应月份」 |
| **② 事件时点** | 按事件发生时刻落进覆盖该时刻的那一期 | 「股价刷新这个操作也是有时间的,即便有两个活跃账期也只会归属一个账期」 |
| **③ 永远最新** | 无条件落最新 OPEN 期 | 余额轴只有一个「现在」 |

#### 用户主动操作(19 个)

| # | 操作 | 入口 | 写什么表 | 归属判据 | 双活跃下是否要改 |
|---|---|---|---|---|---|
| U1 | 手填账户余额 | `/entry/{id}/balance` | `period_snapshot` | ① 显式 | 页面已有 `?period=`,**只需改默认值** |
| U2 | 记收入 | `/entry/income` | `cash_flow` | ① 显式 | 同上 |
| U3 | 记支出 | `/entry/expense` | `cash_flow` | ① 显式 | 同上 |
| U4 | 删收入 / 支出 | `/entry/{income,expense}/{id}/delete` | `cash_flow` | **该流水所属期** | 无需改(按行的 `period_id`) |

### 4.4 既有二分法的缺口:第三种期状态

`FactSlice` 的二分只有两档:

| 状态 | 现行判定 | 收益类用不用 |
|---|---|---|
| CLOSED | 可信 | 用 |
| OPEN | 不可信(可能半填) | **不用** |

双活跃引入了**第三种**:

> **补录期** —— 已自然结束、数据在宽限末期已完整、但状态仍是 OPEN。

照现行逻辑它被归进「不可信」,于是**双活跃下所有收益类指标集体锚回上上期**。
这就是报表倒退的根因,而且**不只报表页** —— dashboard 的「本月资产收益」「人赚 vs 钱赚」
「账户表现」全都一起退。

**本版的处置**:收益类锚点判据从「最新 CLOSED」改成
「**最新 CLOSED,或已自然结束且填报完成的 OPEN**」。

「填报完成」用现成判据,不发明新的:`snapshot_todo` 无 PENDING **且** 全员已 `complete`
(这正是 `markCompletedByMember` 触发自动关账的条件)。

> **为什么不是简单地「宽限期内就认补录期」**:如果用户压根没填,补录期就是真的半填,
> 那时锚它会重演 2026-08 那次「整段净资产变化全算成投资收益」。
> **判据必须是「填完了没有」,不是「关了没有」。**
>
> **这条其实顺带修了一个既有缺陷**:今天一个填完但还没到 00:30 的期,
> 同样被收益类当成不可信。只是现在那个窗口只有几小时,没人注意到。

### 4.5 四个交叉场景(逐个给结论)

**① 用户在进行期刷新股价,同时补录期还开着。**
估值写进行期(③ 永远最新)。补录期的 `period_snapshot` **一个字节都不动**。
补录期的余额是 8/31 那个时点的事实,9/2 的股价与它无关。

**② 用户往补录期补了一笔影响余额的支出。**
补录期末余额变 → 进行期预填值**若仍是 `CARRIED_FORWARD` 则跟着变**(FR-623),
否则不动。dashboard 的净资产**会变**(因为它锚进行期,而进行期的余额变了),
但**本月资产收益不变**(收益类锚补录期,补录期还没关账)。

**③ 补录期关账那一刻。**
六件事一起发生(§1.2)。矩阵 F 列的所有 `↑` 同时触发:收益类锚点前移、
月均支出把补录期纳入、AI 月报生成、属性与分组定格。
**这是双活跃窗口里唯一一次「一堆数字同时跳」的时刻** —— 必须在 UI 上可预期(FR-616)。

**④ 用户改一笔已入账流水的账户,而那笔在补录期、新账户的快照在进行期。**
`ExistingFlowUpdateService` 用两次 `applyImportedExpense`(旧账户 negate、新账户正数)强制平账。
**双活跃下两次调用都必须落在那笔流水自己的期**(U12,该流水所属期),
不能一半落补录期一半落进行期 —— 否则两期余额同时错,而且方向相反。

### 4.6 不受双活跃影响的部分(明确划出边界)

| 部分 | 为什么不受影响 |
|---|---|

| 持仓明细(`stock_holding`) | 挂账户不挂期 |

## 5 · 不做什么

- **不改账期定义。** 8 月还是 8/1–8/31,宽限只改「什么时候锁上」。
- **不做三期及以上同时 OPEN。** 宽限最长 T+5,不可能跨到第三期。
  所有判据按「最多两期」写死并断言,**多出第三期视为数据异常**。
- **不允许无限期不关账**(FR-612)。永不关账 = 属性永不定格、月报永不生成、
  报表永远没有可锚的快照。**「随你便」在这里不是自由,是把系统拖进没有出口的状态。**
- **不动「余额只有一个现在」原则**(FR-622)。
- **不为收益类指标造「实时预览」。** 矩阵里那些 `⏳` 是**故意**的:
  补录期关账前收益类就是不该动,这是 v1.6.30 用一次 prod 事故换来的规矩。
- **不删除管理页重开账期那条路**。
- **不改 `ExistingFlowUpdateService` 的双次平账实现**(§4.5 ④只是明确它的落期)。

**撞上「刻意不做」清单的**:无。

### 口径变更声明

**改的是什么**:两件。

1. 选了 T+N 的家庭,上一期**关账时点推迟 N 天**,所有「按已关账期取数」的指标随之推迟。

**哪些会跟着动(仅对主动改了配置的家庭)**:

| 指标 | 会不会变 | 说明 |
|---|---|---|
| 补录期家庭消费 / 储蓄率 / 支出构成 | **会** | 那正是用户要修正的数 |
| 补录期指标 / FIRE / 再平衡 / AI 月报 | **晚 N 天出** | 数值更准,但出得晚 |
| 补录期分类属性 / 分组定格 | **晚 N 天定格** | 见 §1.2 |
| **进行期余额 / 估值** | **不变** | FR-622 |
| **进行期预填延续值** | **可能变** | FR-623,仅 `CARRIED_FORWARD` |
| 月均支出 / 近 N 期窗口 | **修正** | FR-628,这是**修 bug** |
| 收益类指标在宽限期内 | **不再倒退** | §4.4,这也是**修 bug** |

**零差异基线**:基线取已发布 tag **v1.22.5**。`close_delay_days = 0` 时所有指标逐分不变。
**这是能不能发的硬门。**

## 8 · 开关与默认值

| 开关 | 默认值 | 关掉 / 默认时的行为 |
|---|---|---|
| `family.close_delay_days` | **0** | 与 v1.22.5 完全一致 |
| `family.auto_close_enabled` | **1** | 为 0 = 手动关账(仍受 FR-612 兜底约束) |

## 10 · 失败模式(pre-mortem)

**① 30 处审计漏一处,而且不报错。**
`findCurrentOpen` 在双 OPEN 下**静默返回最新期** —— 漏掉的那处不抛异常、不进日志,
只给出一个**看起来合理但是错的数**。
→ 护栏 `v1230-DUAL-OPEN-SWEEP`:30 处全部登记白名单,
**新增任何调用点必须显式归类**(A/B/C/D),否则红。

**② 收益类指标在宽限期内集体倒退。**
不只报表页 —— dashboard 的「本月资产收益」「人赚 vs 钱赚」「账户表现」一起退(§4.4)。
用户的感受是「升级之后少了一个月」。
→ e2e 断言:宽限期内**填报完成**的补录期被收益类采纳;**未填完**的不被采纳。

**③ 月均支出把半填期算进去。**
`recentClosed` 只剔除一个 id。症状:月均支出**突然变低**,FIRE 目标跟着它走。
→ 单测构造双 OPEN,断言返回的期**全部** CLOSED。

**④ 进行期预填值被补录悄悄改掉,或该改的没改。**
→ e2e 双向断言:`CARRIED_FORWARD` 的会变、手填过的**一分不动**。

**⑤ 宽限到期那天没人关账。**
关账挂在「新期滚动」这个事件上;T+2 那天没有滚动。
→ e2e 推进系统日期跨过宽限到期日,断言期已 CLOSED。

**⑥ 提醒在双 OPEN 下只发进行期。**
补录期宽限只剩 1 天、一条提醒都不发 —— 而那正是最需要提醒的时刻。
→ e2e 断言两期提醒窗口独立判定。

**⑦ 用户填错期。**
→ FR-625 两期同时呈现 + 当前期高亮;双端截图人工核对。

**⑧ 换账户改流水时,两期余额同时错且方向相反。**
`ExistingFlowUpdateService` 的双次平账若一半落补录期一半落进行期(§4.5 ④)。
→ e2e 断言两次调用落在同一期(该流水所属期)。

## 12 · 回滚与关闭

- **回滚到 T+0**:改配置即可,下一次扫描就按新判据关。不产生悬挂状态。
- **回滚 jar**:配置列还在但没人读,`PeriodOpener` 回到「新期滚动即关上期」。
  正处在宽限窗口里的补录期会在下一次滚动时被关掉,**数据不丢**(它本来就是正常的 OPEN 期)。
- **迁移不回滚**(项目惯例)。新列带默认值,老 jar 无感。

**唯一不可逆的**:宽限期内补进去的收支本身。撤销 = 和普通流水一样删掉那几笔。
