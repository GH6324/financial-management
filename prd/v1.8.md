# v1.8 · 支出链路改造:逐笔录入 + 落到账户(PRD)

> 起因:[issue #9](https://github.com/LuoDi-Nate/financial-management/issues/9) 一位用户提出想看每月支出的统计与汇总;
> 与此同时,收入侧在 v0.12 已经改成「逐笔录入 + 选定账户 + 自动写入该账户余额与流水」,
> **支出侧却还停在「每人一个月一个总数」**,两侧不对称。本版把支出侧对齐收入侧。

---

## 1 · 现状:两侧为什么不对称

| | 收入侧(v0.12 起) | 支出侧(至今) |
|---|---|---|
| 录入粒度 | **逐笔**,一个月可录多条 | 每人一个月**一个总数** |
| 归属账户 | 每条选一个现金账户 | **无归属** |
| 是否动余额 | **动** —— 立即加进该账户余额 | 不动 |
| 是否留流水 | 留(`cash_flow` INCOME) | **不留**(只写 `period_member_cashflow.total_expense_input`) |
| 能不能分类 | 有类目(工资 / 奖金 / 利息…) | 无(只有一个总数) |

不对称带来三个具体问题:

1. **看不到支出构成** —— 这是 issue #9 的原始诉求。
2. **账户级收益率偏低**。账户级 PnL = `(期末 − 期初) − (收入 − 支出 + 转入 − 转出)`。
   从某张卡消费了 5,000,今天这 5,000 只进了 PMC 总数、不挂在该账户上,
   于是那张卡的余额下降被当成了**投资亏损**而不是外部流出。
3. **填报体验割裂** —— 收入是"逐笔加一笔"、支出是"填一个数",同一页两套心智。

---

## 2 · 目标与非目标

**目标**

- 支出侧对齐收入侧:**可录多条 · 每条选账户 · 自动写入该账户余额与流水 · 可选类目**
- 因此自然得到**支出构成**(按类目 / 按账户 / 按成员的占比),兑现 issue #9
- **历史数据一行不动**,老口径继续可用、继续正确
- 账户级收益率因此变准(消费不再被当成投资亏损)

**非目标**

- 不做逐笔明细导入(不接银行/支付宝账单 API,不做 OCR 账单)
- 不做预算与超支告警(那是另一个产品方向)
- 不强制用户迁移到新方式 —— 见 §4
- 不处理「多币种 + 逐笔模式 + 看历史窗口」三者同时成立时的汇率镜头差异:逐笔汇总按
  「该账期可得的最新 base→账户币 汇率」折本位币(逐期汇率),事实表用的是**窗口末**锚定的
  单一镜头汇率。单币种家庭(含 beta / prod)两者恒等,故本版不动

## 3 · 功能需求

### FR-270 · 支出可逐笔录入并落到账户

填报页支出区改成与收入区同构:

```
支出   先选账户 · 填金额 · 选类目          [+ 加一笔]
┌──────────────────────────────────────────────────────┐
│ 金额 ¥ [    ] 类目 [消费 ▾] 支出账户 [招行储蓄卡 ▾] 备注 [   ] │
└──────────────────────────────────────────────────────┘
已录入:
  还贷     招行储蓄卡-工资   ¥6,800   08-01   已出账 + 流水   删
  消费     招行储蓄卡-工资   ¥3,200   08-15   已出账 + 流水   删
本月家庭支出(本位币)= Σ 支出录入 · 汇入人赚 / 储蓄率            ¥10,000
```

- 每条写一行 `cash_flow`(kind=EXPENSE),并**从所选账户余额中扣除**该金额
- 删除时冲回余额并移除流水(与收入侧删除行为一致)
- 类目来自「管理 → 现金流类别」

### FR-270a · 类目体系:停在「性质」这一层(**已定**)

**用户拍板:不做「餐饮」这种消费品类,就「日常开支 / 还贷」这个层级。**

所以**沿用现有 `cash_flow_category` 的 4 个支出类目,不新增品类**,只做一件事:
把 `consumption` 的显示名从「消费」改成「**日常开支**」。

| code | 改后显示名 | 性质 |
|---|---|---|
| `consumption` | **日常开支** | 一般开销的归集项 · **新建支出的默认类目** |
| `loan_payment` | 还贷 | 刚性 |
| `interest_paid` | 利息支出 | 刚性 |
| `to_relatives` | 转账给亲属 | |

- **只改 `display_name`,`code` 不动** → 历史 `cash_flow` 行零影响,立刻显示成「日常开支」
- 这四个是**内置的**,`/admin/cash-flow-categories` 目前是**只读**页(没有增删端点)——
  所以「想细分自己加」这句话在本版**不成立**,别写进任何面向用户的文案。
  真要放开得单独做类目管理(增删 + 停用 + 排序 + 防删掉已被引用的),那是另一件事,本版不做
- 新建一笔支出时,类目默认选中「日常开支」

> **这个决定改变了「支出构成」能回答什么,必须诚实记录:**
> 它回答的不是「餐饮占几成」,而是「**刚性支出(还贷 + 利息)占了多少、日常开支占多少**」。
> 对家庭账来说这个划分其实更有用 —— 刚性支出压不下去,日常开支才是可调的部分。
> 但这**不完全等于 issue #9 那位用户可能想要的东西**;他至今没回粒度问题,
> 回复他时要说清是这个层级,别让他以为能看到品类明细。

### FR-271 · 保留「一个总数」这条路

**不是所有人都愿意逐笔录支出。** 支出笔数远多于收入,强制逐笔会直接违反「每月 10 分钟」这条硬约束。
所以两种方式**并存**,用户自己选:

| 方式 | 适合谁 | 得到什么 |
|---|---|---|
| **总额**(现状) | 消费集中在一两张卡、只想知道总数的人 | 储蓄率 / 紧急储备 / 人赚钱赚照常算,**没有构成** |
| **逐笔**(新增) | 想看构成、或消费分散在多个账户的人 | 上述全部 + **支出构成** + 账户级收益率更准 |

在「家庭设置 → 填报模板」旁边新增一个**支出录入方式**开关(家庭级,**默认「总额」** —— 保持现状,老用户升级后行为不变)。
切到「逐笔」后,支出区变成 FR-270 的形态;切回「总额」时已录的逐笔数据保留、不删。

### FR-272 · 支出构成视图

有逐笔数据时,报表页「储蓄能力」段下方出现**支出构成**。三个可切维度:

| 维度 | 回答什么 |
|---|---|
| **按类目** | **刚性支出(还贷 + 利息)vs 日常开支** 的比例 —— 刚性压不下去,日常才是可调的 |
| **按账户** | 钱主要从哪张卡出去;也是账户级收益率变准的来源 |
| **按成员** | 谁花得多(家庭内部对账用) |

- 可切「本期 / 近 6 期 / 近 12 期」
- 每一格可点开看该格的逐笔明细(复用资产透视的明细抽屉形态)
- 只有总额数据的月份显示「只填了总数 · 无构成」——**不隐藏、不假装没有**
- 历史逐笔行的类目都是 `consumption`,改名后自动显示为「日常开支」,**无需迁移也不需要「未细分」这个状态**

### FR-273 · 口径优先级必须明确且可解释

同一个月可能**两种数据都有**(先填了总数,后来又录了几笔)。规则:

> **逐笔模式**下:同一账期内若有逐笔支出记录,则该期支出 = Σ 逐笔;否则 = PMC 总额。
> **总额模式**下:该期支出 = PMC 总额;取不到就交回各页原有的回落路径。
> 二者**永不相加**。

**⚠ 这条在开发中被改过一次,原稿是错的,记录在此以免重犯。**
初稿写的是「无条件逐笔优先」(不看模式)。第 3 步做完跑「总额模式逐位比对」时被拦下:

- beta:紧急储备 8.0 月 → 1.9 月(月均支出凭空涨 4 倍)
- prod 复核:2026-06 的 PMC 总额 ¥32,797,而该期逐笔只有 ¥3,000
  —— 无条件逐笔优先会让当月支出变成 3,000,**少算 89%**,
  连带污染储蓄率 / 月均支出 / 紧急储备 / 人赚钱赚 / XIRR / 应急目标基线

根因:`cash_flow` 里本来就有 EXPENSE 行 —— 它们来自**账户级流水**那条老路径,
不是「用户主动选择逐笔录入」。把它们当成用户的逐笔支出是误读。
所以逐笔优先只在家庭**显式切到逐笔**之后才生效。

同一次比对还拦下两个连带问题:

- **PMC 取数来源不能随手换**:单期走 `findFamilyAggregateForPeriod`、近 N 期走
  `findFamilyAggregateRecent` —— 后者带 `HAVING filledMembers > 0` 和 `LIMIT`,两者不等价
- **总额模式下口径服务不自己兜底 cash_flow**:各页原来的回落读的是**事实切片**
  (排除归档账户 + 已换汇),而逐笔 SQL 是另一套过滤。beta 43 条支出里 24 条
  (¥395,340 · 74%)属归档账户,漏掉这个过滤会让家庭 XIRR 从 −56.19% 漂到 −50.60%。
  改成返回「没有」交回调用方原路径后,「总额模式逐位不变」才是结构性成立的

页面上必须说清当前用的是哪一种:该期支出旁标注「逐笔 · 12 笔」或「总额 · 手填」。
tooltip 给出真实算式(与全站 tooltip 一致的做法)。

> 这条规则与收入侧现行规则同构(收入是「PMC 手填 > 0 则用之,否则用 cash_flow 汇总」),
> 但**优先级相反** —— 支出侧以**逐笔为准**。理由:逐笔是更细的事实,总额是它的摘要;
> 而收入侧的历史数据在 PMC 里,反过来。这个不一致是历史造成的,**必须在文档和 tooltip 里写明**,
> 不能让下一个人靠猜。

### FR-274 · 支出扣余额必须防重复计

这是本版最大的风险点,和收入侧那个坑同源:

> 录一笔支出 → 系统从该账户余额扣掉 → 如果用户**已经**照银行 App 填了月末余额(已含这笔消费),
> 再录这笔支出就会**扣第二次**,余额凭空少一笔。

处置:

1. **填报顺序引导**:支出区文案与手册统一为「先录收支,最后核对余额」;
   支出区标注「录入后会从所选账户余额中扣除」。
2. **录入后即时提示**:每录一笔,该账户行余额高亮闪一次并显示 `−3,200`,让用户看见余额被改了。
3. **对账提示**:若某账户在本期既有逐笔支出、又被手工改过余额,
   在该账户行给一条提示「本期已录 N 笔支出(共 ¥X),若你填的余额已含这些消费,请勿重复扣减」。
   仅提示、不阻断 —— 用户可能确实需要手工修正。
4. 使用手册的「演示 A」增加支出侧的对照(现有演示只讲了收入)。

## 4 · 历史数据兼容(硬要求)

### 4.1 一行都不改

- `period_member_cashflow.total_expense_input` **保持原样**,不迁移、不清空、不折算
- 不新增数据库表;逐笔支出复用现有 `cash_flow`(kind=EXPENSE)
- 唯一 schema 改动:`family` 表加一列 `expense_entry_mode`(`TOTAL` / `ITEMIZED`,默认 `TOTAL`)
  —— 符合「迁移只 ADD COLUMN NULL/带默认」的红线,老 jar 回滚后该列被忽略,行为退回总额模式

### 4.2 老数据在新视图里怎么显示

| 场景 | 表现 |
|---|---|
| 历史月份只有 PMC 总额 | 支出总数照常显示;构成视图里该月标「只填了总数 · 无构成」 |
| 用户切到逐笔后的新月份 | 有构成 |
| 同一月两种都有 | 按 FR-273 以逐笔为准,并在页面标明 |
| 从未填过支出的月份 | 与现状一致:灰柱、不参与中位数 |

### 4.3 回滚

纯读路径 + 一个带默认值的新列。回滚只回 jar:老 jar 不认 `expense_entry_mode`,
所有家庭退回总额模式,已录的逐笔支出仍在 `cash_flow` 里(老逻辑本来就会把它算进 `periodExpense` 的 fallback),
**不会丢数据、不会双算**(因为老逻辑是 PMC 优先)。

## 5 · 受影响功能清单(逐个确认)

改动支出口径会波及以下 **18 处**。逐个确认,不留"应该没事"。

### 5.1 直接读 PMC 总支出 —— 需要接新口径

| # | 位置 | 现在怎么用 | 本版处置 |
|---|---|---|---|
| 1 | `FactViewServiceImpl.netInflowExpense` | PMC 优先,否则 cash_flow | **改**:逐笔优先(FR-273),否则 PMC |
| 2 | `FactViewServiceImpl.averageExpense` | 近 ≤12 期 PMC 均值 → 紧急储备分母 | **改**:每期按 FR-273 取值后再求均值 |
| 3 | `HouseholdCashflowService.avgMonthlyExpense` | PMC 优先 → 报表月均支出 | **改**:同上 |
| 4 | `HouseholdCashflowService.currentSavingsRate` | 最近 1 期 PMC | **改**:同上 |
| 5 | `HouseholdCashflowService.medianMonthlySavings` | 近 6 期 PMC | **改**:同上 |
| 6 | `HouseholdCashflowService.filledMonthRatio` | PMC 有行即算已填 | **改**:逐笔也算已填,否则用了逐笔的月会被判成"没填" |
| 7 | `GoalProgressService` 应急目标 auto_baseline | 过去 3 期 PMC 总支出的**中位数** | **改**:同上。这条最隐蔽 —— 不改会让应急目标基线凭空变小 |
| 8 | `GoalService` / `GoalProgressService` 储蓄率类目标 | PMC 收支 | **改**:同上 |
| 9 | `CheckupController` 流动性规则 | 近 12 月月均 EXPENSE | **改**:同上 |
| 10 | FIRE 目标「自适应近月真实支出」 | PMC | **改**:同上,并跑 `FireAutoExpenseTest` |

> 1–10 全部收敛到**一个新方法** `expenseForPeriod(familyId, periodId)`,内部实现 FR-273 的优先级。
> **不允许各处自己判断** —— 这正是 v1.6.29 那次「同页两套收入口径」的教训。

### 5.2 因支出落到账户而数值会变 —— 需要提前告知

| # | 位置 | 影响 |
|---|---|---|
| 11 | 账户级 PnL / 收益率(`PnlCalculator.periodPnl`) | **会变准**:消费不再被当成投资亏损。用了逐笔的账户,历史收益率会被重算得更高 |
| 12 | 账户级 NAV 序列 / 最大回撤(`NavSeriesBuilder`) | 同上,净外部流入含 EXPENSE |
| 13 | 账户级 vs 基准(报表第四表) | 随 11 变动 |
| 14 | 资产透视的收益类度量(本期/累计收益额与收益率) | 随 11 变动 |

> **11–14 只影响启用逐笔的家庭、且只影响其启用之后的账期**;总额模式下 cash_flow 无 EXPENSE 行,数值与今天完全一致。
> 发布说明必须写清这一点(参照 v1.6.29 的做法:静默改动用户看到的数字是信任成本最高的改动)。

### 5.3 展示层需要跟改

| # | 位置 | 处置 |
|---|---|---|
| 15 | 填报页支出区 | 逐笔模式下换成收入区同构形态;总额模式不变 |
| 16 | 报表「储蓄能力」段 | 加支出构成(FR-272);「数据源」说明文案已过时(仍写 `Period.total_income_input`),一并修正 |
| 16b | `cash_flow_category` 的 `consumption` 显示名 | 「消费」→「日常开支」。**只改 display_name,code 不动** → 历史行零影响。需扫一遍模板里有没有写死「消费」这个中文串 |
| 17 | 仪表盘「收支趋势」/「人赚 vs 钱赚」 | 数据源走新方法,形态不变 |

### 5.4 确认**不受影响**的(也要写出来)

- **转账 / 划转**:与收支无关,`transfer` 表独立,不动
- **开账基线**:只看 `period_snapshot` 首次出现,与支出无关
- **家庭 XIRR / 资产年化 TWR**:走 `pmcFirstNetInflow`,它调用 §5.1 的统一方法,口径自动跟上
- **贷款符号归一 / 持仓估值 / 券商同步 / 基金穿透**:均与支出链路无交集
- **审计日志**:逐笔支出走既有 `cash_flow` 写入路径,自动有审计
- **CSV 导出**:已按 `cash_flow` 导出,逐笔支出自动包含

## 6 · 验收标准

1. 总额模式下,全站所有指标与升级前**逐位相同**(用 v1.6.30 那套模拟器复算 prod 快照比对)
2. 逐笔模式下,`Σ 逐笔支出 == 该期支出口径值`,且储蓄率 / 紧急储备 / 人赚钱赚三者自洽
3. 同期两种数据并存时**不相加**,页面标明用的是哪一种
4. 应急目标 auto_baseline 在逐笔模式下与手工中位数一致
5. 删除一笔支出后,账户余额与该期支出总额同时回退
6. 老 jar 回滚后功能退回总额模式,无数据丢失、无双算
