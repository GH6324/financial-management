## 0 · 这一版在解决什么

### 0.1 背景与现状

支出侧现在有两种录入方式(`expense_entry_mode`):

| 模式 | 每月动作 | 能看到什么 |
|---|---|---|
| **TOTAL**(默认) | 每人填**一个总数**(PMC) | 只有总额,没有构成 |
| **ITEMIZED** | 逐笔选账户 + 类目,扣账户余额 | 有构成,但类目是**全局写死的 4 个** |

用户 @brdol 的诉求(#18):按购物/餐饮/交通/运动这类自定义场景看支出,按月按年统计,加支出报表。

### 0.2 与「刻意不做」的冲突,化解在结构上

「消费品类细化」被刻意不做,因为它会把录入拖向记流水,打穿**每月 10 分钟**硬约束。化解钥匙是提交者自己给的:**逐笔归 APP,分类归我们** —— 流水留在支付宝/微信/银行 APP,月底只把**分类汇总数**弄进来。

本版的中心结构决定(v1 已定,v2 不变):

```
分类填报 = TOTAL 模式「那一个总数」的展开形式
Σ(各分类) 同一事务写回 PMC.total_expense_input
→ 家庭支出口径(储蓄率/月均/紧急储备/FIRE)一行不改,ExpenseLedgerService 零改动
→ 分类明细在旁表,只喂支出报表,永远不成为第三条口径来源
```

### 0.3 v2 的新增:数怎么进来,给三条通道

v1 只设计了「手抄」。评审指出三个没回答的问题,v2 的答案:

| 通道 | 适用 | 动作成本 | AI 参与 |
|---|---|---|---|
| **① 手抄** | 任何渠道,永远可用 | 抄 5-10 个数,1-2 分钟 | 无 |
| **② 文件导入** | 支付宝 / 微信(zip/csv) | 传 1-2 个文件,秒级 | 仅微信的「商户→类目」映射建议(可选) |
| **③ AI 截图导入** | 任何渠道的**月度分类统计页**(含银行 App) | 传几张截图 | qwen-vl 只转写「类目名+金额」,不做数学 |

三条通道殊途同归:都落到**同一个分类填报预填**,用户确认后合计写回 PMC。不配 AI key 的家庭 ①② 照样全功能。

### 0.4 本版新引入的名词

| 词 | 定义 |
|---|---|
| **支出类目** | 家庭自定义支出分类,一级平铺(刻意不做二级,见 §1.1)。内置「其他」兜底不可动 |
| **起步类目包** | 一键导入的预置类目集,**与支付宝账单「交易分类」同名**(见 §1.1 的理由) |
| **分类填报** | TOTAL 模式下把一个总数展开为按类目填。合计即总额 |
| **导入批次** | 一次文件/截图导入的结果,按(账期 × 成员 × 渠道)归位;同渠道同期重导 = 覆盖旧批次 |

## 1 · 调研(v2 · 回答评审的三个问题)

### 1.1 · 问题一:类目树哪里来?

**市面记账软件的三种做法**(来源见 §12):

| 产品 | 结构 | 关键事实 |
|---|---|---|
| **鲨鱼记账** | 仅一级,约 40+ 项平铺 | 无二级;用户抱怨「餐饮下想看买菜/外卖/咖啡占比,做不到」 |
| **钱迹** | 一级 + 二级,可自定义 | **「其他」是默认分类,不能修改或删除;删除某分类后账单移入「其他」** —— 与我们 v1 的设计不谋而合 |
| **随手记** | 一级 + 二级,默认树最细 | 默认把餐饮拆成早/午/晚餐,用户反馈**过细**:「除非真要分析早餐支出,否则『一日三餐』就够」;滚轮选分类被评「要记住位置,操作复杂」 |
| **支付宝账单**(数据源头) | 固定一级,约 20+ 项 | CSV 有「交易分类」列,取值如:餐饮美食/服饰装扮/日用百货/家居家装/数码电器/美容美发/交通出行/住房物业/医疗健康/教育培训/文化休闲/充值缴费/转账红包/投资理财… 自动分类「不是每笔都准」,App 内可手改 |
| **微信账单** | **没有消费分类** | 只有交易类型(商户消费/转账/红包),「参考价值不大」—— 开源社区普遍靠商户名关键字自建映射 |

**结论与决定:**

1. **一级平铺,刻意不做二级。** 我们的粒度是「月度汇总」,不是逐笔 —— 逐笔软件才需要二级来收纳几百条流水;月底填 8 个数,二级只会变成随手记式的「过细之累」。鲨鱼 40+ 项平铺的教训反过来记:**上限 20**(FR-508)防止平铺失控。
2. **起步类目包与支付宝账单同名。** 数的源头(支付宝 CSV 的「交易分类」列、支付宝月账单统计页)就是这套名字 —— 同名意味着**导入零映射、手抄零翻译**。起步包取其高频 10 项:餐饮美食、日用百货、服饰装扮、数码电器、交通出行、住房物业、医疗健康、教育培训、文化休闲、充值缴费(+ 内置「其他」)。一键导入后随便改名/删/停用 —— 它只是起点,不是约束。
3. **删除转「其他」**:钱迹与支付宝记账本同款语义,提交者点名接受,维持 v1 设计。

### 1.2 · 问题二:大陆主流渠道的账单怎么导出?

逐渠道核过(操作路径 + 格式 + 关键坑,来源见 §12):

| 渠道 | 导出路径 | 拿到什么 | 关键细节 |
|---|---|---|---|
| **支付宝** | App「账单 → 右上角 ⋯ → 开具交易流水证明 → **用于个人对账**」→ 发邮箱 | **zip(带密码)→ csv** | 密码在「开具记录」里查;**一次最长可选 1 年**;CSV 前 ~25 行是说明、之后才是表头;列含**「交易分类」**(天然带分类!);编码 GBK |
| **微信** | 「我 → 服务 → 钱包 → 账单 → 常见问题 → **下载账单 → 用于个人对账**」→ 发邮箱 | **zip(带密码)→ csv** | 密码由「微信支付」公众号通知推送;**一次最多 3 个月**;前 ~16 行说明头;**没有消费分类列**,只有交易类型/交易对方/商品 |
| **招商银行** | App「我的 → 全部 → **流水打印**」→ 发邮箱;或网银「交易查询 → 导出选中」 | App 路径 = **PDF**;网银 = **Excel** | App 端拿不到结构化文件是常态;最长跨度 1 年 |
| **工商银行** | App「账户 → 更多 → **历史明细打印**」→ 发邮箱;或网银「流水查询 → 导出」 | App = 明细文件(可选不加密);网银 = **Excel(.csv)/PDF** | 网银导出实为 csv |
| (证明用途) | 支付宝/微信都另有「用作证明材料」 | **PDF 盖章版** | **不适合导入**,页面要提醒用户选「个人对账」那个 |

**结论与决定:**

1. **第一期文件导入只做支付宝 + 微信。** 两大渠道格式全国统一、社区解析成熟(BeeCount/cashbook/china_bean_importers 均有先例);它们通常覆盖一个家庭绝大多数日常支出。
2. **银行渠道第一期不写解析器,走截图导入(§1.3)。** 各行格式互不相同、App 端常只有 PDF —— 没有真实样本就写死解析器必然翻车。后续版本按用户提供的真实样本逐行适配(招行 Excel / 工行 csv 已列入候选)。
3. **zip 直接收。** 支持传 zip + 密码框(zip 内自动找 csv),也支持自己解压后传 csv —— 用户少一步是一步。
4. **编码与说明头由引擎兜**:GBK 自动识别、跳过说明行、定位表头,失败时报人话(「这不像支付宝的对账单 —— 你导出时是不是选了『证明材料』?那个是 PDF 盖章版,要选『用于个人对账』」)。
5. **重复计入是真风险,必须主动挡**:支付宝/微信绑卡消费会同时出现在银行流水里;银行导入(后续版)必须默认过滤交易对方含「支付宝/财付通」的行 —— 开源导入器(china_bean_importers)的通行做法。第一期就把这句话写进导入页文案,防止用户手抄时双计。

### 1.3 · 问题三:AI 怎么介入?

**复用 v1.4 持仓截图导入的整套通道**(`VisionLlmClient` + 多文件上传 + 确认页三态比对 + qwen-vl key 已在管理页配置),换一个提示词场景:

- **拍什么**:支付宝「账单 → 月账单/收支分析」页、微信「钱包 → 账单 → 统计」页、各银行 App 的月度收支统计页 —— 这些页面**本身就显示按类目汇总好的金额**,正是我们要的数。
- **AI 只转写,不算数**(承 `feedback_llm_no_math`):qwen-vl 从截图读「类目名 + 金额」原样输出;跨截图/跨渠道的合并、类目映射、求和全在引擎;识别不清标疑,不硬猜。
- **批量**:一次传多张图(既有 `MultipartFile[]`);**支持传一个 zip 装一堆截图**(引擎解包逐张送)—— 对应维护者点名的「大量截图导入 / zip 导入」。
- **微信 CSV 的类目映射**:微信没有分类列,引擎先按「商户名关键字规则」映射(规则家庭可编辑、记忆化 —— 「美团」→餐饮美食,配一次管一年);规则不命中的余量,可选让 LLM 对**商户名列表**给映射建议(只给建议,金额不过 LLM),不配 key 就全落「其他」等手动分。
- **边界**:AI 不参与支付宝 CSV(它有分类列,确定性解析)、不参与任何求和、不参与「其他」兜底判定。

## 2 · 用户故事

### 2.1 · 最快的一条路:两个文件(主场景 · 新)

月底关账,他在支付宝里点「开具交易流水证明」发到邮箱,微信同理。把两个 zip 丢进导入页、输入解压密码 → 系统解析、按类目汇总、预填分类填报,来源角标「支付宝 ¥x · 微信 ¥y」。他扫一眼、微调「其他」里的余量,确认 —— 合计自动写回月度总额。**全程不到两分钟,一笔流水都没在这记。**

### 2.2 · 截图党的路(新)

她不爱倒腾文件。打开支付宝月账单统计页截一张、微信账单统计页截一张、招行 App 月度收支截一张,三张图(或打包一个 zip)传上去 → qwen-vl 转写各页的「类目名+金额」→ 引擎映射合并 → 预填,确认。

### 2.3 · 手抄的路(v1 保留)

不传任何东西,照着账单把 5-10 个数抄进展开态的分类框,上月金额垫底作参照。

### 2.4 · 回看「钱花在哪」/ 类目生老病死

同 v1(报表三视角;改名跟显示、停用留历史、删除转「其他」)。

## 4 · 不做什么

### 非目标(仍然刻意不做)

- **在本 app 里逐笔随手记**(永远)
- **二级类目**(§1.1 论证:月度汇总粒度用不上,随手记的「过细之累」是反面教材)
- 预算/包络、超支提醒
- **银行渠道的文件解析器**(第一期。没有真实样本不写,走截图;后续按样本逐行适配)
- 账单**自动同步**(网银直连/开放银行)—— 凭据风险与维护成本都不配这个项目的体量
- 收入侧的分类展开

### 评审中要拍板的点

1. 展开粒度按「每人」(v1 已定,维持)
2. 支出报表放报表页扩展(v1 已定,维持)
3. **新:导入批次的成员归属** —— 现方案:导入时选「算谁的」(默认当前登录人),因为 PMC 按人。备选:家庭级导入再按人拆,被否 —— 拆分比例没有事实依据,伪精确
4. **新:微信商户映射的 LLM 建议**默认开还是关 —— 现方案:默认关(纯关键字规则),配了 key 的家庭在导入页可勾选启用。理由:映射建议错了会静默污染分类,关键字规则错了用户一眼能看懂为什么

### 撞上「刻意不做」清单的处理

「消费品类细化」→ 改写为「**逐笔流水录入**仍然刻意不做 —— 分类只到『月度按类目汇总』为止,汇总数怎么来(手抄/文件/截图)不设限」。AGENTS.md 同步。

## 5 · 10 分钟约束核对

| 动作 | 频次 | 耗时 |
|---|---|---|
| 建类目(起步包一键) | 首次 | <1 分钟 |
| 月底进数:文件导入 | 每月 | ~2 分钟(导出发邮箱是渠道 App 里点几下,解析确认秒级) |
| 月底进数:截图导入 | 每月 | ~2 分钟(截 2-3 张 + 确认) |
| 月底进数:手抄 | 每月 | 1-2 分钟 |
| 看支出报表 | 随意 | 0 |

**三条通道都在包络内;完全可选,不用的人 0 增量。** 风险:导入指引没写清 → 用户在渠道 App 里迷路,时间花在找入口上 —— 所以 FR-530/541 把逐步路径当功能做,不是当帮助文档做。

| **外呼** | 截图导入走**已有**的 qwen-vl 通道(v1.4 起就有),无新增第三方;文件解析纯本地 |

### 口径变更声明

同 v1:总额口径零变更;支出构成报表呈现变富、口径不变、历史不回填。
**新增说明**:导入只产生「分类汇总数」,**不产生 cash_flow 逐笔行**、不碰账户余额 —— 导入的世界与 ITEMIZED 的世界不交叉,防止两套事实。
