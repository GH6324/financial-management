## 0 · 这一版在解决什么

> **本文是第 2 稿。** 第 1 稿(「按类目填汇总数」)在 beta 评审时被否掉,
> 原话是「一堆空格让我分门别类做填入,根本没法用」。为什么被否、改了什么,见 §14。

### 0.1 背景与现状

支出侧现在有两种录入方式(`expense_entry_mode`):

| 模式 | 每月动作 | 能看到什么 |
|---|---|---|
| **TOTAL**(默认) | 每人填**一个总数**(PMC) | 只有总额,没有构成 |
| **ITEMIZED** | 逐笔选账户 + 类目,扣账户余额 | 有构成,但类目是**全局写死的 4 个** |

用户 @brdol 的诉求(#18):按购物/餐饮/交通/运动这类自定义场景看支出,按月按年统计,加支出报表。

**真正的缺口在 ITEMIZED 这一行的右格**:逐笔录入早就有了,但它的「类目」是
`日常开支 / 还贷 / 利息支出 / 转账给亲属` —— 那是**性质**,不是「钱花在哪」。
所以这一版不是发明一种新的录入方式,而是**把已有的逐笔录入补完**,再给它配一个批量入口。

### 0.2 中心结构决定(第 2 稿)

**分类依附在「一笔」上,不独立成为一个填报动作。**

这条推翻了第 1 稿的「分类是月度总额的展开」。理由见 §1.4 的交互调研:
所有记账软件里分类都是记一笔时顺手选的,**不存在**「月底打开一张表把总数分配到类目里」这个动作 ——
那是人做不来的运算(你记得中午吃了什么,不记得这个月餐饮总共多少)。

于是三种形式各自独立,互不叠加:

| 形式 | 载体 | 分类 | 这一版做什么 |
|---|---|---|---|
| ① 填一个总数 | `PMC.total_expense_input` | **没有** | **不动** |
| ② 逐笔录入 | `cash_flow` | 每笔一个 | 类目选择器换成自定义分类宫格 |
| ③ 导入明细 | `cash_flow` | 每笔一个 | **新页面**:解析→归类→逐行核对→落库 |

「钱花在哪」= `cash_flow` 按分类聚合。**只有一个来源,不存在口径打架。**

### 0.3 一个不能合并的地方:性质 ≠ 消费分类

`cash_flow.category_code`(`consumption / loan_payment / interest_paid / to_relatives`)是**性质**,
它决定储蓄率与负债口径(AGENTS.md 联动链 L1)。而「餐饮美食」只在 `consumption` 这个性质下有意义。

所以是给 `cash_flow` **加**一个可空的 `expense_category_id`,**不是替换** `category_code`。
合并会静默把储蓄率算错 —— 这类错误不报异常,只是数字慢慢不对。

**但界面上它们是一层**:宫格里既有消费分类、也有那三个性质项,点哪个都是**一次点击**
(点消费分类 → 性质自动是 `consumption`;点那三项 → 消费分类为空)。95% 的笔是日常开支,
分成两步选就是给 95% 的情况加一次点击。

### 0.4 与「10 分钟/月」的关系

「刻意不做逐笔流水账」这条边界在 v1.8 其实已经松动 —— `ITEMIZED` 那时就有了。
真正的硬约束是**每月 10 分钟**,而这一版没有增加任何手工负担:

- 总额模式:一个数,不变
- 逐笔模式:本来就在逐笔记,只是类目更有用了(而且宫格比下拉**更快**)
- 导入:把几百笔的活压进几分钟,**方向恰恰相反**

仍然刻意不做的是「**在本 app 里手工随手记每一笔**」—— 那是渠道 App 的活。
我们要的是把它们已经记好的东西**搬进来**。


## 1 · 调研(v2 起步 · v4 加深)

### 1.1 · 问题一:类目树哪里来?

**市面记账软件的三种做法**(来源见 §12):

| 产品 | 结构 | 关键事实 |
|---|---|---|
| **鲨鱼记账** | 仅一级,约 40+ 项平铺 | 无二级;用户抱怨「餐饮下想看买菜/外卖/咖啡占比,做不到」 |
| **钱迹** | 一级 + 二级,可自定义 | **「其他」是默认分类,不能修改或删除;删除某分类后账单移入「其他」** —— 与我们 v1 的设计不谋而合 |
| **随手记** | 一级 + 二级,默认树最细 | 默认把餐饮拆成早/午/晚餐,用户反馈**过细**:「除非真要分析早餐支出,否则『一日三餐』就够」;滚轮选分类被评「要记住位置,操作复杂」 |
| **支付宝账单**(数据源头) | 固定一级,约 20+ 项 | CSV 有「交易分类」列,取值如:餐饮美食/服饰装扮/日用百货/家居家装/数码电器/美容美发/交通出行/住房物业/医疗健康/教育培训/文化休闲/充值缴费/转账红包/投资理财… 自动分类「不是每笔都准」,App 内可手改 |
| **微信账单** | **没有消费分类** | 只有交易类型(商户消费/转账/红包),「参考价值不大」—— 开源社区普遍靠商户名关键字自建映射 |

**结论与决定(v3 · 按维护者评审意见修订):**

1. **一棵两层树,两个深度供选。** 类目是**一棵树**:一级(大类)+ 可选二级(细类)。
   给用户两个起步包 ——「**简单版**」只建一级 10 项,「**复杂版**」把同一棵树建到二级(每个大类下 2-4 个细类,约 30 项)。
   选择卡上把利弊说白:**简单版维护容易、月底抄数快;复杂版录入多一点,但分析更准**。
   随手记「默认树过细」的教训以另一种方式吸收:**层级就到二级为止,不做三层**;总数上限 40(含二级)。

2. **两版不是两棵树,是同一棵树的两个深度 —— 这是整个兼容设计的地基。**
   复杂版的一级与简单版**完全相同**(严格的细化关系),于是「两版互相映射」不需要映射表:
   **映射就是树的父子边**,天生存在、永不漂移。由此切换语义变得干净:

   | 切换方向 | 历史数据 | 新录入 | 损失 |
   |---|---|---|---|
   | **复杂 → 简单** | 二级明细**保留不动**,报表按父级聚合(合计无损) | 按一级填 | 只有「以后不再细」,历史精度一分不丢 |
   | **简单 → 复杂** | 一级数据在复杂视图显示为「该大类 · **未细分**」 | 按二级填 | 无 —— 历史本来就没有细度可损 |

   「未细分」不是真类目,是「记在一级上的钱」的显示名;随时可以切回「按大类看」,因为父子边永远在。

3. **一级与支付宝账单同名**(高频 10 项:餐饮美食、日用百货、服饰装扮、数码电器、交通出行、住房物业、医疗健康、教育培训、文化休闲、充值缴费 + 内置「其他」)—— 数的源头就是这套名字,同名 = 导入零映射、抄单零翻译。复杂版二级用来接住支付宝的长尾类目(家居家装→日用百货/家居家装,酒店旅游→文化休闲/旅游酒店…),预置映射表全量覆盖。

4. **删除语义按树走,比「一律转其他」更精确**:删**二级** → 数据转到**父级**(变成该大类的「未细分」,一分不丢、大类合计不变);删**一级**(连带其下二级)→ 数据转「其他」。钱迹/支付宝记账本的「转其他」语义保留为最终兜底,提交者点名接受。

### 1.2 · 问题二:渠道档案(页面交互 · 产物规格 · 解析要点)

> v4 加深:每个渠道一份「档案」—— **交互路径**(将来原样进导入页指引)、**产物规格**(解析器的依据)、
> **截图目标页**(AI 通道拍什么)。来源见 §12;路径按 2026-09 核对,指引页脚标注核对日期 + 失效反馈入口。

#### 渠道 1 · 支付宝

**A. 文件导出交互(逐步,进指引):**

1. 支付宝 App → 底栏「我的」→「账单」
2. 账单页右上角「···」→「**开具交易流水证明**」
3. 选「**用于个人对账**」(⚠ 别选「用作证明材料」—— 那是 PDF 盖章版,导不了)
4. 输入支付密码 → 选条件:时间范围(**最长可选 1 年**)、交易类型;**勾选「展示交易对手信息」「展示商品说明信息」**(账单更全,映射更准 —— 指引里要点名)
5. 输入邮箱 → 提交
6. **解压密码**:通过「支付宝服务消息」推送;也可回「开具记录」里查
7. 邮箱收 zip → 直接丢给我们(带密码框)或自己解压出 csv 再传

**B. 产物规格(解析器依据):**

| 项 | 值 |
|---|---|
| 容器 | zip(加密)→ 内含单个 csv |
| 编码 | **GBK** |
| 说明头 | 前 **24 行**为账单说明,第 25 行表头,第 26 行起数据(行数随导出条件略有浮动 → 解析器**按表头特征定位**,不写死行号) |
| 表头列 | 交易时间 · **交易分类** · 交易对方 · 对方账号 · 商品说明 · **收/支** · 金额 · 收/付款方式 · **交易状态** · 交易订单号 · 商家订单号 · 备注 |
| 金额格式 | 可能带 ¥ 与千分逗号 → 正则 `[¥￥,]` 清洗(社区合并工具的通行做法) |
| 关键取值 | 收/支 ∈ {收入, 支出, 不计收支};交易分类 ≈ 20 项(餐饮美食/服饰装扮/日用百货/家居家装/数码电器/美容美发/运动户外/母婴亲子/宠物/交通出行/住房物业/酒店旅游/文化休闲/教育培训/医疗健康/生活服务/公共服务/充值缴费/转账红包/投资理财/保险/其他);交易状态含「退款成功」等 |

**C. 解析口径:** 只取「支出」行;「不计收支」丢弃;退款行按同分类**净额轧抵**;「转账红包/投资理财/保险」默认剔除进「中性清单」(转给家人不是消费、买理财不是支出 —— 清单在确认页可见可改)。分类自动打标「不是每笔都准」(少数派原话)→ 所以确认页必经。

**D. 截图目标页(AI 通道):** 「我的 → 账单 → **月账单**」(或「设置 → 账单 → 收支分析」)—— 按月的**支付分类统计**,点月份倒三角可切按年。指引配一句:「筛选记得选全部类型,代扣/代付才不会漏」。

#### 渠道 2 · 微信

**A. 文件导出交互:**

1. 微信 →「我」→「服务」→「钱包」(老版本:「我 → 支付 → 钱包」—— 指引写两条)
2. 右上角「账单」→ 等列表**加载完毕** → 右上角「常见问题」→「**下载账单**」
3. 选「**用于个人对账**」(另一个「用做证明材料」是盖章 PDF)
4. 选时间范围(**一次最多 3 个月** —— 要整年得分 4 次,指引里明示)→ 可选交易类型
5. 输入邮箱 → 输入支付密码
6. **解压密码**:「微信支付」通知消息里推送 —— 指引提醒「先记密码再去邮箱」
7. 邮箱收 zip → 丢给我们

**B. 产物规格:**

| 项 | 值 |
|---|---|
| 容器 | zip(加密)→ csv |
| 编码 | **UTF-8**(与支付宝不同!解析器按 BOM/探测自动分流) |
| 说明头 | 前 **16 行**说明,之后表头(同样按特征定位不写死) |
| 表头列(11 列) | 交易时间 · **交易类型** · 交易对方 · 商品 · **收/支** · 金额(元) · 支付方式 · **当前状态** · 交易单号 · 商户单号 · 备注 |
| 与支付宝的列对应 | 交易类型↔交易分类 · 商品↔商品说明 · 金额(元)↔金额 · 支付方式↔收/付款方式 · 当前状态↔交易状态(社区映射对照) |
| **没有消费分类列** | 交易类型只有「商户消费/转账/红包/…」→ 靠**商户关键字映射**(FR-532) |

**C. 解析口径:** 只取「支出」;中性交易(零钱充值/提现/理财通/信用卡还款)剔除进中性清单;商户名走关键字规则 → 类目,不命中落「其他」。

**D. 截图目标页:** 「我 → 服务 → 钱包 → 账单 → 右上角**统计**」—— 月账单默认展示**收支构成**,可切年账单。

#### 渠道 3 · 招商银行

**A. 文件导出交互(记录在案,第一期不接文件):** App「我的 → 全部 → 流水打印 → 输邮箱」→ **PDF**(带章);要结构化文件得走**网银**「交易查询 → 导出选中 → Excel」。App 端拿不到 csv 是常态。

**B. 截图目标页(第一期的招行通道):** App 首页「**收支明细**」/「月账单 · 结余月历」—— 招行自带**四十余种场景分类**的收支统计,拍这页给 qwen-vl 转写即可。

**C. 双计警示(最重要):** 招行流水里**必然**包含走支付宝/财付通的扣款 —— 已导支付宝/微信的家庭,银行侧只该补「不走这两者的部分」(工资卡代扣/房贷/线下刷卡)。确认页对银行来源单独放这句话;后续接文件解析时默认过滤「交易对方含支付宝/财付通」行(china_bean_importers 通行做法)。

#### 渠道 4 · 工商银行

**A. 文件导出交互(记录在案,第一期不接文件):** App「首页 → 账户 → 更多 → 历史明细打印 → 选时间 → 填邮箱(可选不加密)」;网银「流水查询 → 导出」= **csv/PDF 可选**。

**B. 截图/指引:** 同招行策略 —— 第一期走 App 收支统计页截图;文件解析等真实样本。

#### 通用结论(v2 结论保留)

第一期文件导入只做支付宝+微信;银行走截图;zip 直收带密码框;编码/说明头由引擎兜、失败给人话(定向识别「证明材料 PDF」这个最常见错误);双计风险主动挡。

### 1.2b · 导入/覆盖/合并模型:来源行(v4 · 评审要求补齐)

**问题:** 同一个(账期 × 成员 × 类目)的数,可能同时来自**手填、历史导入、新导入** —— 谁盖谁?

**模型:每格金额不是一个数,是一组「来源行」之和。**

```
类目显示额 = 手填行 + 支付宝批次行 + 微信批次行 + 截图·招行批次行 + …
                                    └─ 每个渠道在该(期×人×类目)最多一行
PMC 月度总额 = Σ 所有类目显示额(结构不变,仍同一事务回写)
```

**由此,所有冲突场景的答案都是推论,不是逐条规定:**

| 场景 | 行为 | 为什么 |
|---|---|---|
| 首次导入渠道 X | 新增 X 来源行,与手填/他渠道**相加** | 不同来源是不同的钱 |
| **重导**渠道 X(同期同人) | **只替换 X 行**;手填与他渠道**纹丝不动**;确认页显示新旧差额 | 覆盖的粒度是渠道,不是格子 |
| 导入后**手改**某类目金额 | 差额记入**手填行**(= 输入值 − Σ渠道行,**可为负** = 对导入的冲正,显示「手工调整 −x」) | 导入行保持原样可审计;类目合成额不可为负(拒绝并说明) |
| 手改之后**再重导** X | 仍只换 X 行 → **用户的手工修正永远不会被导入冲掉** | 手填是独立来源,不是渠道的从属 |
| 撤销批次 | 批次列表整批移除,其余来源自动回落 | 批次是一等公民,可查可撤 |
| 纯手抄用户 | 只有手填行,一切如 v1 | 模型对不导入的人退化为「就是那个数」 |

**UI 呈现:** 展开态每个类目框下给来源角标(「支付宝 2,180 · 微信 1,000 · 手工 +320」);框本身直接可编辑(改的是手填行)。批次列表(本期导过什么、何时、替换过几次)在导入页可见。

### 1.3 · 问题三:AI 怎么介入?

**复用 v1.4 持仓截图导入的整套通道**(`VisionLlmClient` + 多文件上传 + 确认页三态比对 + qwen-vl key 已在管理页配置),换一个提示词场景:

- **拍什么**:支付宝「账单 → 月账单/收支分析」页、微信「钱包 → 账单 → 统计」页、各银行 App 的月度收支统计页 —— 这些页面**本身就显示按类目汇总好的金额**,正是我们要的数。
- **AI 只转写,不算数**(承 `feedback_llm_no_math`):qwen-vl 从截图读「类目名 + 金额」原样输出;跨截图/跨渠道的合并、类目映射、求和全在引擎;识别不清标疑,不硬猜。
- **批量**:一次传多张图(既有 `MultipartFile[]`);**支持传一个 zip 装一堆截图**(引擎解包逐张送)—— 对应维护者点名的「大量截图导入 / zip 导入」。
- **微信 CSV 的类目映射**:微信没有分类列,引擎先按「商户名关键字规则」映射(规则家庭可编辑、记忆化 —— 「美团」→餐饮美食,配一次管一年);规则不命中的余量,可选让 LLM 对**商户名列表**给映射建议(只给建议,金额不过 LLM),不配 key 就全落「其他」等手动分。
- **边界**:AI 不参与支付宝 CSV(它有分类列,确定性解析)、不参与任何求和、不参与「其他」兜底判定。

### 1.4 交互调研(第 2 稿新增 · 这一节的缺失直接导致第 1 稿被否)

第 1 稿只调研了「账单怎么导出来」,**没调研「记账软件的分类录入长什么样」**。补上:

| 结论 | 证据 |
|---|---|
| **分类是记一笔时顺手选的**,不存在「月底把总数分配到类目」这个动作 | 随手记 / 鲨鱼记账 / 钱迹三家的核心动作都是「记一笔 → 选分类」 |
| **选择器是图标宫格,不是下拉** | 下拉要「点开→滚动→找→点」四步;宫格一步。随手记 v12 把「记一笔」从浮层改成 Tab 主页签,就是为了减层级 |
| **最常见的流失原因是分类太麻烦** | 「填半天分类还不对」是用户吐槽最集中的点 |
| **两级是对的** | 「所有吃饭都是餐饮,早午晚饭还是宵夜不分,明显不够」—— 对鲨鱼记账的真实抱怨 |
| **导入归类是行业公认的烂摊子** | 钱迹按分类名**严格字符串匹配**,对不上全落「其它」;官方建议用户**先在 Excel 里 VLOOKUP 自己归类**;AI 匹配只用于手记新账、不用于导入,且仅 iOS 公测 |
| **「其它」不可删是通行做法** | 钱迹:删掉会导致账单无法归类;删某分类,其下账单自动归「其它」 |

**最后一条是这一版的机会所在**:如果我们把「逐笔明细的自动归类 + 逐行可改 + 记住规则」做好,
就是现成产品普遍做不好的那一段。

## 2 · 用户故事

### 2.1 · 最快的一条路:两个文件(主场景 · 新)

月底关账,他在支付宝里点「开具交易流水证明」发到邮箱,微信同理。把两个 zip 丢进导入页、输入解压密码 → 系统解析、按类目汇总、预填分类填报,来源角标「支付宝 ¥x · 微信 ¥y」。他扫一眼、微调「其他」里的余量,确认 —— 合计自动写回月度总额。**全程不到两分钟,一笔流水都没在这记。**

## 4 · 不做什么

### 非目标(仍然刻意不做)

- **在本 app 里手工随手记每一笔** —— 那是渠道 App 的活。逐笔录入是给「渠道覆盖不到的现金开销」
  和「愿意认真记的人」用的,不是要取代支付宝的记账。导入才是主路。
- **预算包络 / 超支提醒** —— 那是另一个产品(YNAB 那一类),和「摸清家底」不是一件事
- **三层分类** —— 两层已经能表达「餐饮 › 外卖」,三层的维护成本换不来分析价值
- **收入侧自定义分类** —— 收入类目与账户类型有绑定(v0.12),是另一条联动链,这版不动
- **银行账单文件解析** —— 各行格式互不相同,没有真实样本就写解析器,写了大概率是错的。
  页面如实说明原因 + 留反馈入口
- **屏幕监控式自动记账** —— 隐私上不可接受(钱迹也明确拒绝,理由相同)
- **AI 替用户做数学** —— AI 只做「这个商户属于哪个分类」这一件事,不碰金额

### 这一版明确推迟的

- **AI 截图导入**(FR-540~545):它产出分类汇总数,和逐笔载体对不上。代码保留、入口不挂,
  等逐笔线跑顺再决定它落成什么
- **历史逐笔的批量归类**(FR-557):可选项,不做也能用
- **多账户拆分导入**:一批只落一个账户。支付宝账单里其实混着余额宝/花呗/银行卡多个资金来源,
  拆开是对的,但第一期不做 —— 先把主路走通


## 5 · 10 分钟约束核对

| 动作 | 频次 | 耗时 |
|---|---|---|
| 建类目(起步包一键) | 首次 | <1 分钟 |
| 月底进数:文件导入 | 每月 | ~2 分钟(导出发邮箱是渠道 App 里点几下,解析确认秒级) |
| 月底进数:截图导入 | 每月 | ~2 分钟(截 2-3 张 + 确认) |
| 月底进数:手抄 | 每月 | 1-2 分钟 |
| 看支出报表 | 随意 | 0 |

**三条通道都在包络内;完全可选,不用的人 0 增量。** 风险:导入指引没写清 → 用户在渠道 App 里迷路,时间花在找入口上 —— 所以 FR-530/541 把逐步路径当功能做,不是当帮助文档做。

## 6 · 存量影响

| 存量 | 影响 | 保证 |
|---|---|---|
| **没建类目的家庭** | 零 | 填报页 / 报表页与上一版**逐字一致**;宫格、导入入口都挂在「这个家建过类目」之后 |
| **TOTAL 模式的家庭** | 零 | 不提示、不劝导、不出现半个入口 |
| **已有的逐笔支出**(`cash_flow` 里 49 条 EXPENSE) | `expense_category_id` 为空 | 报表里显示为「未分类」并给出笔数;不影响任何金额、不影响储蓄率 |
| **`cash_flow.category_code`** | **不动** | 性质仍是性质。新字段是**加**的,不是替换 —— 储蓄率与负债口径(联动链 L1)完全不受影响 |
| **账户余额轧差** | 导入会增加流水 | 导入的是真流水,本来就该参与轧差。顺序仍是「先录收支、最后核对余额」,导入页明示 |
| **V59 迁移** | **改掉,不是加 DROP** | 那张 `expense_split` 从没在 prod 存在过(v1.21 未发布),直接改迁移最干净 |
| **prod 数据** | 零 | 新增一个可空列 + 三张新表;没有任何 UPDATE/DELETE 触及既有行 |

**回滚只回 jar 不回 DB** → 新列必须可空、新表必须是纯新增,老 jar 见到它们要能照常跑(联动链 L7)。


## 7 · 开关与默认值

**没有开关。** 「这个家有没有建过支出类目」本身就是开关:

| 状态 | 用户看到 |
|---|---|
| 没建过类目 | 与上一版逐字一致 · 逐笔录入区有一行「想知道钱花在哪?建几个支出类目 →」 |
| 建了类目 · TOTAL 模式 | 类目管理页可用;填报页不变(总额模式没有分类,§0.2) |
| 建了类目 · ITEMIZED 模式 | 录入行下方出现宫格 · 导入入口出现 · 报表出现「钱花在哪了」 |

默认值:
- 起步包**不自动建** —— 建类目是用户的主动动作,替他建等于替他决定了分类体系
- 分类**必填但默认「其他」**(FR-554):不拦截提交
- 细类**默认「不细分」**(FR-552):细分永远是加分项,不是门槛
- 导入的「记住我的改动」**默认勾选**(FR-567):越用越准是这个功能的核心价值


## 8 · 隐私与数据红线

## 13 · 实施记录

### 13.0 第 1 稿的实施记录(已作废的那一版)

> 下面 13.1~13.8 记的是<b>第 1 稿</b>(按类目填汇总数)编码时踩的坑。那一版被否了(§14),
> 但这些坑本身仍然有效 —— 其中「一个字符吞掉一整行」「深度不只是展示概念」
> 「护栏判据太宽」在第 2 稿里原样复现过。**留着,不要删。**

> 状态从「待评审」转为**已实现,待验收**。下面记的是设计与现实对不上的地方 ——
> 每一条都是「TDD 没想到」或「踩了才知道」。

### 1 · 待实测 3 的答案:那条 upsert 会静默抹掉收入

`PeriodMemberCashflowMapper.upsert` 的 ON DUPLICATE 分支写的是
`total_income_input = VALUES(total_income_input)` —— **整行覆盖**语义。
只传 expense 的话,**当月收入会被抹成 NULL,而页面上没有任何报错**。
所以另加了 `upsertExpenseOnly`。如果当时直接复用,用户展开一次分类填报就会静默清空收入。

**这条是 TDD 把它列进「待实测」才发现的** —— 读一眼 SQL 就够,但不列出来就不会去读。

### 2 · zip4j 能拉下来,选型五的兜底没用上

离线仓库里没有,在线经阿里云镜像一次拉到(2.11.5,~200KB 无传递依赖)。
「用户自己解压传 csv」这条路仍然保留 —— 不是备选,是长期并存的第二入口。

### 3 · 一个字符差异能静默吞掉一整行

半角 `¥`(U+00A5)在 GBK 里**不可映射**,写进 GBK 文件再读回来变成 `?`。
原来的 `money()` 只 replace 了 `¥` 与 `￥`,于是这一行金额解不出、**整行被 continue 掉**。
真实 GBK 账单用的是全角 `￥`(U+FFE5),但既然一个字符就能悄悄吞一行,
就改成**只保留数字/小数点/负号**的白名单。

顺带把三类「说不清的行」全部改成**计数披露**:收支枚举不认识 / 列数超表头 / 金额解不出。
「静默少算几行」在用户那儿表现为「导入总额比账单少一点」,基本查不出来。

### 4 · 两个同源的「深度」缺陷(TDD 完全没预见)

**① 映射只看一层。** 导入映射原来在 `fillable`(复杂深度=细类)里找,
而渠道给的是**大类名**(「餐饮美食」)→ 找不到就全落「其他」;
偏偏「家居家装」因为复杂版里正好有同名细类而命中,看起来像「大部分认不出来」。
修:在**整棵树**上匹配,细类优先、大类兜底 —— 落在大类上就是「未细分」,一个一等形态。

**② 更严重:钱在账上,页面上没有它的框。** 导入的钱落在大类上,
而复杂深度的填报表单只渲染细类的框 → **那笔钱用户看不见也改不了**,只能在报表里露个脸。
修:表单类目 = 可填的 ∪ **这一期已经有钱的**(含停用的),并标「· 未细分」。

这两条的共同根源:TDD 把「深度」当成了纯展示概念,而它其实**同时影响映射与表单**。

### 5 · FR-518 没按原样做(明确的偏离)

FR-518 要「分类填报与逐笔在同一张图里按类目合并」。实现时没做,原因:
两套类目体系(全局 `cash_flow_category` vs 家庭自定义树)**没有公共键**,
合成一张图得先统一它们 —— 而那是 ITEMIZED 侧的联动链,TDD §十 已定第一期不接。
所以做成**两个相邻的区,各自标明来源**。比合出一张来源含糊的图诚实。

### 6 · 年度累计与趋势必须同锚

第一版 `year()` 算的是整个自然年(含进行中的期),而本期/趋势锚在最新已关账期 ——
于是同一页上「年度累计」不等于「趋势各柱之和」,**两个数都「对」,只是口径不同**。
这是最难向用户解释的一类不一致。改成 `year()` 也只算到锚期为止。

### 7 · 联调中撞到两个「早有记录却没护栏」的坑

- **SELECTid**:文本块以 `SELECT ` 结尾再拼接时,行尾空格被剥掉。
  `AskAccessTokenMapper` 的注释里写着「真在 beta 上炸过」,我三个新 mapper 全中,
  beta 上第一次点起步包就 500。
- **Thymeleaf utility 写在 `${}` 外面**:`#lists.isEmpty(...)` 落在 `${}` 外,
  **渲染期**才炸,编译/单测/启动全过,响应截断在半路、页面半截。
  `feedback_thymeleaf_diagnosis` 早写着这条规则。

两条都补了机器扫描。**只写在注释或记忆里的教训,注定被下一个人再踩一次。**

### 8 · 护栏判据三次写得太宽(自己记一笔)

`NO-TEXTBLOCK-COLS` 第一版判据是「COLS 不许用文本块」——太宽,
把两个**本来正确**的既有 mapper 报成红(它们用的是 `"SELECT " + COLS`,普通字符串保得住尾空格)。
真正的坑是**文本块以关键字结尾**。第二版又抓到了注释里描述这个坑的那句话,
第三版才过 `codeonly`。加上 v1.20 的 `NO-PHANTOM-BTN-CLASS` 误报两次,
这一版一共**三次把护栏绑在错的特征上**。教训:护栏写完要做**反向验证**(注入坏形状看它红不红),
而且要确认它**不会把正确的写法也报红** —— 后半句我一直漏。

## 14 · 第 1 稿为什么被否 · 改了什么

### 14.1 被否的原话

> 「我觉得交互很奇怪,你有仔细调研一下常见记账软件怎么做的吗?
> 现在给我这么大一堆空格让我分门别类做填入,根本没法用好吗?」

### 14.2 我做错的是什么

**把「分类」设计成了一个独立的填报动作。**

第 1 稿的中心决定是「分类 = 月度总额的展开」,产物是填报页上一张 37 格的表:
每个类目一个输入框,月底打开面对一堆 0。beta 上真机截图里那一屏我自己也看到了
(当时的判断是「复杂版录入麻烦是必然代价,PRD 里已经跟用户讲清了」),但没有意识到
**这不是代价问题,是这个动作根本不存在**:

- 人记得住「中午吃了什么」,记不住「这个月餐饮总共多少」。把总数分配到类目里,
  是一个**人做不来的运算** —— 除非先有逐笔,而有了逐笔就不需要这张表了。
- 所有记账软件里,分类都**依附在一笔上**,是记账时顺手选的。没有任何一家有「月底分配」这个界面。

**根因是调研做窄了**:调研了「账单怎么导出来」(渠道路径、文件格式、编码),
**没调研「记账软件的分类录入长什么样」**。前者是实现细节,后者是产品形态 ——
我把功夫全花在了细节上,而形态是错的。

## 15 · 第 2 稿实施记录

### 15.1 MySQL 8.0 的保留字:`COUNT(*) AS rows`

`rows` 是随窗口函数引入的**保留字**,`COUNT(*) AS rows` 直接语法错。
炸的位置很讨厌:**只在真跑到那条查询时才炸** —— 编译过、启动过、单测过
(单测用的是内存假 mapper,根本不碰 SQL),报表页 500。

护栏 `v1210-NO-RESERVED-WORD-ALIAS` 扫一批常见保留字别名。

### 15.2 `th:replace` 会把宿主标签连同它的 class 一起换掉

宫格是这么插进表单的:

```html
<div class="w-full" th:replace="~{entry/_cat-grid :: grid}"></div>
```

`th:replace` 替换的是**整个标签**,`w-full` 随之消失。于是宫格变成
`flex flex-wrap` 行里的一个普通项,挤到「+ 加一笔」右边、左边空一大片。
改用 `th:insert` —— 它保留宿主标签,`w-full` 才有人承载。

**双端截图抓到的。** 功能完全正常,接口全通,只是难看。

### 15.3 `[hidden]` 打不过 Tailwind 的 `flex`

```html
<div data-cat-subs hidden class="flex gap-[6px] ...">
```

HTML 的 `hidden` 属性靠 UA 样式表的 `[hidden]{display:none}` 生效,
而那条规则的优先级**比任何 class 都低** —— 元素上只要有 `flex`/`block`/`grid`,
`hidden` 就完全失效。细类条在没选中任何大类时也露着。

修法是一条全局 CSS:`[hidden] { display: none !important; }`。
写在这里而不是逐处改成 `style="display:none"`:这是**整类**问题,
下一个人不会记得这条规则。

### 15.4 换了控件形态,配套的 JS 会**只在特定路径上**抛异常

类目从 `<select>` 换成宫格之后,v1.19.3 的 `expense-liability.js` 还在调 `cat.options` ——
而 `data-expense-cat` 现在是 hidden input,`Array.prototype.slice.call(undefined)`
在 strict 模式下抛 TypeError。

**但它只在用户选中信用卡那一刻才抛**:首屏默认是现金账户,走的是「恢复」分支、
提前 `return`,所以页面打开一切正常,冒烟测试和护栏都看不出来。

判据教训:**换控件形态时,要把「读这个控件的所有代码」列出来,而不是只看它自己渲染得对不对。**
护栏 `v1193-EXPENSE-CAT-UI-SYNC` 现在钉的是「新实现真的在藏按钮」且「不再出现 `.options[`」。

### 15.5 判据顺序错了,一整个桶变成死的

`NEUTRAL` 关键字表里有「还款」,而分桶判据里「关键字划转」排在「还贷」之前 ——
于是渠道明确标成**支出**的「花呗还款」先被当成划转剔掉了,`NATURE` 桶**永远是空的**,
确认页上那个格子形同虚设。

正确顺序:渠道明说的(不计收支 / 收入)→ 还贷 → 关键字猜的划转。
**渠道说是支出就是支出**;关键字是猜,不该压过渠道自己的判断。

护栏 `v1210-NATURE-BEFORE-NEUTRAL` 直接比较两处判据在源码里的行号。

### 15.6 逐笔载体让「删类目搬家」从一段算法变成一条 UPDATE

第 1 稿搬的是 `expense_split`,那张表上有 `UNIQUE(期,人,类目,来源)`,
裸 UPDATE 会撞键,得先把撞键的行**相加合并**再删源行。

逐笔载体没有这个问题 —— 每一笔本来就是独立一行:

```sql
UPDATE cash_flow cf JOIN period p ON p.id = cf.period_id
   SET cf.expense_category_id = #{toId}
 WHERE p.family_id = #{familyId} AND cf.expense_category_id = #{fromId}
```

这不是刻意设计的,是「分类挂在一笔上」附带的简化。**换载体能消掉的复杂度,
往往比在原载体上优化算法省得多。**

### 15.7 sed 按「注释块起点」删方法,会连坐

删 `/entry/split` 三个端点时,我用「往前找到最近的 `/**`」定位删除起点,
结果连带吃掉了 `entryPeriodListUpperBound`、`refreshStocks`、`parseLongOrNull` 三个
**完全无关**的方法(它们和被删端点共享注释块边界)。编译器当场报错,所以没造成实际损失 ——
但如果被吃掉的是一个没人调用的方法,就会静默消失。

判据:**批量删代码之后,`git diff HEAD | grep '^-.*\b(private|public)\b.*('`
把删掉的方法名列一遍。** 这一步花 5 秒,能挡住一整类事故。

### 15.9 评审第二轮:图标 / 尺寸 / 入口

维护者看完 beta 提了三条,每条底下都是一个更一般的问题。

**① 「所有的分类都需要有一个匹配的 icon」**

纯文字的宫格扫起来慢 —— 图标是给「一屏找一个」提速的,而这正是宫格存在的理由。
做法:内置一份**关键词 → 图标**表(`ExpenseCatIcon`),按类目名猜;
起步包的 10 个大类刻意与支付宝交易分类同名,所以全都命中;自建类目猜不中就落一个中性标签图标。

**不让用户挑图标**:建类目已经是用户嫌麻烦的地方,再加一步挑图标是往伤口上撒盐。

图标一律 inline SVG(`feather` 风格 24×24 · `stroke=currentColor`),不用 emoji ——
`currentColor` 顺带解决了「选中态整块反色时图标要变白」,不需要第二套样式。

**② 「性质另算那几个按钮怎么和上面的不一样大」**

违反 `feedback_sibling_uniform_selfcheck`(并列同类元素必须同尺寸同样式)。
原因:我给性质项用了 `.cat-chip`(细类那种小 chip),而消费分类用 `.cat-cell`。
它们在界面上是**并列的选择项**,不是两个层级。

修:共用 `.cat-cell`,只用 `--nature` 改颜色与边框样式(虚线),**不改尺寸**。
另外 `.cat-row` 用 `repeat(auto-fill, minmax(96px,1fr))` 而不是 `auto-fit` ——
`auto-fit` 会把「只有 3 个性质项」那一排拉成 3 倍宽的格子,同样是尺寸不一致。

**③ 「我请问了,这导入按钮在哪里??」**

**这一版最值钱的能力,没有入口。** 实现时只在报表页一句说明文字里内联了一个链接,
填报页 —— 用户真正在的地方 —— 一个都没有。

这正是 `feedback_verify_user_path` 说的那种漏:我验的是「功能对不对」,
没有**以用户身份从顶层点一遍**。而且也没登记进 `scripts/entry-points.json`(AGENTS.md L11 要求)。

修:挂在分类宫格的标题行(用户正是在那个位置意识到「一笔一笔记太慢」),
类目管理页页头也加一个;两条都登记进入口表,`entry-points-check` 在 PC + 移动都验过可见。

### 15.10 顺带炸出来的:片段参数里的 `T(...)`

给宫格加图标时用了
`~{fragments/_cat-icons :: icon(${T(com.family...ExpenseCatIcon).of(name)})}`,
结果 `/entry` **从 435KB 掉到 93KB**、curl 退出码 18、浏览器永远等不到 DOMContentLoaded ——

判据一开始写成「模板里不许有 `T(com.family`」——**太宽**:项目里有三处普通属性用法
(`th:if` / `th:each` / `th:text`)一直好好的。炸的是**片段参数**这个位置。
用「注入 → 复现 → 还原」证实之后才把判据收窄到 `~{...::...T(com.family`。

这是这一版第 N 次把护栏判据写太宽。**教训已经很清楚了:判据写完必须两个方向都验 ——
坏的报红、好的不报红。** 后半句我一直漏。

### 15.11 第三轮:入口存在 ≠ 入口找得到

「导入按钮在哪」被问了**两次**。

第一次是真漏了(§15.9 ③)。补上之后又被问一次 —— 那时链接**确实存在**,
`entry-points-check` 也过了。问题出在**它只验「可见」不验「分量」**:
一个 10px 灰色 mono 链接,挂在宫格里那条分隔线的右端,还得往下滚 250px 才进视野。
几何上「有面积、未被遮挡、不在折叠容器里」,三条断言全过 —— 人却找不到。

修:主入口移到**支出区标题行**,做成 `btn-ghost` 按钮(33px 高、brass 描边),

「一笔一笔记太慢?传一份支付宝/微信的月账单,几百笔自动归类,你只核对没把握的那十几笔。」
—— 光有按钮不够,还要让人知道它能省什么事。原来那个小字留着,降为就近的次入口。

### 15.12 第四轮:「落到账户」必须可选 —— 这不是体验问题,是正确性问题

维护者:「导入/单笔记录时,是否关联影响账户余额是可选的;用户用我们这个可以只是记录一个支出的构成;
可能费用本身已经提前被扣除了。」

查下去发现比想象严重。`EntryService.applyDeltaToBalance` **直接改写
`period_snapshot.end_balance`** —— 那是用户自己填的期末余额本身,不是什么预填值:

```
上期末 10000 · 真实本期末 9000(用户填了,因为花了 1000)
再记一笔 1000 的支出 → 余额被改成 8000        ← 扣了第二遍
unexplained = 8000 − 10000 − (0 − 1000) = −1000  ← 还凭空出现「解释过头」
```

现有纪律「**先录收支、最后核对余额**」能掩盖这个问题 —— 但那只是一种顺序约定。
**导入天然是反过来的**:月底打开账单页时,余额多半已经核对完了。几百笔一起扣第二遍。

#### 为什么不能做成 `account_id = NULL`

那是最直观的表达(「这笔不属于任何账户」),但**行不通**:
`cash_flow` 没有 `family_id`,**家庭归属是通过 `JOIN account` 得到的**
(`sumRealExpenseByPeriod` 里 `WHERE a.family_id = #{familyId}`)。
account_id 为空 → 这笔不属于任何家庭 → 从家庭支出总额里**消失**。
所以只能做成标记,账户仍然必填(它同时承担「算在谁名下」和「属于哪个家」两个职责)。

#### 三条口径必须一起退出

| | affects_balance=1 | =0 |
|---|---|---|
| 改写期末余额 | 是 | **否** |
| 参与该账户轧差 | 是 | **否**(否则 unexplained 变负数) |
| 算作账户外部流出(NAV/XIRR) | 是 | **否**(否则 NAV 以为「钱是被取走的不是亏掉的」,收益率算高) |
| 计入家庭支出总额(口径 A) | 是 | **是** |
| 计入支出构成 | 是 | **是** |

第三行最隐蔽:余额没动却报一笔流出,**不会报错**,只是账户收益率慢慢变好看。
护栏 `v1210-BALANCE-LINK-OPTIONAL` 同时钉这三条 + 「口径 A 不许跟着过滤」。

#### 默认值故意不一致

逐笔录入默认**勾上**,导入默认**不勾**。不是疏忽 —— **两条路上更常见的顺序是反的**。
追求「两边默认一致」会让其中一边的多数用户每次都要改一下。

#### 撤销也要跟着分

整批撤销时**只有当初扣过余额的才把钱加回**(`batchAffectsBalance`),
否则「只记构成」的批次一撤销,账上会凭空多出一笔钱。
