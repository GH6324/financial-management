# v1.17 · Docker 部署下的富途 OpenD 一键接入(可选 sidecar 方案)

> 状态:**方案已定 · PRD 第二稿待评审**
> 目标版本:app.version = 1.17.0(已 bump)
> 来源:维护者点名 —— 「docker 启动情况下富途 OpenD 的自动集成:目前你要求用户自己打包镜像,我感觉不合理,要一键式的,类比 linux 原生版本;至少也是提供好用户命令、执行一下就 ready 的那种」
> **方案定为 B(维护者定 2026-08-17)**:我们自己维护一个**可选的** launcher 镜像,不把这块职责并进主镜像。第一稿我推荐的是 A(app 容器自管),维护者的判断是:富途相关的东西**不是所有用户都需要,应该可选、不该打包进来**;另外对接 OpenD 本身风险高,**必须强制提示用户校验哈希**,并公开我们的打包过程。
> 相关:GitHub issue #13(Docker 下 OpenD 连不上)只改了文档措辞,没动这个根本问题

---

## 0 · 这一版在解决什么

同一个功能(券商同步 · 富途),两种部署方式的体验差了一个数量级:

| | systemd 原生(拓扑 A) | Docker compose(拓扑 B · 今天) |
|---|---|---|
| 装 OpenD | 向导页点一下「下载并安装」,应用自己下、自己解压 | **你自己准备一个镜像** —— 富途没有官方镜像 |
| 首次登录 | 向导页填账号密码 → 页面上收短信验证码 | **先找一台有桌面的机器**,用 GUI 版 OpenD 登录一次 |
| 填凭据 | 管理页表单 | 写进服务器上的 `.env` 明文文件(密码要自己 `md5sum`) |
| 启动 | 向导页按钮 | 手敲 `docker compose -f docker-compose.yml -f deploy/futu-opend.compose.yml up -d` |
| 页面提示 | 「把 OpenD 装进系统,点几下就好」 | 「这台是容器部署……**本页不能替你一键装**」 |

四条具体的不合理:

1. **把打包工作外包给用户**,而且是外包了一件他多半做不了的事 —— 富途不发布官方 OpenD 镜像,用户实际只有两条路:自己写 Dockerfile 塞富途二进制(要先搞清依赖),或者去拉一个陌生人的镜像(**供应链风险**:这个容器里装的是能操作真实券商账户的网关)。墙内还叠一层:社区镜像基本都在 Docker Hub,而 Docker Hub 被墙。
2. **「先去一台有桌面的机器登录一次」**对自托管用户经常直接不成立 —— 很多人只有一台云主机,家里没有常开的桌面机。
3. **账号 + 密码 MD5 落在 `.env` 明文**,与本项目「运营参数一律走管理页、不写服务器配置文件」的既定原则冲突(`.env.example` 里现在还教用户 `printf '你的密码' | md5sum`)。
4. **自相矛盾**:向导页第 0 步说富途的问卷/协议在「富途牛牛 App / 网页」里做;同一页的 Docker 段又说必须先用桌面版 OpenD 登录一次。两句话不能都对,用户按哪句都可能白折腾。

> 这一版要的结果:**Docker 用户在向导页看到的步骤数和原生一样**(下载 → 登录 → 收验证码),代价是他要同意拉一个**可选的**网关镜像;而不用富途的人,什么都不会多拉、多装、多跑。

## 1 · 调研:实测结论(2026-08-16 / 08-17 · 在 beta 上做的)

不是查文档得来的,是把 OpenD 10.10.7008 拉下来在容器里跑出来的。**这些结论推翻了现状设计的技术前提**,所以先摆证据:

| # | 结论 | 怎么测的 | 影响 |
|---|---|---|---|
| 1 | **我们写死的下载地址已经失效** | `softwarefile.futunn.com:443` 连接超时(80 端口能应答,但旧文件名 404) | 今天点原生向导的「下载并安装」也装不上 —— 这不只是 Docker 的问题 |
| 2 | 官方现行地址是 `softwaredownload.futunn.com/Futu_OpenD_10.10.7008_Ubuntu18.04.tar.gz`;文件名格式和我们拼的 `FutuOpenD_<版本>_Ubuntu16.04.tar.gz` **完全不同** | 跟 302 跳转 | `osTag()` 的 `Ubuntu16.04` / `Centos7` 映射要重做 |
| 3 | 我们的下载白名单只放 `softwarefile.futunn.com`,**用户手填现行官方 URL 会被我们自己拒掉** | 读 `FutuOpendManager.downloadUrl()` | 连"手动救"这条路都堵着 |
| 4 | 有稳定的「取最新版」端点:`https://www.futunn.com/download/fetch-lasted-link?name=opend-ubuntu`(还有 `-centos`/`-macos`/`-windows`)→ 302 到具体版本包 | curl 实测 | **用户不该再手填版本号**(向导页的 placeholder 现在还写着 `9.3.5308`) |
| 5 | 445MB 的包里,**命令行版只占 125MB**,其余 320MB 是桌面 GUI 的 AppImage | 解包点体积;`--exclude '*GUI*'` 可只取 CLI | 服务器上下 445MB 里有 320MB 是纯浪费 |
| 6 | **命令行版 OpenD 不需要 gtk3 / fuse** | 把 CLI 目录放进裸容器(`eclipse-temurin:21-jre`,实测 Ubuntu 26.04 / glibc 2.43),对 `FutuOpenD` / `FTUpdate` / `FTWebSocket` 跑 `ldd`,**零个 "not found"** | 「Docker 里跑不了 OpenD、必须自备装了 gtk3 的镜像」**这个前提是错的**。gtk3 / fuse 是 AppImage(桌面版)的依赖。官方包按 Ubuntu18.04 构建(glibc 2.27),所以 launcher 镜像可以用很瘦的基底 |
| 7 | 我们 `depsInstallCommand()` 教用户装的 `libgtk-3-0` / `fuse`,在 Ubuntu 24.04+ 已改名 `libgtk-3-0t64` / `libfuse2t64` | 查包名 | 原生路径上这行命令今天也会失败,而且**本来就不需要装** |
| 8 | OpenD 10.10 **不再接受命令行传密码**:`-login_pwd_md5` 不在受支持参数里,`-telnet_port` 也不在(只能在 XML 配) | `-help` 输出 + XML 对照 | 我们 `buildStartArgs()` 现在传的正是这两个 |
| 9 | 10.10 改成**交互式登录**:进程起来后日志出 `ProgramStatusType_Loging`,并推 `"desc":"请输入账号"` | 读 `~/.com.futunn.FutuOpenD/Log/GTWLog_*.log`(UTF-8) | 「喂凭据」要走交互通道,不是启动参数 |
| 10 | 交互通道实测可用:XML 打开 telnet 后连上**立刻**收到版本号与登录状态机提示(实测收到「请输入密码」),事件广播给所有 telnet 客户端;运维命令 13 条,含 `req_phone_verify_code` / `input_phone_verify_code` / `relogin` / `update`(自升级) | 在容器里 telnet 进去手动跑了一遍 | **方案 B 的控制面就靠这个**,已验证可行 |
| 11 | **telnet 无鉴权** | 同上 | 谁能连上 22222,谁就能操作这个券商网关 → 见 FR-17 的硬约束 |
| 12 | CLI 需要**开着的 stdin**(`< /dev/null` 会立刻退出);状态写在 `$HOME/.com.futunn.FutuOpenD/`(getpwuid 推出的家目录,mode 700) | 容器里用 pty 才起得住 | launcher 的 entrypoint 要造 pty,不能简单 `exec` |
| 13 | **富途不公布安装包的 md5 / sha256** | 通读官方 OpenAPI 下载页,没有任何校验和;下载响应头只有腾讯云 COS 的 `etag` 和 `x-cos-hash-crc64ecma` | 「比对官方 md5」这件事**官方没给锚点** → FR-13/14 的做法要绕开这个现实,不能假装有 |
| 14 | 那个 `etag` **实测就是文件的 MD5**:`4297cdec5653565556802fcd1b148f05` | `curl -sSI` 拿到 etag,再把 445MB 流式过一遍 `md5sum`,两值逐字符相同 | 用户可以用一条 `curl -sI` 廉价交叉验证我们公示的 MD5 —— 但它和文件走**同一条 TLS 连接、同一个 CDN**,只是"传输没坏",**不是独立信任锚**,文档里必须这么写 |

**一句话**:富途命令行版在容器里跑没有任何依赖障碍;剩下的全是"谁来跑、怎么让用户信得过"的工程与信任问题。

## 2 · 目标 / 非目标

**目标**

- G1 Docker 用户在向导页看到的**步骤数与原生一致**:下载 → 登录 → 收验证码;不需要自备镜像、不需要另一台有桌面的机器。
- G2 **可选**:不用富途的人零成本 —— 默认 `docker compose up -d` **不拉、不起** 这个镜像。
- G3 **不需要手填版本号**。
- G4 富途账号/密码**只在管理页填**,`.env` 不再承载凭据。
- G5 **供应链透明**:我们发的镜像里装了什么、怎么构建的、官方包的哈希是什么、我们镜像的 digest 是什么,全部公开可核对,并在用户第一次启用时**强提示**。
- G6 顺手修掉第 1 节那些**现状即坏**的地方(过期 host / 文件名 / 启动参数 / 错的依赖提示),否则原生路径今天也是坏的。
- G7 墙内退路和离线退路都保留(下载失败能上传 tar.gz;不想让我们管的能继续指向外部 OpenD)。

**非目标(这一版不做)**

- 不做交易下单 —— 富途通道只用来**读**持仓和行情(项目定位:摸清家底,不是交易终端)。
- **不把富途二进制打进任何我们发布的镜像** —— 那是别人的分发物,我们只做"运行时去官方拉 + 校验"。这条对主镜像和 launcher 镜像同时成立(FR-12 机器校验)。
- 不把 OpenD 托管职责并进主镜像(= 不选方案 A,见 §3)。
- 不做 K8s / Swarm 的编排适配。
- 不做多账号并行 OpenD。
- 不替用户过富途的首次问卷/协议(富途要求的人工动作,我们只能讲清楚、放在对的位置)。

## 3 · 方案:选 B

### B(选定)· 我们发一个**可选**的 launcher 镜像

我们维护一个瘦镜像 `ghcr.io/luodi-nate/futu-opend-launcher`,**里面不含富途任何文件**;容器启动时去富途官方下载 OpenD、校验哈希、只解出命令行版、写好配置、用 pty 起进程。app 通过 `11111` 拉数据、通过 telnet 控制面喂账号/密码/验证码并读登录状态(第 1 节 #10 已实测可行)。

- **可选怎么落地**:走 compose profile —— 默认 `docker compose up -d` 不涉及这个服务;要用富途才 `docker compose --profile futu up -d`(或 `docker-up.sh --with-futu`,让用户连 profile 都不用记)。不启用 = 零拉取、零磁盘、零进程。
- 用户看到的:向导页与原生同样三步;多出来的只有**第一次启用时的一次确认**(告诉你要拉一个多大的镜像、它是我们构建的、哈希在这儿、怎么自己验)。
- 维护者定的理由(原话意思):富途相关的东西不是所有用户都需要,**应该可选、不该打包进来**;而且我们要托管制品这件事本身要谨慎、要把打包过程和哈希都声明清楚。

### A(未选)· app 容器自己托管 OpenD

拆掉「Docker 必须 sidecar」的硬拦,让主镜像复用现有 `FutuOpendManager` 直接在 app 容器里起 OpenD 子进程。

**为什么不选**:维护者的判断是它把富途这块**耦合进了所有人都要拉的主镜像** —— 托管逻辑、家目录、两个卷、进程守护,不用富途的人也得带着。可选性做不干净。
> 一处事实澄清,免得以后翻账翻错:A **也不**把富途二进制打进镜像(同样是运行时去官方下载)。A 真正的代价是**职责耦合**与可选性,不是"分发别人的制品"。这条不影响结论 —— B 在可选性和隔离上确实更好,只是选它的理由要写准。

### C(未选)· 默认指向某个社区镜像

**不选**:供应链上把用户的券商账户交给陌生镜像;这类镜像基本在 Docker Hub(墙内拉不动);版本大多停在 9.x(登录方式已经和 10.10 不一样);凭据仍然要进 `.env`。零工作量,但每一条都踩在项目红线上。

### 对比(留档)

| | A · 容器内自管 | **B · 我们发可选 sidecar(选定)** | C · 社区镜像 |
|---|---|---|---|
| 用户动作 | 点向导页,零命令 | **点向导页 + 一次启用确认** | `.env` 三行 + 合并覆盖文件 |
| 不用富途的人的成本 | 主镜像里带着这套逻辑 | **零(profile 不启用)** | 零 |
| 凭据落哪 | 管理页 / 库 | **管理页 / 库** | `.env` 明文 |
| 新增要维护的构件 | 0 | **1 个镜像 × 每次发版** | 0(但依赖第三方) |
| 端口暴露面 | 无(同容器 127.0.0.1) | **compose 内网 11111 + 22222(不对宿主 publish)** | 内网 11111 |
| 供应链信任 | 官方直下 | **官方直下 + 我们的镜像(需公示与可验证)** | 陌生第三方 |
| 主要风险 | 主镜像职责变重 | **无鉴权 telnet 在内网 + 我们要长期跟版** | 账户安全 + 版本过时 |

> 逃生阀保留:`FUTU_OPEND_IMAGE`(想换成自己的镜像)与「OpenD 在别处 · 手填 host:port」(家里 NAS / 反向隧道)都继续可用。

## 4 · 供应链与安全:这一版的硬要求

维护者点名:「对接富途 OpenD 是一件很危险的事情,要强提示用户校验 md5 等;我们托管了一个可选镜像,就要声明打包过程、官方 md5、我们的 md5」。这一节是对这句话的落地,**同时要面对第 1 节 #13 那个现实:官方根本不公布哈希**。

信任链拆成三段,每段都要能被用户独立核对:

| 段 | 我们提供什么 | 用户怎么自己验 |
|---|---|---|
| ① 我们的镜像 | 镜像 **digest**(`sha256:…`)写进 Release 页与向导页;Dockerfile 在仓库里;GitHub Actions 构建日志公开;发布时带 **provenance attestation** | `docker pull ghcr.io/…@sha256:…` 按 digest 拉(不认 tag)· `gh attestation verify` / cosign 验签 · 对着仓库里的 Dockerfile 读一遍我们装了什么 |
| ② 镜像里**没有**富途文件 | 机器护栏:构建后扫镜像层,出现 `FutuOpenD` / `*.tar.gz` 之类富途制品即构建失败 | `docker run --rm --entrypoint ls <image> /opt` 自己看;或读护栏脚本 |
| ③ 官方安装包 | **我们下载、核对并公示** 每个支持版本的 `sha256` + `md5`(并明确标注:**这是我们算的,富途官方未公布任何校验和**);运行时校验不匹配就**拒绝启动**并报错 | 自己 `curl` 下来 `sha256sum` 对一遍;或 `curl -sI <url>` 看腾讯云 COS 的 `etag` —— **实测该 etag 就等于文件 MD5**(第 1 节 #14),一条命令就能和我们公示的 MD5 对上 |

> 关于 `etag` 这条交叉验证要说清它的极限:它和文件走同一条 TLS、同一个 CDN,证明的是"传输没坏 / CDN 上的对象没变",**不是**独立于富途与 CDN 的第三方锚点。真正的独立价值来自"多方各自算一次都一样" —— 所以我们把哈希**钉进公开仓库**(有 git 历史、有人 review),用户自己算的值、我们仓库里的值、CDN 的 etag 三者对上,才是有意义的交叉。

由此产生一个必须明说的取舍(FR-13):**"自动装最新版" 与 "哈希已被我们核对过" 是冲突的**。处置:

- **默认**:装我们**已核对并钉住哈希**的最新版本(镜像里带一张 `版本 → sha256/md5` 表)。装的时候校验,不符就停。
- **想更新**:用户可以显式勾「用官方当前最新版(我们还没核对过这一版)」。此时页面**明确告知**:我们无法为这一版提供哈希锚点,只能靠 TLS + CDN ETag;并把实际算出的 sha256/md5 显示出来让用户自己核对、自己判断。
- 两种情况下算出的哈希都写进日志和向导页,不藏。

## 5 · 用户视角需求(FR)

| # | 需求 | 验收标准(以用户身份点) |
|---|---|---|
| FR-1 | Docker 部署打开券商向导页,**步骤数与原生一致**;没有「本页不能替你一键装」、没有自备镜像的教程 | 在 beta 用 compose 起一套,进 `设置 → 数据源接入 → 富途`,与原生逐步对照 |
| FR-2 | **不填版本号**:安装时应用自己确定要装哪一版(默认已核对版本) | 向导页不再有版本号输入框;安装记录里能看到实际版本(如 `10.10.7008`) |
| FR-3 | **不用富途的人零成本**:默认 `docker compose up -d` / `docker-up.sh` 不拉、不起 launcher 镜像 | 全新机器起一套不启用富途,`docker images` 里没有 launcher;`docker ps` 只有既有服务 |
| FR-4 | 启用是**一条命令 + 页面确认**:`docker compose --profile futu up -d`(或 `docker-up.sh --with-futu`);向导页在检测到网关没起时**直接把这条命令显示出来并可一键复制** | 照页面给的命令跑一次,回到页面状态变为「网关已就绪,待登录」 |
| FR-5 | 只解出命令行版所需的部分,**约 125MB 而不是 445MB** | 装完看卷体积 |
| FR-6 | 富途账号 / 密码**只在管理页填**;`.env` 里的 `FUTU_ACCOUNT` / `FUTU_PWD_MD5` 从"必填"降为不再需要,`.env.example` 删掉 `md5sum` 教程 | 不配任何 `FUTU_*`,整条链路走通 |
| FR-7 | 验证码在**页面上**收发,不要求用户 `docker exec` / telnet | 走一次真实登录:页面「已发送」→ 输入 → 就绪 |
| FR-8 | **重启不重来**:`docker compose restart` / 宿主重启后不用重新下载;能免密自动恢复就自动,需要验证码时页面明确提示 | 起来 → 就绪 → `restart` → 看是否重新下载 |
| FR-9 | 下载被墙 / 失败有退路:**上传 tar.gz** 或指定已有包路径,Docker 下同样可用(上传的包也走 §4 的哈希校验) | 断网模拟一次,走上传路径装成功 |
| FR-10 | 逃生阀:仍支持「OpenD 在别处」(家用机 / NAS / 自备镜像),向导页给手填 host:port 的入口 | 填一个外部地址,连通性测试通过 |
| FR-11 | 文档不再自相矛盾:富途首次问卷 / 协议在哪做,只有一个说法,并写在用户会撞上它的那一步 | 通读向导页 + `docs/broker-sync-guide.md`,无冲突表述 |
| **FR-12** | **我们发布的任何镜像都不含富途文件**,并有机器护栏钉住 | 护栏在 CI 里跑;`ls` 进镜像自己看 |
| **FR-13** | 安装包**哈希校验**:默认装我们核对过的版本、校验不符**拒绝启动**;要装未核对的新版必须用户显式同意,并当场显示算出的哈希 | 故意改一位钉住的哈希 → 安装被拒且报错说人话;勾「用最新版」→ 出现明确风险提示 |
| **FR-14** | **强提示 + 公示**:第一次启用富途时,向导页给一块「你正在引入什么」:镜像 digest、Dockerfile 与构建日志链接、官方包 sha256/md5(注明官方未公布、这是我们算的)、验证命令;文档同一份内容 | 页面存在该区块且哈希与仓库里钉住的值一致(可机器校验) |
| **FR-15** | 镜像来源**可验证**:按 digest 可拉、带构建 provenance;README / Release 页给出验证命令 | 照命令验一次通过 |
| **FR-16** | 无鉴权 telnet **绝不出容器网络**:launcher 不对宿主 publish 22222;文档明确警告不要自行映射 | `docker ps` 看端口映射为空;compose 文件里无 `ports:` |
| **FR-17** | 网关容器**只跑网关**:不挂载宿主敏感目录、不用 host 网络、非 root 运行、只写自己的卷 | 读 compose 与 Dockerfile 自查 |
| FR-18 | 原生路径同时被修好(过期 host / 文件名 / 启动参数 / 依赖文案) | 在 beta 用 systemd 路径也跑一次安装 |

**预览**:`preview/v1.17/opend-docker.html`(向导页统一后的 mockup + 「你正在引入什么」公示块 + 就绪态里的网关容器与 digest)

## 6 · 顺带回答:老虎(Tiger)有没有同一个问题?

**没有,而且结构上不会有。** 查证了代码:

- 老虎走的是官方 Java SDK 直连 HTTPS(`TigerBrokerClient.java:38-50`,`TigerHttpClient` + `tigerId` / RSA 私钥),**不需要任何本地常驻网关程序**、不占端口、不落文件。
- 凭据从 `FamilyConfigService` 读(管理页填、存库):`K_BROKER_TIGER_ID` / `K_BROKER_TIGER_KEY` / `K_BROKER_TIGER_ACCOUNT`。Docker 与原生完全同一条代码路径。
- 全仓库**只有富途 OpenD 这一处**按部署方式分叉:`FutuOpendManager.java`(7 处 `DOCKER`)+ `broker/opend-wizard.html`(10 处 `th:if="${channel != 'DOCKER'}"`)。老虎的向导页 `broker/link.html` 里**一处都没有**。

所以「Docker 和原生体验不一致」目前是**富途独有**的问题,根源正是"富途要一个本地网关进程"。这一版收拾完之后,这个分叉点就只剩「网关跑在哪」一个可见差异(而它有页面上的一次确认覆盖)。

顺带一条与本版无关但值得记下的对照:老虎的 RSA 私钥是**明文存库**的(和富途密码一样),这不是这一版的范围,但如果以后做凭据加密,两家要一起做。

## 7 · 兼容与迁移(prod 已上线,必须向后兼容)

- **现在按 sidecar 跑着的用户**:`deploy/futu-opend.compose.yml` 不删;如果我们的 launcher 服务沿用同一个服务名,他们的 `broker_config` 里存的 `opend:11111` **照旧生效**,升级后无需动作(想换成我们的镜像只是把 `FUTU_OPEND_IMAGE` 去掉)。
- **`.env` 里已写 `FUTU_ACCOUNT` / `FUTU_PWD_MD5` 的**:升级后不再被 compose 要求(不再声明为 required),存在也不报错;文档建议改到管理页填并删掉这两行。
- **systemd 用户**:不受影响,只会变好(第 1 节 #1/#7/#8 几处坏的被修掉)。
- **DB**:预期无 schema 变更;若凭据要加密存储,走新增列 + 读时兼容,不改既有列语义。
- **富途账户本身**:任何"重新登录"都可能触发富途的设备验证 → 升级说明要写明「第一次升级后可能要再收一次验证码」。
