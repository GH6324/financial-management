# v1.17 · Docker 部署下的富途 OpenD 一键接入

> 状态:**PRD 待评审**(第 3 节三个方案请点一个;我的推荐是 A)
> 目标版本:app.version = 1.17.0(已 bump)
> 来源:维护者点名 —— 「docker 启动情况下富途 OpenD 的自动集成:目前你要求用户自己打包镜像,我感觉不合理,要一键式的,类比 linux 原生版本;至少也是提供好用户命令、执行一下就 ready 的那种」
> 相关:GitHub issue #13(Docker 下 OpenD 连不上)只修了文档措辞,没动这个根本问题

---

## 0 · 这一版在解决什么

同一个功能(券商同步 · 富途),两种部署方式的体验差了一个数量级:

| | systemd 原生(拓扑 A) | Docker compose(拓扑 B · 今天) |
|---|---|---|
| 装 OpenD | 向导页点一下「下载并安装」,应用自己下、自己解压 | **你自己准备一个镜像** —— 富途没有官方镜像 |
| 首次登录 | 向导页填账号密码 → 页面上收短信验证码 | **先找一台有桌面的机器**,用 GUI 版 OpenD 登录一次 |
| 填凭据 | 管理页表单 | 写进服务器上的 `.env` 明文文件(密码要自己 `md5sum`) |
| 启动 | 向导页按钮 | 手敲 `docker compose -f docker-compose.yml -f deploy/futu-opend.compose.yml up -d` |
| 页面提示 | 「把 OpenD 装进系统,点几下就好」 | 「这台是容器部署……**本页不能替你一键装**」 |

四条具体的不合理:

1. **把打包工作外包给用户**,而且是外包了一件他多半做不了的事 —— 富途不发布官方 OpenD 镜像,用户实际只有两条路:自己写 Dockerfile 塞富途二进制(要先搞清依赖),或者去拉一个陌生人的镜像(**供应链风险**:这个容器里装的是能操作真实券商账户的网关)。墙内还叠一层:社区镜像基本都在 Docker Hub,而 Docker Hub 被墙。
2. **「先去一台有桌面的机器登录一次」**对自托管用户经常直接不成立 —— 很多人只有一台云主机,家里没有常开的桌面机。
3. **账号 + 密码 MD5 落在 `.env` 明文**,与本项目「运营参数一律走管理页、不写服务器配置文件」的既定原则冲突(`.env.example` 里现在还教用户 `printf '你的密码' | md5sum`)。
4. **自相矛盾**:向导页第 0 步说富途的问卷/协议在「富途牛牛 App / 网页」里做;同一页的 Docker 段又说必须先用桌面版 OpenD 登录一次。两句话不能都对,用户按哪句都可能白折腾。

> 这一版要的结果:**Docker 用户看到的向导页,和原生用户看到的是同一页、同样的按钮数。**

## 1 · 调研:实测结论(2026-08-16 · 在 beta 上做的)

不是查文档得来的,是把 OpenD 10.10.7008 拉下来在容器里跑出来的。**这些结论推翻了现状设计的技术前提**,所以先摆证据:

| # | 结论 | 怎么测的 | 影响 |
|---|---|---|---|
| 1 | **我们写死的下载地址已经失效** | `softwarefile.futunn.com:443` 连接超时(80 端口能应答,但旧文件名 404) | 今天点原生向导的「下载并安装」也装不上 —— 这不只是 Docker 的问题 |
| 2 | 官方现行地址是 `softwaredownload.futunn.com/Futu_OpenD_10.10.7008_Ubuntu18.04.tar.gz`;文件名格式和我们拼的 `FutuOpenD_<版本>_Ubuntu16.04.tar.gz` **完全不同** | 跟 302 跳转 | `osTag()` 的 `Ubuntu16.04` / `Centos7` 映射要重做 |
| 3 | 我们的下载白名单只放 `softwarefile.futunn.com`,**用户手填现行官方 URL 会被我们自己拒掉** | 读 `FutuOpendManager.downloadUrl()` | 连"手动救"这条路都堵着 |
| 4 | 有稳定的「取最新版」端点:`https://www.futunn.com/download/fetch-lasted-link?name=opend-ubuntu`(还有 `-centos`/`-macos`/`-windows`)→ 302 到具体版本包 | curl 实测 | **用户不该再手填版本号**(向导页的 placeholder 现在还写着 `9.3.5308`) |
| 5 | 445MB 的包里,**命令行版只占 125MB**,其余 320MB 是桌面 GUI 的 AppImage | 解包点体积;`--exclude '*GUI*'` 可只取 CLI | 服务器上下 445MB 里有 320MB 是纯浪费 |
| 6 | **命令行版在我们 app 镜像的基底上零额外依赖** | 把 CLI 目录放进 `eclipse-temurin:21-jre`(= 我们 Dockerfile 的基底,实测 Ubuntu 26.04 / glibc 2.43)裸容器里,对 `FutuOpenD` / `FTUpdate` / `FTWebSocket` 跑 `ldd`,**零个 "not found"** | 「Docker 里跑不了 OpenD、必须自备装了 gtk3 的镜像」**这个前提是错的**。gtk3 / fuse 是 AppImage(桌面版)的依赖,不是 CLI 的 |
| 7 | 我们 `depsInstallCommand()` 教用户装的 `libgtk-3-0` / `fuse`,在 Ubuntu 24.04+ 已改名 `libgtk-3-0t64` / `libfuse2t64` | 查包名 | 原生路径上这行命令今天也会失败,而且**本来就不需要装** |
| 8 | OpenD 10.10 **不再接受命令行传密码**:`-login_pwd_md5` 不在受支持参数里,`-telnet_port` 也不在(只能在 XML 配) | `-help` 输出 + XML 对照 | 我们 `buildStartArgs()` 现在传的正是这两个 |
| 9 | 10.10 改成**交互式登录**:进程起来后日志出 `ProgramStatusType_Loging`,并推 `"desc":"请输入账号"` | 读 `~/.com.futunn.FutuOpenD/Log/GTWLog_*.log`(UTF-8) | 「喂凭据」要走交互通道,不是启动参数 |
| 10 | 交互通道实测可用:XML 打开 `telnet_ip=0.0.0.0` + `telnet_port=22222` 后,telnet 连上**立刻**收到版本号和登录状态机提示(实测收到「请输入密码」),事件广播给所有 telnet 客户端;运维命令 13 条,含 `req_phone_verify_code` / `input_phone_verify_code` / `relogin` / `update`(一键自升级) | 在容器里 telnet 进去手动跑了一遍 | 是可行的控制面…… |
| 11 | **但 telnet 无鉴权** | 同上 | ……谁能连上 22222,谁就能操作这个券商网关。**这条直接决定方案 B 的安全代价** |
| 12 | CLI 需要**开着的 stdin**(`< /dev/null` 会立刻退出);状态写在 `$HOME/.com.futunn.FutuOpenD/`(getpwuid 推出的家目录,mode 700) | 容器里用 pty 才起得住 | 容器里托管要给它一个真家目录 |
| 13 | 我们镜像里的 `finance` 是 `useradd -r` 建的系统用户,**没有家目录** | 读 Dockerfile | 方案 A 必须给它建一个并挂卷,否则 OpenD 起不来 |

**一句话**:app 容器里跑 OpenD 命令行版,不缺任何依赖。现状那四处「Docker 环境请用 sidecar(不在 app 容器内托管 OpenD)」的硬拦,没有技术必要性。

## 2 · 目标 / 非目标

**目标**

- G1 Docker 用户和原生用户走**同一条向导**:同样的步骤数、同样的文案、同样的按钮。
- G2 **不需要手填版本号**,不需要自己找镜像,不需要另一台有桌面的机器。
- G3 富途账号/密码**只在管理页填**,`.env` 不再承载凭据。
- G4 顺手修掉第 1 节里那些**现状即坏**的地方(过期 host / 过期文件名 / 过期启动参数 / 错的依赖提示),否则原生路径今天也是坏的。
- G5 墙内退路和离线退路都保留(下载失败能上传 tar.gz;不想让我们管的能继续指向外部 OpenD)。

**非目标(这一版不做)**

- 不做交易下单 —— 富途通道只用来**读**持仓和行情(项目定位:摸清家底,不是交易终端)。
- **不把富途二进制打进我们的镜像** —— 那是别人的分发许可,我们只做"运行时去官方拉"。
- 不做 K8s / Swarm 的编排适配(仍在「刻意不做」清单里)。
- 不做多账号并行 OpenD。
- 不替用户过富途的首次问卷/协议(这是富途要求的人工动作,我们只能把它讲清楚、放在对的位置)。

## 3 · 三个方案 · 请拍板

### 方案 A(推荐)· app 容器自己托管 OpenD,和原生走同一套代码

拆掉「Docker 必须 sidecar」的硬拦,让容器部署直接复用现有的 `FutuOpendManager`(它已经会下载、解压、起进程、收验证码了)。补三件事:镜像里给 `finance` 建家目录;两个命名卷(OpenD 安装目录 + 运行状态目录)保证重启不重来;启动参数按 10.10 的现实改成"起进程 + 交互登录"。

- 用户看到的:**和原生一字不差**。向导页点「下载并安装」→ 填账号密码 → 页面收验证码 → 就绪。没有新命令、没有 `.env`、没有第二台机器。
- OpenD 的 API 端口仍然是 `127.0.0.1:11111`(和 app 同容器),**不需要对外暴露任何端口**,也不需要打开那个无鉴权的 telnet。
- 代价:app 容器多一个子进程(常驻内存约 200MB,和原生一样)、镜像卷多两个;OpenD 崩了不会独立重启(靠我们的进程守护,和原生同款)。

### 方案 B · 我们自己发一个 launcher sidecar 镜像到 GHCR

我们维护一个瘦镜像:里面**不含**富途二进制,启动时去官方拉、解包、起 OpenD、开 telnet;app 通过 telnet 喂账号/密码/验证码并读状态(第 1 节 #10 已实测可行)。

- 用户看到的:`.env` 里加一行 `FUTU_OPEND=1`,`docker compose up -d` 就好 —— 「一条命令 ready」达成,但仍然是"多一个容器"的心智。
- 代价:① 多一个镜像要跟着每次发版构建/推送/被扫描;② 11111 和 22222 要进 compose 网络,**无鉴权 telnet 暴露在 compose 内网**(同宿主别的容器可达);③ 跨容器起进程、传验证码,失败模式比方案 A 多一层;④ 我们要替富途的分发做长期兜底(官方改地址时,坏的是我们的镜像)。

### 方案 C · 默认指向某个社区镜像

把 `FUTU_OPEND_IMAGE` 的默认值填成一个现成的第三方镜像。

- **不选**:供应链上把用户的券商账户交给陌生镜像;这类镜像基本在 Docker Hub(墙内拉不动);版本大多停在 9.x(已经和现行 10.10 的登录方式不一样);凭据仍然要进 `.env`。零工作量,但每一条都踩在项目的红线上。

### 对比

| | A · 容器内自管 | B · 我们发 sidecar | C · 社区镜像 |
|---|---|---|---|
| 用户动作 | **点向导页,零命令** | `.env` 一行 + `up -d` | `.env` 三行 + 合并覆盖文件 |
| 与原生体验一致 | **完全一致** | 接近(多一个容器概念) | 不一致 |
| 凭据落哪 | **管理页 / 库(加密)** | 管理页(telnet 喂进去) | `.env` 明文 |
| 新增要维护的构件 | **0** | 1 个镜像 × 每次发版 | 0(但依赖第三方) |
| 端口暴露面 | **无(同容器 127.0.0.1)** | 内网 11111 + 无鉴权 22222 | 内网 11111 |
| 供应链信任 | 官方直下 | 官方直下 | **陌生第三方** |
| 墙内可用性 | 同原生(下载失败有上传退路) | 同原生 | **差(Docker Hub)** |
| 主要风险 | app 容器职责变重、卷要挂对 | 多一层跨容器失败模式 | 账户安全 + 版本过时 |

**推荐 A。** 理由是维护者提的那句话本身:「类比我们 linux 原生版本的」—— A 就是把原生那条路直接给 Docker 用,而不是再造一条。而且 B/C 都要引入无鉴权 telnet 或第三方镜像,A 一个都不需要。

**为什么不选 B**:B 的全部额外价值是"OpenD 挂了不影响 app 容器",但代价是我们要长期维护一个镜像 + 在内网暴露一个无鉴权控制口。这个隔离性对家庭自托管的收益,盖不住这两笔成本。
**为什么不选 C**:见上,四条红线。

> 不管选谁,`FUTU_OPEND_IMAGE` / 「指向外部 OpenD 地址」这条**逃生阀都保留**(家里 NAS 已经跑着 OpenD 的人、或者不愿意让我们碰这块的人,照旧手填 host:port)。

## 4 · 用户视角需求(按方案 A 写;选 B 则 FR-1/6/7 的实现换壳,验收标准不变)

| # | 需求 | 验收标准(以用户身份点) |
|---|---|---|
| FR-1 | Docker 部署打开券商向导页,看到的**和原生同一页**:没有「本页不能替你一键装」,没有自备镜像的教程 | 在 beta 用 compose 起一套,进 `设置 → 数据源接入 → 富途`,页面步骤数与原生一致 |
| FR-2 | **不填版本号**:点「安装」时应用自己问官方要最新版 | 向导页不再有版本号输入框;安装日志里能看到实际装的版本(如 `10.10.7008`) |
| FR-3 | 只下命令行版所需的部分,装完占用**约 125MB** 而不是 445MB | 装完看容器里 OpenD 目录体积;`docker system df` 卷体积 |
| FR-4 | 依赖提示按实测来:**不再无条件教用户装 gtk3 / fuse**;真缺库时按实际缺的那个提示 | 全新容器上直接安装 → 不需要任何 `apt install` 就能起 |
| FR-5 | 富途账号 / 密码**只在管理页填**;`.env` 里的 `FUTU_ACCOUNT` / `FUTU_PWD_MD5` / `FUTU_OPEND_IMAGE` 从"必填"降为"可选逃生阀",`.env.example` 删掉 `md5sum` 那段教程 | 不配任何 `FUTU_*` 变量,`docker compose up -d` 正常起;整条链路走通 |
| FR-6 | **重启不重来**:`docker compose restart` / 宿主重启后,OpenD 不用重新下载;能免密自动登录的就自动,需要验证码的在向导页明确提示 | 起来 → 就绪 → `restart` → 回向导页看状态;确认没有重新下载 |
| FR-7 | 验证码在**页面上**收发(和原生一致),不要求用户 `docker exec` 或 telnet | 走一次真实登录,页面出现「已发送验证码」→ 输入 → 就绪 |
| FR-8 | 下载被墙 / 失败时有退路:**上传 tar.gz** 或填服务器上已有的包路径,Docker 下同样可用 | 断网模拟一次,走上传路径装成功 |
| FR-9 | 逃生阀:仍支持「OpenD 在别处」(家用机 / NAS / 自备镜像),向导页给手填 host:port 的入口 | 填一个外部地址,连通性测试通过 |
| FR-10 | 文档不再自相矛盾:富途首次问卷 / 协议到底在哪做,只有一个说法,并且写在用户会撞上它的那一步 | 通读向导页 + `docs/broker-sync-guide.md`,无冲突表述 |
| FR-11 | 原生路径同时被修好(过期 host / 文件名 / 启动参数 / 依赖文案) | 在 beta 用 systemd 路径也跑一次安装 |

**预览**:`preview/v1.17/opend-docker.html`(向导页 Docker 分支统一后的静态 mockup:旧 vs 新对照 + 三步终态 + 逃生阀入口)

## 5 · 兼容与迁移(prod 已上线,必须向后兼容)

- **现在按拓扑 B 跑着 sidecar 的用户**:`deploy/futu-opend.compose.yml` 不删,继续能用;向导页把「指向外部 OpenD」保留成显式选项,他们的 `broker_config` 里存的 `opend:11111` 照旧生效,**升级后不需要任何动作**。
- **`.env` 里已经写了 `FUTU_ACCOUNT` / `FUTU_PWD_MD5` 的**:这两个变量升级后不再被要求,但存在也不报错(不再被 compose 声明为 required)。文档提示可以删掉,并建议改到管理页填。
- **systemd 用户**:不受影响,只会变好(第 1 节 #1/#7/#8 那几处坏的被修掉)。
- **DB**:预期无 schema 变更;若凭据存储要加密字段,走新增列 + 读时兼容,不改既有列语义。
- **富途账户本身**:任何"重新登录"都可能触发富途的设备验证,升级说明里要写明"第一次升级后可能要收一次验证码"。

## 6 · 风险与未决(TDD 阶段要给答案)

| 风险 | 说明 | 现在的想法 |
|---|---|---|
| 官方地址再变 | `fetch-lasted-link` 也是非契约端点,富途改了我们又坏 | 白名单放开到 `*.futunn.com` + 上传退路兜底 + 一条 qa 护栏钉住"地址失效时报错要人话" |
| 免密重启 | `-login_by_remember` 能否在容器里跨重启免密,**未实测** | TDD 前实测;不行就退化成"重启后页面提示要收一次验证码" |
| 设备锁 / 验证码时效 | 短信码 1 分钟 1 次、10 分钟内 10 次的限流 | 页面上显式倒计时,别让用户狂点 |
| app 容器变重 | 多一个 200MB 常驻子进程,beta 只有 3.5G | 只在用户真的启用富途时才装/起;不启用零开销 |
| 富途二进制的分发许可 | 我们不打包、只运行时下载 —— 保持这条线不越 | 镜像里不含富途文件(护栏可机器校验) |
| 首次问卷到底在哪做 | 第 0 节第 4 条的矛盾,**目前我也没有确凿答案** | TDD 前用一个真实账号走一遍,把结论写死进文档 |
