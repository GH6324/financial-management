## 0 · 这一版在解决什么

### 0.1 背景与现状

v1.21 + v1.22 把**进数**这条线做完了:自定义两层类目、支付宝/微信账单整月导入、
逐行校准、分类/账户逐笔可改、批次可撤。现在 `cash_flow` 里躺着一批**带分类的逐笔支出**。

但**读**这条线是什么状况,得先盘点清楚 —— 这一版所有的加法都落在这片地上。

#### 现有的支出相关组件(全量盘点)

报表页上**并排挂着两个 section**,`reports/index.html:60` 和 `:62`:

| # | 文件 | section id | 标题 | 数据口径 | 它回答什么 |
|---|---|---|---|---|---|
| ① | `_expense-mix.html`(193 行 · v1.8 FR-272) | `sec-expense-mix` | **钱花在哪了** | `cash_flow.category_code`(**性质**:日常开支/还贷/利息/转账给亲属) | 支出里有多少是还债、多少是过日子;可切**账户 / 成员**两个维度 |
| ② | `_expense-cat-mix.html`(131 行 · v1.21) | `sec-expense-split` | **钱花在哪了** | `cash_flow.expense_category_id`(**消费分类**:餐饮美食/交通出行/日用百货…) | 消费的那部分具体花在哪个类目 |

②又内含三块:本期构成(堆叠条 + 列表 + 下钻)、年度累计(横条)、近 12 期趋势(堆叠柱)。
另有下游三处消费同一批支出数:`_savings.html`(储蓄率)、`checkup`(流动性维度)、
`dashboard`(月均支出豆腐块)。

#### 盘点盘出来的第一个问题:①和②是撞的

两个 section 的 **eyebrow 一模一样**(「支 · 出 · 构 · 成」)、**标题一模一样**(「钱花在哪了」)、
**在页面上紧挨着**、在长文目录里也紧挨着(「支出构成」/「支出构成 · 分类」)。
用户往下滚,会连着读到两个同名的大标题,而两块的**合计对不上** ——
①的合计 = 家庭支出总额(与储蓄率同口径),②的合计只算消费,本来就更小。

这不是本版造成的:v1.21 加②的时候,没有处理 v1.8 留下的①。
但本版要往这个区域加东西,**不先收拾就是在浑水上继续盖楼**。处理方案见 §3.6。

#### 第二个问题:①②都只是陈列

两个 section、四块内容,没有一块回答「**所以呢**」。用户看完知道「餐饮 ¥3,182 占 31%」,
下一个问题 ——「这算多吗?比上个月呢?这笔钱砍得掉吗?」—— 页面一个都不答。

**更要命的一点**:`月均支出` 在这个 app 里**不是一个展示字段,是一个承重结构**。

```
紧急储备月数 = 流动资产 ÷ 月均支出        FactViewServiceImpl.java:126-129
应急金目标   = 月均支出 × N 月            LiquiditySurplus.java:41
体检 · 流动性 = RuleContext(avgMonthlyExpense) CheckupController.java:80-96
报表 · 储蓄率 = (收入 − 支出) / 收入      ReportsController.java:591
```

而今天的 `月均支出` 是**近 12 个已关账期的一个扁平平均**(`FactViewServiceImpl.averageExpense`,
走 `expenseLedger.recentClosed(familyId, 12)`)。它把装修、买车、一次旅游、一笔大额医疗
**和每月的水电房贷混在同一个平均里**。后果是:

- 去年装修花了一笔 → 月均支出被永久抬高 12 个月 → **紧急储备被低估、FIRE 目标被高估**
- 而用户在页面上**看不到这件事**,也没有任何地方能说「那笔不算」

也就是说:我们已经在用支出数据做决策了,**只是用的是一个粗糙的版本**。
v1.21 把细节数据拿进来了,但决策层还在吃那个粗糙的平均数。

### 0.2 服务谁

**维护者本人 + 自建用户里已经在用 v1.21 导入的那部分。**

不是给「想省钱的人」——那是记账 App 的用户。是给**已经把钱记清楚了、想知道这对自己家的
资产和目标意味着什么**的人。非技术家人是**次要受益者**:她要能看懂「这个月为什么多花了」,
不需要看懂刚性弹性那一层。

### 0.3 主推动力

**让支出数据参与决策,而不是参与展示。**

一句话判据,用来砍 FR:**这个组件能不能改变用户的一个决定?**
不能的就是陈列,陈列已经够多了。

### 0.4 和竞品的根本分歧:我们不做预算

调研(§1)里三个主流中文记账 App —— 鲨鱼记账、钱迹、随手记 —— 支出分析的**重心全在预算**:
月度预算 + 分类预算 + 超支预警 + 日历红蓝标。

**我们不跟。** `AGENTS.md` §1「刻意不做」里写着**预算包络**,这一版不推翻它。理由不是
「做不了」,是**预算解决的是「别花超」,我们解决的是「这些钱花掉之后,家底和目标怎么样了」**。
前者是月度自律工具,后者是资产决策工具 —— 前者每天要看,后者每月看一次。
我们的硬约束是 10 分钟/月,只有后者装得进去。

### 0.5 本版新引入的名词

| 名词 | 定义 |
|---|---|
| **支出性质** | 每个类目的一个标记,三选一:**刚性** / **弹性** / **一次性**。判据见 **§0.6**。与 `category_code`(性质:consumption/loan_payment/…)和 `expense_category_id`(钱花在哪)**是第三个正交维度**,不许合并(理由见 §6.3) |
| **一次性支出** | 偶发大额、不代表日常生活水平的开销(装修/买车/旅游/大额医疗/婚丧)。它**不该进月均支出**,因为月均支出的用途是回答「我每个月过日子要多少钱」 |
| **常态月均** | 剔除一次性支出后的月均。**并列**于既有的 `月均支出`,**不取代它** |
| **支出归因** | 本期与上期的差额**拆到类目**的瀑布。与报表页已有的「资产变化归因」是同一种表达,换了对象 |
| ~~**周期性支出**~~ | 类目 + 金额近似恒定 + 连续多期出现的笔,推定为订阅/月供/保费一类。**本版已移出**(§3.4),名词留在这里是因为 §1 调研里反复提到它 |

既有名词(性质 / 消费分类 / 口径 A/B / `affects_balance` / 封板 / 已定稿)单一定义在
`AGENTS.md` 与 `prd/v1.21.md`,这里不重复。

### 0.6 刚性 / 弹性 / 一次性 到底怎么分

先说实话:**这个区分没有客观判据**。没有会计准则规定房贷是刚性、下馆子是弹性;
任何 App 给的都是**约定**。所以我们要的不是「正确」,是**可解释 + 可改 + 默认不用管**。

#### 判据是两个问题,不是一个三选一

三选一要求用户在脑子里同时比较三个概念,很难答。拆成**两个是非题**就都能答了:

```
          ┌─ 这笔开销,每个月(或每年固定几次)都会再来吗?
          │
     不会 ─┴─ 会
      │        │
  ┌───┴───┐    └─ 少了它,家里的日子过不过得下去?
  │ 一次性 │        │
  └───────┘   过不下去 ──→ ┌──────┐
                          │ 刚性  │
              难受但能过 ─→└──────┘
                          ┌──────┐
                          │ 弹性  │
                          └──────┘
```

两个问题问的是**两个不同的轴**,这是刻意的:

| 轴 | 问题 | 它服务哪个用途 |
|---|---|---|
| **复发性** | 还会再来吗? | **修分母** —— 不复发的不该进「我每月过日子要多少钱」 |
| **可压缩性** | 砍得掉吗? | **看空间** —— 收入掉一半时,有多少腾挪余地 |

所以「一次性」的精确判据是 **不可预期 + 不重复**,而**不是**「金额大」。
年缴的保险费金额大、但每年都来 → 它是刚性,不是一次性。

用户在类目管理页上看到的就是这两句问句本身(FR-612),不是「刚性/弹性/一次性」三个干巴巴的词。

#### 起步包 10 个大类的预设(FR-611)

`ExpenseCategoryService.STARTER` 的真实 10 个大类,按上面两问预设:

| 起步包大类 | 会再来? | 砍得掉? | **预设性质** |
|---|---|---|---|
| 住房物业(房租房贷/水电燃气/物业) | 每月 | 过不下去 | **刚性** |
| 充值缴费(话费网费/会员订阅) | 每月 | 过不下去 | **刚性** |
| 教育培训(学费/书籍课程) | 每学期 | 过不下去 | **刚性** |
| 医疗健康(看病买药/保健) | 不定但必然 | 过不下去 | **刚性** |
| 餐饮美食 | 每月 | 难受但能过 | 弹性 |
| 日用百货 | 每月 | 难受但能过 | 弹性 |
| 交通出行 | 每月 | 难受但能过 | 弹性 |
| 服饰装扮 | 每月 | 难受但能过 | 弹性 |
| 文化休闲(旅游酒店/影音演出/健身) | 每月 | 难受但能过 | 弹性 |
| 数码电器 | **不会** | — | **一次性** |

10 个里只有 1 个天生是一次性。**这恰恰证明 FR-613 逐笔勾是必需的** ——
真实的一次性大额几乎都藏在别的桶里:一趟旅游藏在「文化休闲」、一场手术藏在「医疗健康」、
一次装修藏在「日用百货」。靠改类目性质处理它们是错的(会把整个类目都变成一次性)。

#### 两个诚实的边界

1. **年缴/季缴项会砸单月**。保险费、学费落在某一个月,那个月支出暴涨,
   而它们被判为**刚性** → 不剔出常态月均 → **那个月的分母还是被砸了**。
   三桶结构解决不了这个,Monarch 为此专门加了第四类「非月度周期性」。
   本版的处理:**承认它,不假装解决** —— 用户可以对那一笔勾「一次性」,
   但语义上不准确。是否加第四桶或「按年摊平」标记,列入 §13 待裁决第 3 条。
2. **弹性 ≠ 该砍**。这一块**不给好坏评价、不设阈值红绿灯**(FR-634)。
   「刚性占比 62%」只陈述可压缩空间的大小,不说这是好是坏 ——
   花钱没有对错,是不是超出承受能力要看别的指标。

## 1 · 调研:别人怎么做支出分析

> 维护者要求「至少 3 个热门记账软件,至少包含鲨鱼记账」。实际调研 5 个:
> 中文 3 个(鲨鱼记账 / 钱迹 / 随手记)+ 海外 2 个(Copilot Money / Monarch Money),
> 外加一篇把「报表该怎么设计」讲透的长文(少数派 · MoneyWiz 实操)。
> 海外那两个是**唯一和我们定位重叠**的样本 —— 它们同时管净资产和支出,中文三个基本只管支出。

### 1.1 · 鲨鱼记账(维护者点名)

**基本盘**:生活记账 App,暖黄色调,主打「极简操作」。iOS/Android/鸿蒙/Windows 全平台。

**怎么记**:最少 **2 步** —— 顶部切「支出/收入」页签(默认支出)→ 点类目 → 弹数字键盘输金额 → 完成。
备注会被系统记下来,变成**下次记账的快速标签**(一个很聪明的低成本习惯学习)。

**怎么分析 —— 页面结构**(这是我们要抄的部分):

```
┌─ 明细(首页) ────────────────────┐   ┌─ 图表页 ─────────────────────────┐
│ ┌──────────────────────────────┐ │   │ [ 周 ][ 月 ][ 年 ]   ← 分段切换   │
│ │ 2026-09  ▼                   │ │   │ 总支出 ¥12,600  日均 ¥420        │
│ │ 收入 ¥28,000   支出 ¥12,600  │ │   │                                  │
│ └──────────────────────────────┘ │   │  ╭─╮      ╭╮      折线:每天/每月 │
│  09-18 ─────────────────────     │   │ ╱  ╰─╮  ╭─╯╰─╮    消费趋势        │
│   餐饮 · 外卖          −¥38      │   │╱      ╰─╯     ╲                   │
│   交通 · 地铁          −¥6       │   │                                  │
│  09-17 ─────────────────────     │   │ 支出排行(条形)                  │
│   日用百货              −¥212     │   │ 餐饮美食 ████████████ ¥3,182 ▲红 │
│   ...                            │   │ 交通出行 ███████ ¥1,940          │
│  (按天分栏 · 单条可点开改)       │   │ 日用百货 █████ ¥1,430            │
└──────────────────────────────────┘   └──────────────────────────────────┘
```

**三个值得偷的细节**:

1. **周/月/年分段切换 + 同时给「总额」和「平均值」**。平均值这个数很关键 ——
   它让不同长度的周期可比。我们今天的 12 期趋势柱只有总额,没有基准线。
2. **占比上升的类目打红色标记**。这是整个中文记账圈里**唯一一个主动说「所以呢」的地方** ——
   不是让用户自己比,是系统指出来。极低成本,极高价值。
3. **「必要消费 / 冲动消费」用颜色区分**。方向对(承认支出不是均质的),
   但用的词是**价值判断**(「冲动」),我们不跟这一点 —— 见 §4。

**它的弱点**:饼图、预算、数据导出、搜索全在 VIP 后面;图表页**看得出高低,看不出为什么**
(体验报告的原话是「图表版块相对成熟」,但通篇没提归因)。

### 1.2 · 钱迹

**基本盘**:无广告、极简,3 步记一笔。3000 万下载 / 600 万用户,评分 4.9。

**怎么分析**:
- 统计支持**年 / 月 / 自定义时间段**,可对**单个分类**做详细统计
- 三种图:**饼图 / 条形图 / 折线图**
- **多维度标签**(商家、项目、城市)—— 一笔可以挂多个标签,统计按标签汇总
- **资产负债表** + **资产曲线**(少见:一个记账 App 做到了净资产视角)
- 预算:年度/月度总预算 + 分类预算,**日均预算动态更新**,接近/超限日历标红

**值得偷的**:
1. **「自定义时间段」**。月不是唯一周期 —— 少数派那篇说得更狠:「**最佳的统计周期是工资发放周期**」。
   我们的账期天然就是月,但 v1.23 刚做完「关账宽限」,账期边界已经是可配置的了。
2. **标签维度与分类维度正交**。我们的「支出性质」本质上是同一个思路的极简版:
   **不做自由标签(维护成本高),只做一个三值的正交维度**。

### 1.3 · 随手记

**基本盘**:中文记账里体量最大、最接近「家庭财务」定位的一个。三端同步(App/网页/PC)。

**怎么分析**:
- 内置 **5 种报表**(iPad 版号称近 20 种图表):开支走向 / 预算比较 / **资产负债** / **资金流动** / 收支比例
- **首页即报表** —— 当前版本把报表提到了第一屏,不再是二级页面
- **多账本 + 跨账本报表**(旅游账/装修账/宝宝账/结婚账…)
- **自定义月起始日**,设置后流水、报表、预算全按这个周期算
- AI 记账:语音「早餐15元,通勤打车28元」自动拆分入账;截图/小票识别

**值得偷的**:
1. **「情景账本」其实就是我们的「一次性支出」**。用户之所以要单开一个「装修账」,
   正是因为他知道**装修的钱不该和日常混在一起看**。随手记的解法是让用户手动开一个账本
   (重),我们的解法是给类目/笔打一个标记(轻)——**同一个洞察,成本差一个数量级**。
2. **首页即报表**。用户不是来看流水的,是来看结论的。

### 1.4 · Copilot Money(海外 · 支出分析最强)

**基本盘**:Apple 生态优先,$95/年。定位是 **tracker, not a financial concierge**。

**怎么分析**:
- **每用户一个机器学习分类模型**,你纠正它就学。首轮准确率约 91–93%,
  轻量纠正几个月后 >95%。**约 30 笔之后自动分类开始生效**
- **Recurring 专页**:从交易模式里**自动识别订阅和账单**,金额变化时更新并提醒 ——
  专门对付 "subscription creep"(悄悄涨价的订阅)
- **Intelligence 信息流**:自动生成的个性化洞察
- 自然语言搜索交易
- 明确**不做** zero-based budgeting;它是**回溯型**的:告诉你钱已经怎么花了

**值得偷的**:
1. **Recurring 识别是这次调研里投入产出比最高的一个功能**。中文三个 App **一个都没做**。
   它抓的是**无感扣款** —— 那是一类用户永远不会主动去查、但确实在漏的钱。
2. **「回溯型而不是规划型」正是我们的定位**。Copilot 是海外最贵的那一档,
   它主动放弃了预算 —— 这是一个独立证据,说明「不做预算」不是我们在自我安慰。

### 1.5 · Monarch Money(海外 · 家庭协作 + 净资产,和我们最像)

**基本盘**:$99.99/年,**household-first**(有独立的配偶登录 + 只读分享给理财顾问)。
把投资、退休、负债**折进一个可定制的净资产视图** —— 这是所有样本里离我们最近的一个。

**怎么分析**:
- **Weekly Recap**:每周一段摘要,串起**支出 / 储蓄 / 收入 / 净资产**的重大变化,
  突出总支出与**主要驱动因素**、现金流趋势、**订阅变化**、净资产周环比
- **Month in review**:月末报告 = **Top 消费类目** + 月度现金流趋势 + **净资产变化图(按资产/负债拆)**
- **Insights**:页面上点一下「✦」,就地给出当前视图的要点
- 预算有两套模型:**Flex**(固定 / 非月度周期性 / 弹性 —— 三分!)或 **分类限额**

**值得偷的 —— 这是整轮调研最重要的两条**:

1. **Monarch 的 Flex 预算把支出分成「固定 / 非月度周期性 / 弹性」**。
   这和我们 §0.5 的**刚性 / 一次性 / 弹性**三分是同一个抽象,**而且是各自独立想出来的**。
   一个 $100/年的美国产品和我们撞了同一个三分法,说明这个切法是对的。
   差别在用途:Monarch 用它**定预算**,我们用它**修正月均支出的分母**。
2. **「Month in review」= 支出 Top 类目 + 现金流 + 净资产变化,三件事放在一份报告里。**
   我们的报表页**已经有后两件了**(封板快照 / 资金流瀑布 / 环比同比 / 归因),
   缺的恰恰是第一件。也就是说 —— **我们不需要新建一个页面,我们需要把缺的那一块补进已有的报告。**

### 1.6 · 少数派 ·「如果不做报表分析,那你每天记账也可能只是白费功夫」(MoneyWiz 实操)

这篇把「报表该有哪几张」讲得最透,作者的框架是 **2 必修 + 2 选修**:

| | 报表 | 回答 | 图 |
|---|---|---|---|
| 必修 1 | **资产净值走势** | 有多少钱 | 折线(可按账户拆)+ 现金流柱图 |
| 必修 2 | **支出分类统计** | 钱花到哪去 | 柱图(一级可下钻二级)+ 分类走势折线 |
| 选修 1 | **品牌消费集中度** | 经常跟谁交易 | 按「交易对象」的饼图 + 单品牌走势 |
| 选修 2 | **预算报表** | 花超没有 | 预算 vs 实际的柱图(饼图在超支后会失去意义) |

三句作者原话,值得直接抄进我们的设计原则:

> - 「**没有统计数据的输入,哪来的数据分析输出?**」—— 这正是 v1.21 做完之后 v1.24 才有可能存在的理由。
> - 「**最佳的统计周期是工资发放周期**」,先扣掉房租、话费、订阅费等**固定支出**,再看剩余的变量。
> - 报表的目的是「**调整**」而非「**改正**」——「**花钱永远没有对错**」,关键是找到平衡点。

第三句直接决定了我们的文案纪律(§4):**不做价值判断**。鲨鱼记账的「冲动消费」标签、
一堆 App 的「你这个月超支了!」,都踩在这条线上。

### 1.7 · 通用分析框架(多方交叉后收敛出来的)

| 维度 | 指标 | 用途 | 我们做不做 |
|---|---|---|---|
| **时间** | 环比 / 同比 | 趋势与季节性剥离 | **环比做**;分类同比**数据不够**(见 §4) |
| **结构** | 刚性 / 弹性占比 | 判断财务刚性程度 | **做** —— 这是主线 |
| **对象** | 商家集中度 / 复购频次 | 发现隐性浪费 | **不做** —— 没有商户字段(见 §4) |
| **周期性** | 订阅识别 / 年费提醒 | 防无感扣款 | **做** |
| **结余** | 结余率 = (收入−支出)/收入 | 现金流健康度 | **已有**(储蓄率) |

其中一条经验法则值得单独记:
**弹性支出适合看环比**(响应快、可调整),**固定支出适合看同比**(变化慢,阶梯式上涨只有同比看得出)。

### 1.8 · 调研结论 → 对我们 PRD 的四条直接影响

1. **不新建页面,补进报表页。** Monarch 的 Month in review 证明了「支出 + 现金流 + 净资产」
   本来就该在一份报告里,而我们那份报告已经存在 —— 缺的只是支出那一块的深度。
   (顶栏已有 7 个 tab,加第 8 个的代价远大于收益。)
2. **三分法是对的,但用途和竞品不同。** 他们用来定预算,我们用来**修分母**。
   这是我们唯一能做而他们做不到的事 —— 因为只有我们同时握着净资产、流动资产和 FIRE 目标。
3. **订阅识别是中文市场空白。** 三个中文 App 一个都没做,两个海外产品都做了且都放在显眼处。
4. **一条都不要做价值判断。** 少数派那句「花钱永远没有对错」是这一版所有文案的红线。

## 2 · 用户故事

维护者原话(2026-09-20):

> 我们在上个版本中增加了详细的支出明细的部分;但是针对这部分数据 **价值获取分析没有做**;
> 我们现在启动下一个迭代,目标是**如何帮助用户进行自己家庭支出的分析**。

拆成四个可验收的场景:

**S1 · 这个月为什么多花了(非技术家人也要看得懂)**
> 妻子打开报表页,看到「本期比上期多花 ¥4,260」。她想知道是哪儿多的。
> 今天:她得自己把两个月的类目列表并排比。
> 期望:**一眼看到 `旅游 +¥3,900 · 餐饮 +¥620 · 交通 −¥260`**,而且知道旅游那笔是一次性的。

**S2 · 我的紧急储备到底够几个月(维护者)**
> 「8.2 个月」这个数是拿去年那笔装修一起平均出来的。
> 期望:**页面同时给两个数** —— 「按全部支出 8.2 月 / 剔掉一次性后 11.6 月」,
> 并且能点开看到被剔掉的是哪几笔。

**S3 · 有没有在悄悄漏钱(维护者)**
> 几个视频会员、一个云盘、一份保费,每月自动扣。没人会主动去查。
> 期望:**一张「每月都在扣」的清单**,合计多少、占月支出多少、哪个涨价了。

**S4 · 砍到什么程度才够(维护者 · 服务 FIRE 目标)**
> FIRE 目标按现在的支出算要 N 年。如果只保留刚性支出,要几年?
> 期望:**刚性 / 弹性 / 一次性的三分占比**,让「能砍的空间有多大」变成一个数而不是一种感觉。

### 3.4 分组 D · 周期性支出 —— **已移出本版**(FR-640~645 编号留空)

这一块是三个候选里**该被砍的那个**,理由有三条:

1. **判据最弱**。`BillCommitService.java:175` 把商户名 `trimNote(l.merchant())` 塞进了
   `note` 字段,**没有独立商户列**。只能靠「同类目 + 金额 ±5% + 连续 ≥3 期」推定,

三条硬规矩,第 1 稿三条全违反(维护者原话:「极其丑陋」):

1. **用实色,不用低 alpha。** 第 1 稿全部是 20–55% alpha 叠在米色纸底(`--paper #F4EFE6`)上,结果饱和度被纸底稀释、明度全被拉到 85–92,整张图灰蒙蒙。要低饱和就直接选低饱和的实色,别让纸底替你调色。
2. **靠明度拉开,不靠饱和度。** 晚清账册风不允许高饱和,那唯一能用的维度就是 L*。第 1 稿刚性(淡灰蓝)和弹性(淡灰绿)在纸上几乎不可区分,就是因为只差色相不差明度。
3. **一个语义一个色,全页复用。** 三分条 / 12 期分层柱 / 归因瀑布的一次性段用同一个值。**反过来也成立**:弹性最初配了绿 `#6E8B6A`,和枚举色板第 4 位水青 `#6F8C8A` 在低饱和下几乎同色 —— 同一页上「弹性」和「交通出行」撞成一个颜色是纯粹的误导,所以弹性改成浅 slate。

**另外两处与色无关、但同属「读不出来」的修法:**

- 归因瀑布的增减条加 `min-height: 9px`。没有下限时,¥310 的差按比例算出来只有 2px,在图上退化成一根横线 —— 小额差本来就该看得出方向。
- 一次性的斜纹从 5px 改到 3px。粗斜纹在小面积上像施工警示带。

## 4 · 不做什么

### 非目标(这一版刻意不做)

- **预算 / 超支预警 / 日历红蓝标** —— `AGENTS.md` §1 明文「刻意不做预算包络」,这一版不推翻。
  理由见 §0.4:预算是月度自律工具(每天看),我们是资产决策工具(每月看一次)。
  Copilot Money($95/年,海外支出分析最强的一个)**主动放弃了预算**,这是一个独立佐证。
- **任何价值判断的文案** —— 不说「冲动消费」「你这个月花超了」「建议减少」。
  承少数派那句「**花钱永远没有对错**」。系统的职责是**指出变化**,不是**评判选择**。
  唯一的例外是纯事实陈述(「9 月起从 ¥15 涨到 ¥25」)。
- **商家 / 交易对象维度**(MoneyWiz 的「品牌消费集中度」)—— 我们**没有商户字段**。
  导入时商户名被 `trimNote()` 塞进了 `cash_flow.note`(`BillCommitService.java:175`),
  而 `note` 同时装着手填备注。在一个混了两种来源的自由文本上做聚合,
  产出的排行榜**看起来很专业但是错的**。要做得先加一个真正的 `counterparty` 列 —— 那是下一版的事。
- **分类同比** —— 需要 13 期的分类数据,而 v1.21 才发布不到一个月。做了也是一年的空白。
  **总额同比可以做**(PMC 从 v0.1 就有),见 FR-624。
- **记账习惯激励**(打卡 / 连续天数 / 徽章 / 财富币)—— 鲨鱼记账有一整套,那是留存设计。
  我们的用户每月来一次,不需要被激励留存。
- **消费建议 / 省钱攻略 / 优惠券** —— 不是我们的轴。
- **自定义统计周期**(钱迹的「自定义时间段」/ 随手记的「自定义月起始日」)——
  我们的账期是一等公民且 v1.23 刚把它的边界做成可配置的,再叠一层独立的统计周期
  会造成两套时间口径。**分析周期 = 账期**,不给第二个。

### 推迟到后续版本

- **周期性支出清单「每月都在扣」**(原 FR-640~645 · 移出理由见 §3.4)。保留的设计:
  识别判据**工程算不是 AI 算** —— 同一类目下金额落在 ±5% 区间、连续出现 ≥3 期;
  每条给「标签 / 月均金额 / 已连续 N 期 / 最近一期金额」,**金额变了要标出来**
  (Copilot 的 subscription creep);给合计「每月固定扣款 ¥X,占月均支出 Y%」;
  可「不是订阅」一键忽略;**不做任何去取消的引导**,我们只负责让它被看见。
  **前置条件**:先给 `cash_flow` 加独立商户列 —— 现在商户名被
  `BillCommitService.java:175` 塞进了自由文本 `note`,判据立不住
- **商户字段 + 商家集中度**:要加 `cash_flow.counterparty` 列并改导入写入路径,值得单独一版
  (它同时是上面那条的前置)
- **分类同比**:攒够 13 期自动可用,到时候只是放开一个显示开关
- **支出预测**(下个月大概花多少):有了刚性/弹性分层之后才有意义,但预测要背准确性的责任,想清楚再做

### 6.2 口径变更声明

**本版不涉及口径变更。** 这不是省略,是一个**刻意的设计选择**,理由写清楚:

「用常态月均替换月均支出」是这一版**最有价值也最危险**的一件事。替换会让每个现存用户的
紧急储备月数、应急金目标、体检流动性评分**在升级的那一刻全部改变**,而他们没做任何事。
`feedback_metric_refactor_baseline` 的教训就是这类改动。

所以本版采取**双读数**:既有数字**逐字不变**,常态月均作为**并列的第二个读数**出现
(FR-650~652)。用户自己判断哪个更贴近他家的情况 —— 这比我们替他决定更诚实,
**而且两个数摆在一起本身就是信息**(差多少 = 一次性支出对判断的干扰有多大)。

**零差异基线怎么建**:
1. 基线来自**已发布的 tag `v1.23.0`**(不是当前 master —— 否则分不清代码差异和数据漂移)
2. 在 beta 快照上,用 v1.23.0 的 jar 跑一遍,抓下 dashboard / 报表 / 体检 / 目标四页的
   全部既有 KPI 数值
3. 换 v1.24 的 jar,同一份快照,同样抓一遍
4. **既有 KPI 必须逐字相等**;有任何一个不等就停下来查因,不许「大概是四舍五入」
5. 落成 `scripts/regression-data.sh` 的一组断言 + 一条 qa-run 护栏
   `v1240-EXISTING-KPI-UNCHANGED`(扫 `averageExpense` 的实现没有读 `one_off` / `expense_nature`)

**调用方清单**(靠人列必漏,所以配 grep 护栏):
`FactViewServiceImpl.averageExpense:1130` 是唯一的计算点,消费方 4 处 ——
`DashboardController:324,423` · `CheckupController:80,150` · `ReportsController:591` · `LiquiditySurplus:41`。
护栏守的是「**这个方法不许读新列**」,比守「消费方没变」更靠得住。

#### ③ 矩阵:组件 × 操作

列按「对数据的影响形态」归并成 5 类:
**A** = 新增/改一笔支出 · **B** = 勾/取消「一次性」 · **C** = 改类目性质 · **D** = 改类目树(v1.21 已有) · **E** = 关账 / 开新期(v1.23)

图例:`↑` 立即变 · `—` 不变 · `⏳` 到某事件才变

| 组件 / 指标 | A | B | C | D | E |
|---|---|---|---|---|---|
| 本期构成 | ↑ | — | — | ↑ | — |
| 年度累计 / 12 期趋势 | ↑ | — | — | ↑ | — |
| **环比 · 同比数字条** | ↑ | — | — | — | ⏳ |
| **归因瀑布** | ↑ | ↑ | — | ↑ | ⏳ |
| **三分堆叠 + 12 期分层** | ↑ | ↑ | ↑ | ↑ | ⏳ |
| **常态月均** | ⏳ | ⏳ | ⏳ | — | ⏳ |
| 紧急储备(主数字) | ⏳ | **—** | **—** | — | ⏳ |
| 紧急储备(常态读数) | ⏳ | ⏳ | ⏳ | — | ⏳ |
| 储蓄率 / 月均支出 | ⏳ | **—** | **—** | — | ⏳ |
| 人赚钱赚 / XIRR / 净资产 | ⏳ | **—** | **—** | — | ⏳ |

**读出来的三条规律**(读不出规律说明抽象没找对):

1. **B 列和 C 列在「既有指标」那几行全是 `—`。** 这正是 §6.2 的双读数承诺的机器表达:
   一次性标记和支出性质**只被新指标读**。这条规律就是护栏 `v1240-EXISTING-KPI-UNCHANGED`
   要守的东西 —— 一旦哪天有人让 `averageExpense` 读了 `one_off`,这一列会出现 `↑`,护栏会红。
2. **常态月均那一行全是 `⏳`。** 因为它锚**已定稿**期(与 `averageExpense` 同窗口,L12/L16),
   进行中账期的改动要等那期定稿才进均值。**这一行和紧急储备主数字的形态完全一致** ——
   它们本来就该同步,并排显示的两个数如果更新节奏不同,用户会以为算错了。
3. **C 列只在「分层类」组件上是 `↑`,在「金额类」组件上全是 `—`。**
   改类目性质**不改变任何一分钱的归属**,只改变这些钱**被分进哪一堆**。
   这是「性质是第三个正交维度」这句话的直接后果。

#### ④ 明确不受影响的边界

以下**确定不受影响**,理由不是「没查」而是「查了,它们的取数里没有支出分类这一层」:

- **全部存量类指标**(净资产 / 总资产 / 总负债 / 流动资产 / 配置环 / 环比同比资产)——
  读 `period_snapshot.end_balance`,与 `cash_flow` 的分类字段无关
- **全部收益类指标**(XIRR / TWR / YTD / 本月资产收益 / 人赚钱赚)——
  读的是 `cash_flow` 的**金额与方向**,不读 `expense_category_id`,更不读新增两列
- **账户余额 / 轧差 / `affects_balance` 那条链** —— 本版**一个字节都不碰**。
  `one_off` 是一个纯**分析期标记**,不参与任何余额语义(这一点要写进列注释,
  因为 `affects_balance` 已经有过一次「一个标记要同时退出三条链」的教训,L13 硬约束⑤)
- **v1.23 的双活跃账期全部判据** —— 本版不新增任何取期逻辑(见 ① 的结论)

## 8 · 隐私与数据红线

- **AI 只接收已经算好的聚合数字和类目名**(FR-653),不接收逐笔明细、不接收商户名、
  不接收 `note`。承 `feedback_llm_no_math`:**AI 不做任何数学**,所有数字工程算好填进 prompt
- **三分、归因、常态月均全在服务端工程代码里算**,不调 LLM。判据是确定性的,可复现、可解释,

## 11 · 回滚与关闭

- **回滚 = 回 jar 即可**。两个新列都是可空/有默认值,老 jar 见到它们照常跑(L7)
- **数据不需要回滚**:`one_off` / `expense_nature` 是纯分析期标记,没有任何金额依赖它们
- **关闭 = 无数据**:没有逐笔分类数据的家庭本来就看不到新块,不需要额外开关
- **最坏情况**(某个新块算错):该块可以单独摘掉,其余块与既有三块不受影响 ——
  因为它们之间没有数据依赖,各自独立从 `cash_flow` 聚合

## 13 · 裁决记录

> **五条全部已裁(维护者 · 2026-09-20)**,结论与建议一致:
> 1 = 双读数 · 2 = 做逐笔勾 · 3 = 2 新增 + 1 合并 · 4 = 甲(三桶不变) · 5 = 甲(父子两层)。
> 下面保留原始待裁项与当时的取舍,作为后续回看「为什么是这样」的依据 ——
> 结论好记,**代价容易忘**,而代价才是改主意时要重新掂量的东西。

| # | 议题 | 裁决 | 认下的代价 |
|---|---|---|---|
| 1 | 双读数 vs 换口径 | **双读数** | 用户要自己看两个数;常态月均永远只是「第二个读数」,不会成为主口径 |
| 2 | 逐笔「一次性」勾 | **做** | 本版唯一新增的录入动作(一年 3–5 次);两条写入路都要守(L13) |
| 3 | 组件额度 | **新增 2 + 合并 1** | 周期性支出整块推迟一版 |
| 4 | 年缴/季缴砸单月 | **甲 · 三桶不变** | 语义不准(保险费本质是「非月度周期性」不是「一次性」),靠用户手勾兜住;§0.6 边界 1 要如实写出这个不准 |
| 5 | 合并方式 | **甲 · 父子两层** | 消费分类不再是可切维度,交互与账户/成员不统一;换来的是合计永远对得上 |

<details>
<summary>原始待裁项(裁决前的完整取舍)</summary>

1. **双读数 vs 直接换口径**(§6.2)。我选了双读数(既有数字不变,并列加一个)。
   代价是用户要自己看两个数;收益是没有任何现存用户的数字会一夜之间改变。
   如果你认为「常态月均本来就是更对的那个口径,该直接换」,那就是一次**真正的口径变更**,
   要按 `feedback_metric_refactor_baseline` 走完整流程(默认关 + 零差异基线 + 页面写明口径期)。
2. **逐笔「一次性」勾是否值得做**(FR-613)。它是本版唯一增加录入动作的东西(一年 3-5 次),
   但没有它,「文化休闲类目里那笔全家出游」就只能靠改整个类目的性质来处理 —— 那是错的。
3. **组件额度怎么花**(§3.6)。额度 3 个,我分成:**新增 2 个**(归因瀑布 · 三分与常态月均)
   **+ 1 个用在合并那两个撞车的 section 上**,并把「周期性支出」整块移出本版(§3.4)。
   另一种分法是:三个额度全用来新增(含周期性),合并留到以后 ——
   但那样这一版结束时,页面上会有**三个**支出 section,其中两个还叫同一个名字。
4. **年缴 / 季缴项砸单月**(§0.6 边界 1)。保险费、学费落在某个月,被判刚性 → 不剔出常态月均
   → 那个月的分母还是被砸。三种解法:
   **甲**(我选的)= 三桶不变,让用户对那一笔勾「一次性」,语义不准但零新概念;
   **乙** = 加第四桶「非月度周期性」(Monarch 的做法),语义准但三分条变四分条、判断负担 +1;
   **丙** = 给类目加一个「按年摊平」标记,常态月均里除以周期数计入 —— 语义最准,工程量中等。
5. **合并的方式**(FR-662)。我认下了两块的**父子关系**(消费分类 = 资金性质里「日常开支」那片的展开),
   两层同屏、第二层默认展开。另一种做法是把消费分类做成第一层的一个**并列维度**(和账户/成员并排),
   一个图四个维度 —— 交互更统一,但切维度时**合计会跳**(性质四分合计 = 家庭支出总额,
   消费分类合计只有消费部分),而「合计对不上」正是合并前那个困惑的来源。

</details>
