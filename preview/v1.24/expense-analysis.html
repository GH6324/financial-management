支出分析:从「摆出来给你看」到「所以呢」

v1.21/v1.22 把进数做完了 —— 账单能导、逐笔能改、分类能自定义。现在 cash_flow 里躺着一批带分类的逐笔支出,而读这条线只有三块:本期构成、年度累计、12 期趋势。 三块都在「摆出来给你看」,没有一句「所以呢」。
更要紧的是:月均支出在这个 app 里不是展示字段,是承重结构 —— 紧急储备月数、应急金目标、体检流动性、FIRE 年限全都吃它,而它今天是一个被装修、买车、 旅游污染的扁平 12 期平均。这一版的第一价值不是「你花太多了」,是让那几个指标变诚实。

竞品调研的结论先说

鲨鱼记账 / 钱迹 / 随手记 三家的支出分析重心全在预算 + 超支预警 —— 而 AGENTS.md 把「预算包络」 写进了刻意不做。照抄等于跑偏。海外的 Copilot Money($95/年)主动放弃了预算, 定位是 "tracker, not a concierge";Monarch 的 Flex 预算把支出分成「固定 / 非月度周期 / 弹性」 —— 和我们独立想出来的刚性 / 弹性 / 一次性是同一个抽象。 差别在用途:他们拿它定预算,我们拿它修分母。 只有我们同时握着净资产、流动资产和 FIRE 目标 —— 这件事他们结构上做不了。

这一问管什么它在系统里的用处
问题 1 · 会不会再来
复发性		 修分母。一次性的从「常态月均」里剔掉 —— 紧急储备月数、应急金目标、FIRE 全都吃这个分母。这是这一版真正承重的地方。
问题 2 · 砍不砍得掉
可压缩性		 看空间。要省钱,能动的只有弹性那一段。刚性占比一抬, 说明生活成本上了台阶,那是另一类决定(搬家 / 换方案),不是「这个月少点外卖」。

「一次性」的判据是「不可预期 + 不重复」,不是「金额大」。 每月 ¥5,400 的房贷比一次 ¥2,899 的电脑大得多,但它是刚性。 反过来一笔 ¥300 的意外罚单,金额很小,照样是一次性。 按金额设阈值是错的 —— 大额刚性会被误剔, 分母就虚低,紧急储备月数虚高。

老实交代一个边界:年缴 / 季缴(保险、学费)会砸在单个月上。 它复发、也砍不掉,所以是刚性 —— 但摊在那一个月里,会让那个月看着突然贵了。 三分桶解决不了这个,Monarch 是专门加了第四类「非月度周期性」才处理的。 要不要加第四类,是等你裁的事之一。

最危险的一件事 · 为什么是双读数不是换口径

「用常态月均替换月均支出」只要改一行代码,而且测试会全绿(测试数据里没有一次性笔)。 但它会让每一个现存用户的紧急储备月数、应急金目标、体检流动性评分在升级那一刻全部改变, 而他们什么都没做。
所以:既有数字逐字不变,常态月均作为并列的第二个读数出现。 用户自己判断哪个更贴近自家情况 —— 这比我们替他决定更诚实,而且 两个数摆在一起本身就是信息:差多少 = 一次性支出对判断的干扰有多大。
配套:零差异基线(基线取自已发布 tag v1.23.0,不是当前 master)+ 护栏 v1240-EXISTING-KPI-UNCHANGED(静态扫 averageExpense 没有读新列)。

5④ 有没有在悄悄漏 · 已移出本版 三个组件的额度要花在合并上,这个是三选一里被砍的那个
为什么砍它,而不是砍归因瀑布或三分
理由说明
判据最弱 我们没有商户字段。导入时商户名被 trimNote() 塞进了 cash_flow.note(BillCommitService.java:175),而 note 同时装着手填备注。判据只能退到「同类目 + 金额 ±5% + 连续 ≥3 期」—— 三个组件里,只有这个是推定出来的,另外两个是算出来的。
不承重 归因瀑布回答「为什么变了」,三分修的是常态月均这个分母 —— 分母一改, 紧急储备月数 / 应急金目标 / FIRE 都跟着更准。周期性支出对分母没有任何贡献, 它只是一份清单。
它等得起 会员涨价这种事，晚一个版本发现，代价是几十块。合并两个撞名的节、 把配色修对，是每个打开报表页的人天天都在承受的。

设计结论原样留在 PRD §4「推迟到后续版本」,前置条件写清楚了:先给 cash_flow 加独立商家列 (导入时不再把商户名并进 note)。有了那一列,判据就能从「推定」升成「认得出」,再做才值。

9这一版明确不做 每一条都有理由,不是没想到
不做为什么
预算 / 超支预警AGENTS.md 明文「刻意不做预算包络」。预算是月度自律工具(每天看),我们是资产决策工具(每月看一次),10 分钟/月只装得下后者。Copilot Money 主动放弃了预算 —— 这是一个独立佐证。
任何价值判断的文案不说「冲动消费」「你这个月花超了」「建议减少」。少数派那句「花钱永远没有对错」是这一版的红线。系统的职责是指出变化,不是评判选择。配 qa-run 护栏 v1240-NO-JUDGEMENT 扫判断词。
商家 / 交易对象维度没有商户字段,商户名和手填备注混在同一个 note 里。在脏的自由文本上做聚合,产出的排行榜看起来很专业但是错的。要做得先加 counterparty 列。
分类同比需要 13 期的分类数据,v1.21 发布不到一个月。总额同比可以做。
记账激励(打卡 / 徽章)那是留存设计。我们的用户每月来一次,不需要被激励留存。
自定义统计周期账期是一等公民,v1.23 刚把它的边界做成可配置。再叠一层独立统计周期 = 两套时间口径。分析周期 = 账期,不给第二个。

11等你裁的五件事 PRD §13 的同一份清单
  1. 三个组件的额度怎么花。我花成「归因瀑布 + 三分 + 合并既有两节」,把周期性支出整个移出本版。 另一种花法是「归因瀑布 + 三分 + 周期性」,把合并留到以后 —— 但那样线上那两个都叫「钱花在哪了」的节会继续并排挂着,而且这一版还要在它们旁边再加三块,更挤。
  2. 合并用哪种方式。我选了父子双层(消费分类是性质里「日常开支」那一片的展开),两层同屏、第 2 层默认展开。 另一种是并列双维度(像账户/成员那样做成一个切换器,同一份数据换个切法)—— 并列的好处是结构更简单,坏处是回避了「两个合计为什么不一样大」这个真问题,用户还得自己想。
  3. 年缴 / 季缴要不要加第四类。保险、学费这种会砸在单个月上:复发、砍不掉,所以按判据是刚性, 但摊在那一个月会让那个月看着突然贵了。甲 不管,三类到底(简单,但那个月的常态月均确实偏高); 乙 加第四类「非月度周期性」(Monarch 的做法,准,但判断负担从 2 问变 3 问); 丙 不加类,但在年缴月给一行提示(折中)。我倾向甲 —— 这一版已经够满了,而且这个误差是偏保守的方向。
  4. 双读数 vs 直接换口径。我选了双读数。如果你认为常态月均本来就是更对的那个口径、该直接换 —— 那就是一次真正的口径变更,要走「默认关 + 零差异基线 + 页面写明口径期」的完整流程。
  5. 逐笔「一次性」勾要不要做。它是本版唯一增加录入动作的东西(一年 3–5 次)。 没有它,「文化休闲里那笔 ¥8,600 的全家出游」只能靠改整个类目的性质来处理 —— 那是错的。
