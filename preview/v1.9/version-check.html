自动检查更新 已关闭
需 要 你 拍 板 的 取 舍

① 圆点放版本徽记上 —— 已拍板,发现率优先。 背景:member.role_label 是自由文本(丈夫/妻子/foo),项目里没有管理员角色, /admin 也不做权限区分 —— 全家都能进,所以做不到「只给维护者看」。 我评审时提的反对是「非技术家人也会看到,而她既不理解也无法处理」,维护者接受这个代价。 既然选了它,就得把「看到点之后不知道干什么」解决掉:徽记可点 + hover 一行说明。 彻底消掉这个代价要引入维护者角色 → 记进 PRD §8。

② 自动检查默认开。 默认关 → 绝大多数人永远不知道有更新,功能等于没做。默认开 → 一天一个不带身份信息的 GET, 代价是服务器 IP 对 GitHub 可见。我选默认开 + 把「发了什么」写在用户眼前。这条你可能不同意,评审时说。

③ 「含 N 个迁移」这一格是本版和同类实现最不一样的地方。 写 PRD 时实测过 GitHub 的 compare API 能给出两 tag 之间的改动文件清单 (v1.7.1...v1.8.0 精确报出 V53__expense_entry_mode.sql), 所以不是猜的。拿不到时显示「无法确定,升级前自行核对」,不假装没有。

④ 不给一键更新按钮。 四道坎:unit 是 Restart=on-failure(退出码 0 不会被拉起)、 jar 是 root:root 而 app 跑 finance 用户(无权替换自己)、 Release 没有 jar 资产、以及我们有 DB 迁移。详见 PRD §7。

徽记提示样式 · 四个备选(v1.9.2 改版)

v1.9.0 用的是 描边小圆点。实测 --brass-soft #E8D9B6 落在 --paper #F4EFE6 上,对比度只有约 1.2:1(WCAG 非文本元素最低要求 3:1)—— 等于看不见。下面是四个备选,底色都是本页真实的纸色。

◇ v1.9.0

A · 描边圆点(v1.9.0 现状)
对比度 ≈ 1.2:1 · 5px · 已否决:太弱

◇ v1.9.0NEW

B · 实心 NEW 标签 ← 选定
对比度 ≈ 4.1:1 · 是文字不用猜 · 不动、不闪

◇ v1.9.01

C · WordPress 式红色计数药丸
最醒目,但红色在本项目里是告警语义;「有新版」是事实不是事故 · 否决

◇ v1.9.0 · 有新版

D · sub2api 式整体变 chip
够醒目,但整块换底会跟 logo 抢视线,顶栏本来就窄 · 否决

选 B 的理由:① 对比度从 1.2:1 提到 4.1:1,过 3:1 门槛;② 「NEW」是文字,不需要用户学会「圆点=有新版」; ③ 不用红色 —— 红在本项目是告警色,占用它会稀释真告警;④ 静态不闪,符合「每月十分钟、不打扰」的定位。 另外 hover 时标签底色转墨色,给一点可点击的暗示。

点徽记 → 弹窗(不再跳配置页)

v1.9.0 点徽记是跳 /admin?tab=version —— 用户被丢进「配置」语境,还得自己在页面里找那张卡。 参考 sub2api 的 VersionBadge(点徽记展开面板、不跳页)与 WordPress 的更新弹层,改成就地开弹窗:
