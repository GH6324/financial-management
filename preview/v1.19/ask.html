分 水 岭 已 查 清 · 选 型 改 了

原来挂着的问题是「百炼 Managed Agents 支不支持应用侧执行工具」。查完三个接口,答案是 不支持,而且我们本来就不该用它。

候选工具在哪执行结论
Managed Agents 平台侧沙箱。客户端只能写 message 事件 数据要进去只有两条:开公网 MCP 口,或把家底写进云端沙箱文件。 而它的强项(代码执行 / 文件处理 / 长时任务)我们一个都用不上
Assistant API 客户端 官方标注「下线中」,全站提示迁移。不能往上建
Responses API ✓ 客户端:模型返回 tool_call → 我们执行 → 回传 function_call_output 官方推荐方向。端点 /compatible-mode/v1/responses —— 与我们现有通义客户端同一个 base、同一把 key

选它的三条理由:① 工具在我们进程里跑,暴露面和现在六个 AI 调用点完全一样,不新增; ② 不开公网口 —— 这个产品发 Docker 给陌生人自建,很多人在 NAT 后面没有域名, 而百炼的 MCP 没有固定出口 IP、做不了白名单; ③ 没有云端资源要管 —— instructions + tools 随请求发, 原方案里「建 Agent / 全量替换 + 乐观锁 / 只能归档不能删」整块消失。

代价照实说:多轮交给 previous_response_id,社区反馈它与 function_call_output 配合有时序问题 → 我们本地始终存全量(PRD 本来就要求), 云端失效时用本地历史重拼重试一次。

#原问题我的决定与依据
1 「托管形式」怎么定义? 查了代码:透视现有 8 个维度,没有这一维。 做成派生视图(自己盯 / 交给产品 / 不动 / 随时可取), 零新增录入 —— 新加一个透视维度要用户逐个账户打标,违背 10 分钟硬约束。 另外三个切法(机构 / 主理人 / 数字来源)直接复用现有维度。 规则是我定的,可能和你的直觉不符 —— 这是全版唯一一处「我们替用户下定义」的地方
